# Linked metadata fixed reference cases

This is the first fixed case set for the [native V4 linked metadata design](../../../docs/design/draft/ir/linked-metadata.md). The implementation plan remains local while the future IR revision is reviewed. The [draft corpus](metadata-contract-draft.json) has literal expected facts, assertion carriers, sources, and diagnostics. Its [schema](metadata-contract-draft.schema.json) checks the reference envelope. The `status: reference` marker is deliberate: `morphir mck check` and `schema check` admit the corpus and verify its declared fixture closure, but count its cases separately from executable IR cases. The shared runner has no metadata adapter operation or Ion comparison yet. These cases are **not** executable compatibility evidence and mint no IR revision until the shared runner, adapter protocol, and supported profiles adopt them.

The input fragments omit a future V4 `formatVersion`. Their Node URIs address existing 4.0.0 nodes and predicate examples. A full future document must use the IR revision that its adopted MCK cases mint. The [three profile fragments](metadata-fixtures/profiles/value.json) express the same Value facts; Ion is a proposed future node spelling rather than a claim about `ionVersion: 0.1.0-draft.1`.

Cases 0001–0007 fix the compact property form, repeated objects, typed `@json` data, graph and assertion identity, and annotation-name resolution. Cases 0008–0012 and 0024 fix context imports, scoping errors and exact byte identity. Cases 0013–0019 and 0025 fix validation, optional detailed provenance, profile equivalence and the default-graph boundary. Cases 0020–0023 fix publication and sidecar/source behavior. Cases 0026–0047 pin the bounded context grammar, scope and import semantics, coercion, and rejection paths. Case 0048 keeps URI-looking text inside typed `@json` data as an opaque string. Cases 0050–0070 pin the data-value boundary, source state, equality, and validation failures described below. Cases 0071–0072 distinguish a missing required interpreter from an available one. Case 0073 keeps a path-looking literal as data rather than opening a fixture. Existing case IDs 0001–0049 remain stable. The `schemaClosure` fixture supplies explicit declarations, closed data shapes, and object kinds to these cases; a future executable contract must state how a real archive carries and verifies that closure. It cannot infer node-link semantics from a display string. The V3 sidecar entry point is a type declaration; the native predicate examples are value declarations. The reference fixture records the former's projection mapping explicitly.

### Bounded authoring context grammar

This draft defines the accepted subset of JSON-LD 1.1 context syntax for Morphir metadata. The `@context` value at artifact, document `$meta`, node `attributes`, or specification `annotations` scope is one inline object, one reference string, or a nonempty array of one or more reference strings followed by at most one inline object. An inline object alone is not wrapped in an array. An array cannot contain a second object, a reference after its object, `null`, or a nested array. A context file is a UTF-8 JSON object with exactly one `@context` member whose value follows this grammar. Duplicate JSON object members are invalid. These restrictions also apply to imported context files; JSON-LD `@import` is not an alternative import spelling in this contract.

Each reference is either a relative `.jsonld` path confined to the explicit workspace or verified archive root, or `morphir://context/sha256/` followed by exactly 64 lowercase hexadecimal digits. A reference never triggers an HTTP fetch. A local context file resolves its relative references from its own directory; a content-addressed context has no file base, so any relative reference within it fails. The loader rejects a path that escapes the root after normalization and symlink resolution, an absent file, a repeated import in one transitive closure, and a cycle. For a content-addressed reference, the explicit trusted resolver must provide exact bytes and the loader must verify their SHA-256 before parsing. Matching bytes alone do not grant trust. Published external references resolve only within the verified archive inventory. Export resolves imports and writes an inline context or an inventoried local file; published output has no unresolved import chain.

An inline context object admits `@vocab` with one Morphir declaration Node URI stem and explicit term definitions. A term definition is a string target or an object with `@id` and optionally `@type`, `@prefix`, or `@protected`. A target is a complete Morphir declaration Node URI or a compact IRI using a declared prefix. A prefix definition has a stem-valued `@id` and `"@prefix": true`; `@prefix` cannot appear on a non-prefix target. A fact key must resolve to a predicate declaration; an `annotations.entries` name must resolve to an annotation declaration. The reader checks that role at the usage site, so one context grammar serves both forms without conflating their declarations. The only accepted `@type` values are `"@id"` for a node-reference object and `"@json"` for one closed Morphir data value. An uncoerced string remains literal data. `@protected` may be `true` on a term or prefix definition and prevents replacement in a narrower scope. A protected binding may be inherited unchanged. This draft does not admit context-level `@protected`, term-scoped `@context`, `@base`, `@language`, `@direction`, `@container`, `@reverse`, `@nest`, `@propagate`, `@version`, `@import`, or another JSON-LD keyword. It reports `unsupported_context_keyword` and the offending keyword before expanding any facts at that scope; it never silently applies only the recognized members.

An exact term alias wins over compact-IRI expansion; a compact IRI uses an explicit prefix; an otherwise unprefixed key uses `@vocab`. An absolute Morphir declaration Node URI needs no context. The prefix or vocabulary stem must produce a complete declaration Node URI whose final local name obeys Morphir's canonical `Name` rules. An ergonomic spelling such as `targetNames` therefore needs an explicit alias to `target-names`. Expansion preserves an unknown but syntactically valid declaration URI for reading; semantic validation reports a missing or wrong-role declaration. Coercion does not validate a value against the predicate's declared object kind or data type by itself.

The effective scope order is artifact, document, then the relevant node container. `attributes.@context` affects only its own `attributes.facts`; `annotations.@context` affects its own `annotations.facts` and short `entries` names. Neither inherits the other's local context. The document context governs `$meta.@graph` and supplies defaults to both node containers. A node may explicitly replace an unprotected inherited alias, prefix, coercion, or `@vocab`; the replacement ends at that node. A protected inherited binding cannot be changed. A missing local definition inherits the outer one.

For an array, the loader resolves all reference definitions and rejects different meanings for the same term, prefix, coercion, or `@vocab` among imports, independent of reference order. It also rejects the same imported resource appearing twice, even through different paths. Identical definitions from distinct resources can coexist. Only after import-collision checks does the trailing inline object explicitly replace an unprotected imported definition. It cannot cure a collision between imports or replace a protected binding. The resulting accepted context follows JSON-LD 1.1 expansion semantics within this bounded grammar.

### Context diagnostics in the reference corpus

The new context cases keep literal outcomes in the corpus. `context_term_collision` and `context_vocab_collision` name conflicting imported bindings; `duplicate_context_import` and `context_import_cycle` name repeated resources and cycles; `context_path_escape`, `context_resource_unavailable`, `context_resource_untrusted`, `context_digest_mismatch`, `remote_context_forbidden`, and `relative_import_without_base` name resource failures. `protected_term_redefinition`, `unsupported_context_keyword`, and `invalid_context_form` name grammar or scope failures. A rejected context contributes no partially expanded facts. These diagnostics are contract identifiers for the future runner, not claims that the current MCK executes these cases.

### Typed target-language names

The `targetNames` predicate names a declared Morphir record with required `frontend` and `backend` fields. Each field has type `morphir/SDK:dict#dict String String`. For metadata's closed data mapping, a `Dict String T` inside one `@json` object uses a JSON object: every member name is a string key and every member value validates against `T`. The shared validator must add this bounded mapping; the current decorator validator does not support `Dict`. Other Dict key types remain unsupported until their JSON member spelling is specified. The semantic `targetNames` consumer validates each language ID as a lower-case ASCII identifier with optional hyphen-separated alphanumeric segments (`^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`), while preserving the exact spelling value. This permits new language IDs without changing the record type. Case 0004 accepts several language IDs, case 0025 rejects a non-string target spelling, and case 0048 proves that a Node-URI-looking string nested in `@json` is still data.

Each predicate in the reference closure declares its interpretation requirement. `descriptive` predicates need only context, declaration, subject, object, and type validation. `targetNames` additionally requires the `target-name-language-ids` interpreter for the language-ID rule; a type-valid object without that interpreter is preserved for roundtrip but is not semantically validated. A case's `given.availableInterpreters` overrides the reference environment; when omitted, all interpreters named by the fixture are available. Case 0049 rejects an invalid language ID with the interpreter present. Cases 0071 and 0072 use the same valid object with the interpreter absent and present, respectively. An unavailable interpreter never turns a malformed declared type into an accepted fact: basic type validation still precedes interpretation.

### Data values, absence, and equality

The closure declares each new predicate as a Value specification and its object as a Morphir type specification. `label-list` is `List String`, `display-info` is a closed record with required `title: String` and `enabled: Bool`, `review-state` is a custom type with `pending` and `approved String` constructors, `optional-label` is `Maybe String`, and `unit-marker` is Unit. Their JSON values follow the existing decorator `ValueValidator` vocabulary: lists and tuples are arrays, records are objects with exactly their declared fields, `Maybe` uses `null` for None and the inner JSON value for Some, Unit uses `null`, and custom values are arrays with a constructor tag followed by its arguments. The fixture's `integer-keyed-map` is deliberately unsupported: only `Dict String T` has a JSON object mapping. The closure gives each shape explicitly; the expected outcomes are independent of the implementation validator.

A bare property array denotes repeated values for one predicate. Case 0054 therefore yields two scalar `aliases` facts. A context with `"@type": "@json"` instead makes the *whole* array, record, constructor array, or Dict object one typed object; cases 0050–0053 give its exact `@value` and `@type`. The type declaration validates that one object after context expansion. A JSON object without `@json` coercion is not implicitly a Morphir record or Dict. This rule also keeps a nested URI-looking string inside `targetNames` as data.

The absent `aliases` property in case 0055 and present empty array in 0056 both yield zero facts. Their `sourceState.facts` expectations record the different written inputs; the normalized graph alone cannot recover that distinction. A bare `null` in 0057 yields no fact under the bounded JSON-LD expansion rule, and its written input remains explicit in `sourceState`. Typed `@json` null in 0058 and 0060 yields one fact each, validated as `Maybe String` None or Unit respectively. Case 0059 shows a present `Maybe String` value. The typed object retains `"@type": "@json"`; it does not collapse into the bare-null no-fact case.

`compareFacts` expands and validates each input independently, then compares the normalized subject, predicate, typed object, and graph. Case 0061 keeps a scalar fact equal when metadata envelope keys and context definitions are written in different orders. Cases 0062 and 0063 keep closed records and nested Dict objects equal when their JSON member order changes. JSON object member order does not participate in data identity; array order does. Case 0064 therefore yields two distinct typed list facts. Each `facts` array in these expectations states the exact normalized set, while `equal` and `distinctFacts` state the comparison result. The array order in the expectation is for legibility, not fact identity.

Cases 0065–0070 fix rejection codes and paths for a wrong list element, missing record field, wrong constructor argument, unknown constructor, unsupported non-string Dict key, and a non-null Unit value. `predicate_object_type_mismatch` applies to values that fail a supported declared shape, `unknown_constructor` names a tag absent from a resolved custom type, and `unsupported_data_type` means the declared generic cannot be mapped to JSON at all. A rejected assertion contributes no fact. These are reference diagnostics for the future runner; the current MCK still has no metadata operation. The corpus remains `status: reference` and mints no IR format version.
