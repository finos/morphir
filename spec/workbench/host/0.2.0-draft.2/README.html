Scope and negotiation

This exact HTTP mapping adds checking-policy negotiation to the frozen host draft.1. The descriptor has exactly profile, contractVersion, offer, capabilityChecks. Its profile is morphir/workbench/host and version is 0.2.0-draft.2. The offer retains the exact morphir/workbench/executions 0.2.0-draft.1 identity and operation contract.

The checking offer has exactly profile morphir/workbench/admission, contractVersion 0.1.0-draft.1, runtime scheme, evaluator scheme-portable-v1/shared-sdk/bounded, and policies ["strict","permissive"] in that order. The admission spelling is a frozen wire identifier. User-facing documentation and controls use capability checking.

Unknown profiles, prereleases, build suffixes, runtimes, evaluators, policies and members reject. A descriptor is received through an authenticated HTTP session. Compilation capability, a native MEP offer, a Rust protocol v1 descriptor with executions disabled, or an unauthenticated body cannot create this offer. Strict-only providers continue to publish their qualified draft.1 mapping. Explicit permissive requests never fall back to strict, another provider, another runtime or a local evaluator.

Immutable submission

The exact draft.2 request has required contractVersion, model, entry, inputs, runtime, providerId, and optional admission. Runtime must be Scheme and providerId must equal the negotiated provider. Inputs have exactly format json or ion-text and source text. No paths, caller manifests, caller plan IDs or accepted boundaries are allowed.

Omitting the selection resolves once to strict. Explicit selection has exactly the frozen capability-policy profile, version and policy. The client copies source, entry, arguments and selection synchronously before any await. The authenticated host validates request framing, authority, decoding, complete selected public boundary and arguments before accepting. Strict checks the model according to its existing rules. Permissive permits unreachable unsupported code while keeping all mandatory model, type, argument and resource checks. Reached unsupported code remains a terminal evaluation failure.

The initial reply has exactly identity, calls, receipt, plan. Calls is exactly ["workbench"]. Receipt is the unchanged initial executions draft.1 receipt. Plan is the execution-plan draft.1 projection. All identity fields must agree with the negotiated authority and with each other. Runtime, evaluator, policy and selected boundary must agree with the captured submission. The client rejects rebinding or reuse of an accepted authority-scoped execution or plan ID, even with a new snapshot ID.

Authentication and authority

Authentication is a transport responsibility, separate from descriptor shape. The gateway checks the current authenticated session and selected provider for every operation. A rejected or expired credential cannot mutate an execution. A changed host, session, provider, operation inventory or checking offer cannot replace the selection of an accepted execution. Authentication secrets are never included in execution plans, receipts or compatibility projections.

The provider retains the accepted plan and immutable input snapshot. A worker claims that exact retained selection once. A claim checks owner authority, execution/plan identity, runtime, policy and provider. A second exact claim rejects. A mismatched claim rejects without consuming the valid claim. Workers use the real selected Scheme evaluator, echo the retained plan and publish typed outcomes through the host's captured-context validator after confirmed completion. No supplied terminal or proxy response establishes actual execution.

Execution lifecycle

Query, cancellation, release, their bodies and receipts remain the frozen host draft.1 forms. Query never re-executes. Cancellation acknowledgement is separate from terminal cancellation and may race with a value or failure. Release follows confirmed terminal completion; cleanup failure remains separate from the primary terminal outcome.

A lost submit reply leaves submission uncertain. The client cannot safely retry, silently submit elsewhere or manufacture an identity. A lost query reply preserves the accepted cursor and selection. Same-authority reconnection can query the same execution without a new claim. A changed offer or expired authentication preserves retained evidence and cannot fabricate success, cancellation or cleanup. Release and shutdown retain once-only execution semantics, including after a lost reply.

Independent evidence

Shared Rust MCK owns exact fixed inputs and expectations. Boundary checks qualify production decoders, controlled client traces qualify production request capture and state transitions, and provider traces qualify the real owner/evaluator. Controlled fixtures alone establish no authentication, network, worker isolation or packaged platform claim.

Actual authenticated gateway requests, selected Node worker logs, typed terminal publication, browser workflows and packaged Proton workflows require separate receipts. Those receipts identify the actual gateway/provider and platform. They establish no production Rust v1 daemon policy support, generated browser backend capability or unevidenced operating system support. Frozen host draft.1, native drafts.1 and .2, executions and all earlier MCK kits remain separately qualified.
