Exact native mapping

The profile morphir/workbench/native at exact version 0.2.0-draft.2 adds desktop capability checking policies. It preserves the page, session, invocation correlation, workspace, lifecycle, byte budgets and cleanup obligations of native 0.2.0-draft.1. The old mapping remains frozen. Drafts never fall back or translate. A session binds one mapping; a different version on the same live page rejects without changing its authority. HTTP support is separate.

Negotiate checking capabilities

Open and check require a closed capabilityChecks member exactly when executions is advertised. It contains the exact policy profile/version, Scheme runtime, bounded evaluator and the ordered policies below. Workspace-only and empty descriptors forbid it. The descriptor and its offer remain stable for the session. Reconnection compares the entire descriptor, including checking capabilities, before adopting an existing cursor.

{
  "profile": "morphir/workbench/admission",
  "contractVersion": "0.1.0-draft.1",
  "runtime": "scheme",
  "evaluator": "scheme-portable-v1/shared-sdk/bounded",
  "policies": [
    "strict",
    "permissive"
  ]
}

Capture the execution selection

The native execution.submit payload retains contractVersion:0.2.0-draft.1 for execution semantics, source text, entry and JSON or Ion arguments. This new outer mapping additionally requires runtime:scheme and providerId captured from the exact native offer. Its optional admission member uses the existing exact policy selection. Omission resolves to strict once, before acceptance. Null, unknown versions, unknown policies, unadvertised runtimes and changed providers reject without fallback or partial acceptance. The historic wire member and policy profile keep their compatibility spellings; user-facing language is capability checking.

Each accepted selection captures source, arguments, exact resolved policy, authenticated provider, runtime, evaluator and selected public boundary. Editing UI defaults, input fields or later descriptors never changes that accepted execution. The worker claims the exact retained plan once, receives that selection and uses it in actual planning and evaluation. A new explicit submission allocates a fresh execution, snapshot and plan.

Validate the accepted plan

Submit success contains exactly identity, calls, receipt and plan. Its plan uses the unchanged execution-plan 0.2.0-draft.1 projection. The ordered call inventory remains ["workbench"]; receipt sequence zero, submitted state and cancellation flag remain frozen. All nested identities must agree. The client checks the returned policy, runtime, evaluator, provider and selected public boundary against the captured submission before publishing any accepted receipt. Query, cancel, release, later receipts and typed outcomes keep their frozen shapes.

The response envelope itself has no version. A decoder therefore uses the exact mapping captured for the originating invocation. It never guesses based on plan presence. Lost, malformed or mismatched submit replies leave effects unknown and do not authorize automatic retry. Only an authoritative error with effect:none establishes rejection for that request.

Preserve desktop authority

Policy negotiation grants no additional page, window, filesystem or executable authority. Revocation, navigation, shutdown, asynchronous boundaries, cancellation races and cleanup retain the frozen native rules. A successful plan projection does not prove actual execution or cleanup. Mismatched selection rejects before owner state changes. A matching repeated claim still rejects. Worker completion validates the retained accepted boundary; the worker cannot widen it by returning an edited plan.

Independent checks and implementation evidence

The qualified MoonBit renderer retains a bounded replay history of at most 256 accepted executions per application page. After that limit it refuses a new submission during local preflight, before calling the host. Opening a fresh application page creates a new native authority and history. Releasing a terminal execution does not erase its replay protection.

MCK draft.20 checks opaque request/reply boundaries; draft.21 checks the production native client; draft.22 checks the production native owner and actual selected Scheme evaluation with controlled dependencies. The single shared Rust runner compares fixed parent-owned expectations and its saved-report checker recomputes verdicts. None of these controlled fixtures establishes framework caller provenance, OS picker authority, worker isolation or packaged-platform support. Those require separate real process and packaged Proton qualification. Native 0.2.0-draft.1, execution/host 0.2.0-draft.1 and MCK14 through19 remain byte-for-byte frozen.
