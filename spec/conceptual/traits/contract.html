Typed trait declaration and application contract

morphir-ukvn.7.7.2 · M2 · 18 October 2026 · Proposed exact draft 0.1.0-draft.1

This reference design defines morphir-traits/0.1.0-draft.1. Its vocabulary, record spelling and mappings are local proposals under the pinned design direction. They do not freeze the DSL or claim maintainer approval. The corpus contains authored observations, not results from a trait validator.

Scope and composition

A trait declaration names a payload type, permitted targets and any required interpretation. An application attaches one payload to one identified subject. A stored application can be useful before a consumer knows how to interpret it. A consumer must report that gap when the requested operation needs its meaning.

The exact profile is morphir-traits/0.1.0-draft.1; records use recordVersion: "0.1.0-draft.1". These versions are independent of the M1 conceptual profile, model revisions, provider releases, IR format, expression profiles and transport versions. Prereleases match exactly. Future released versions follow the repository SemVer policy and established version libraries; M2 implements no negotiation.

The existing M1 graph gains an optional traits member with {recordVersion, profile, definitions: TraitDefinition[], applications: TraitApplication[]}. This is an extension of the graph already retained in rich IRUnit metadata. It introduces neither a new envelope nor a Distribution variant. Rich IRUnit and MEP MorphirModel remain distinct existing carriers. MEP transport projection requires its own explicit mapping and loss checks.

An M1 reader preserves this unknown member as Ion data. If any application requires semantic interpretation, the graph's requiredSemantics must include this exact trait profile and every required application profile. A request to validate even descriptive traits also explicitly admits the trait profile. An M1-only reader must then report unsupported; merely retaining traits is never validation. An optional descriptive extension need not make ordinary M1 inspection fail. Required semantics gate interpretation, not lossless storage; inspection can expose unsupported applications as gaps without claiming their validation. A containing graph may mark traits critical when any use of the graph requires understanding the extension. An omitted required admission entry is malformed under M2, not permission to ignore the application.

All M1 rules for case-sensitive IDs, exact opaque revisions, sources, unknown members and critical apply. Definition and application IDs are unique across the containing graph's existing record lists and both trait lists. Nested records inherit the outer version. A changed definition or payload requires a changed revision and model snapshot; a rename alone does not create a new logical identity.

Trait declarations

Every field below is required unless marked optional. Records retain unrecognized noncritical members without interpreting them. Trait definitions are declarations in the conceptual extension; they are not automatically native linked-metadata predicate declarations.

Definitions have stable IDs such as urn:example:trait:encoding. A resolved application reference uses M1's five-field reference shape; its entity ID selects a trait definition in the extension and its entity revision selects that definition's exact revision. The M2 resolver recognizes this record kind without adding it to M1's built-in entity vocabulary. A declaration that is absent at a claimed resolved identity is invalid. An intentionally unresolved declaration remains a visible gap.

The containing model owns the application assertion. The target may belong to another exact model dependency; this neither edits that dependency nor grants its author approval. SourceRefs refer to the asserting model's sources, not an ambient source with a matching name. A dependency resolves only through M1's declared, caller-supplied closure. Revision or digest pins establish identity; authority requires a separate trust decision. Retained source text keeps its exact whitespace and final newline.

Target kinds

Kind and target shapeRequired subject
{kind: "model", model: {id, revision}}The exact local or explicitly supplied dependent model snapshot, without a fabricated entity.
{kind: "concept", ref}M1 concept entity.
{kind: "type", ref}M1 declaration with role type.
{kind: "member", ref}M1 declaration with role field, parameter or result, and a resolved parent of the appropriate type/function role. This does not create a standalone IR node for a field.

References reuse M1 resolved/unresolved distinctions. For unresolved targets, expectedKind must agree with the proposed kind: concept, declaration for type/member/function, or the profile's operation/serviceBinding kind. Resolved references with missing records, wrong actual kinds or mismatched revisions are invalid. An unknown target kind is retained but unsupported, never coerced to the nearest known kind. An unresolved target or unavailable target profile can support inspection with gaps, but cannot satisfy validation or generation.

These are Morphir applicability categories, not a claim that a foreign trait can use every category. Importers must retain source-specific applicability restrictions and require the relevant mapping profile. A Smithy operation is not silently relabeled as a pure function. Module and service scopes do not create implicit inheritance: each application targets one subject unless a separately qualified semantic profile explicitly defines propagation.

Types and references

The payload artifact is an ordinary formatVersion 4 Specs document. It declares label, elaboration, encoding, concept-link, foreign-condition, prompt and string-map using existing TypeAliasSpecification, Record, Reference and SDK types. Its artifact ID/revision comes from the explicit case environment. A schema points to the actual declaration by FQName. Labels, fixture paths and type names cannot establish revision identity or trigger a package download.

morphir-metadata-json/0.1.0-draft.1 is a proposed exact name for this corpus's reuse of the bounded existing linked-metadata/decorator data mapping, not a new type system or a claim that a codec advertises that name. String and Bool retain their JSON scalar types; Int requires an exact integer. The corpus uses small exact integers only. Records have exactly their declared fields; lists and tuples use ordered arrays; Unit and Maybe None use typed null; Maybe Some uses the inner value; custom values use constructor-tag arrays. String-keyed Dict uses JSON objects. Other Dict key types, higher-order values, unsupported recursive data profiles and opaque types without a public data mapping are unsupported rather than reinterpreted. Morphir type structure, arity and closure remain authoritative. This exact data profile supplies intrinsic meanings for the SDK scalar and collection type identities listed here; no ambient SDK checkout is consulted. Other referenced declarations require an explicitly supplied exact artifact closure. Wider number transport and recursive validation limits belong to their owning profiles.

Typed null is a present payload, distinct from an absent application. Application lists are not JSON-LD property arrays. The linked projection wraps each whole structured payload with @json, preserving lists, records, constructor arrays and null as one typed object. URI-looking strings inside those objects stay data.

The proposed morphir-entity-reference-data/0.1.0-draft.1 binding translates a closed record's state, model-id, model-revision, entity-id and entity-revision fields to M1's resolved reference. State must be resolved; all identity/revision fields are nonempty and must resolve exactly. The hyphenated fields follow canonical IR Name spelling. The declaration's binding selects the record and supplies its expected target kind. All binding paths must exist. This bounded profile does not interpret arbitrary strings or synthesize missing imports. Its unresolved-record and collection-path variants remain open; unresolved subjects and definitions already use M1's full unresolved variant.

The related-concept declaration applies that binding to its entire payload. The prompt's optional arguments record is retained data until a future prompt profile declares and validates its argument bindings. Merely resembling a reference does not resolve it. This deliberate gap keeps a representable foreign record separate from verified template semantics.

Validation and admission

A future consumer reports each stage separately. The reference corpus authors expected observations for these stages but does not implement them.

  1. Admit exact record and requested profile versions; check required members, variants, uniqueness and critical members. Reject duplicate wire members before decoding discards occurrences.
  2. Resolve declaration, target, schema artifact and sources in the explicit dependency closure. Check revisions, actual target kind, permitted target set and schema type-argument arity. Intentionally unresolved references remain gaps; unexpectedly absent resolved references are invalid.
  3. Validate the payload against the resolved Morphir type and selected data profile, including declared reference bindings. Unsupported data mapping is not a valid value.
  4. Check application/declaration interpretation agreement and graph admission requirements. Validate basic supported payload shapes even when a semantic interpreter is unavailable; a wrong-typed arity must not become accepted because an interpreter is missing.
  5. Admit all required exact semantic and subject profiles before a requested check, export or generation. A supported profile advertisement alone is not evidence that execution succeeded. Run semantic rules only within their qualified consumer and record its result separately.
  6. Preserve competing assertions. A consumer requiring one distinct value must resolve its conflict explicitly or refuse; list order gives no precedence.

Inspection may return valid-with-gaps for unknown descriptive applications, unresolved references, unavailable subject profiles or conflicts. Validation returns valid, invalid or unsupported; preservation returns preserved; a requested lossy export or ambiguous selection can return refused. A valid attachment does not prove its payload's domain claim, its source's authority, an implementation's behavior or a protocol's conformance.

Diagnostic codes are local proposals with a traits. prefix. Their suffixes identify target_kind, target_identity_kind, payload_type, reference_revision, reference_missing, type_arity, source_missing, duplicate_id, interpretation_mismatch, missing_required_semantics, unsupported_semantics, unsupported_target_profile, unsupported_record_version, unsupported_profile, unsupported_critical, unresolved_definition, unresolved_target, application_conflict, unmapped_subject and provider_unverified. Missing-schema and unsupported-mapping diagnostics remain separately identifiable as reference_missing and unsupported_data_profile. M1-only admission retains conceptual.unsupported_semantics, and bare export uses the existing data.lossy_conversion.

Each diagnostic has a code and RFC 6901 path selecting the materialized graph or case operation input; an optional relatedPath identifies the earlier conflicting record. Missing-field diagnostics select the parent and name the missing field. Diagnostics compare as sets; record order matters only for identifying a later duplicate. Fatal malformed input precedes optional gap reports. Cases isolate the intended observation and do not forbid other relevant inspection gaps.

Preservation and conflicts

Unknown definitions, applications, members and descriptive Ion values survive rich round-trips with their exact identities, revisions, annotations, numeric precision, decimal scale, symbols, typed nulls, order and source text. Unknown semantic requirements also remain retainable; a requested interpretation that needs them returns unsupported. No checkpoint, signature extraction or public projection may silently drop the graph extension.

Two assertions can carry equal values and different provenance. Keep both applications and contributors even when a normalized fact set coalesces their values. Distinct values remain distinct. For this JSON subset, object member order does not change data identity, while array order does; no equality is invented for unsupported Ion or semantic profiles. A single-value constraint concerns a resolved definition revision and exact subject snapshot. A changed definition revision or different target revision cannot silently participate in the same selection.

No last-writer-wins or automatic source ranking is defined. Inspection retains conflicts; selectOne refuses unresolved ambiguity. A later explicit resolution must record its authority and preserve rejected/historical assertions according to the owning transformation's rules. Changed definition, source, subject or artifact revisions require reassessment of dependent evidence. They do not rewrite historical applications or grant current proof.

Bare IR has no general place for conceptual applications. Export must expose the loss and refuse unless an explicit loss-authorizing operation exists. Occupied rich metadata owners follow M1's refusal rule rather than overwriting unrelated data. M2 adds no such loss authorization or multi-profile metadata merger.

Linked metadata mapping

A conceptual application maps to linked metadata only through an explicit predicate mapping and a representable IR subject. The existing linked-metadata contract owns its context grammar, assertion carriers, publication, authentication and data mapping. M2 neither widens that grammar nor registers conceptual IDs as IR Node URIs.

A mapped predicate must be a real value declaration in the provider IR. Its public output type supplies the data schema; the provider's native schema facts declare allowed subject roles, object form and interpreter. A published Library uses public value definitions and an authenticated inventory. A Specs fragment can describe a value specification. A sidecar closure or this conceptual TraitDefinition is never substituted for those provider declarations.

The authored provider fragment illustrates a label predicate with native schema facts in a proposed future V4 document. It deliberately has no formatVersion and is not a valid 4.0.0 document, publishable Library or proof of authenticated provider restore. The complete 4.0.0 payload artifact only provides ordinary type specifications. The two inputs have separate exact fixture identities.

The projection recipe binds one exact definition reference to the predicate URI and exact provider artifact, then supplies explicit conceptual-target-to-IR-node mappings, and assertion owner artifact/revision plus carrier. A fixture's fixture-assumed admission marker is author-provided reference setup, never production trust. Publication with an unverified provider refuses before emitting an artifact. Matching digest bytes or a revision string alone cannot authenticate a publisher.

The target node becomes the fact subject; the containing asserting artifact owns the assertion. An external attachment uses that artifact's document graph and does not edit the subject artifact. Retain each application ID and source mapping alongside the projection so conceptual ownership and source text remain recoverable. The current linked-metadata assertion identity mechanism, when selected, supplies its own identifiers; M2 does not introduce another assertion envelope or replace implicit subject rules.

Each entire data payload is one typed @json object. Node links use the existing explicit object-form and context rules only when the declared mapping chooses that form. A raw URI string in a payload remains literal data. A concept without an agreed IR mapping produces unmapped_subject; it must not be assigned a fabricated declaration address.

Linked metadata retains graph conflicts and all contributors. assertionSources entries remain complete replacement contributor sets for their exact selectors, not incremental additions. Projection may not erase an unknown contributor when updating a known one. Context imports remain explicit, finite, confined and pinned under the existing grammar. Publication binds local and foreign nodes to verified artifact revisions and inventories its contexts; missing providers do not trigger ambient file or network acquisition. Named graphs and general RDF exchange remain separately scoped work.

Reference cases and checks

cases.json contains 47 independently authored observations. The environment supplies one exact IR artifact, a data-profile name and empty default semantic admission requirements. Cases using semantic traits supply their graph requirements explicitly. Each case starts with model.json. If input.traits supplies definitions or applications, it replaces that complete list in the graph; omitted lists remain unchanged. If input.dependencies is present it replaces the graph dependency list, and input.modelInputs supplies exactly the named model snapshots. Graph requiredSemantics uses input.graphRequiredSemantics when supplied, otherwise the environment's graphRequiredSemantics. Operation input requiredSemantics is a separate request. This composition describes fixture construction only; it never derives expected observations.

Diagnostic paths select the resulting graph or explicit operation input. Available semantic profiles default to the empty environment set and can be overridden explicitly. Case 0003 assumes a qualified interpreter as reference input; this repository provides none. Round-trip cases insert the literal Ion asset at the named pointer before the requested operation. No test computes those observations by calling a validator under test.

Open decisions

  • Final trait/profile names, traits extension spelling, application syntax and reference-binding vocabulary require review. No DSL punctuation is chosen here.
  • The bounded reference-data profile covers resolved scalar references only. Generic reference traversal, unresolved payload references, target selectors and inheritance remain separate decisions.
  • Operation/serviceBinding identity and applicability profiles belong to their owners. Their names in a target list do not count as support. Prompt argument binding and complete Smithy source inventories remain open.
  • Native predicate mapping identifiers, application-to-assertion identity mapping, publication packaging and revision migration need consumer integration. A conceptual declaration does not enroll a trusted provider.
  • Full Ion typed-data validation, recursive shape limits, wide-number JSON policy, semantic equality and generic trait parameter policy need qualified profiles. The finite corpus uses concrete payload schemas and claims no complete parity.
  • Conflict resolution authority and historical evidence reassessment use existing conceptual provenance principles; no automatic merge, trust hierarchy or current-evidence promotion is defined.
