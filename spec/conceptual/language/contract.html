Profile and authority

morphir-declarations/0.1.0-draft.1 is an exact prerelease profile. Its SemVer is independent of the Morphir IR format and other conceptual profiles. No draft-to-draft compatibility is promised. This is the L1 contract proposal for downstream implementation, grounded in the parent conceptual design draft 0.17 and the existing IR draft types, U1 union contract and M1 model contract. The parent semantic design remains in bead morphir-ukvn.7.

Required direction includes alias/custom-type distinctions, opaque identity, optional leading constructor pipe, rank-1 generics, finite tuples of arbitrary arity ≥2, untagged unions and bodyless fn. The exact fragment delimiters, ASCII identifier subset and AST encoding below are scoped L1 draft choices. They do not select the enclosing namespace/package keyword, exports, implementation syntax or the complete future language.

A fragment is supplied in one explicit module context by L2/L4. It neither declares that context nor infers an IR package from a dotted name. Named types remain unresolved paths. Type syntax alone does not establish successful resolution, assignability, value validation or execution capability. L1 fixes interfaces and expected cases; it does not qualify an implementation.

Morphir source files use .mfs, including source focused on contracts or specifications. The extension does not distinguish those files from other Morphir source. .morphir is reserved for a future Morphir model package; its container encoding remains undecided. The declaration source fixtures use .mfs and retain their exact original bytes.

Declaration grammar

The complete token grammar is grammar.ebnf. Space, tab, LF, CRLF and // line comments separate tokens. Source bytes remain unchanged. Identifiers use ASCII upper/lower initial letters followed by ASCII letters, digits or underscore; type, alias, opaque and fn are reserved. Broader identifier syntax belongs to a later explicit profile. Source spelling is not canonical IR Name encoding.

Source formAST and meaning boundary
type alias A = Balias with a type expression; B must resolve.
opaque type alias Id a = Stringopaque-alias; nominal identity and phantom parameters survive resolution.
type A = B | C Intcustom with two constructors, B nullary and C with one argument. An initial pipe is optional.
opaque type A = Bcustom whose constructor access is defining-module only. Ordinary custom types still follow L2 export policy.
type alias A = B | CAlias to an untagged union of existing types. No constructor or wrapper is introduced.
fn identity(value: a) -> afunction-spec with an explicit AST binder for implicitly quantified a, one input and an output. No body is supplied or synthesized.

Application binds tighter than union, which binds tighter than the right-associative arrow. Thus List a | Int -> Bool is (List a | Int) -> Bool, and a -> b -> c is a -> (b -> c). Only a named type can head an application in this first-order profile. List (a | b) has one union argument. Union lists preserve authored order, duplicates and nesting; no flattening, sorting or deduplication occurs in the syntax AST. U1 owns membership, substitution and ambiguity semantics.

Constructor arguments are atoms: C A B has two arguments; C (List a) has one applied argument. A union or arrow used as a constructor argument must be parenthesized. This removes the constructor-pipe versus union-pipe ambiguity without depending on current names in scope.

() is Unit, (A) is grouping, and (A, B, C, D) is one flat four-element tuple. Grouping adds no semantic AST variant; the retained source and outer expression span preserve its spelling. Singleton tuples and trailing commas/pipes are rejected in this profile. Records are closed ordered field lists, including {}. Extensible records need a later explicit AST/grammar extension. There is no language-level tuple maximum; a consumer's size limit is a resource diagnostic, not an arity rule.

A complete declaration may end with a semicolon. Otherwise it ends at the next declaration keyword or fragment EOF; newline alone is whitespace. Delimiters and complete type expressions establish boundaries. Function parameter lists use comma separators, and output arrows belong to the output type after the first signature arrow. Two inputs and one tuple input remain distinct. A function-valued output remains the output, not additional inputs.

type alias Pair a b = (a, b)
opaque type alias LoanId = String
type Maybe a = Nothing | Just a
type alias Identifier = String | Int
fn map(items: List a, transform: a -> b) -> List b

AST records

The normative field inventory is ast/types.ts; independently materialized JSON appears under declarations/cases.json. The TypeScript declarations describe authored wire records, including deliberate invalid fixture data. They are not validated domain values. In particular, array types permit negative arity and duplicate-ID cases for consumer tests.

Identity and source spans

Each source ID identifies exactly one retained source revision inside a fragment. Duplicate source IDs are invalid, including different revisions under one ID. Node IDs are nonempty and unique across all nodes in that fragment. They identify authored syntax records for diagnostics and fixture references; they are not M1 conceptual identities, IR FQNames or promises of identity across edits. A later consumer must record an explicit syntax-to-semantic identity mapping. IDs must not be used as proof that spelling or offsets stayed unchanged.

{"sourceId":"source:pair","start":0,"end":29,"unit":"utf8-byte"}

Spans are half-open UTF-8 byte ranges into the exact referenced Source text, reusing the M1 recovery span convention with an explicit source reference. Require finite nonnegative integer offsets, start ≤ end ≤ byteLength(text), and both endpoints on UTF-8 code point boundaries. Zero-width spans may identify an insertion point. A source ID must exist. Preserve CRLF, comments, Unicode and a final newline exactly; never convert UTF-16 string indices into byte offsets without encoding the prefix. No normalization or BOM removal is implicit.

A declaration span covers its declaration from the first keyword through the final token, excluding a separator semicolon and surrounding comments/whitespace. Child spans select their authored text and stay within the owning declaration; overlapping parent/child spans are normal. An implicit function binder uses its first variable occurrence's span, so its span may equal that occurrence's span. Grouping extends the root expression span to include the outermost surrounding parentheses; child spans stay unchanged. There is no separate Group node. For example, the named root of (List a) includes the parentheses, while its a child selects only a. Recovery for absent or incomplete nodes belongs to L8; malformed source cases need not invent a complete declaration tree.

Parser comparisons permit a bijective renaming of node IDs while requiring exact source IDs, spans, ordered structure and binder origins. The parser is not required to invent fixture authors' node IDs. Constructed-AST resolution cases use the supplied node IDs directly. A full round-trip that rewrites source must publish new source revisions and spans; this profile does not claim that a semantic AST alone reconstructs original formatting.

Binders and resolution

A type declaration lists all parameters explicitly, each as a binder with origin: declared. A variable occurrence carries its authored lowercase name, not a fabricated resolved binder reference. L4 binds it within the enclosing declaration. Reject duplicate type-parameter names and unbound variables in aliases, opaque aliases and constructor payloads. Constructors inherit their custom type's parameters. Opaque phantom parameters remain in the binder list even when unused by the representation.

A standalone function implicitly quantifies free type variables over its whole signature. Its AST makes those binders explicit with origin: implicit, once per distinct variable spelling in first-occurrence order. Traverse inputs left to right, then output; traverse nested nodes in their recorded field/list order, and function types input then output. The binder's source span is the first occurrence. Different declarations have independent binders. Builders never infer or generate them; L3's syntax adapter owns this desugaring. Explicit fn[a] punctuation is not selected.

Named input parameters retain identity, spelling, order and type. Duplicate input names and the reserved input name result are semantic diagnostics. Record field names and custom constructor names must be unique in their owning lists. An alias may refer forward to another declaration; constructed fixture resolution does not depend on file order. Reject unproductive alias cycles; allow mutually recursive algebraic declarations guarded by constructors. General recursion in executable predicates is a different capability.

Named type application checks arity against the explicitly supplied declaration environment. Parameters stand for complete types; applying a variable as a type constructor is outside rank-1 first-order syntax. Arrow types may occur structurally in declarations even when an evaluator cannot check higher-order values. Opacity, generic instantiation, assignability and IR lowering belong to L4/U2/U3 and must not be inferred merely because a fixture parses.

Diagnostics use stable codes in declarations.syntax.*, declarations.structure.*, declarations.resolve.* and declarations.unsupported.*. A syntax diagnostic carries a span; an AST diagnostic carries a JSON Pointer into the supplied fragment and may carry a related pointer. The fixture freezes the primary code/location; human wording and additional noncontradictory diagnostics may vary. An operation reports resource exhaustion separately, never as a successful parse or false semantic result.

The fixture expected object is an independently authored oracle. Integrity tests check its references, locations and frozen assets; they do not execute these observations. Consumers must report actual observations against the shared runner's existing adapter contracts when the corresponding integration task arrives. This package adds no alternative conformance runner.

Extension contract and remaining choices

L1 exposes core declaration nodes, IDs and spans for a later source-item union, keeping container and declaration-family ownership separate. L2 owns namespace/module/import containers and exports, published in the morphir-scopes/0.1.0-draft.1 contract; L9 owns intent, traits, requirements and contracts; D4 owns dictionary declarations; H6 owns Smithy service/condition/protocol/prompt declarations. Each extension publishes a versioned discriminated AST family and a source/parser/printer adapter which consumes and preserves core declaration references, binders and source revisions. An extension cannot redefine a core discriminator or erase required core content.

The core Declaration union remains closed. Unknown family nodes are not accepted as validated core declarations through an arbitrary payload field. A consumer may preserve their exact source or opaque extension data using an explicitly supported rich/recovery carrier, but must report unsupported when interpretation is required. Known structural references to extension declarations retain explicit syntax IDs until their owning resolver provides semantic identities.

Optional critical lists on fragments, sources and nodes name required members at that record level. Names must be distinct and present. Unknown uncritical members may be ignored for interpretation and should survive rich preservation; unknown critical members yield unsupported. A known discriminator with a missing required field is malformed, not an extension. These rules do not make arbitrary unknown data executable.

Choices deliberately outside this fragment profile
  • Enclosing keyword, dependency-alias punctuation, module exports and canonical-name collision policy are L2 decisions.
  • Explicit function binder notation, full Unicode identifier repertoire, extensible records, trailing-comma variants and any implementation-body syntax need an explicit subsequent profile.
  • Refinement/contract expression grammar and source attachment syntax belong to L9/C3. L1 retains declaration IDs and source revisions for their future links; a bodyless function is already a complete specification.
  • Raw/interpolated strings and templates remain L5/L6; incomplete source snapshots remain L8. A retained comment containing Unicode is not a claim of general Unicode identifier or string-literal support.

Fixtures and consumer handoff

cases.json pins stage-specific inputs, independent expectations and requirement-to-case coverage. Every referenced source, AST, environment, grammar and contract asset is byte-counted and SHA-256 pinned in assets.json. Every syntax input supplies source as an object with asset path, id and revision independently of its expected AST, including negative cases. Source-positive cases pair exact source with a literal expected AST; resolution cases supply constructed ASTs even without a production parser. Source-negative cases retain source and an expected diagnostic only. Malformed-AST cases are deliberate raw records.

Fixture builders only deep-clone or append authored records. They preserve duplicate IDs, invalid arity, source bytes, ordered arguments and nested/duplicate union members. They do not resolve names, infer binders, assign identities, calculate semantic expectations or normalize input. This lets downstream tests represent both valid and invalid cases faithfully.

The versioned repository package is canonical after landing; the L1 bead mirrors this reviewed HTML. The prose and tables render standalone with optional highlighting, while corpus execution and relative source links require the adjacent repository assets listed in assets.json.

L3 consumes grammar, source pairs and implicit-binder rules. L4 consumes the AST, explicit environment and resolution outcomes without waiting for L3. L8 consumes exact sources, local IDs and byte-span conventions. L9/D4/H6 consume the extension seam and own their new family grammars. A passing integrity suite establishes that these inputs are consistent and recoverable, not that any consumer conforms. Implementation support and unresolved gaps must be recorded by the consuming task.
