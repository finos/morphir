Scopes, modules, imports and exports

L2 · morphir-ukvn.7.5 · morphir-scopes/0.1.0-draft.1 · 19 October 2026

Give the parser and resolver one bounded source-organization contract. Namespace spelling and file layout do not choose package ownership. Modules collect declarations across the complete supplied source set, while each contribution keeps its lexical imports. This package publishes grammar, constructed scope facts and independently authored observations. It implements no parser, resolver, semantic checker or compatibility runner.

Profile and decisions

morphir-scopes/0.1.0-draft.1 is an exact prerelease profile, independent of the IR format and composed with L1 morphir-declarations/0.1.0-draft.1. Its local choices make the parent conceptual design draft 0.17 consumable. They do not claim maintainer approval of a complete language. The source keyword is namespace; package is not a second layer or an accepted synonym in this profile. .mfs identifies authored source, including contract-focused files. .morphir remains reserved for a future model package whose container encoding is undecided.

General implementation bodies, explicit function generic punctuation, text/templates, contract/trait/requirement authoring and module composition remain with their owning tasks. L2 does not select their grammar. A later profile may add supported families through a versioned adapter without widening L1's closed declaration union.

Container and export syntax

grammar.ebnf defines the container grammar and its L1 join. A namespace or module uses either braces or a mandatory header semicolon. Model wrappers use braces. Namespace/module paths contain one or more L1 ASCII upper identifiers separated by dots; a model has one upper identifier. Imports end in a semicolon. Exports and selected imports use type T, fn f or constructor T.C. The data selector for fn has kind value.

namespace Finos.Lending;
module Types exposing (type Quantity, type Choice, constructor Choice.Yes) {
  type alias Quantity = Int
  type Choice = Yes | No
}
module Returns exposing (fn remaining);
import Finos.Lending.Types as Types;
import sdk::Collections.List as List;
fn remaining(outstanding: Types.Quantity, returned: Types.Quantity) -> Int

A module alias is explicit: import Finos.Lending.Types as Types;. A selected import is explicit: import Finos.Lending.Types exposing (type Quantity);. These are separate forms in this profile. An import without either form, a wildcard or a combined as/exposing form is rejected. Importing a type never implicitly imports a constructor. Constructor selectors identify the owning type even if type and constructor share a spelling.

L2 adds namespace, model, module, import, as, exposing and constructor to L1's reserved keywords within the composite profile. They cannot be lower identifiers there. A complete declaration ends before a following container/import keyword, separator semicolon or owning region boundary. Standalone L1 retains its own reserved set; the composite restriction does not silently revise that profile. No statement is terminated merely by a newline.

Lexical regions and reopening

A file starts with an empty source namespace, independently of the build's IR Package name. A namespace header selects a sibling prefix relative to its enclosing lexical base. namespace Loans; followed by namespace Accounting; at file root selects Loans and Accounting, never Loans.Accounting. Inside a namespace block, headers are relative to that block's base, not the previous sibling header. A namespace block extends the currently active prefix and restores the exact prior region on exit.

A module path is relative to its enclosing namespace; at file root it is fully qualified within the compilation unit. A module header ends before the next sibling module, namespace or model item, or the end of its owning block/file. A block module ends at its brace. Following sibling modules never nest implicitly. A model wrapper groups modules and conceptual context, but its name adds no module path segment. Namespace declarations inside a model or module and declarations outside modules are syntax errors in this bounded profile.

Structural brace nesting and a selected header region are distinct. A sibling module declaration of either form closes the previous module header. Thus module A; ... module B { ... } returns to the owning namespace/file after B, not A; further core declarations need another module. A top-level namespace item also closes a selected module header before being interpreted in its enclosing namespace, rather than becoming a namespace nested inside that module. By contrast, namespace A; namespace B { ... } enters A.B and restores A on exit. A namespace header replaces the current sibling header relative to the surrounding brace/file base. No block restores an already-closed module header.

Regions carry ordered entries. Collect all declarations in the complete supplied source set before resolving imports or references, allowing forward references and cyclic module-import graphs. An import is effective only for following entries and child regions entered after it. A later enclosing import does not retroactively affect an earlier child. Closing a block restores inherited bindings; starting a sibling header ends the prior header's local imports.

Reopening a canonical module merges disjoint declarations and unions explicit exports, retaining each contribution's source, region and import environment. Repeated exports of the same owned declaration across contributions are redundant and accepted; duplicate selectors within one list are diagnosed. Duplicate declarations in the same category or distinct authored module paths that normalize to the same canonical path are errors, never last-writer-wins merges. The same authored module path may reopen. A type and its constructor may share a local spelling because their categories differ.

Constructor collision keys are module, constructor category and canonical local Name. The owning type ID checks ownership, not an extra naming namespace: type A = Same and type B = Same in one module conflict. Type A and constructor A may coexist in their distinct categories.

Reordering sources or splitting/combining files preserves resolved semantics only when the explicit build context, declaration IDs and every contribution's namespace/import environment are retained. A new file does not inherit the old file's header or imports. File extensions and filenames do not determine module identities.

Build and model context

The input names one compilation unit, one explicit canonical IR Package name, a closed list of source IDs and one output-model snapshot. Each source ID occurs once and names supplied exact bytes/revision; adapters normalize filesystem aliases before this boundary and reject inconsistent duplicate membership. The contract performs no path discovery or I/O. Changing a namespace cannot change package ownership. Multi-package compilation requires separately declared units and dependency edges.

A model wrapper resolves its source-qualified name from namespace plus model name. A supplied modelBindings record associates each wrapper region with an existing model ID, exact revision and metadata snapshot. It must agree with context.model, including any qualified name. That optional qualifiedName is an authored source-model path, not an IR FQName or PackageName. Conflicting IDs, revisions, names or metadata properties are diagnostics; no model is synthesized or silently selected. Snapshot metadata is preserved, not interpreted as executable source. Identical wrapper bindings may reopen. Merging newly authored conceptual metadata belongs to the M1/L9 adapter, which must supply one coherent snapshot before this boundary.

Module-only source requires the same explicit output-model context and retains it unchanged, including required intent, requirements, contracts and provenance. It needs no fake model wrapper. A model wrapper named LendingRules containing module Returns is not equivalent to a standalone module LendingRules. Missing context is a structured context diagnostic, never an inferred artifact from a filename. Empty modules and empty supplied source files are valid when context is complete.

Names and identities

Keep authored identifiers, canonical IR Names and stable declaration IDs separate. Dots delimit source path components. Each component becomes one canonical Name under the source-spelling rule below; components join with / for ModuleName. Preserve the build PackageName independently. The IR FQName encoding remains package:module#local; a constructor also retains its owning type identity and category. See IR naming. Scope resolution never lowercases a complete qualified path or infers a package/module split from it.

Exact ASCII source-spelling normalization

This profile uses the existing camel/Pascal segmentation direction, applied as source spelling rather than permissive canonical decoding. Split an identifier at underscores, discarding empty chunks. Within each chunk scan left-to-right: a single uppercase letter flushes the current word and starts a lowercase word; a run of two or more uppercase letters is one initialism. If such a run is followed by a lowercase letter, its last uppercase letter starts the next word. Lowercase letters and digits append to the current word; after an emitted initialism, subsequent digits start a new word. Flush a final word. Serialize ordinary words lowercase and initialisms uppercase, joining segments with hyphens. Reject an empty result. This fixes source conversion separately from decoding already-canonical names.

Canonical facts in constructed inputs are authored adapter inputs, not normalization results calculated by fixture builders. A production adapter must validate the supplied spelling/canonical association against this rule. Existing canonical Name readers remain unchanged; feeding a raw source token to a canonical-first decoder is not this adapter.

Symbol IDs name existing logical declarations; L1 fragment/node references retain syntax identity and exact source spans. Reference observations preserve original IDs, links, refinements, contracts and provenance. Source-only rewrites require refreshed source revisions/spans and an explicit identity mapping, as in L1/M1. This contract promises neither automatic edit-stable node IDs nor semantic identity based only on normalized spelling.

Import lookup

Unprefixed import paths are fully qualified module paths inside the current unit, even under a namespace. import Types as T; does not search the current namespace for Types. Use the complete path. A dependency import sdk::Collections.List selects the exact supplied dependency slot sdk, normalizes the authored public path to collections/list, then looks that key up in the slot's Package export table. An alias may map it to internal module data/sequences. Never bypass that table by looking up the internal path directly.

Dependency slots bind explicit resolved-node IDs, revisions and IR Package names. Two slots may bind different releases with the same IR Package name. A resolved target must retain the slot and resolved-node binding alongside its IR FQName; FQName alone cannot distinguish those graph instances. Unknown slots, unavailable export paths, missing exported modules or private declarations are diagnostics, with no fallback to another package, file or network. Package acquisition and version solving are outside this contract.

A module alias grants qualified lookup of public declarations, not unqualified names. Selected imports grant only explicitly selected public names in their own category. Alias bindings occupy the module-qualifier namespace; selected type/value/constructor bindings use their declaration categories. Distinct bindings for the same key in an effective lexical environment are errors, including inherited conflicts; they are not shadowed by import order. Repeating the identical target binding under the same key is accepted redundancy and retains both source records. A selected import colliding with a current-module declaration in the same category is an error. Different categories remain distinct.

Lookup uses an explicitly supplied local binder first for an unqualified reference, then the collected current-module declarations and applicable explicit imports. Binder shadowing does not authorize conflicting import declarations. Qualified references require their module alias; no implicit parent-module or namespace search exists. Probes carry an expected category, and constructor probes include the owning type ID. Arbitrary longer dotted reference paths are unsupported by this lookup profile rather than guessed as implicit imports.

Cyclic module imports do not imply recursive values or alias validity. L4 separately rejects unproductive type-alias cycles and validates constructor-guarded recursion under L1. No bodyless function becomes callable through an import. Initializer/evaluation cycles and implementation availability are separate semantic/capability checks.

Public surfaces and opacity

Declaration exports, constructor access and package-level module exports are different boundaries. An omitted module exposing list means no public declarations; exposing () is explicitly empty. Current-module declarations remain usable by all contributions of that same module. Imports from another module, including the same unit, require explicit declaration exports. A dependency additionally requires an entry in its Package export table.

Exports name owned declarations collected across the whole module, so a header can export a later declaration or one in another contribution. They cannot export an imported declaration. An unknown target, wrong category, repeated selector within one list or import-only target is rejected. Exporting a constructor requires exporting its owning type and the constructor being public under that type's L1 constructorAccess. Opaque custom constructors and opaque-alias representations never become public through a selector. No wildcard implicitly exposes them.

The public signature graph must be closed over accessible public type identities. A public transparent alias or function signature that exposes a private type is rejected, including a transitive private dependency. Public opaque types hide their representation dependencies; consumers see only the public nominal specification. L4 derives those dependencies from L1 declarations and checks them; independently authored visibility fixtures state expected failures without implementing that checker here. Changing source visibility does not publish a package or supply implementations.

Constructed records

types.ts defines fixture-facing records. They are scope facts and references to L1 nodes, not a replacement parser AST or a widened core declaration union. Required arrays remain arrays so deliberately duplicated or invalid inputs can be represented. Raw structural-negative JSON need not satisfy the TypeScript input type.

The explicit named-type environment is the final type-lookup fallback after local binders, module declarations and imports. It supplies the fixture-only public abstract type Int. No implicit prelude is assumed; type identities and visibility are supplied, while numeric semantics and IR projection mappings are outside this package. A consumer requiring those mappings must obtain them explicitly. The pinned env.json is copied into each constructed input, so a resolver need not fetch context from a hidden file.

Locations reuse L1 half-open UTF-8 byte spans into exact source text/revision. Sources and L1 fragment source records agree byte-for-byte. L1 fragments are extracted declaration projections under the composite profile; their full container sources are not standalone L1 fragment inputs. Region spans contain their entries; nested parent spans may overlap children. Empty/end-of-file probes are allowed. Required references exist; syntax IDs are unique within their L1 fragment. Duplicate unit symbol IDs are structural errors. A declaration belongs to one module contribution, while imports never clone or move it.

Unit symbol IDs are unique within the compilation unit. Dependency symbol identities are keyed by resolved-node ID plus symbol ID, not globally across all supplied slots. The same logical symbol ID may occur in different release nodes, and two slots may repeat one exact node. Repeated inventories for the same resolved node must agree on revision and content. Reference observations preserve the selected slot as well as node, revision and symbol ID.

Optional critical fields follow L1's record-local rule: distinct present required-member names, unknown critical members yield unsupported, malformed known members are rejected. Unknown uncritical data may be retained for rich preservation; it does not create a recognized symbol family. L9/D4/H6 own future versioned categories, payloads and lookup rules. A requested unknown family/profile must report unsupported.

Stable primary diagnostic codes use scopes.syntax.*, scopes.structure.*, scopes.resolve.*, scopes.visibility.* or scopes.unsupported.*. A source diagnostic carries an exact span. A facts diagnostic carries an existing JSON Pointer into its supplied input and may identify related locations. Human wording and additional noncontradictory diagnostics may vary. Alias-cycle rejection is semantic, not a parser failure. Resource exhaustion is a separate inconclusive failure, never an accepted or resolved observation.

Syntax cases have source-only inputs and a parse-only SyntaxOutline oracle containing regions, imports, L1 fragments and declaration-node associations. They contain no logical symbol IDs, model snapshots, lookup probes, links or provenance to invent from source. Regions use declaration entries referring to L1 nodes, not semantic symbol entries. Syntax/region/import node IDs may be bijectively renamed while preserving all references; exact source IDs, byte spans, spellings, declaration structure and L1 binder origins must agree. A separate scope adapter consumes explicit semantic identity/model bindings and lookup probes from constructed inputs. Probe comments are retained source, never instructions to synthesize references.

Expected tables, bindings and diagnostics are literal independently authored assets. Integrity tests verify pinned bytes, references, locations and required coverage, but do not run a name resolver or calculate expected semantic results. Later implementation adapters report actual results through the existing shared conformance machinery; this package creates no second runner or current compatibility claim.

Fixtures and handoff

cases.json records source/facts/expected assets and requirement coverage. assets.json pins byte lengths and SHA-256 hashes for the whole reference package. Literal .mfs sources preserve LF/CRLF, Unicode comments and exact final newlines. Source cases carry identities/revisions independently of their authored facts.

Fixture builders clone or append supplied records without resolving names, assigning identities, normalizing spelling or fetching files. The same-file, split-file, reordered-file and header/block variants share independently written semantic observations while retaining different source locations. Negative cases preserve the original invalid inputs instead of repairing them in a helper.

mise run conceptual:fixtures-check
bun test spec/conceptual/language/scopes/fixture-builders.test.ts \

L3 consumes the container grammar and source/fact examples. L4 consumes constructed facts, explicit dependency export tables and scope/visibility outcomes without waiting for L3. L8 consumes source IDs, regions and locations without confusing recovery nodes with conceptual gaps. Tree-sitter issue #1083 can extend the declaration subset from this contract; a CST is not semantic qualification. L9 supplies conceptual-family metadata and expression adapters, preserving existing model and declaration IDs.
