Typed contracts, cases and observations

This is the shared reference contract for morphir-contracts/0.1.0-draft.1. It defines records, outcomes and authored examples. It does not deliver a checker, evaluator, admission routine, encoding validator, implementation binding or compatibility runner. Scope and versions

C1 fixes the interface that later tasks consume: typed clauses, typed cases, exact values, capability budgets, diagnostics and observations. A supplied candidate result can be checked before an operation implementation exists. Computing a result from a relational specification is a separate capability and is not promised here.

Terminology follows CONTEXT.md: the modeled result and its retained carrier are a Morphir model. C1 records carry a model identity and revision, and no other carrier term is used for that result in this contract.

The exact profile is morphir-contracts/0.1.0-draft.1. Records use recordVersion: "0.1.0-draft.1". The exact-value profile is morphir-contracts/exact-values/0.1.0-draft.1 and the bounded expression profile is morphir-contracts/expressions/0.1.0-draft.1. These versions are independent of the M1 conceptual profile morphir-conceptual/0.1.0-draft.1, model revisions, contract revisions, IR format versions and provider releases. A prerelease matches only exactly, under the repository SemVer policy. C1 implements no version negotiation.

The pinned design is beads morphir-ukvn.7, sections contracts, evidence, rentals and acceptance items 21 and 22. The parent plan names draft 0.16; the stored design has since advanced. C1 pins the named sections and their semantics, not a draft number. Maintainer decisions on 19 October 2026 fix the flat layout spec/conceptual/contracts/, the design outcome set with exhaustion as an execution-error detail, and the canonical partial-return corpus with exact Int values as string lexemes.

Contract and clause records

A contract record names one operation, its ordered typed inputs, its result type, its revision and its clauses. Clause records are separate, identified records so a report can name the exact clause that was satisfied or violated.

contract {
  id: Id, revision: Revision, operation: { name, inputs: [{ name, type }], result: type },
  requirementRefs: [Id], clauses: [clauseKey]
}
clause {
  id: Id, kind: refinement | invariant | precondition | postcondition | frame,
  subjectType?: typeKey, contract?: contractKey,
  binders: [{ name, role: self | argument | result, position?, type }],
  matchBinder?: { name: "resultValue", role: "constructor-payload", type },
  modelClauseRef?: Id,
  text: String, expressionProfile?: ProfileId, expression: Ast
}
Clause kindBindings and interpretation
Type refinementself is a value of the underlying type. The predicate determines admissible values. A failed refinement on a supplied value is invalid.
Record invariantself is the complete record. It can relate multiple fields. A failed invariant on a supplied value is invalid.
Operation preconditionNamed input arguments only. False means the contract does not promise a result for that call. It produces not_applicable. It is not a guard, exception or modeled rejection.
Operation postconditionNamed inputs and result. All applicable postconditions must hold. False produces violated with the clause identity.
Frame conditionAn explicit postcondition that states which identities or fields remain unchanged. It uses postcondition bindings and the violated outcome. No implicit preservation of unspecified fields is assumed.

Ordinary business rejection belongs in a result alternative and its postconditions. In the corpus, OverReturn is a modeled rejection. An over-return checked against an Ok candidate violates the rejection clause. The same over-return checked against an unknown constructor is an invalid candidate, not a violation.

Binder names come from the operation signature. A checker does not keep a separate argument-name list, and it does not infer a package from a dotted source name. Duplicate or reserved binders are invalid contract records in a checker; this corpus contains none. Two inputs remain distinct from one tuple input, and a function-valued result is not flattened into inputs.

Typed values and exact encoding

Cases carry typed values as test descriptions under the exact-value profile. This profile is not a new wire encoding and does not replace an IR value encoding.

TypeCase spelling
IntA JSON string that matches (0|-?[1-9][0-9]*). Precision is arbitrary and comparison is by integer value. Zero has the one lexeme 0. A JSON number, plus sign, signed or padded zero, leading zero, decimal point or exponent is invalid, not a coercion.
BoolA JSON boolean.
StringA JSON string, retained exactly. An empty string is a valid String.
FloatA JSON string that carries the authored decimal lexeme, as a test description only. No float predicate is evaluated in this draft.
RecordA JSON object with exactly the declared fields. Field order is not semantic. A missing field, extra field or wrong field type is invalid.
Custom typeA JSON object with exactly one member. The member name is the constructor and its value is the payload: {"Ok": ...}. A constructor without a payload uses null: {"OverReturn": null}. Extra members and an unknown constructor name are invalid.
TupleA JSON array with exactly the declared arity and order. Each element uses its element type spelling. A flat tuple and nested tuples remain distinct.
Untagged unionThe spelling of exactly one member type. Membership is resolved against the declared members during admission. A value admitted by more than one member is ambiguous: it is invalid, never resolved by member order.
Refined typeThe base spelling, then the named refinement clause. Refinement failure is invalid, before any postcondition.

Exact integers above the JS safe range and above the machine-integer range appear in the corpus as string lexemes. A checker that routes them through a machine integer or a JS number has a defect. Case contracts-0016 exists so that rounding hides a real violation if precision is lost.

Bounded expression profile

The first predicate profile supports Bool, arbitrary-precision Int, String, transparent and opaque aliases with refinements, immutable records, tuples, untagged unions of supported member types and algebraic data types with finitely many named constructors, including Result. Parameterized declarations are instantiated at concrete argument types for checking examples. Named types resolve within functional modules and explicit imports.

Supported expressions are literals, parameter and field references, arithmetic addition and subtraction, comparisons, Boolean connectives, conditionals, exhaustive matching and a small versioned set of pure predicates such as string non-emptiness. In a match on a custom result, the selected constructor payload is bound as resultValue inside that arm. Its type is the payload type of the selected constructor, and the clause record declares it as a matchBinder with that type. Every other binder in an expression is declared in the clause record. Bindings and operand types resolve before execution, and an undeclared binder is an invalid clause record. A match without an arm for every constructor of its subject type is also an invalid clause record. Inside an expression, a binder of a refined type has its base type; the refinement is an admission obligation on supplied values, not an implicit subtype or coercion in the expression.

Calls to arbitrary user functions, recursion, host effects, clock access and random draws are outside this profile. Such a clause is unsupported. There is no general quantifier or temporal-logic solver in this delivery. A future profile can add exact decimals, units of measure, dates, collection quantification or proof backends. Each such profile states its semantics and capability claims under its own version.

Declaration expressiveness, structural validation and executable predicate operations have separate capability inventories. A floating-point signature can be represented while its predicate operations remain unsupported, as case contracts-0017 shows.

Capability budgets

Execution is bounded by an explicit budget record. No budget is inferred from a type, a contract or a previous check.

budget { maxSteps, maxDepth, maxValueNodes, maxIntDigits }

Each evaluated expression node is one step. Depth is expression and value nesting depth. maxIntDigits counts decimal digits in an exact Int lexeme, without the optional minus sign. The limits bound the whole check, including value admission: digit, depth and value-node limits are checked when supplied values are admitted. The corpus default is { maxSteps: 1000, maxDepth: 64, maxValueNodes: 10000, maxIntDigits: 256 }. A case can supply a smaller budget; a case that omits budget uses that environment default, and an observation records the effective budget. The default is a profile rule, not an inference from a type, a contract or a previous check. A check that would exceed any limit stops; using exactly a limit is allowed. It reports execution-error with detail { kind: "exhaustion", limit: "maxSteps" } (or the limit that was reached). An exhausted check cannot establish satisfied, violated or not_applicable. A budget never turns an exhausted check into a pass. Each of the four limits has an exhaustion case in the corpus.

Cases and supplied-result mode

A case is an authored, identified record with an expected observation. The expected observation is established independently of any checker. A checker produces an observation; a runner compares it with the expected observation. These two results stay separate.

case {
  id, description,
  input: {
    mode: supplied-result | typed-value,
    contract?: contractKey, type?: typeKey,
    context: { model: { id, revision }, contractRevision },
    inputs?: { binderName: TypedValue }, candidate?: TypedValue, value?: TypedValue,
    availableProfiles?: [ProfileId], budget?: budget
  },
  expected: {
    outcome, detail?: { kind: exhaustion, limit },
    clauses: [{ clause: clauseKey, observation }], postconditionsEvaluated?: Bool,
    diagnostics: [{ code, path }]
  }
}
ModeMeaning
supplied-resultThe case supplies named inputs and, for postcondition checks, a candidate result. No implementation is required or invoked. If the candidate is absent and the contract applies, postconditions are not evaluated and the outcome is inconclusive with contracts.missing_result. Absence is never satisfied.
typed-valueThe case supplies one typed value. Refinement and record-invariant clauses for that type are the whole check. No operation, candidate or implementation is involved.

A negative case passes as a case when its observed outcome equals its expected outcome. The contract observation itself stays violated, invalid or whichever outcome was observed. Generating a case is not passing it, and a case record is not execution evidence.

Checks in supplied-result mode use this order, and an earlier outcome stops later phases:

  1. Resolve the named model and contract revisions against the supplied context. An exact revision that is not provided is inconclusive (contracts.revision_unavailable). Then resolve the selected profile and type inventory: a clause whose expression profile or operator is not supported is unsupported, and a case that names a type outside the inventory is unsupported (contracts.unsupported_type). Capability is decided before any value is admitted or evaluated.
  2. Check that each named input is present. An absent input is inconclusive (contracts.missing_input).
  3. Admit each input under its type, refinement and invariants, under the effective budget. A failure is invalid; a reached limit is execution-error. Budget limits are checked in the phase that consumes them: digit, depth and value-node limits in this admission phase, and step limits during precondition and postcondition evaluation. An exhaustion in an earlier phase stops later phases, so admission exhaustion precedes candidate admission (case contracts-0042).
  4. Evaluate preconditions. A false precondition is not_applicable. This precedes candidate presence and candidate admission, so a false precondition with an absent or invalid candidate is still not_applicable (cases contracts-0029 and contracts-0030).
  5. Check candidate presence. An absent candidate in an applicable case is inconclusive (contracts.missing_result).
  6. Admit the candidate under the result type. A failure is invalid.
  7. Evaluate each postcondition and frame clause. Any false clause makes the outcome violated; otherwise it is satisfied.

The case states postconditionsEvaluated: false where an earlier phase stopped the check. In typed-value mode only steps 1 and 3 apply, against the named type: an unknown type is unsupported, an admitted value that meets its refinement or invariant is satisfied, and a failed one is invalid.

An omitted availableProfiles means the environment supportedProfiles. An omitted budget uses the environment default, and an exhaustion path under /budget then names the limit in that effective budget, as recorded in the observation.

Observations and outcomes

An observation record names the case, the context, the mode, the overall outcome, one observation per evaluated clause, any diagnostics, and the budget that bounded the check. It retains the model, contract and source revisions from the case context. A changed revision makes a prior observation historical for a new context. It does not delete or rewrite that observation.

OutcomeMeaning
satisfiedAn applicable, supported contract was evaluated and every evaluated clause held.
violatedAn applicable, supported contract was evaluated and at least one postcondition or frame clause did not hold. The clause identities are named.
not_applicableThe operation precondition is false. Postconditions are not evaluated.
invalidA supplied input or candidate fails its type, refinement or record invariant. This is a diagnostic outcome, not a violated postcondition.
inconclusiveRequired information is missing: a named input, a candidate result in supplied-result mode, or the exact named revision. Missing information is unknown, not false and not satisfied.
unsupportedThe case needs a type, expression profile or predicate capability that the selected profile does not support. Unsupported is never satisfied.
execution-errorEvaluation failed or reached its limits. Exhaustion is the detail kind for a reached budget limit. An execution error cannot establish a guarantee.

No outcome except satisfied is a passing contract observation. A runner can still report a case as passed when the observed outcome matches an expected non-satisfied outcome. The observation and the case result are different facts.

Diagnostics and revision scope

A diagnostic has a code and a path. The path is an RFC 6901 pointer into the case input. The empty string selects the root. Messages can explain a problem, but messages are not fixed oracle strings. Diagnostic order is not semantic. Compare code, path and stated detail as a set.

CodeBoundary
contracts.invalid_inputA supplied value fails its declared type, refinement or record invariant, or a candidate fails its result type.
contracts.ambiguous_valueA supplied value is admitted by more than one member of an untagged union, so no single member semantics applies. This is found during admission, unlike a capability gap decided before admission.
contracts.missing_inputA named input binder has no supplied value. The value is absent, not rejected.
contracts.missing_resultA supplied-result case supplies no candidate. Postconditions are not evaluated.
contracts.unsupported_semanticsA clause needs an unsupported expression profile or predicate.
contracts.unsupported_typeA case names a type outside the selected inventory.
contracts.execution_exhaustedEvaluation reached a declared limit. Always an execution-error detail.
contracts.revision_unavailableThe case names a model or contract revision that the context does not provide exactly. A different revision is not evaluated silently.

Path rules are part of each code. contracts.invalid_input names the supplied value that failed. contracts.missing_input names the absent input slot. contracts.missing_result names /candidate. contracts.unsupported_semantics and contracts.unsupported_type name the case slot that selects the unsupported capability (/contract or /type). contracts.execution_exhausted names the reached limit under /budget. contracts.revision_unavailable names the revision slot that did not resolve.

These codes belong to the contracts profile. They parallel the M1 graph codes without replacing them: a graph inspection still reports conceptual.invalid_input and its other codes for graph records. A contracts checker reports the codes above for case checks. Every observation retains the source and revision scope of its case: model id and revision, contract revision, and, when an implementation is bound by a later task, that implementation identity and revision. Runtime outcomes from a bound implementation remain distinct from contract observations.

Reference corpus

The environment also records the one model identity and revision that case contexts resolve against. A case that names another model revision is case contracts-0037.

cases.json holds 42 independently hand-authored cases. Its corpusVersion is exact 0.1.0-draft.1 and its status is reference-only. environment.json holds the type, contract and clause records that case keys resolve against. The literal lengths and SHA-256 digests in assets.json detect accidental changes. They do not compute expected outcomes. No expected outcome in this corpus was produced by a checker.

The canonical operation is the proposed partial-return extension from the pinned design. It is separate from the canonical rental request fixture, whose historical behavior stays unchanged. acceptReturn(loan, returned) returns an Ok loan with the balance reduced and the id and asset preserved, or the modeled rejection OverReturn for a larger return. Zero is accepted. Negative quantities are invalid refined inputs. The separate remaining operation carries the precondition example, and requireLabel shows that an empty string is a valid String whose precondition is false.

Coverage groups in the corpus name satisfied, violated, not_applicable, invalid, inconclusive, unsupported and execution-error cases, plus frame, supplied-result and exact-int groups. The operation names and case keys are fixture instructions. They are not a new CLI, RPC protocol or MCK operation registration.

Open decisions

This draft fixes the record structure, outcome set, value profile, expression profile boundary, budget fields and case modes that consumers need. It does not settle these items, and it does not invent approval for them:

  • Textual DSL grammar for contracts, delimiters, file extensions and source spelling of clauses.
  • Exact step, depth and digit counting in a real evaluator, beyond the counting rules stated here. C3 owns that calibration.
  • Float, decimal, units-of-measure, date and collection-quantification profiles. Each needs its own versioned semantics.
  • Bound-implementation invocation, implementation identity issuance and evidence storage. C4 owns these.
  • Whether the contracts profile joins the M1 conceptual graph as contract entities with this exact record spelling, or maps to it through an adapter. Until that is settled, each C1 clause that restates an M1 graph clause carries a modelClauseRef to that M1 entity. The M1 entity stays the graph authority and the C1 record stays the contracts-profile authority. Neither record silently replaces the other.
  • General proof, solver-based input synthesis and computing a result from a relational specification.
