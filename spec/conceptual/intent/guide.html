A source edit

A requirement keeps its source identity when its wording changes. Its old evidence retains the revision it examined. The portable MoonBit intent library accepts these facts as caller-supplied records, produces a read-only requirements view, and reports whether each observation still has the requested revision context.

The original source retains Track returns.\r\n Keep identity.\n at document revision doc-1. The edited source retains Accept partial returns.\n at doc-2. Both use document ID urn:document:return, local Source ID urn:source:return and fragment anchor return.

The complete before/after contexts and literal example expectations are authored data. They are not generated from test results. Every observation in these examples is marked hand-authored-fixture; none claims that a domain evaluator ran.

KB identity and lifecycle

The existing KB service derives its short intent ID from the leading digits of a filename. That number is scoped to a bundle. Its JSON view includes path and slug, but no document revision. The adapter therefore requires the caller's stable document, source and entity identities, exact revision, anchor and original excerpt. Bundle, short number, slug and state remain KB origin metadata. The adapter never derives logical identity from a path or short number.

The service owns Backlog, Refinement, InProgress, Released, Cancelled and Superseded. Missing state remains absent. All seven input possibilities are tested. A lifecycle change produces no contract, scenario or observation. Human acceptance remains review evidence. There is no PRD command in the pinned KB service; prd_view projects supplied requirements without creating another register.

Functional, data, performance, operational and regulatory requirements use the M1 category namespace. Explicit extensions such as example:availability coexist with them. EARS classification belongs in notation, independently of category. A requirement may refine several intents, and several requirements may refine one intent.

Constructed model API

The library is finos/morphir-conceptual/intent. It implements an inspection slice of the exact M1 contract. The caller owns the complete model; the slice preserves source and requirement data and the links needed for assessment. It does not decode or replace the graph's Ion carrier.

In particular, a scenario's retained content is opaque, and this library does not validate contract binders or declaration signatures. Full record decoding and semantic validation remain separate work.

Evidence currency

Assessment compares the complete model, entity, source-document and implementation revision sets. Order does not matter. A changed revision or added subject makes the old observation stale. A missing required dependency makes assessment inconclusive. Requirements come from both the claim's and observation's declared contexts, explicit model links, source refs and run clauses. Supplied entity, document and artifact snapshots participate even when their declared dependency has no graph link. Exact references select their snapshots; conflicting unlinked candidates remain inconclusive.

PRD example links include scenarios in supplied dependency models. Each relationship is validated in its owning model. A scenario for another revision of the same contract does not satisfy the selected contract's example link.

Each support or contradiction keeps its own relationship identity, evidence kind, payload and currency. Analysis, review and run remain distinct. An observed Ion null differs from absent output. No observation means unknown. A malformed graph or claim query yields an invalid assessment without usable observations.

ResultWhat it establishes
CurrentRecorded context matches the complete requested context and supplied relevant snapshots.
StaleThe recorded context differs from the requested or supplied relevant snapshot.
InconclusiveRequired context or a relevant source is unavailable.
Support and contradiction togetherBoth authored assertions are retained. Neither overrides the other.

Currency says nothing about whether the claim is true. Accepted review does not become a run, type analysis does not become behavioral proof, and generated scenarios do not become executed evidence. The API has no proof Boolean.

This delivery adds no parser, DSL, evaluator, carrier, runtime provider claim, capability admission, source discovery, synchronization, CLI lifecycle or compatibility runner. It does not verify source digests or prove equivalence to prose. The source slice accepts exact revisions; a future digest adapter must verify original bytes before admitting their identity. Original M1 models and rich carriers remain authoritative outside this bounded inspection slice.
