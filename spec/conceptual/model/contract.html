Conceptual model contract

morphir-ukvn.7.7.1 · M1 · 18 October 2026 · Proposed exact draft 0.1.0-draft.1

This is the shared reference contract for morphir-conceptual/0.1.0-draft.1. It specifies records, boundaries and authored examples. It does not deliver a compiler, semantic checker, evaluator, model transport implementation or compatibility runner. The concrete record choices below are local draft proposals, not a claim of maintainer approval of syntax, trait names or implementation details.

Scope and versions

A conceptual model can describe an agreed concept before anyone chooses its data representation. It can also retain requirements as prose, complete function specifications without implementations, source snapshots, typed contracts, claims and observations. A valid graph does not imply that its contracts are executable or that its requirements have been met.

This draft chooses a finite built-in graph vocabulary and an existing rich IRUnit carrier. It makes no changes to the IR Distribution variants, IR format-version contract or MEP envelope. The conceptual profile, graph record version, model revision, semantic IR format, transport envelope, expression dialect and provider capability versions are independent.

IdentifierRule

Model, entity, source and artifact revisionsOpaque snapshot identities, compared exactly. They are not version ranges. A caller must not reuse a revision for changed content.
IR formatThe examples use canonical formatVersion: 4 for the existing draft IR 4.0.0. No IR 4.1.0 format is introduced.

Follow repository SemVer policy for future contract versions. Parse versions with the language's established SemVer library; released 0.y versions use minor compatibility and prereleases match exactly. Nothing in M1 implements version negotiation. A consumer cannot advertise conformance from passing the fixture-construction tests.

The first preview may use built-in semantics for this vocabulary without authenticating a metadata provider. That does not change the trust rules for separate linked-metadata providers, nor does it authenticate an author or make a claim true.

Record conventions and graph

The following tables define a concrete draft data shape. Names are case-sensitive. A field is required unless followed by ?. Empty lists are written explicitly. String means Unicode text; Id and Revision are nonempty strings. IDs in these examples are absolute URIs. Consumers treat them as opaque identities and never derive an ID from a label, file position, normalized name or local alias. Nat means an exact nonnegative integer. Record member names occur at most once. Variant tags select exactly one shape; fields belonging to another variant are invalid.

IonValue means the full Ion value model, including annotations, exact numbers, symbols and typed nulls. The JSON graph fixtures deliberately use its JSON-compatible subset. They are data examples, not a JSON replacement for the rich carrier. Unknown members are descriptive unless named in the containing record's critical list; readers retain their Ion values. Unknown critical members or semantic profiles prevent a required interpretation, with an unsupported result. This retention rule does not permit an unsupported discriminator to be interpreted as a known variant.

dependenciesList of {model: {id, revision}, inputId: Id}. Each input is explicitly supplied in the build context; no ambient lookup or fetching is permitted.
requiredSemanticsList of exact, versioned semantic profile identifiers required to interpret this graph. Empty means storage does not require a particular expression interpreter; a requested check still admits the profiles of the clauses it uses.

Record list order is retained for round-trips and diagnostics. Identity and relationship semantics do not depend on that order. Duplicate IDs across the graph's four record lists are invalid, including duplicates whose revisions differ. A later version of an entity belongs in another model snapshot or in explicitly identified historical evidence, not in a second same-ID row. Dependencies may contain another revision of the same logical model, but every reference must select one exact snapshot.

Identity, references and sources

An entity reference uses one of these variants. A resolved subject must point into the local graph or its declared, supplied dependency closure. There is no fallback to the newest matching name.

{
  "state": "resolved",
  "modelId": "urn:example:lending", "modelRevision": "model-1",
  "entityId": "urn:example:requirement:balance", "entityRevision": "r1"
}
{
  "state": "unresolved",
  "locator": "https://example.invalid/policy#return",
  "expectedKind": "sourceFragment",
  "reason": "The caller has not supplied this source."
}

The resolved variant requires all five fields. The unresolved variant requires state, nonempty locator, expectedKind and nonempty reason; it may additionally retain proposedId. Its locator is descriptive and never an acquisition instruction. A declared unresolved target is a visible gap. A resolved target that is absent, of the wrong kind or at a different revision is invalid. The unresolved target's expected kind must also satisfy the relationship signature.

Source fieldType and meaning
recordVersion, idSource-record version and identity within this graph.
document{id: Id, revision?: Revision, digest?: {algorithm: "sha256", value: String}}. A digest is lowercase 64-digit hexadecimal of the supplied original document bytes. A digest establishes byte identity, not authenticity. At least a revision or verified digest is needed for pinned evidence.
resolution"retained" or "unresolved". Retained requires at least one retained fragment. Unresolved requires a reason and may retain an excerpt without claiming the full document resolved.
locatorString identifying a caller-supplied location, URL, KB document or OKF document. Never implicitly dereferenced.
fragmentsList of {anchor: Id, text: String}. Anchors are unique within this source. Exact wording is retained, including spaces, line endings and final LF. An empty text is valid.
reason?, descriptive?, critical?Unresolved explanation and ordinary extension fields.

A SourceRef is {sourceId: Id, anchor: Id}. Both select a local Source record and retained fragment exactly; the document revision comes from that Source record. A SourceRef to a missing fragment is invalid. An unavailable external source is represented by an unresolved relationship target or an unresolved Source with no SourceRef to absent text. Inspection reports unpinned sources even when some wording has been retained.

A sourceFragment entity gives retained wording a graph identity and can be a derivedFrom target. It does not become an IR metadata owner. An explicit source refresh creates a new snapshot, source revision and reassessment context. Moving or renaming a file preserves IDs. Changing logical IDs requires an explicit old-to-new mapping owned by a separate transformation; this draft defines no automatic identity migration.

Entity records

Every Entity has recordVersion, id, revision, kind, name: String, sourceRefs: SourceRef[] and content. It may have the independent concern fields in the next section, descriptive and critical. Names and aliases have no identity semantics. An unknown kind is retainable but unsupported for kind-dependent checking. The content shape is selected by kind.

KindRequired content; optional fields marked ?
intent{text: String, rationale?: String}. Desired outcome and its reason.
requirement{category: Id, text: String, notation?: IonValue}. Initial categories are morphir:requirement-kind/functional, data, performance, operational and regulatory with that same prefix. Other namespaced categories are retained. EARS pattern classification belongs in notation, independently of category.
concept{definition?: String, aliases: String[], context?: String}. Absence of definition is reported; a generated view must not invent one. A concept is not an IR type.
dataElement{definition?: String, type?: IonValue, units?: Id, format?: Id}. A named representation linked to a concept by represents. A missing type remains a representation gap.
sourceFragment{sourceId: Id, anchor: Id}. Same resolution rules as SourceRef.
declaration{role, fqName?, typeParameters?, signature?, visibility?, representation?, publicSpecification?}, detailed below.
contract{clauseKind, subject, notation, binders, expression, compiledArtifact?}, detailed in Contracts, claims and evidence.
scenario{valueProfile: Id, inputs: IonValue, expected: IonValue, origin, typeArguments?: {parameter: Type}}. Origin is {kind: "authored", author: Id} or {kind: "generated", generator: {id, version}, configuration: IonValue, seed?: String}. A test definition is not run evidence.
implementation{artifact: {id, revision}, fqName: String, availability: "declared" | "supplied"}. Supplied means the caller supplied the exact artifact in the current context; identity alone does not make code executable.
claim{subject: ResolvedRef, proposition: String, author: Id, scope: IonValue, context: RevisionContext}. Evidence links are independent graph relationships.
evidence{evidenceKind, origin, context, ...}, detailed below. Observations may support and contradict the same claim.

Declaration role is function, type, field, parameter or result. A resolved function has a declared typeParameters: String[] and a signature in the existing v4 ValueSpecification shape. Argument names and their declared order remain available to contract binders. A projected declaration requires an explicit fqName; a checker does not infer the package from a dotted source namespace. A type declaration has typeParameters and its existing IR publicSpecification when supported. The visibility can be transparent or opaque. A known representation is {state: "known", type: IonValue, access: "public" | "defining-module"}; an undecided one is {state: "undecided", reason: String}. Known opaque representation data stays in the defining model, while public IR hides it.

Field, parameter and result declarations can retain a type and a resolved parent reference as additional content fields. This records dictionary links without inventing standalone IR nodes. These roles have no additional lowering rule in M1. A generic parameter is declared, not missing; a bodyless function can be a complete public specification.

Independent concerns

These fields are separate tagged sums. Omission means no fact was recorded about that concern. It never means complete, approved or implemented. Combining fields does not suppress any diagnostic.

FieldVariants and obligations
elaboration?{state: "open", aspects: [{id, question, rationale, sourceRefs}]} with at least one aspect; or {state: "settled", rationale: String}. Aspect IDs are local to the entity. This concerns domain knowledge, not parser validity.
definition?{state: "completeSpecification"}; {state: "completeDefinition"}; or {state: "authoredPartial", reason: String, sourceRefs: SourceRef[]}. Applies to declarations. A partial definition is authored work in progress and does not require an editor error.
recovery?{state: "clean"}; or {state: "recovering", sourceRef: SourceRef, diagnostics: Diagnostic[]} with at least one diagnostic. A recovery diagnostic has code, message and optional half-open span: {start: Nat, end: Nat, unit: "utf8-byte"} relative to the retained fragment's UTF-8 bytes. Syntax recovery may exist before typed IR exists.
review?{state: "unreviewed" | "pending", entityRevision, modelRevision}; or {state: "accepted" | "rejected", entityRevision, modelRevision, reviewer: Id, rationale: String}. These are assertions about the stated revision, not execution observations. A changed applicable revision makes the review historical.
implementation?{state: "unbound"}; or {state: "bound", binding: ResolvedRef} targeting an implementation entity. Applies to a declaration. A bound artifact must declare the same FQName and a compatible signature before invocation. The availability field and consumer evaluator still govern whether execution is possible.

A concept with an undecided representation remains valid conceptual knowledge. Using it as an executable type requires an explicit representation mapping. A checker reports that missing mapping instead of manufacturing Any, a type variable, an opaque representation or a passing result.

The existing IR IncompleteTypeDefinition, IncompleteBody, Hole and Draft forms keep their existing meanings. This contract does not automatically lower elaboration, review state, opacity or polymorphism into any of them. A future compiler can reuse a form only where the origin and semantics match; it must retain the reason and original source in the graph. Domain elaboration and compiler recovery can both apply to one declaration.

Relationship records

A Relationship has recordVersion, id, predicate: Id, subject: ResolvedRef, target: EntityRef and sourceRefs: SourceRef[]. Optional descriptive and critical fields follow the record rules. The relationship ID belongs to its enclosing model revision; it needs no independent revision field. Its direction is significant.

PredicateSubjectTargetMeaning
morphir:derivedFromrequirementsourceFragmentRetains the source of an interpretation.
morphir:refinesrequirementintentStates an obligation associated with the intent.
morphir:formalizescontractrequirementAsserts a formalization; does not prove equivalence to prose.
morphir:governedBydeclaration with function or type rolecontractAssociates obligations with the exact declaration named by the contract subject. Clause kind determines the permitted declaration role.
morphir:exercisesscenariocontractIdentifies what a case examines.
morphir:implementsimplementationdeclaration with function roleAsserts an implementation relationship. Does not establish fulfillment or grant a binding by itself.
morphir:supports, morphir:contradictsevidenceclaimScopes observations to claims, without precedence between supporting and contradicting observations.
morphir:representsdataElement or declarationconceptExplicit connection between meaning and representation. Does not grant assignability or conversion.

The graph may have multiple relationships to the same subject or target. It is not a maturity ladder and no transitive proof is implied. Duplicate relationship IDs are invalid; distinct assertion records with identical endpoints are preserved. Self-links, cycles and multiplicity have no extra inference rules in this bounded vocabulary; endpoints must still satisfy their signature.

Extension predicates use namespaced identities and an explicitly supplied, versioned signature/interpreter profile. An unknown descriptive predicate can remain opaque without semantic validation. An unknown required predicate is unsupported. A relationship cannot claim a known built-in predicate while bypassing its endpoint checks through descriptive metadata. Semantic dictionary mapping directions such as exact, close, broader and narrower need their own named profile with revision, provenance and review rules; M1 does not silently treat them as equality or coercions.

Contracts, claims and evidence

A Contract keeps authored notation and a resolved expression together. Its required subject: ResolvedRef names the declaration being constrained. Its required clauseKind is refinement, invariant, precondition or postcondition. Refinement constrains a type declaration and binds self to one value of its representation. Invariant constrains a record type declaration and binds self to the complete record. Preconditions constrain a function and bind only its input arguments. Postconditions constrain a function and bind its inputs and result. A frame condition is an explicit postcondition about retained fields, with no implicit preservation rule. A governedBy edge, when present, must agree with the contract subject; the edge alone never supplies a missing clause kind. notation is {profile: Id, text: String}. Each binder is {id: Id, role: "argument" | "result" | "self", name: String, type: IonValue, position?: Nat}. Argument binders require a unique zero-based position matching the declaration's argument order and name. Result and self binders do not have positions. Their presence must match clauseKind; argument names cannot use the reserved result name. Binder IDs are unique within the contract. Expression references name binder IDs; they cannot capture an ambient name.

expression is {state: "unresolved", reason: String} or {state: "resolved", profile: Id, ast: IonValue}. Resolved means the expression is represented in a specified typed dialect; a consumer still needs that dialect and its typing/evaluation capability. The fixture equality dialect is test vocabulary and does not define Morphir predicate syntax. An optional compiledArtifact is {artifact: {id, revision}, compiler: {id, version, profile}, contractRevision: Revision, argumentMap: [{binderId, position}]}. It identifies a derived executable artifact, retaining linkage to its authored contract. The authored contract remains authoritative.

A RevisionContext is the following shape. Each list contains distinct IDs. Revision matching compares all IDs and revisions, including the relevant subject set, rather than selecting a matching subset.

{
  "model": { "id": "urn:example:mixed", "revision": "model-2" },
  "entities": [
    { "id": "urn:example:requirement:identity", "revision": "r2" },
    { "id": "urn:example:contract:identity", "revision": "k2" },
    { "id": "urn:example:declaration:identity", "revision": "d2" },
    { "id": "urn:example:scenario:identity", "revision": "s2" },
    { "id": "urn:example:implementation:identity", "revision": "impl-2" }
  ],
  "sources": [{ "id": "urn:example:identity-source", "revision": "source-2" }],
  "implementations": [{ "id": "urn:example:identity-library", "revision": "library-2" }]
}

Context source IDs identify documents, not local Source record IDs. When a source uses a digest as its snapshot identity, write its canonical sha256:<hex> string as the context revision and verify those bytes on admission. The context must include every source, entity and implementation on which the claim or observation depends. Missing required context is an inconclusive evidence assessment, never a current proof. Evidence for another context remains a valid historical record and is stale for the requested assessment. This draft offers no fine-grained preservation proof across changed revisions.

Evidence contentFields
CommonevidenceKind: "run" | "analysis" | "review", origin: String, context: RevisionContext. Origin describes the producer; it is not authentication.
RunvalueProfile: Id, input: IonValue, output: {state: "observed", value: IonValue} | {state: "absent", reason: "notInvoked" | "executionError" | "missingResult"}, clauses: [{entityId, entityRevision, observation}], evaluator: {id, version, profile}, environment: {target: String, configuration: IonValue}, limits: {steps: Nat, depth: Nat}. Limits must be positive for a claimed run. An observed output can be an actual Ion null. An absent output has no value and cannot count as a satisfied result obligation. A false precondition, invalid input, error or missing candidate must not fabricate an output. Clause observation is satisfied, violated, not_applicable, invalid-input, unsupported, error or inconclusive. No evidence is created by preserving a graph, generating a test, advertising a capability, adding an implements edge or accepting a review. Missing evidence is unknown. A consumer may report both support and contradiction without claiming general contradiction detection or proof of prose equivalence. Hand-authored evidence in this corpus is a test input, explicitly marked hand-authored-fixture; no observation in M1 represents a real evaluator run.

Capability records and admission

A Capability has recordVersion, id, provider: {id, revision}, exact profile, operations, semanticProfiles and limits. Operations are a list drawn from preserve, inspect, check, project and execute. Semantic profiles are exact, versioned interpreter identifiers. Limits are positive exact integers {bytes, depth, values}. Optional descriptive and critical follow the extension rules.

These records describe conceptual consumer support. They are separate from MEP runtime provider capability claims and from domain claims. They do not authorize a protocol method, establish a guarantee, or prove that the provider has been qualified. Each requested operation needs the matching capability, the exact conceptual profile and every required semantic profile. Checking additionally needs resolved, well-typed clauses; execution also needs a resolved supplied implementation and an admitted evaluator. The consumer's prerequisites cannot be disabled by an empty caller requirement list.

A preservation-only reader can retain a contract whose evaluator it does not support. It must refuse a request to check that contract with conceptual.unsupported_semantics. Unsupported operations, profiles, critical fields or limits produce an unsupported/refused result without a successful artifact or passing evidence. Readability, structural validity, typing, evaluation support, implementation binding, review and evidence are distinct reported facts.

Rich carrier and projection

The conceptual graph is the typed Ion value in one existing IRUnit NodeMetadata entry owned by unit:<unit-id>. For this draft, that entry's data is the Graph struct itself, including its exact profile. Unknown descriptions can be nested in the graph. Other existing metadata owners, annotations and provenance remain intact. A transform that finds unrelated pre-existing data at the same unit owner must refuse a conflicting composition rather than overwrite it; defining a general multi-profile container is outside M1.

Fixture recipeExisting MoonBit carrier field
unitIdIRUnit.id and the SourceSnapshot unit_id passed to decode.
irIRUnit.distribution, an existing IRFile containing formatVersion and distribution.
metadata[].nodeIdNodeMetadata.node_id. The graph's sole owner is the already valid unit:<id>.
metadata[].dataNodeMetadata.data, a typed IonValue. Entity IDs stay inside this value.
annotations, provenanceIRUnit's existing symbol-token annotations and Ion provenance values.

The existing MoonBit checkpoint codec writes a morphir_pipeline-annotated struct with profile: "morphir-pipeline-v1", contract: "ir-unit", unit_id, ir, metadata: [{node_id, data}] and provenance. That profile string retains its existing spelling; the conceptual draft does not rename it. The fixture recipe uses readable camelCase construction fields and is deliberately not another wire encoding. Existing codec and owner validation remain responsible for serialization and ownership.

A prose-only graph uses an empty Specs distribution with an explicit build package. Mixed graphs project resolved public declarations into that same primary package's module specifications. Source namespaces qualify model/module names and do not select a package. The mixed fixture supplies example/model as build context and projects example/model:api#identity. Its conceptual Customer has no invented type. Its implementation is a separate supplied Library artifact with exact identity, revision and FQName.

Signature-only functions project as ValueSpecifications. Opaque public types hide their known representations. If a consumer cannot project a declared feature, such as the proposed native Union node, retain its complete typed declaration in the graph and list every omitted declaration and dependent signature in projectionGaps. Such a carrier is not a complete public specification. Bare IR export refuses this loss. M1 does not implement Union lowering or change the IR support table.

Definition-to-specification conversion may initialize ordinary IR annotations to empty in existing implementations. A conceptual transform must retain the separately stored graph, source, revision context and links across that conversion. An empty output annotation list does not authorize dropping the graph.

MEP may transport model bytes through its existing additive model-transport contract only after its own exact bilateral tuple and evidence admission. This draft neither adds a conceptual tuple to an implementation nor changes MEP's envelope. IRUnit storage, conceptual meaning and transport negotiation stay separate.

Preservation and loss

Rich text and binary round-trips preserve the graph's logical record values, IDs, revision scopes, source strings, unknown descriptive values, annotations and provenance. Ion binary byte identity or text whitespace outside retained strings is not required. Ion value identity does require integer precision, decimal scale, symbol versus string distinctions, typed nulls, annotation order and struct field multiplicity inside opaque descriptive values. Known record fields cannot be duplicated. A consumer that lacks a required symbol catalog must report the existing codec failure rather than guess symbol text.

The unknown descriptive asset requires 9007199254740993, decimal 123.4500, symbol pending, null.string, two ordered top-level annotations and a nested unknown annotation to survive. A JSON serialization through a host number type cannot meet that obligation. The JSON fixtures therefore do not stand in for a tested Ion codec.

Bare semantic IR JSON cannot carry the required conceptual graph. Export must report the existing data.lossy_conversion refusal and produce no successful bare artifact. An explicitly requested human report can contain ordinary JSON/JSON Lines without claiming a lossless model export. Unknown descriptive data can remain unvalidated; unknown required semantics cannot disappear during checked generation or execution.

Diagnostics and inspection

The corpus uses draft observation codes, not new RPC error numbers. A diagnostic has code and path, an RFC 6901 pointer into the materialized graph or the operation input. The empty string selects the root; / selects an empty-name member and is not the root. Optional relatedPath identifies an earlier duplicate. Messages may explain the problem but are not fixed oracle strings. For a relationship kind mismatch the observation also records expected and actual subject/target kinds.

Inspection also retains source recovery diagnostics unchanged and reports unsupported clauses and projection gaps. Fatal structural errors take precedence over optional inspection-gap reporting; the negative cases name only their isolated fatal observation. Gap lists in cases specify required observations, not a prohibition on additional relevant inspection information. Diagnostic order is not semantic; compare code, path and stated detail as a set. For duplicate IDs, use authored list order to identify the later occurrence.

valid-with-gaps concerns graph representation; preserved concerns a round-trip; current/stale concern evidence currency. None means a contract was satisfied. invalid, unsupported and refused name different boundaries. General contradiction detection, proof of equivalence and domain approval are outside this draft.

Reference corpus and builders

cases.json contains independently hand-authored input variants and literal expected observations. The literal asset lengths and SHA-256 digests in assets.json detect accidental changes; they do not compute semantic expectations. Its corpusVersion is exact 0.1.0-draft.1, and its status is reference-only. The case operation names are fixture instructions, not a new CLI, RPC protocol or MCK operation registration.

To materialize a case, load its input.graph relative to this directory, then concatenate the optional additions.sources, entities, relationships and capabilities lists in written order. The builder deliberately preserves duplicate and invalid records. It never deduplicates, repairs references or derives expected outcomes. Load optional ir and implementationInputs as separate authored files. An Ion insertion reads exactly one Ion value from the named asset and puts it at the graph pointer, creating the described descriptive struct if absent. Never parse that asset through JSON.

For roundTrip, construct the existing IRUnit using the supplied unitId, IR and graph metadata; encode/decode with each requested existing codec and compare retained values. For attachGraph, attach to an unoccupied unit metadata owner or refuse the collision without changing existing data. For definitionToSpecification, extract the supplied Library's public signature and retain the separate graph; compare to the literal expected IR asset. For inspect, report the graph concerns and reference validity, optionally restricted to subjects. For check, admit the named provider and required semantic profiles. Optional subject identifies the declaration being checked, inputs supplies named values, candidate supplies an explicit candidate output when present, and valueProfile identifies their interpretation. The scalar fixture profile is test vocabulary: integers are exact base-10 strings; binder, integer literal, field selection, subtraction, equality, greater-or-equal and less-or-equal AST nodes have their ordinary exact-integer meanings. These few authored examples specify future observations and provide no current evaluator. The scalar provider advertisement in the fixture is hypothetical, not a qualification claim. For exportBareIr, attempt an explicit bare export. For assessEvidence, compare the named historical observation to the complete supplied revision context before any trust decision. requestedProfile, when present, is the caller's exact required profile.

Future runtime tasks consume these fixtures according to their scope. Shared qualification must use an adapter in the existing Rust morphir mck ownership path. It must retain the literal expected results as independent inputs. The fixture builders must not become a second conceptual checker or compatibility runner. A later parser frontend or library can consume this corpus without depending on a second runner.

Paper round-trips

Prose-only construction and recovery
  1. Read prose-only.json. Keep urn:example:lending at model-1, all four entity IDs/revisions, both Source records and all three relationships.
  2. Use caller package example/prose and unit prose. The hand-authored prose-only.ir.json is a valid empty Specs carrier. No concept becomes a type or a hole.
  3. Construct one metadata entry unit:prose containing the graph, then use the existing rich codec. On decode, that same owner recovers the graph, including the paragraph's interior blank line, two leading spaces and final LF.
  4. Inspection can still distinguish the pending requirement review, Borrower's open identifying-information question, missing contract/example and explicitly unresolved external source. It performs zero network requests. Exporting only Specs would lose these required facts and must refuse.

Open decisions and handoff

This draft fixes enough local record structure to build independent adapters and review preservation examples. It does not settle the textual language grammar, delimiters, file extension, trait vocabulary, dictionary publication format, expression/type checker internals, import resolver, transformation lineage protocol or general multi-profile metadata container. Plain fn is the pinned design's starting function-specification form; no sample here is claimed to compile.

M2 defines the typed trait contract. M3 consumes M1 and M2 for the portable model library, rich codecs and their focused tests. Later checker and evidence tasks implement their own scoped runtime semantics. Shared compatibility registration and qualification use the existing Rust MCK runner with explicit adapters in the separately tracked integration work. No implementation may generate expected outcomes by calling itself.

Broader dictionary mappings and RDF, N-Quads, OWL, Turtle, TriG and JSON-LD profiles remain explicit architectural candidates. They require independent exchange and reasoning semantics. Native Union projection, Smithy mappings, EARS/Gherkin generation, executable refinement rules and full language round-trips retain their own later acceptance work. M1 makes no claim of implementing them.
