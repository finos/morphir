The Moon-Lander framework modules were not published in releases 0.3.0 to 0.5.0, by oversight. A Moon-Lander release that publishes them is in progress. The notebook work needs only moonrockz/notebooks, which is already on the registry.

Goals and non-goals

Goals: every capability in the table above comes from one Moon-Lander module in the CLI and in the Workbench; user-visible behavior is kept except where the specs change it (JSON configuration and the --config rename); the work lands in as few pull requests as needed, with one commit series per group so that a group can be reverted on its own.

Non-goals: changes to MEP, the Workbench worker protocol or any other wire format; replacing telemetry with logging; configuration environments (morphir.Production.toml) and local override files (morphir.local.toml); configuration editing (stays with pkgs/morphir-toml-edit); protocol definitions, which later work does in Smithy through moonrockz/smithy, not with moonrockz/openrpc.

How a CLI run works after the change

Take morphir project list --json --log-level debug on native. The diagram shows the order. The host fixes the arguments, environment and working directory once, then loads configuration, then builds the services record that every handler shares. The command is a typed request sent through the mediator, so the cancellation, timing and error middleware is the same for every command. When the command ends, for any reason, the stop hooks run in reverse order and the logging bridge drains the log queue before the console driver ends the process.

On wasm and wasm-gc the same builder runs through run_embedded with the WASI file tree. There is no signal probe, so only a host cancellation or the cancel file stops a run, and commands that need interruption keep their current refusal.

Where each module is used

ADR 0002 keeps the engine synchronous and leaves file, network and process access to host adapters. The modules follow that line: the pure ones may be used by engine packages, the host ones only by apps and pkgs/morphir-host.

Decisions

DEP-1. Take every module from mooncakes.io at one exact version

Each moon.mod that needs a module imports it at an exact version, as with moonrockz/ion. Moon-Lander releases share one version across its modules, so all Moon-Lander imports in this repository move together, in one pull request and one Renovate group. A group of tasks starts only when its module is on the registry.

Alternatives: a git submodule or path dependency on a Moon-Lander checkout (rejected by the maintainer; it adds build plumbing and couples our CI to an unreleased tree); copying the code (rejected; we would maintain a fork).

DEP-2. Pure modules may enter the engine; host modules stay at the edge

See the table in Where each module is used. The engine takes a &@logging.Logger and configuration values; it never starts a host or a sink. This keeps ADR 0002 and lets the Workbench browser build use the same engine code.

Alternative: confine all Moon-Lander imports to the apps. Rejected, because the configuration merge and the worksheet notebook mapping must run in the browser Workbench too.

CFG-1. Map Morphir discovery onto Moon-Lander conventions, with extra layers off

The conventions for the name morphir already find morphir.toml, .morphir/morphir.toml and .config/morphir/config.toml by walk-up, refuse two in one directory, read morphir.user.toml, honor MORPHIR_HOME, and give the system and global user directories per platform. morphir-workspace.json, morphir.json and morphir.json5 become configuration sources (CFG-4). Environment files and the local override layer stay off, because they would read files that Morphir ignores today. The environment source with prefix MORPHIR already uses __ as the separator, skips _ after the prefix, refuses an empty segment, and merges a shorter path last, as @config.environment does.

Alternative: keep Morphir discovery and use only the Moon-Lander merge. Rejected; discovery is where the isolated mode for morphir-o6vm.10 comes from.

CFG-2. Workspace members stay in Morphir, on Moon-Lander values

Morphir members have their own defaults and take only the shared() part of the root file and the root user file. The Moon-Lander member layer selects one member per run, which does not fit a command that loads all members. pkgs/morphir-engine/workspace keeps the member walk and builds each member's configuration from Moon-Lander sources and merge, so values and provenance come from one engine.

CFG-3. Link the TOML, YAML and JSON parsers

The executables override the formats virtual package with a set of TOML, YAML and JSON/JSON5, so only the Ion parser is not linked. YAML uses Moon-Lander's default YAML profile and is read from .yaml and .yml files. Both .json and .json5 files are parsed as JSON5, which accepts strict JSON, so a morphir.json may hold comments and trailing commas. Tools that read morphir.json as strict JSON, such as morphir-elm, reject such a file; that is the author's choice. Reading YAML replaces the YAML refusal in ADR 0002, which ADR 0004 records. A parity corpus (task group 3) checks that the Moon-Lander TOML parser and moonbit-community/toml give the same values for every configuration file in the repository's tests and fixtures, and that every morphir.json fixture gives the same project values as the current legacy reader.

CFG-4. Three format layers below a selected file

The workspace primary layer becomes three sources in one directory, each found in the three layouts (morphir.*, .morphir/morphir.*, .config/morphir/config.*): JSON (.json, .json5), then YAML (.yaml, .yml), then TOML. A later layer wins, so TOML is the most specific format, and every key that only a lower layer sets stays in effect. Ambiguity is checked inside each layer only: morphir.yaml with morphir.yml is an error, morphir.yaml with morphir.toml is not, but it is bad form, so it gives the warning config.yaml_beside_toml. Inside the JSON layer, morphir-workspace.json merges first and morphir.json or morphir.json5 after it; it takes the canonical keys only. Members use the same layers and rules as the root, so a morphir-elm member with only morphir.json keeps working. User override files follow the same order.

Configuration warnings have codes (config.yaml_beside_toml, config.json_keys_below_toml) and one host-only suppression list: --suppress-warning <code>, MORPHIR_DIAGNOSTICS__SUPPRESS (comma-separated) or diagnostics.suppress in the system or global user file. The loader reads diagnostics.suppress from the host layers only, so a workspace cannot hide its own mixed files.

Before the merge, a reader turns the morphir-elm fields into canonical keys, each with the JSON file as its origin, and puts the Elm checkpoint defaults in the defaults layer, as the current legacy function does. --config <path> adds one source above the TOML layer and below the member layer; when it names a file that discovery also found, that file is taken out of its discovered layer so it is merged once.

{
  "name": "Acme.Billing",
  "sourceDirectory": "elm-src",
  "exposedModules": ["Acme.Billing.Api"]
}
[project]
source_directory = "src"

With these two files, project.source_directory is src from morphir.toml and project.name is Acme.Billing from morphir.json. With --config morphir.json, project.source_directory is elm-src.

If the Moon-Lander conventions treat files of different formats in one directory as ambiguous, or cannot add a source above the project file, Morphir registers these sources itself through the builder's source provider and files a Moon-Lander issue for the convention.

The Scheme script option moves to --config-script, because --config now names a configuration file. A .scm path given to --config fails with a usage error that names --config-script, so a script user gets a clear fix instead of a format error.

Alternatives: keep --config for scripts and add --config-file (rejected by the maintainer); choose the meaning of --config by extension (rejected: one option with two meanings).

CFG-5. Write TOML only

TOML is the default Morphir format. Scaffolding already writes morphir.toml (pkgs/morphir-engine/workspace/scaffold.mbt), and edits go through pkgs/morphir-toml-edit, which keeps formatting and comments. Reading YAML and JSON does not add writers for them. A write to a workspace with JSON or YAML files and no TOML file creates morphir.toml in the same directory, which is valid because TOML is the top layer (CFG-4). Because a TOML value replaces a lower value whole, each written key holds its full new value: project add writes every member in workspace.members, not only the new one. ensure_new_config also refuses a new project where any primary file, of any format, exists.

Alternatives: edit YAML and JSON in place (rejected: no format-preserving editors, and JSON5 comments could be lost); refuse every non-TOML workspace (rejected by the maintainer, because a TOML file beside them works).

LOG-1. One Logger value per run; sinks by host

The services record holds one &Logger made with min_level and with_category. On native and js it writes through a moon-lander-logging-hosting-async session: console on standard error, and, when enabled, rolling files with the stem morphir-diagnostics in .morphir/logs/, guarded by the module's ownership marker so that retention never removes telemetry files. On wasm and wasm-gc a small Logger writes text lines to standard error through @platform.

Alternative: send diagnostics into the telemetry session. Rejected; telemetry has typed observations with a consumer (apps/morphir-otel) and must keep its format.

LOG-2. Name the option --log-level

--log already turns on telemetry, so the level option cannot be --log or --verbose= without confusion. --log-level matches the configuration key logging.level and the variable MORPHIR_LOGGING__LEVEL.

HOST-1. Run the CLI through the host, and keep Morphir exit codes

main builds the host with @lander.cli("morphir", args), and runs it with @console.run and the logging bridge on native and js, and with run_embedded on wasm. The host's default code for an unhandled failure is 1, while Morphir uses 2 for every failure except compile. A failure middleware maps each command failure to Morphir's code and calls set_exit_code, so the application/lifecycle codes hold. Cancellation is a StopReason, not the message text "Cancelled". The cancel file becomes a host stop request polled by the same check as signals.

Moon-Lander's own change add-host-lifecycle is still open. Group 6 uses only what the published release documents; any gap becomes a Moon-Lander issue, not a local workaround.

HOST-2. The desktop Workbench embeds the host under Proton

Proton owns the window event loop. The desktop app builds a host whose hosted services are the native Workbench services, starts it when Proton starts, and asks it to stop with the Embedder stop reason from Proton's on_shutdown hook. Running host executions are cancelled through the same lifetime.

MED-1. Typed requests behind unchanged names

Each CLI command becomes a request type with a Sender. One table maps the parsed argparse subcommand to a request value; the mediator runs it through the shared middleware. In the Workbench, the native service and the engine boundary decode op into a request value once, then send it. Operation names, payloads and results do not change. The engine boundary uses the synchronous mediator; the native service uses the async mediator, where handlers wait for I/O.

NB-1. Worksheet forms are cells; observations are outputs

The mapping lives in a new pure package, pkgs/morphir-engine/worksheet/notebook, so the CLI and the browser Workbench share it. Each top-level form is a code cell with language scheme; each block of whole-line ;; comments between forms is a Markdown cell. With evaluation, an observation becomes an execute_result with text/plain (the preview) and application/vnd.morphir.observation+json (the observation's JSON), and a failed outcome becomes an error output. Notebook metadata records the profile morphir/worksheet-notebook, version 0.1.0, under metadata.morphir. DIB cells use the kernel name scheme.

;; # Totals
(define prices '(3 4 5))

(apply + prices)

This worksheet exports as three cells: Markdown # Totals, then two Scheme code cells.

NB-2. Stay compatible with the shared notebook profile

morphir-o6vm.11 plans one Morphir notebook profile for workspaces and itest scenarios. This change keeps its metadata under its own profile name and reads moonrockz/notebooks models only, so the shared profile can later adopt or extend it without a second notebook reader.

DOC-1. Record the adoption as ADR 0004

docs/adr/0004-adopt-moon-lander.md records DEP-1, DEP-2, the import rule and the configuration formats (CFG-3, CFG-4), which replace the YAML refusal in ADR 0002, and CONTEXT.md gets the terms host lifetime, stop reason, diagnostic log and worksheet notebook.

Migration plan

The maintainer asked on 2026-10-28 for as few pull requests as needed. Group 1 happens in the Moon-Lander repository. Groups 2 to 9 land in one pull request in this repository, with one commit series per group in this order: dependencies and ADR (group 2), configuration with the parity corpus (group 3), logging, which reads its level from configuration (group 4), dispatch (group 5), the CLI host (group 6), the desktop host (group 7), notebooks (group 8) and the integration checks (group 9). A group gets its own pull request only when it is blocked and the rest is ready, for example when group 6 waits for a Moon-Lander hosting feature. The old configuration loader and the old exit-code mapping are removed in the commits that prove parity, so reverting those commits restores them.

Open questions

  • Which Moon-Lander version is the first with the framework modules on the registry. The pins take that version; nothing else in the plan depends on its number.
  • Whether .NET Interactive users want a different DIB kernel name than scheme. The name is one constant in the mapping.
