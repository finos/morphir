Context

See proposal.md for the reason for this change. The contract is in spec/mep/model-transport.md (MEP 0.2.0-draft.1). A tuple has five members: operation, profile, codec, envelopeVersion and irVersion. Peers compare all five exactly. The host sends its offer in InitializeParams.modelTransport, and the extension returns its session support in ExtensionCapabilities.modelTransport. Both are ordered lists, but the draft did not give the order a meaning.

Constraints: the draft is shipped by several SDKs, so the change must add no wire member and keep the draft version. The Rust SDK already selects the intersection in host order (NegotiatedModelTransport::select). The JSON profile cannot carry rich Ion content without loss, and the spec already refuses a lossy projection with data.lossy_conversion.

Goals and non-goals

Goals: one rule that every host and extension can apply to find the tuple for each operation, with exactly one failure outcome for negotiation; a defined host behavior when a model for generation is not in an agreed tuple.

Non-goals: a new wire member or draft version; host conversion for compileModel dependencies; a universal conversion algorithm; a lossy export policy other than explicit loss for one generation; changes in finos/morphir-rust, finos/morphir-moonbit or finos/morphir-gleam (they follow in their own repositories); the MCK cases (bead morphir-hv6m).

Negotiation and dispatch flow

host offer       [compileModel/ion-binary, compileModel/morphir-json]
extension        [compileModel/morphir-json]
session support  [compileModel/morphir-json]   -> use morphir-json

host offer       [compileModel/ion-binary]      (host requires Ion)
extension        [compileModel/morphir-json]
session support  []                             -> extension.tuple_unavailable

Decisions

Damian Reeves decided NEG-1 to NEG-4 on 2026-10-30 and CONV-1 to CONV-3 on 2026-10-31. The host-conversion details CONV-4 to CONV-8 (decisions A to E) followed later on 2026-10-31, with the confirmation that the host converts to the first agreed tuple in host order. CONV-4 to CONV-8 replace the parts of CONV-2 and CONV-3 that they cover. The spec states them for every host and uses the MoonBit names only as examples.

NEG-1. Offer order expresses the default

The host lists every tuple it supports for an operation in preference order, and the first tuple is the default. Alternative rejected: explicit wire members, for example a default tuple or a preferred rank on ModelTransportSupport, and a required flag. They would need a new draft version and new SDK types in every language, and they can disagree with the list order. Order is already on the wire and the Rust SDK already keeps it.

NEG-2. The extension keeps host order

The extension returns the intersection in host order, and the host uses the first agreed tuple. Alternative rejected: the extension orders its selection by its own preference. Then two peers can each claim the first place, and the host would need a tie rule. The host owns the default because the host owns the retained model and the user's request.

NEG-3. A required format is a single-tuple offer

When the host requires one format, for example an explicit --model-format, it offers only that tuple. Alternative rejected: a required wire flag (see NEG-1). A single-tuple offer gives the same result with the existing intersection rule.

NEG-4. Only an empty agreement fails

An empty agreement for a requested operation is the only negotiation failure, reported as extension.tuple_unavailable. A missing default with another agreed tuple is not an error. Alternative rejected: refuse when the default is not agreed, an option that finos/morphir-moonbit#281 asked about. finos/morphir-gleam#31 shows that a JSON-only guest works when the host also offers JSON.

CONV-1. The host converts a model for generation

For generateModel, when the model is not in an agreed tuple but the host can convert it to one, the host converts and sends the converted model. Only when it cannot convert does it report extension.tuple_unavailable. Alternatives rejected: (a) refuse with extension.tuple_unavailable: this refuses work that the host can do; (b) the extension converts: the extension agreed only tuples it can read, and the host owns the retained model and its loss rules; (c) a retry after admission fails: the spec already forbids an automatic JSON retry. The conversion happens before dispatch.

CONV-2. New payload and evidence rules

The converted model is a new payload with its own length, digest and revision. The loss rules are in CONV-5 and CONV-7, and the identity rule is in CONV-6. Required guarantees and evidence for the original do not carry over automatically, because evidence binds the original revision. Alternative rejected: keep the revision as exact transcoding can. A profile change is not an exact transcoding, and a shared revision would let evidence for the original appear to match the converted model.

CONV-3. Details left to the host

When the host can convert to more than one agreed tuple, it converts to the first agreed tuple in host order to which it can convert. This was a recommendation in finos/morphir#1115 and is now a rule. The spec leaves to the host only: which conversions it implements; the name of its lossy-conversion error and how the user allows loss; the format and location of the conversion record and of the dropped-data report; and whether it tells the user about a lossless conversion. Alternative rejected: define a conversion algorithm in this draft. No second host implements conversion yet.

CONV-4. The host library converts (decision A)

The host converts, not a front end and not the extension. In the MoonBit implementation, the host library pkgs/morphir-host converts with the engine codec registry (pkgs/morphir-engine/data/registry.mbt), and every host front end (CLI, browser host, worker host) shares it. Alternatives rejected: (a) each front end converts: the front ends would drift in loss rules and identity values; (b) the extension converts: see CONV-1.

CONV-5. Directions and explicit loss (decision B)

The host converts in both directions. morphir-ir/morphir-json to morphir-model/ion-binary is always lossless. morphir-model to morphir-ir/morphir-json is allowed only when it is lossless, unless the user explicitly allows loss for one generation (MoonBit working name --allow-model-loss, scoped to one morphir generate). Alternatives rejected: (a) always refuse a lossy conversion: a user with a JSON-only backend who accepts the loss cannot generate; (b) a persistent setting that allows loss: later runs would lose data without a request from the user.

CONV-6. Identity of the converted model (decision C)

The converted model keeps its modelId. Its revision is derived deterministically from the SHA-256 digest of the converted payload bytes; the MoonBit form is sha256:<lowercase hex>. The link to the original is in the conversion record (CONV-8). Alternatives rejected: (a) a new modelId: the model is the same logical model, and consumers that key by modelId would lose it; (b) a random or time-based revision: the same input would give different revisions, and builds would not be reproducible; (c) keep the original revision: see CONV-2.

CONV-7. Outcome of a lossy conversion (decision D)

Without permission, the host refuses with its lossy-conversion error and publishes nothing. In the MoonBit CLI this is data.lossy_conversion with exit code 2 and committed: [], before the operation session, the same as morphir generate today, and the message names the flag. With permission, the MoonBit CLI exits 0, gives one warning for each kind of dropped data (metadata, provenance, annotations), and adds conversion: {from, to, dropped} to the JSON report. Alternative rejected: report the refusal as extension.tuple_unavailable. The agreed tuple is available, and the user can continue by allowing the loss; the two outcomes need different actions.

CONV-8. Conversion record (decision E)

The host writes a conversion record with the original and converted tuples, the original revision and payload SHA-256, the converted revision and payload SHA-256, and the dropped list (empty without permission for loss). In the MoonBit CLI the record is mep/conversion.json next to the guest's artifacts. The path is reserved for the host: if a guest returns an artifact at that path, the command refuses. The guest's own retention sidecars stay as the guest returns them. The record does not copy the original bytes, which the host already retains. Alternatives rejected: (a) copy the original bytes next to the artifacts: this duplicates the retained model; (b) put the link in a guest sidecar: the guest could change or omit it.

Risks and trade-offs

RiskMitigation
An older extension reorders its selection, and the host reads the order as the extension's preference.The host finds the first agreed tuple by host offer order, not by session order. The MCK checks the order (bead morphir-hv6m).
A host converts with loss and the backend generates from incomplete content.The host refuses a lossy conversion unless the user explicitly allows loss for that one operation. Then the host reports the dropped data and lists it in the conversion record. The new revision stops old evidence from matching.
An extension returns an artifact that replaces the conversion record.The record location is reserved for the host, and the host refuses a result that uses it.
Hosts differ in which conversions they implement, so the same extension works with one host and not another.The outcome is still defined: convert, lossy-conversion error, or extension.tuple_unavailable. Hosts state their conversions in their own documentation.
The rule is not checked by the MCK, so implementations can drift.Bead morphir-hv6m adds cases (a) to (e) and runner support.

Migration plan

No wire change, so no peer must upgrade at the same time. Hosts that refused a non-default agreement change to the first agreed tuple (MoonBit: finos/morphir-moonbit#281). Extensions that reordered their selection change to keep host order. Hosts that convert add the explicit loss permission, the deterministic revision and the conversion record. Rollback is a text revert of finos/morphir#1115 and finos/morphir#1117; no data or version changes.
