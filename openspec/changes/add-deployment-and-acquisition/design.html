Context and evidence

See the proposal for motivation. The important distinction is between the host a user runs, the runtime arrangement of that host, the channel that installed it, and the language toolset it can use. The executable name alone identifies none of these reliably.

Inspection used morphir-dotnet main at 4e3321f3c13821105115b4f4f7857a611c5a3c21. src/Morphir/Morphir.csproj names the direct executable morphir. src/Morphir.Tool/Morphir.Tool.csproj packages Morphir.Tool as dotnet-morphir and references the F# frontend. Both target .NET 10. Existing scripts/publish-single-file.cs already attempts a managed self-contained publish. Its presence is groundwork, not proof of a maintained release offering or clean-machine acquisition workflow.

The F# frontend now has a process guest, src/Morphir.Frontend.FSharp.Extension, packaged as Morphir.Frontend.FSharp.Extension, with extension identity org.finos.morphir.fsharp-frontend and executable morphir-fsharp-frontend. Its project explicitly says FSharp.Compiler.Service is neither trim-safe nor AOT-safe. Its current delivery is a framework-dependent .NET tool. The built-in F# backend is morphir.fsharp. A separately packaged F# backend process guest is new work in this proposal.

The parent already defines authenticated tool release metadata and extension acquisition separately. Its current morphir tool install command is limited to unsigned local developer Desktop packages. Reusing the contract does not mean remote CLI acquisition is already implemented. The .NET extension roadmap also has pending installation and host-runtime steps; this design does not count them as delivered.

Where prior art informs the design
  • PowerShell demonstrates runtime-bundled distributions, framework-dependent archives and tool installation alongside ordinary installers. We borrow explicit artifact labeling and installation guidance.
  • Aspire demonstrates that a Native AOT executable can itself travel through the .NET tool channel. We keep channel and deployment separate even though the existing Morphir tool stays managed.
  • dotnetup provides a standalone lifecycle manager, side-by-side SDK/runtime acquisition, non-admin installation and explicit self-update. We borrow the lifecycle boundary rather than make ordinary compile acquire software.
  • rustup provides project selection, proxy dispatch and component sets. We keep Morphir deployment profiles distinct from toolset presets, because rustup uses the word profile for a component set.

Goals and boundaries

A developer without .NET should acquire the standalone host and F# tools, compile a supported source package and generate F# without installing an SDK. A teammate should restore exact selected artifacts on another supported platform. An existing .NET developer should retain the tool installation and invocation they already use.

The first delivery manages the .NET host and its toolsets. Implementation identity remains explicit so a later MoonBit provider can join without changing the lock's meaning. It does not require a Rust CLI release, replace task adapters, implement an SDK manager, make arbitrary .fsproj builds runtime-independent, or add assembly-loading plugins to the AOT host. WASM engine implementation stays in the separate host change.

UP-1. Make morphirup a small standalone coordinator

Ada first obtains morphirup as a Native AOT executable built in morphir-dotnet. It needs no installed Morphir or .NET. It owns bootstrap, selection and lifecycle. Runtime-neutral recipe/request/lock contracts live in the parent. A pure resolver produces a plan; bounded I/O adapters perform authentication, download, extraction, extension installation and activation. The manager has no compiler or generator implementation.

Direct archives remain useful without the manager. NuGet and system package managers keep ownership of installations they created. morphirup can inspect them and propose an explicit side-by-side manager-owned install, but it does not overwrite them. It does not require package-manager adoption to ship the first release.

Alternative: add remote installation only to morphir. Rejected because it leaves a bootstrap dependency and makes updating the running host harder. Alternative: write a new extension installer inside the manager. Rejected because existing descriptor, store, lock and claim checks must agree across hosts.

UP-2. Plan, verify and activate one complete generation

Ada asks for F# setup. Planning can refresh metadata but never runs a downloaded artifact or changes the selected installation. Applying setup stages the entire candidate and runs readiness checks before activation. Public toolset recipes are ordinary authenticated TUF targets that bind host descriptors, extension descriptors and selected artifact hashes. They do not change extension descriptor syntax or pretend that every existing extension repository is signed.

# Proposed interface. These commands do not exist yet.
morphirup setup --implementation dotnet --deployment native-aot --preset fsharp --channel stable --plan
morphirup setup --implementation dotnet --deployment native-aot --preset fsharp --channel stable --yes
morphirup show --json
morphirup doctor --json

A plan names the source authority, exact release/digest, download bytes, disk requirements, update owner and process-probe behavior. --yes authorizes the displayed setup operation in automation. It never means bypass signatures, ignore incompatibility, modify unrelated installations or install a system SDK. If the resolved plan changes before execution, the final receipt records the actual exact plan; an --expect-plan digest refuses a mismatch for approval-sensitive automation.

Reuse the tool metadata v1 profile without silently changing its numeric schemaVersion. Represent separately published .NET offerings as distinct tool ids in authenticated metadata, with a new versioned recipe mapping them to implementation/deployment identities. New contracts use 0.1.0-draft.1. Use established SemVer libraries, exact draft requirements and the repository's unknown-optional/critical-member rules. Any needed evolution of a released descriptor gets its own versioned delta.

Store verified bytes through the existing tool and extension content stores. Add immutable toolchain metadata under MORPHIR_HOME/toolchains/generations/<id>/, plus user-default and project activation pointers. A generation contains local launch receipts and exact copies/references of the selected extension records and locks. A project generation does not replace the global extension selection. Hosts consume an additive generation-scoped selection overlay while retaining global catalog compatibility.

The operation journals preparation and publication. Write the new project lock and selection to a new generation, then switch one project pointer under a lock. The pointer records the portable lock digest. A crash between filesystem publications is recovered from the journal before a new run; uncertain or mismatched state never falls back to a mixed configuration. An in-flight run pins the old generation. Repair restores exact bytes, while update resolves new versions.

Alternative: install the host, change the global default, then install extensions. Rejected because an incomplete toolset would become visible. Alternative: overwrite the shared global extension lock on every project switch. Rejected because two projects could interfere.

FS-1. Deliver F# as capabilities with a standalone process option

Ada's host is AOT. Setup resolves the self-contained morphir-fsharp-frontend process guest, including FCS and its managed runtime. It uses the existing Content-Length MEP transport. The default generator remains the host's built-in morphir.fsharp. Ben's managed host can use the same managed F# frontend composition that currently lives in the tool. An explicit provider selection always wins.

Publish an additional self-contained F# backend process guest from morphir-dotnet, reusing Morphir.CodeGeneration.FSharp and the existing MEP backend methods. Give it a distinct external identity, proposed morphir-fsharp-backend, and exact claims from its actual supported tuples. No protocol members are invented. This makes the backend independently acquirable by MoonBit or another compatible host. External delivery is a required first-delivery proof even though default .NET setup avoids downloading a duplicate built-in.

Compilation here means supported F# source to Morphir IR. It does not mean every arbitrary .fsproj can build without an SDK or NuGet restore. If users ask to compile generated F# into a .NET application, report that consumer workflow's SDK and package prerequisites separately. Readiness uses a small fixed source package with no external dependency resolution.

Alternative: bundle an SDK with every Morphir install. Rejected because the frontend needs compiler services, not a complete SDK for this workload. Alternative: move the F# frontend into AOT. Rejected by its dependency constraints. Keep the existing frontend .NET tool available as an explicit framework-dependent delivery.

LOCK-1. Keep requests, portable locks and local receipts distinct

Ada commits the project request and portable lock. The request can say stable; the lock records the exact resolved host and providers. Platform closures can be prepared together for the supported team platforms. Frozen restore refuses a platform absent from the lock; explicit setup/update can extend the lock. Different platform closures never silently re-resolve stable independently.

Request identity is SHA-256 of the request file's UTF-8 bytes. Reformatting therefore requires explicit lock refresh, a simple rule that avoids cross-language canonical TOML. The local receipt binds SHA-256 of the exact lock bytes, the platform and every installed object identity. Generation ids are local opaque ids, not public release versions. Recipes, request/lock formats, installation receipts and manager JSON result formats each start at 0.1.0-draft.1; these names do not change MEP or IR versions.

# Proposed CI workflow after acquiring morphirup
morphirup restore --locked
morphirup run -- compile
morphirup run -- generate --target fsharp

# Offline replay once exact artifacts are present
morphirup restore --locked --offline
morphirup run --offline -- compile

Selection order is explicit CLI selector, MORPHIRUP_TOOLCHAIN, nearest project file within established discovery boundaries, then user default. Overrides select an installed complete generation. show explains the source. run never downloads. A broken project lock does not fall through to a user default.

Existing [toolchain.<name>] sections in morphir.toml define task adapters and keep their meaning. Use the new file instead of colliding with them. Installed tools and durable trust data live in Morphir Home. Compilation and generation continue to use the configured out root, normally .morphir/out, and existing task result paths. Clearing outputs cannot erase a toolchain.

Alternative: check in local absolute executable paths. Rejected because they are neither portable nor acquisition instructions. Alternative: put installed executables in .morphir/out. Rejected because outputs are disposable and task-owned.

PATH-1. One proxy, explicit ownership and predictable dispatch

The manager owns a bin directory with morphirup and an optional morphir dispatch proxy. It does not rename the NuGet tool. An external dotnet-tool installation remains externally owned; users update it with the dotnet tool mechanism. An explicitly manager-owned tool delivery is installed to an isolated tool path through the SDK, with exact package provenance recorded. The manager never installs an SDK implicitly.

On Windows, ship a real proxy executable; do not depend on symlink privileges or a PowerShell execution-policy exception for normal launch. Resolve the selected executable to an absolute path and spawn with an argument vector, no shell command string. Preserve streams, working directory, exit status and cancellation. Windows background child windows are suppressed, and cancellation terminates the owned process tree. A selected child cannot recursively find the proxy through PATH.

Bootstrap works by absolute path. Persistent PATH/profile edits require an explicit morphirup env --install operation. Record exactly the manager-owned addition for reversible removal. Repeated setup adds no duplicate entries. doctor reports which morphir wins PATH, runtime/ABI availability, selected lock and update ownership without changing any of them.

Alternative: quietly replace any morphir on PATH. Rejected because Rust, MoonBit, direct .NET and package-managed installations may coexist. Alternative: copy rustup's full override syntax immediately. Rejected because one explicit run command and a reported precedence rule cover the first delivery.

QUAL-1. Verify language readiness and runtime hosting separately

Ada sees separate acquired, verified, capability-checked and workflow-qualified states. Setup does not say ready merely because it extracted archives. A process probe runs with Ada's rights, under the existing launch controls. Plan-only never executes it. The fixed smoke workflow checks known F# source to known semantic IR and expected generated F# files. A failed probe leaves the previous generation selected.

A WASM recipe names its required ABI. The public runtime value stays wasm; engine identity and ABI are separate. A host supporting morphir-bytes-v1 cannot qualify an extism-kernel-v1 guest merely because both are WASM. The separate host proposal must qualify its packaged engine across every offering before setup advertises the corresponding capability.

Alternative: merge deployment, acquisition, WASM engines and bounded generation into one release gate. Rejected because process-based F# setup is useful independently. Keep evidence per repository and per feature. Use the existing shared MCK runner with explicit independent adapters for IR/MEP behavior. Acquisition/crash/ownership checks are integration tests, not a second compatibility runner.

Acceptance and delivery sequence

  1. Publish reproducible offering metadata and direct archives. Test the four offerings from their packaged outputs on all six declared platforms. Unsupported combinations remain visibly unsupported until qualified.
  2. Prove one clean-machine AOT setup plus self-contained F# frontend and built-in backend. Acquire rather than build artifacts on the consumer machine. Check fixed outputs, exact provider identities and no SDK/system runtime.
  3. Publish the standalone F# backend and exercise explicit external selection. Preserve the existing built-in backend's identity and default behavior.
  4. Restore a multi-platform project lock, rerun offline and prove that a moving stable channel cannot change a frozen build. Test missing platform closures and expired metadata according to existing trust rules.
  5. Interrupt downloads, fail probes, race activation and run a long command during update. Verify the previous generation remains usable and each run observes one complete selection. Exercise tampered archives, learned revocations, archive traversal refusal and PATH conflicts.
  6. Qualify the separate WASM-host output when available. Do not count process F# acceptance as WASM support. Add MoonBit toolchain acquisition/adoption later with its own release and receipts.

Group focused tests and reuse packaged artifacts. Broad clean-machine platform qualification belongs in manual or release qualification, not a new job per profile on every PR. Shared fixed IR/MEP expectations stay in finos/morphir; .NET publishes its adapter and packaging receipts.

Risks and trade-offs

Self-contained FCS packages may be large.Report full download/installed sizes; reuse content-addressed artifacts. First prove compatibility untrimmed. Treat further trimming as measured work.

Several installations expose morphir on PATH.Report ownership and resolution; support explicit manager dispatch without overwriting external files.

Migration and recovery

Land shared contracts and fixed cases first, then .NET packaging, standalone language guests, manager resolution/activation and project dispatch. Adopt generation-scoped selection in the .NET registry as an explicit update to that repository's availability/delivery requirements. Preserve its existing top-level host strings and add offering identity rather than silently redefining their values. Existing direct/tool commands keep working.

Users can adopt project requests gradually. Imported external installations remain externally owned and are not moved into manager directories. An unsigned developer artifact requires the existing explicit developer policy, with separate provenance. Bootstrap's official root is provisioned out of band in the manager release; public recipes must use production trust, never fixture keys.

Rollback selects a verified prior complete generation, subject to known revocations. Active run leases protect in-use files. Cleanup removes only unreferenced manager-owned generations and disposable caches; trusted roots, known revocations and locks survive. Interrupted self-update stages a new manager executable and replaces it only through a platform-qualified helper after the old executable exits.

No unresolved product decision is hidden in the implementation tasks. Signing-key custody, exact installer endpoint names and binary-size targets can be established during release preparation without changing the contracts. Before implementation, attach this proposal to its owning Beads epic and cross-repository tasks after tracker recovery.
