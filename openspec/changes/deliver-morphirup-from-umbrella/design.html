Context

Observed at the pin 318b1bfd (morphir-dotnet 0.5.0-alpha.1). The source's release, deployment.yml, calls its own morphirup-build.yml for five platforms with toolchain: true. For win-x64, win-arm64 and osx-arm64, that job packs the setup toolchain with PackWindowsToolchain and runs the WindowsReleaseSetup test group on the produced archives. The release job then runs FlattenReleaseAssets, MorphirupChecksums and WindowsToolchainChecksums. The toolchain files carry names and hashes, and the bundle names its asset URLs by the release source. The published finos/morphir-dotnet v0.5.0-alpha.1 has 43 such assets.

Goals and non-goals

Goals: a finos/morphir release carries those 43 assets under their names, built and assembled by the source, qualified on each platform, and recorded in the manifest.

Non-goals: changing the names or the bundle format (local-toolchains 0.1.0-preview.5 is separate work), signing, or building anything with a second implementation here.

Decisions

The journey follows win-arm64 in the release v0.5.0-alpha.2, from the build to morphirup setup --yes.

BUILD-1. The source's workflow builds morphirup at the pin

release.yml calls finos/morphir-dotnet/.github/workflows/morphirup-build.yml@<pin> for each morphirup platform, with repository, ref: <pin>, toolchain: true and upload-host-offering: true, as cli-offering.yml is called. For win-arm64 this one job, on windows-11-arm, does four things: it packs the manager and the toolchain, runs the setup journey on what it produced, uploads morphirup-win-arm64 and windows-release-toolchain-win-arm64, and uploads the host as morphir-dotnet-self-contained-win-arm64. The binding check requires each source workflow to be called once, at the pin, with the pin as its literal ref.

At 318b1bfd, morphirup-build.yml has none of those three inputs. Its checkout therefore takes the caller's repository, and its Windows step compares HEAD with the caller's GITHUB_SHA. A cross-repository call needs repository and ref on its checkout and in that comparison. That is a source change, delivered with the next source release. Alternative: run the same build targets in a job written here. Rejected: it would be a second definition of the release build, which then drifts from the source's own.

HOST-1. One host archive, one name

A toolchain's host archive is named morphir-dotnet-<version>-self-contained-<rid>.zip (.tar.gz on osx-arm64). That is also the name of the self-contained offering. The two are separate PackRelease builds, and they are not byte-identical: in v0.5.0-alpha.1, win-x64's is 72,694,361 bytes in finos/morphir-dotnet and 72,718,523 bytes in finos/morphir. The candidate, the bundle and SHA256SUMS name the toolchain job's bytes. So on those three platforms the offering is the toolchain job's host archive, and cli-offering.yml does not build self-contained there. The parent qualifies it like any other offering and checks that the toolchain's copy has the same bytes. Alternative: let the toolchain take the offering's archive as an input. Rejected: it would split one source build across two jobs and two workflows.

ASM-1. The source's targets assemble the assets

The publish job downloads morphirup-* and windows-release-toolchain-* apart from the offerings. It checks each toolchain against its producer's SHA256SUMS. It then runs the three source targets from the pinned ecosystem/morphir-dotnet checkout, and reads both checksum files back with sha256sum -c. Run locally on the published v0.5.0-alpha.1 files, the targets wrote both checksum files byte-identical to that release's. The manifest step then requires the exact 43 names, checks every checksum entry against the files, checks each host archive against its offering, and attaches each file once.

QUAL-1. Qualification reuses the source's journey

Each platform's qualify job starts its manager as a user does: morphirup-win-arm64.exe --version must print 0.5.0-alpha.2+<pin> with no .NET on the path, and win-arm64/morphirup.exe in the archive must be the same bytes. The acquired setup journey is the source's own WindowsReleaseSetup group, which morphirup-build.yml runs in the job that produced the archives. Publication needs that job, so a failed journey publishes nothing. No step is added to pull request CI.

Risks and trade-offs

RiskMitigation
Until the pin includes the morphirup-build.yml inputs, the reusable call is invalid, and a dry run fails before it builds.The wiring and its checks are unit-tested here. The pin moves to the source release that carries the inputs and local-toolchains 0.1.0-preview.5.
At 0.1.0-preview.4 the bundles name finos/morphir-dotnet URLs.Names, checksums and the setup journey do not depend on the URLs. The first release that ships morphirup from finos/morphir is the one whose pin writes 0.1.0-preview.5 bundles.
The release takes longer: five more platform jobs.They run in parallel with the offerings. The three self-contained offerings they replace are no longer built twice.

Migration plan

Land the source inputs and 0.1.0-preview.5 in finos/morphir-dotnet and cut 0.5.0-alpha.2. Move the pin to it, dry-run the release from a branch, then tag v0.5.0-alpha.2 here. Rollback: revert the morphirup job and the offering exclusion; finos/morphir-dotnet keeps publishing morphirup meanwhile.
