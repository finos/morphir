Goals and non-goals

Goals: one command opens any reviewed document correctly; repeated commands reuse one server; documents convert between the referenced and standalone forms.

Non-goals: the other jobs of mission control; editing documents in the browser; publishing to the project site; serving to other machines.

How an open command works

Decisions

These are proposals made while capturing intent. Each can change before implementation.

D1. MoonBit native app in apps/morphir-mission-control

Build the app as a MoonBit native program with argparse subcommands and --json output, following the repository script conventions. It can use render_markdown from apps/morphir-site/content and @http.Server from moonbitlang/async directly. Alternative: TypeScript on Bun, like serve.ts; rejected because Markdown rendering would then need a second renderer and the repository prefers MoonBit for its tools.

D2. One server for each checkout, found through a record

The server writes .dev/mission-control/server.json with its process id, port, checkout root and app version. An open command reads the record and calls GET /_health. The server answers with its checkout root and version. The command reuses the server only when both match; otherwise it starts a new one and replaces the record. The server binds 127.0.0.1 on a free port that the operating system chooses.

{ "pid": 4242, "port": 51873, "root": "/path/to/checkout", "version": "0.1.0" }

Alternative: a fixed port; rejected because two checkouts or worktrees would then compete for it.

D3. URLs mirror checkout paths; rendered views have their own routes

RouteContent
/<path>A checkout file. Markdown files are rendered into the template; other files are served as they are.
/_bead/<id>The bead's design, read from the tracker on each request.
/_change/<name>/Index of an OpenSpec change, active or archived, linking to each file.
/_healthCheckout root and app version, as JSON.

Any request path that ends in docs/templates/assets/<file> returns that asset, whatever comes before it. A page with a wrong relative prefix, such as an archived design, still gets its styles. A page from /_bead/<id> gets the referenced form with root-relative asset paths.

D4. The transform marks inlined assets so it can reverse them

Standalone output replaces each known asset reference with an inline element that names the asset:

<style data-agent-asset="agent-document.css">…</style>
<script data-agent-asset="highlight/highlight.min.js">…</script>

The referenced conversion replaces each marked element with a link that has the correct relative prefix for the output path. Only files in docs/templates/assets/ are known assets. Any other script or stylesheet stops the conversion. The transform never uses the network.

Risks and trade-offs

RiskMitigation
A stale record points at a reused process id.Trust the health check, not the process id.
A server stays running after it is no longer needed.A stop command; the idle policy is an open question.
Bead designs come from a shared tracker that other people write.Serve on loopback only, with a Content-Security-Policy that allows scripts only from the shared assets, so a script in a design does not run.
apps/morphir-site/content is native-only and owned by the site.Depend on its public API; move the renderer to a shared package if both apps need changes.

Open questions

Task group 1, bead morphir-ukvn.5.97.1, records the answers.

  • What else mission control does, besides documents.
  • When the server stops: on a command, after a time with no requests, or both.
  • What a standalone copy is for: sharing with people who have no checkout, storing in beads, or both. This decides whether beads-companion design store writes the standalone form.
  • Confirm D1, the implementation language.
