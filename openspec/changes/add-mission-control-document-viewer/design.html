Goals and non-goals

Goals: one command opens any reviewed document correctly; every bead in the tracker can be read as a web page; repeated commands reuse one server; documents convert between the referenced and standalone forms.

Non-goals: the other jobs of mission control (see Vision); editing documents or beads in the browser; publishing to the project site; serving to other machines.

Vision: later work

Mission control coordinates intent and tasks for the people and agents who work on Morphir. Viewing documents is its first part, and this change builds only that part. The table lists the rest of the vision so that this change does not close it off. Each row needs its own OpenSpec change.

One consequence for this change: the server routes in SRV-2 and the document kinds in open must stay open to new kinds, so that tasks and OKF bundles can be added later without a second server.

How an open command works

Decisions

The maintainer confirmed these decisions on 2026-10-25, in task group 1 (morphir-ukvn.5.97.1).

APP-1. MoonBit native app in apps/morphir-mission-control (confirmed)

Build the app as a MoonBit native program with argparse subcommands and --json output, following the repository script conventions. It can use render_markdown from apps/morphir-site/content and @http.Server from moonbitlang/async directly. TypeScript on Bun, like serve.ts, was not chosen: Markdown rendering would then need a second renderer, and the repository prefers MoonBit for its tools.

SRV-1. One server for each checkout, found through a record

The server writes .dev/mission-control/server.json with its process id, port, checkout root and app version. An open command reads the record and calls GET /_health. The server answers with its checkout root and version. The command reuses the server only when both match; otherwise it starts a new one and replaces the record. The server binds 127.0.0.1 on a free port that the operating system chooses.

{ "pid": 4242, "port": 51873, "root": "/path/to/checkout", "version": "0.1.0" }

Alternative: a fixed port; rejected because two checkouts or worktrees would then compete for it.

SRV-2. URLs mirror checkout paths; rendered views have their own routes

RouteContent
/<path>A checkout file. Markdown files are rendered into the template; other files are served as they are.
/beads/, /beads/<id>The Rabbita bead browser: the list of all beads, and one bead's page.
/_api/beads, /_api/beads/<id>Bead data as JSON for the browser, with the time the tracker was read.
/_bead/<id>/designThe bead's design as a document in the template, read from the tracker on each request.
/_change/<name>/Index of an OpenSpec change, active or archived, linking to each file.
/_healthCheckout root and app version, as JSON.

Any request path that ends in docs/templates/assets/<file> returns that asset, whatever comes before it. A page with a wrong relative prefix, such as an archived design, still gets its styles. A page from /_bead/<id>/design gets the referenced form with root-relative asset paths.

STD-1. The transform marks inlined assets so it can reverse them

Standalone output replaces each known asset reference with an inline element that names the asset:

<style data-agent-asset="agent-document.css">…</style>
<script data-agent-asset="highlight/highlight.min.js">…</script>

The referenced conversion replaces each marked element with a link that has the correct relative prefix for the output path. Only files in docs/templates/assets/ are known assets. Any other script or stylesheet stops the conversion. The transform never uses the network.

SRV-3. The server stops on a command and when idle

stop ends the server for the checkout. The server also exits by itself after 30 minutes with no requests; --idle-minutes changes the period. On either exit the server removes .dev/mission-control/server.json, so the next open starts a new server. If the server dies without removing the record, the stale-record check in SRV-1 handles it.

STD-2. The standalone form is for sharing without a checkout

A standalone copy goes to people, or to machines, that have no checkout and do not want to pull the repository. Committed documents and designs stored in beads keep the referenced form, so beads-companion design store does not change and tracker designs stay small. The viewer serves a bead design with root-relative asset paths (SRV-2), so a referenced design in beads still renders.

UI-1. A Rabbita interface around server-rendered documents

The app's own pages, the bead browser and the change index, are Rabbita views compiled to JavaScript and served by the native server. Documents stay pages in the agent document template, rendered by the server, so they look the same inside and outside the app. A bead page shows the bead's fields, Markdown text and comments in Rabbita, and shows its design in a frame from /_bead/<id>/design.

The frame has the sandbox attribute without allow-same-origin, and the design response has a Content-Security-Policy that allows scripts and styles only from the shared assets and no remote images. A script that someone put in a design cannot then reach the app or the bead data. Markdown fields render with raw HTML escaped, for the same reason.

<iframe src="/_bead/morphir-ukvn.5.97/design" sandbox="allow-scripts" title="Design"></iframe>

The pin is the one that apps/morphir-site and apps/morphir-workbench use, so the three apps move to a new Rabbita release together.

BEAD-1. Bead data comes from the bd command and is projected

The server runs bd list --json --all for the list, and bd show --json and bd comments --json for one bead. It does not pull from the remote: it shows the local database and the time it read it, and reads again when the page asks. The list response keeps only the fields that the list shows. A dependency keeps only its id, title, status, type and dependency type, because bd show --json can embed the full related bead, with a design of several megabytes.

Risks and trade-offs

RiskMitigation
A stale record points at a reused process id.Trust the health check, not the process id.
A server stays running after it is no longer needed.A stop command and a 30-minute idle exit (SRV-3).
Bead designs come from a shared tracker that other people write.Serve on loopback only, with a Content-Security-Policy that allows scripts only from the shared assets, so a script in a design does not run.
The tracker has thousands of beads, and some designs are several megabytes.The list response leaves out long text; a bead page loads one bead; designs load only in their frame (BEAD-1).
A front end adds a JavaScript build to a native app.Use the build that apps/morphir-site already uses for its Rabbita islands.
apps/morphir-site/content is native-only and owned by the site.Depend on its public API; move the renderer to a shared package if both apps need changes.
