Context

See proposal.md, "Why", for the motivation. This change is the MVP pipeline: it uses and requires no trust. add-extension-trust adds trust decisions and Sigstore verification as a fast follower. The facts that shape the approach:

  • The extension lifecycle commands in apps/morphir/extension.mbt and the explicit --services-pin/--services-helper route described in apps/morphir/docs/extension.md delegate repository, store, catalog and lock work to a Rust helper (apps/morphir/native-services/) that links morphir-distribution, morphir-host and morphir-host-native from finos/morphir.
  • Running an extension also needs explicit pins and helpers: core-wasm-process runs inside a pinned Node host, and native and Extism guests go through the Rust helper. A separate change, being planned in the mep-worker-host worktree, gives the CLI its own host on a worker model: an MEP channel connects workers (out-of-process native guests; WASM guests in Web Workers in the browser) to the host. This change waits on it for probing and activation.
  • Published bundles already exist and must stay readable: release.json descriptor 2.0.0-draft.2 with claim sets at 0.1.0-draft.2, each artifact with its .sha256 file (finos/morphir-python extension/python/v0.4.1, finos/morphir-elm extension/elm/v0.1.0 to v0.4.1, which are the Elm classic extension under its old name).
  • GitHub serves raw.githubusercontent.com, api.github.com and Pages with Access-Control-Allow-Origin: *, but release asset downloads (github.com/.../releases/download and its release-assets.githubusercontent.com redirect) carry no CORS header. Checked 2026-10-30.
  • morphir compile selects its frontend in apps/morphir/compilation.mbt from the built-in @moonbit_frontend and @elm_frontend providers, with a --provider override.
  • adopt-moon-lander (morphir-ukvn.5.99) moves configuration, hosting and logging onto Moon-Lander. This change uses whatever configuration loader is current when each group lands.
  • The MoonBit CLI already has morphir toolchain setup. The new top-level morphir setup is a different command.

Goals and non-goals

Goals:

  • One acquisition implementation, in MoonBit, that serves native, Node and browser hosts. Only the I/O edges differ.
  • Short default paths. A user reaches a working compile in one command (morphir setup or the compile itself). A publisher needs at most three commands, an owner at most three (anti-goal: four or more).
  • Installed state is checked at install (digest, probe) and checked offline at every activation.
  • Everything the trust follow-up needs is recorded now: publisher identities in index entries, attestations on releases and on the index.

Non-goals:

  • Trust decisions, trust prompts and signature verification. They are add-extension-trust.
  • The extension host itself. It is the worker-host change; this change calls it.
  • Signing in the CLI. Publishing signs with actions/attest inside the generated workflow.
  • A hosted registry service. Admission runs in the owner's GitHub workflow.
  • Reading or migrating Rust CLI extension state, or local-directory repositories that the Rust tooling created.
  • Package (model) acquisition. Tool acquisition.
  • Browser storage edges and an in-browser acceptance test. This change builds the package for js and wasm, filters to WASM artifacts on hosts that cannot start processes, and records mirrored locations; the Workbench wires the browser edges later.

How the parts fit

Decisions

DIST-1. A pure MoonBit acquisition package with host edges

A new package (working name pkgs/morphir-extensions) owns repository reading, resolution, store, catalog and lock logic as pure functions over bytes and records. The host supplies four edges: HTTP GET, durable storage (filesystem under MORPHIR_HOME, or browser storage), clock and an interactive prompt. Probing and activation go through the worker host (HOST-1). apps/morphir wires the native and Node edges; the Workbench wires the browser edges later.

Alternatives: extend the Rust helper with GitHub support (rejected: the Rust CLI and its library path are being sunset, and it cannot run in the browser); port the Rust library one to one (rejected: we want the new layout and a smaller surface, see DIST-2).

DIST-2. A new versioned layout under MORPHIR_HOME

$MORPHIR_HOME/extensions/v1/
  layout.json                      # {"layout": 1}
  store/sha256/<hex>               # checked artifacts, read-only
  catalog.json                     # active extension per id
  locks/<id>.json                  # selection, digests, publisher identity when recorded
  repositories.json                # configured repositories, enabled flag
  repositories/<name>/index/...    # last accepted index (cache)
  repositories/<name>/state.json   # accepted serial, fetched-at

Writes go to a staging file and are renamed into place; the store is written before the catalog and lock that refer to it. Files outside extensions/v1/, including Rust CLI state, are never read or changed. The trust follow-up adds trust.json and attestation bundles in locks within v1, as optional members. A later incompatible layout uses v2/ and an explicit migration.

DIST-3. Keep the publisher formats, add an index format

The reader accepts the release descriptor 2.0.0-draft.2 and claims 0.1.0-draft.2 exactly as published, including the draft.1 conversion rules in finos/morphir docs/design/draft/extensions/distribution-and-acquisition.md. The repository index is a new document, morphir-extension-index 0.1.0-draft.1: an index.json with repository name, serial, recommended extensions, owner identity and the SHA-256 digest of each history, and one JSON Lines history per extension id whose records add the optional publisher identity, channel and artifact locations to the descriptor's per-artifact data. The CLI refuses a history whose digest differs from the one in index.json, so the root binds everything that resolution reads. Without this binding, a later signature on the root would not protect the publisher identities and artifact digests in the histories. Local-directory and GitHub-hosted repositories use the same format. Must-ignore-unless-critical applies, as for the descriptors.

HOST-1. Probe and activation through the worker host

The acquisition package asks the worker host to describe a staged artifact (identity, version, claims) and to start an installed one from its stored artifact and recorded runtime. It never starts processes or loads WASM itself. Until the worker host lands, groups 1 and 2 can land with the probe behind an interface and tested with an in-memory worker; installing for real (task 1.6), provider acquisition (group 4) and frontend removal (group 6) wait for the worker host.

REPO-1. Repository locations and the index branch

A GitHub-hosted repository is written github:<owner>/<repo>[@<branch>][/<path>]. The default branch is morphir-index, an orphan branch like gh-pages, protected so that only the admission workflow writes to it. The CLI reads it from raw.githubusercontent.com, which allows cross-origin reads, and never needs the GitHub API to read an index, which avoids its rate limit. Release assets are downloaded from their release URL on native and Node. A GITHUB_TOKEN in the environment is sent only to GitHub hosts, and only when present.

REPO-2. Index freshness by serial

The admission workflow increases index.json's serial on every change. The CLI refuses a lower serial than the one it last accepted, which stops an accidental or malicious rollback to an older index. The workflow also attests index.json with actions/attest; the MVP does not verify that attestation, and add-extension-trust does.

REPO-3. Capability lookup over index claims

A query is (role, language-or-target, IR release). The CLI filters index records by claim, platform (process artifacts), runtime support of the current host (WASM only where processes cannot start), host version (requires.host) and channel, and orders the results: the repository's recommended provider first, then by repository order, then newest version. No artifact is downloaded to answer a query.

PROV-1. Provider selection reads the catalog, then the repositories

Compile and generate build their provider list from the installed catalog, apply an explicit choice (the existing --provider option, or the workspace's frontend provider setting), and on a miss run REPO-3. Interactive runs offer the result and install it through the same path as extension install; non-interactive runs fail with the command to run, unless --install-missing is given. The @elm_frontend and @moonbit_frontend imports leave apps/morphir/moon.pkg only after the finos index offers both frontends (see Migration plan).

PROV-2. Compile keeps its output contract

morphir compile keeps its options (--language, --provider, --model-format), its outputs (ion-binary, ion-text, morphir-json checkpoints) and its JSON report when the provider is an installed extension. An adapter maps the extension's model-envelope.json and model.ionb result into the checkpoint backend. The existing compile tests must pass unchanged after group 6; differences are bugs, not migrations.

UX-1. Setup: recommended set first, capability view on customize

The first screen lists the recommended set (from each enabled repository's index.json) plus providers the workspace configuration needs, with "Install the recommended set" selected. "Customize" shows roles, then languages or targets, with a provider choice per row. Both end on one review screen that confirms the selection. The screens use arrow-key selection when the terminal allows raw input and numbered prompts otherwise. Unattended: --defaults, --add <id>, --remove <id>. The trust follow-up adds its single trust prompt to the review screen.

PUB-1. Publishing inside the release workflow

Signing stays with GitHub's action, so the generated workflow has three steps around one command:

morphir extension publish --stage dist          # bundle, descriptor, describe probe
# uses: actions/attest@v4   with: subject-path: dist/artifacts/*
morphir extension publish --release dist        # GitHub release with bundle and .sigstore.json files

morphir extension publish setup writes that workflow (permissions contents: write, id-token: write, attestations: write) and prints the publisher identity. The publisher's default path is: publish setup, commit and push, push a tag. The three-command limit counts the publisher's commands, not the jobs inside the workflow. The MVP creates attestations so that releases admitted now can be verified once add-extension-trust lands.

publish --stage does not build the extension. It takes artifacts the publisher's own build made (one portable WASM artifact, or one native executable per platform) and an optional existing release.json, and produces the bundle; it is the MoonBit replacement for extension bundle. Native artifacts are probed on a runner of their platform, so for native extensions the generated workflow is a matrix of stage jobs followed by one attest-and-release job. Releases made before this change have no index records and are not admitted; publishers cut new releases through the workflow.

PUB-2. Admission by the owner's scheduled workflow

morphir repository setup creates the morphir-index branch with an empty index, a morphir-publishers.json file on the default branch and the admission workflow (schedule every 30 minutes plus workflow_dispatch). morphir repository publisher add <id> <owner/repo> <workflow> edits the publishers file, which the owner merges through their normal review. The workflow runs morphir repository admit, which lists releases of each registered publisher repository, checks digests and claims with the same code users run, appends index records with the registered publisher identity, increases the serial, attests index.json and pushes to the index branch. With mirroring on, it also copies admitted artifacts to the repository's Pages site. In the MVP the workflow path is recorded but not checked; the trust follow-up checks it through the release attestations.

Commands that write to GitHub use GITHUB_TOKEN in a workflow, and on a workstation use GITHUB_TOKEN or the token from gh auth token when gh is installed. If the token cannot set branch protection, repository setup still creates everything else and prints the exact protection settings for the owner to apply.

Alternatives: publishers push to the owner (rejected: a token per publisher, the thing trusted publishing avoids); an OIDC exchange service (deferred: no service to run now; admit is the step it would call).

Risks and trade-offs

RiskMitigation
Until add-extension-trust lands, the CLI installs from any enabled repository without checking who published an artifact.Only finos is enabled by default, and its index is written only by its owner's protected workflow; digests and probes still run; releases and indexes carry attestations from day one, so the follow-up can verify everything already admitted.
The worker host takes longer than planned.Groups 1 and 2 and the publishing tooling proceed with an in-memory worker in tests; real installs, provider acquisition and frontend removal wait (HOST-1).
GitHub disables scheduled workflows in public repositories after 60 days without activity.The admission workflow records a heartbeat, and repository list shows index age so users notice a stalled index.
The first Elm or MoonBit compile now needs the network.morphir setup and --install-missing; local-directory repositories for air-gapped sites; the frontends leave the binary only after the finos index serves them.
Browser hosts cannot download release assets.Owner mirroring (PUB-2); the CLI reports entries that have no cross-origin location.
Users lose extensions installed by the Rust CLI.Documented as breaking; morphir setup reinstalls the common set in one command.

Migration plan

  1. Land the MoonBit acquisition core with the index format, local-directory repositories and the new layout; switch the lifecycle commands to it and drop their helper flags (group 1). Real installs need the worker host.
  2. Land GitHub-hosted repository reading, with serials and capability lookup (group 2).
  3. Land the publish command and the owner admission tooling (group 3). Create the finos index in finos/morphir and publish the Elm, Gleam, MoonBit and Python extensions through it. The Elm and Gleam moves are in progress in finos/morphir-elm (vnext) and finos/morphir-gleam.
  4. Land provider acquisition (group 4) and morphir setup (group 5), once the worker host is available.
  5. Remove the built-in Elm and MoonBit frontends after the finos index serves both and the setup and on-demand paths pass their acceptance tests (group 6).
  6. add-extension-trust follows: trust decisions, prompts and Sigstore verification of releases and indexes.

Rollback: until step 5, the built-in frontends still compile, so a faulty acquisition release does not stop compiles. Each step is its own release.

Open questions

  • The admission schedule interval (30 minutes is a starting value).
  • Browser storage for the layout: the Origin Private File System or IndexedDB. Decided when the Workbench wires the browser edges.
  • Whether the owner mirror uses Pages or another CORS-enabled host for large artifacts.
