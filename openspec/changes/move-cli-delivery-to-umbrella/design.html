Context

See proposal.md for why. What the design starts from, as observed in this checkout on 10 November 2026:

  • crates/morphir was the Rust CLI: about 100,000 lines with 43 integration test files, released by release.yml on v* tags for six Rust targets. Its last release is v0.4.0-beta.12.
  • The MCK commands lived in that crate as a thin layer (commands/mck*.rs) over the morphir-mck engine. They depended only on the engine, morphir-bdd, clap, reqwest and tokio, so they could move without the product. kb was equally self-contained over morphir-kb and morphir-okf.
  • finos/morphir-dotnet main (7c26348, with #574) defines the four offerings in build/Helpers/ReleaseProfiles.cs and builds each with --target PackRelease --deployment <id> [--rid <rid>], writing the artifact, <artifact>.build-launch.json and <artifact>.build-contents.json. Its own deployment.yml still ships the legacy single-file asset.
  • The release version of that source is the latest released heading of its CHANGELOG.md: 0.4.0-alpha.4. finos/morphir already has a Rust tag v0.4.0-alpha.4.
  • Evidence from finos/morphir-dotnet#570 (workflow wasm-offerings.yml, run 42851276092): win-x64 behaviour differed when the produced executable was launched itself rather than through dotnet exec (CET), and a macOS packaged input scenario fails where /var resolves to /private/var. This change consumes that evidence; it does not change CET flags or implement WASM engine work.

Goals and non-goals

Goals: one place that builds and releases the Morphir CLI from a pinned .NET source; no Rust product in this repository; one MCK runner reachable as morphir-mck and through morphir mck; every former gate kept or retired by name.

Non-goals: publishing a release; changing the .NET source (other workers own it, including the delegating morphir mck); the .NET MCK runner that is the destination of the shared runner; removing ecosystem/morphir-rust; rewriting the user guides that still describe Rust CLI commands; the Contract Versioning text of AGENTS.md (#1152).

Decisions

The journey follows the maintainer who pushes cli/v0.4.0-alpha.4, then the contributor who runs a compatibility gate after the Rust CLI is gone.

SRC-1. The source is a submodule pin with a recorded commit

The workflow first establishes what it is building. ecosystem/morphir-dotnet is a submodule (first at 7c26348, now at the candidate 8c15df5, see SRC-2), and .config/cli-release.json records the same commit and repository. tools/cli-release.ts verify-source reads the gitlink from the index and .gitmodules, and every release job runs it. The recorded copy turns an accidental submodule bump into a failing check instead of a silent change of product. Alternatives: the gitlink alone (a bump would change the release without a reviewed expectation), or a branch reference (not reproducible).

BLD-1. Build with the source's own release profiles

Each offering is built by the source's PackRelease profiles, through its cli-offering.yml (SRC-2). The source's build checks each publish folder against its launch metadata. Native AOT compiles only on its own operating system, so every RID has its own runner. This repository keeps only independent expectations (the deployment ids and RIDs) and a test that they equal what the pinned ReleaseProfiles.cs defines. Alternatives: calling morphir-dotnet's deployment.yml (it ships the legacy asset and publishes to NuGet from that repository) or porting its packaging (a second implementation the maintainer ruled out).

SRC-2. Build through the source's reusable offering workflow, from a marked candidate pin

finos/morphir-dotnet draft PR #590 (head 8c15df59ce902c3ec06bb2df0c8ab4a88445a39d on 10 November 2026, branch feat/mck-dispatch-parent-delivery) adds .github/workflows/cli-offering.yml: inputs repository, ref (the same pinned commit), deployment, rid, os and configuration; outputs artifact-name (morphir-dotnet-<deployment>-<rid|any>), artifact, sha256 and release. It runs PackRelease, compares the SHA-256 with the launch metadata, starts the produced file from a path with spaces (comparing --version before +), uploads one flat artifact and publishes nothing. Its own start check is not this repository's qualification.

The offering job calls it for 19 matrix entries (three deployments on six platforms, and the portable tool once). A uses: reference cannot be an expression, so the commit appears literally in uses and in ref, and the release tests check both against .config/cli-release.json and the gitlink. Because #590 is unmerged, the config marks the pin as a candidate (source.candidate). The release then builds and qualifies, which exercises the interface, but the manifest step refuses and nothing can be published. Removing the marker is part of choosing the final pin on the source's main. Alternative: calling PackRelease directly at 7c26348, the first version of this change, which duplicated the source's build steps here.

QUAL-1. Qualify by launching what ships

The produced artifact is what users run, so qualification starts it. An archive is extracted with tar and its launch path from the launch metadata is executed directly; the framework-dependent apphost is started itself, never dotnet exec morphir.dll, because the #570 evidence showed the launched file behaves differently on win-x64. Native AOT and self-contained run with no dotnet directory on PATH and no DOTNET_ROOT. The tool package is installed from the produced .nupkg into a tool path and a local manifest and run as dotnet-morphir and dotnet morphir. Every path is resolved against the directory the tool was started from before any subprocess runs elsewhere, and a zip is read with Windows' own tar.exe (Git's GNU tar reads no zip) or unzip. Each invocation runs three scenarios: --version must print the launch metadata's release, alone or with build metadata of at least 7 hex digits that prefix the pinned commit (0.4.0-alpha.4+<sha>). This is stricter than the source's own start check, which compares only the part before +, because this repository owns the provenance. Metadata naming any other commit fails, and so does an artifact whose build contents do not name the pinned commit and a clean tree (BIND-1), --help must exit 0, and ir verify on a copied greeting-example.json is the packaged input. The artifact's SHA-256 must equal its launch metadata. Alternative: the source's own E2E tests (they build from source and do not prove the acquired bytes).

QUAL-2. Pending triage is recorded, not hidden and not passed

The macOS packaged-input failure is recorded in pendingTriage with its evidence. On osx-x64 and osx-arm64 that scenario still runs and keeps its exit code, but its status is pending-triage, the offering's qualified flag is false there, and the release notes print the triage. Launch and help failures still fail the release. Alternatives: skipping the scenario on macOS (silent) or failing every release until triage (blocks unrelated platforms).

TOOL-1. The tool package installs only its own bytes, through one source-owned helper

dotnet tool install queries every configured source in parallel and takes the fastest one that has the version. --add-source only adds a feed, and the global packages folder is reused. So a feed in the working directory's or the user's NuGet configuration, or a warm cache, holding another Morphir.Tool of the same version (nuget.org has 0.4.0-alpha.4) can be installed instead of the produced package. The installs therefore use a generated configuration with <clear /> and one feed holding the produced package (--configfile), and fresh packages, HTTP and plugin caches. Every <id>.<version>.nupkg copy NuGet keeps must have the artifact's SHA-256: in the tool store (.store/<id>/<version>/<id>/<version>/) and in the packages folder (<id>/<version>/). That layout was observed on Windows with SDK 10.0.403, not assumed. NuGet's contentHash is not a plain file hash, so the comparison uses the copy's own SHA-256.

finos/morphir-dotnet is adding a shared install helper (.github/scripts/install-tool-package.ps1, used by cli-offering.yml; committed locally there, not pushed or pinned). One isolation implementation should exist, owned by the source. isolatedToolInstall here is the interim. A test fails as soon as the pinned source carries the helper, and then qualification calls the helper and keeps only the parent's independent byte check (verifyInstalledCopies).

Interface reported by the source owner for e7d780c7 (not pushed, not run on Linux or macOS): pwsh -File install-tool-package.ps1 -Package <built .nupkg> -ToolPath <new folder> -WorkDir <new folder>. It reads the id, version and single command from the package. It installs with --tool-path only. It prints the installed command path on stdout, exits 0 or 1, and requires PowerShell 7. It checks that the store holds exactly one package, whose <id>.<version>.nupkg has the built SHA-256 and whose tools/ entries match the built package. It has no --local mode and no machine-readable result. The parent's dotnet morphir qualification needs a local install, and its byte check needs the stored paths. So dropping the interim needs either the proposed -Local and -ResultFile additions, or a parent --local install of its own, which would again be a second implementation. That choice is with the root thread.

PUB-1. Publish only the source's own release, and never decide its version

The release version is the CHANGELOG's latest dated release, which says nothing about whether the pinned commit is that release. At the candidate pin 8c15df5, v0.4.0-alpha.4 in finos/morphir-dotnet is bec7df3, and Unreleased has entries. Removing the candidate marker alone would publish other bytes under an identity the source already released. Publication is refused unless three conditions hold: no candidate marker, nothing under Unreleased, and the source's tag v<version> (read with git ls-remote, peeled) naming exactly the pin. Neither the version nor the tag is chosen here. When the gate blocks, the remedy is a source release, not a parent override.

BIND-1. Bind the run to its tag, its commit, the pin and each artifact's origin

A dispatch can name one tag while running the workflow definition of another ref, whose literal uses commit then differs from the tag's. release-info therefore refuses three things. It refuses a run whose GITHUB_REF is not refs/tags/<tag>. It refuses a checkout that is not the tag's commit, read with git rev-parse, never from GITHUB_SHA. And it refuses a release.yml whose literal uses commit and ref are not the pin. Every later job checks out the commit it outputs, and the manifest step refuses a checkout that differs from it. The manifest records that commit; there is no unknown fallback. Each artifact is tied to the source by its .build-contents.json. Its pack origin must be the pinned commit with a clean working tree, and its artifact, release, deployment, platform and SHA-256 must match the launch metadata.

DRY-1. A dry run validates everything and creates nothing

A dispatch defaults to dry-run: true; a tag push is a publication. A dry run builds, qualifies and runs every validation of the manifest step: artifacts, origins, qualification records, kit, legacy names and asset names. It records the publication blockers in the manifest (publication: {dryRun, publishable, blockers}) and writes dry-run-assets.txt, and the evidence is uploaded. It never writes release-assets.txt, and the create step runs only when the run is not dry and release-info found the pin publishable. A publication with blockers fails after writing its evidence. Neither a dry run nor its evidence is production qualification. No fork, dispatch or tag has been made.

REL-1. Official CLI tags are cli/v<version>

The .NET version line restarts below the Rust one, and v0.4.0-alpha.4 already names a Rust release here, so reusing v* would collide with or overwrite history. Official releases use cli/v<version>, like extension/python/v*. release-info requires exact canonical SemVer without build metadata that equals the pinned CHANGELOG's latest release. Existing v* tags and releases are not touched. This is a proposal for review, not a decision: no tag or version-number decision has been made, and nothing here tags. The host release version must not silently jump to clear the Rust numbers; the version stays whatever the pinned CHANGELOG releases (see Open questions).

REL-2. Publish once, with a manifest, never replace

publish-release needs every qualification job, refuses a tag whose release exists and a candidate pin, writes release-manifest.json and release notes, and creates the release with every asset in one gh release create --verify-tag. The manifest step collects artifacts recursively from the downloaded folders and requires exactly one artifact for each deployment and platform: a missing, repeated or unexpected artifact, or a repeated asset name, is an error. It requires exactly one qualification for each deployment and platform, matching its artifact's release, file name and SHA-256: a missing, repeated, unexpected or mismatched record is an error. It writes release-assets.txt, the exact absolute paths to attach, and the create step reads that list instead of globbing. Qualification reports are uploaded from the hidden .dev folder with include-hidden-files and a glob that names only the reports. The workflow never uploads into or edits a release and never creates a tag. The manifest names the tag, the finos/morphir commit, the source repository and commit, the kit's corpusHash, algorithm and revision from morphir-mck kit status (the runner's own identity, not a second hash scheme), every artifact's SHA-256 and each qualification. The old incremental --clobber upload and select_release_assets.py go.

LEG-1. Legacy names alias the Native AOT executable

This follows the maintainer decision of 9 November 2026 (finos/morphir#1146, REL-1 of the morphir-dotnet adoption; reconciled in #584 e8f4a00b): future legacy assets morphir-<rid>[.exe] and morphir-<rid>-v<version>.tar.gz carry the same bytes as the native-aot offering, assets already published stay as they are, and the trimmed managed single-file build is retired. There are four offerings, not five. publish-release runs cli-release.ts legacy-aliases. It takes the platforms from the pinned LegacyAsset.TrimmedSingleFile (win-x64, osx-arm64, linux-x64, linux-arm64), extracts each packed and qualified native-aot archive after checking its SHA-256, copies the executable under the bare name, and writes the tarball with the executable under <rid>/, which the proto plugin strips. It refuses an alias whose bytes differ from the executable. The manifest lists each alias with the artifact it aliases. Nothing calls PublishSingleFile.

MCK-1. One runner, standalone, with the old command tree

The contributor's gate becomes cargo run -p morphir-mck-cli -- check spec/ir/mck instead of cargo run -p morphir -- mck check spec/ir/mck. crates/morphir-mck-cli builds the binary morphir-mck from the moved command modules and a clap tree copied from the old MckAction; the moved tests drop the leading mck argument and nothing else. Two behaviours had come from the product and are now stated in the runner: serde_json's preserve_order (JSON member order, which the frozen package reports depend on; without it 6 acceptance tests and 1 JSON test failed) and the multi-threaded runtime. The .NET CLI's morphir mck ARGS starts morphir-mck ARGS, which the source-side adoption worker implements; spec/mck/cli-contract.md states the rule. The copied-binary acceptance still runs with an empty PATH; its product checks (the metadata preview and the two itest package examples) left with the product. The runner is development-only and stays in Rust only until the .NET runner replaces it.

DEV-1. A narrow internal development tool

crates/morphir-dev-tools builds morphir-dev with the kb tree unchanged. The library-level gates that lived in the CLI crate's tests (mep_contract, tool_release_metadata_conformance, package_runtime) are this crate's tests, because they never started the CLI. The tool has no product commands and is never released. Alternative: putting kb into morphir-mck (mixes kit and knowledge base) or porting it to TypeScript now (scope; the kb skill and the morphir-scala port depend on this behaviour).

DOC-1. Remove what can no longer be regenerated

docs/cli, docs/man and completions were generated from the Rust binary and checked for freshness against it. With the binary gone they would describe a product that does not exist and could not be refreshed, so they are deleted with their generator, their sidebar entry and the usage tool pin. User guides that describe Rust CLI commands are not rewritten here.

Risks and trade-offs

Contributors with scripts calling cargo run -p morphir.The mise tasks and tools are updated; mise run mck and mise run kb are the new entry points.

Migration plan

  1. Merge after #1147 (this branch is stacked on it).
  2. When finos/morphir-dotnet #590 is merged, move the pin to the merged commit on its main, update uses and ref to the same commit, and remove source.candidate (SRC-2).
  3. Choose the final delivery pin once the source-side MCK dispatch lands; update .config/cli-release.json and the gitlink together.
  4. Tag cli/v<version> from main only when the maintainer decides to release. Rollback is deleting the new tag before any release exists; an existing release is never replaced.

Open questions

  • Tag prefix: cli/v* (REL-1) or another spelling. Changing it touches one config value and the workflow trigger.
  • The first .NET release numbers below the last Rust release (0.4.0-alpha.4 after 0.4.0-beta.12). Whether the .NET line jumps ahead is a morphir-dotnet versioning choice.
