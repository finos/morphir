Context

See proposal.md for why. What the design starts from, as observed in this checkout on 10 November 2026:

  • crates/morphir was the Rust CLI: about 100,000 lines with 43 integration test files, released by release.yml on v* tags for six Rust targets. Its last release is v0.4.0-beta.12.
  • The MCK commands lived in that crate as a thin layer (commands/mck*.rs) over the morphir-mck engine. They depended only on the engine, morphir-bdd, clap, reqwest and tokio, so they could move without the product. kb was equally self-contained over morphir-kb and morphir-okf.
  • finos/morphir-dotnet main (7c26348, with #574) defines the four offerings in build/Helpers/ReleaseProfiles.cs and builds each with --target PackRelease --deployment <id> [--rid <rid>], writing the artifact, <artifact>.build-launch.json and <artifact>.build-contents.json. Its own deployment.yml still ships the legacy single-file asset.
  • The release version of that source is the latest released heading of its CHANGELOG.md: 0.4.0-alpha.5 at the current pin. finos/morphir already has Rust tags up to v0.4.0-beta.12, so the first .NET release needs a newer version; the source cuts 0.5.0-alpha.1 for it (finos/morphir-dotnet#637).
  • Evidence from finos/morphir-dotnet#570 (workflow wasm-offerings.yml, run 42851276092): win-x64 behaviour differed when the produced executable was launched itself rather than through dotnet exec (CET), and a macOS packaged input scenario fails where /var resolves to /private/var. This change consumes that evidence; it does not change CET flags or implement WASM engine work.

Goals and non-goals

Goals: one place that builds and releases the Morphir CLI from a pinned .NET source; no Rust product in this repository; one MCK runner reachable as morphir-mck and through morphir mck; every former gate kept or retired by name.

Non-goals: publishing a release; changing the .NET source (other workers own it, including the delegating morphir mck); the .NET MCK runner that is the destination of the shared runner; removing ecosystem/morphir-rust; rewriting the user guides that still describe Rust CLI commands; the Contract Versioning text of AGENTS.md (#1152).

Decisions

The journey follows the maintainer who pushes a tag v<version>, then the contributor who runs a compatibility gate after the Rust CLI is gone.

SRC-1. The source is a submodule pin with a recorded commit

The workflow first establishes what it is building. ecosystem/morphir-dotnet is a submodule (first at 7c26348, then 8c15df5, merged #590 commit 0885f172 and 3da850d7 and bddc8e05, now at 318b1bfd, the 0.5.0-alpha.1 release commit, still a marked delivery candidate until its tag exists, see SRC-2), and .config/cli-release.json records the same commit and repository. tools/cli-release.ts verify-source reads the gitlink from the index and .gitmodules, and every release job runs it. The recorded copy turns an accidental submodule bump into a failing check instead of a silent change of product. Alternatives: the gitlink alone (a bump would change the release without a reviewed expectation), or a branch reference (not reproducible).

BLD-1. Build with the source's own release profiles

Each offering is built by the source's PackRelease profiles, through its cli-offering.yml (SRC-2). The source's build checks each publish folder against its launch metadata. Native AOT compiles only on its own operating system, so every RID has its own runner. This repository keeps only independent expectations (the deployment ids and RIDs) and a test that they equal what the pinned ReleaseProfiles.cs defines. Alternatives: calling morphir-dotnet's deployment.yml (it ships the legacy asset and publishes to NuGet from that repository) or porting its packaging (a second implementation the maintainer ruled out).

SRC-2. Build through the source's reusable offering workflow, from a marked candidate pin

finos/morphir-dotnet PR #590 merged on 11 November 2026 at 0885f17264856521f0218151693c2b08810790ec, with the earlier 51be09f helper/routing work; its CI run 42898613660 was build evidence, not qualification. The delivery tuple now names source main at 318b1bfd1722d36f6c51a6c95d85b4d84f6623e7, the merge of finos/morphir-dotnet#637 that releases 0.5.0-alpha.1. It contains #640 (host-independent smoke lock files) and #641 (the ir verify fix) and leaves nothing under Unreleased. cli-offering.yml, install-tool-package.ps1 and the release profiles are unchanged since bddc8e05.

The offering job calls it for 19 matrix entries (three deployments on six platforms, and the portable tool once). A uses: reference cannot be an expression, so the commit appears literally in uses and in ref, and the release tests check both against .config/cli-release.json and the gitlink. Although #590 is merged, the config retains source.candidate because a commit on main does not establish a source release or acquired-artifact qualification. The release then builds and qualifies, which exercises the interface, but the manifest step refuses and nothing can be published. Remove the marker only after the source version/tag, forward-only parent version and actual qualification gates pass. No version, tag, release or dispatch is authorized by this pin. The external acquisition contract tests keep their separate f89dda45 pin in .config/toolchain-contract-tests.json. Alternative: calling PackRelease directly at 7c26348, the first version of this change, which duplicated the source's build steps here.

QUAL-1. Qualify by launching what ships

The produced artifact is what users run, so qualification starts it. An archive is extracted with tar and its launch path from the launch metadata is executed directly; the framework-dependent apphost is started itself, never dotnet exec morphir.dll, because the #570 evidence showed the launched file behaves differently on win-x64. Native AOT and self-contained run with no dotnet directory on PATH and no DOTNET_ROOT. The tool package is installed from the produced .nupkg into a tool path and a local manifest and run as dotnet-morphir and dotnet morphir. Every path is resolved against the directory the tool was started from before any subprocess runs elsewhere, and a zip is read with Windows' own tar.exe (Git's GNU tar reads no zip) or unzip. Each invocation runs three scenarios: --version must print the launch metadata's release, alone or with build metadata of at least 7 hex digits that prefix the pinned commit (0.4.0-alpha.4+<sha>). This is stricter than the source's own start check, which compares only the part before +, because this repository owns the provenance. Metadata naming any other commit fails, and so does an artifact whose build contents do not name the pinned commit and a clean tree (BIND-1), --help must exit 0, and ir verify on a copied greeting-example.json is the packaged input. The artifact's SHA-256 must equal its launch metadata. Alternative: the source's own E2E tests (they build from source and do not prove the acquired bytes).

QUAL-2. Pending triage is recorded, not hidden and not passed

A known failure can be recorded in pendingTriage with its evidence. On the platforms it names, that scenario still runs and keeps its exit code, but its status is pending-triage, the offering's qualified flag is false there, and the release notes print the triage. Launch and help failures still fail the release. Alternatives: skipping the scenario (silent) or failing every release until triage (blocks unrelated platforms). The macOS packaged-input failure where /var resolves to /private/var (finos/morphir-dotnet#570) was recorded this way until 13 November 2026. The source fixed it in finos/morphir-dotnet#584, and the marker was then removed, because it also hid that morphir ir verify never finished on osx-arm64 (dry run 43410195591; its fix, finos/morphir-dotnet#641, is still open, and the tagged v0.5.0-alpha.1 commit will contain it). macOS now qualifies the packaged input like every other platform, and the next dry run is its acquired-artifact evidence.

TOOL-1. The tool package installs only its own bytes, through one source-owned helper

dotnet tool install queries every configured source in parallel and takes the fastest one that has the version. --add-source only adds a feed, and the global packages folder is reused. So a feed in the working directory's or the user's NuGet configuration, or a warm cache, holding another Morphir.Tool of the same version (nuget.org has 0.4.0-alpha.4) can be installed instead of the produced package. The installs therefore use a generated configuration with <clear /> and one feed holding the produced package (--configfile), and fresh packages, HTTP and plugin caches. Every <id>.<version>.nupkg copy NuGet keeps must have the artifact's SHA-256: in the tool store (.store/<id>/<version>/<id>/<version>/) and in the packages folder (<id>/<version>/). That layout was observed on Windows with SDK 10.0.403, not assumed. NuGet's contentHash is not a plain file hash, so the comparison uses the copy's own SHA-256.

The source owns the one isolation implementation: .github/scripts/install-tool-package.ps1, which cli-offering.yml uses, present at the pin. Qualification runs it twice per platform, each time in new folders: -ToolPath, -WorkDir and -ResultFile for the tool path, and the same with -Local. The helper copies the package into its own feed and installs through its own nuget.config (clear sources, no fallback folders, its own packages folder). It isolates the caches, checks the store or packages folder, and writes the result file only after every check has passed, with absolute paths.

The parent reads each result and keeps its own check (helperResultProblems). The mode and package SHA-256 must be the produced ones. Every reported copy, and every <id>.<version>.nupkg the parent finds itself in the tool store or packages folder, must have the artifact's SHA-256 by the parent's own hashing. Paths must be absolute. The invocation must be the installed command with no arguments, or dotnet morphir from the manifest folder, never an entry assembly. Each invocation is started exactly as reported: file, argument array, working directory and environment, where null removes a variable. The interim parent install is gone. A real-install test runs the helper against a conflicting feed and a warm cache in both modes, and the parent's own hashing refuses a copy changed afterwards.

PUB-1. Publish only the source's own release, and never decide its version

The release version is the CHANGELOG's latest dated release, which says nothing about whether the pinned commit is that release. At the candidate pin bddc8e05, the CHANGELOG's latest release is 0.4.0-alpha.5, whose tag v0.4.0-alpha.5 in finos/morphir-dotnet is 3abb0de0, and Unreleased has entries. Removing the candidate marker alone would publish other bytes under an identity the source already released. Publication is refused unless three conditions hold: no candidate marker, nothing under Unreleased, and the source's tag v<version> (read with git ls-remote, peeled) naming exactly the pin. Neither the version nor the tag is chosen here. When the gate blocks, the remedy is a source release, not a parent override.

BIND-1. Bind the run to its tag, its commit, the pin and each artifact's origin

A dispatch can name one tag while running the workflow definition of another ref, whose literal uses commit then differs from the tag's. release-info therefore refuses three things. It refuses a run whose GITHUB_REF is not refs/tags/<tag>, except a dry run from a branch (DRY-1). It refuses a checkout that is not the tag's commit, read with git rev-parse, never from GITHUB_SHA; a dry run from a branch is bound instead to the branch's triggering commit, which must equal the checkout. A run that is not dry never runs from a branch. And it refuses a release.yml whose literal uses commit and ref are not the pin. Every later job checks out the commit it outputs, and the manifest step refuses a checkout that differs from it. The manifest records that commit; there is no unknown fallback. Each artifact is tied to the source by its .build-contents.json. Its pack origin must be the pinned commit with a clean working tree, and its artifact, release, deployment, platform and SHA-256 must match the launch metadata.

DRY-1. A dry run validates everything and creates nothing

A dispatch defaults to dry-run: true; a tag push is a publication. A dry run builds, qualifies and runs every validation of the manifest step: artifacts, origins, qualification records, kit, legacy names and asset names. It records the publication blockers in the manifest (publication: {dryRun, publishable, blockers}) and writes dry-run-assets.txt, and the evidence is uploaded. It never writes release-assets.txt, and the create step runs only when the run is not dry and release-info found the pin publishable. A publication with blockers fails after writing its evidence. A dry run may also be dispatched from a branch, to rehearse a release before its tag exists: release-info then binds the run to the branch's triggering commit instead of the tag's, the tag input only names the version, and every other binding of BIND-1 holds. A publication is never dispatched from a branch. Neither a dry run nor its evidence is production qualification.

REL-1. Official CLI tags are v<version>, and only ever move forward

Decided by the maintainer on 10 November 2026: official CLI releases use v<version>, the namespace the deleted Rust CLI's releases used. The first version of this change proposed cli/v<version>; that was not taken. The Rust tags and releases (v0.4.0-alpha.1 to v0.4.0-beta.12) stay as they are. Because the namespace is shared, a release must be newer than every other v* tag in finos/morphir and never reuse one. versionCollisionBlockers compares the version with every other v<semver> tag (read with git ls-remote --tags; the release's own tag is left out), and the publication gate refuses a version that is not newer. Reusing an existing tag itself is refused twice: by the existing-release step, and by the binding check, since that tag's commit is the old release and never the new checkout. The version is still the pinned CHANGELOG's, and nothing here chooses or bumps it. The source's latest release, 0.4.0-alpha.5, is below v0.4.0-beta.12, so publication stays blocked until the source releases a version that passes; 0.5.0-alpha.1 (finos/morphir-dotnet#637) is the first that does. release-info still requires exact canonical SemVer without build metadata that equals the pinned CHANGELOG's latest release.

REL-2. Publish once, with a manifest, never replace

publish-release needs every qualification job, refuses a tag whose release exists and a candidate pin, writes release-manifest.json and release notes, and creates the release with every asset in one gh release create --verify-tag. The manifest step collects artifacts recursively from the downloaded folders and requires exactly one artifact for each deployment and platform: a missing, repeated or unexpected artifact, or a repeated asset name, is an error. It requires exactly one qualification for each deployment and platform, matching its artifact's release, file name and SHA-256: a missing, repeated, unexpected or mismatched record is an error. It writes release-assets.txt, the exact absolute paths to attach, and the create step reads that list instead of globbing. Qualification reports are uploaded from the hidden .dev folder with include-hidden-files and a glob that names only the reports. The workflow never uploads into or edits a release and never creates a tag. The manifest names the tag, the finos/morphir commit, the source repository and commit, the kit's corpusHash, algorithm and revision from morphir-mck kit status (the runner's own identity, not a second hash scheme), every artifact's SHA-256 and each qualification. The old incremental --clobber upload and select_release_assets.py go.

LEG-1. Legacy names alias the Native AOT executable

This follows the maintainer decision of 9 November 2026 (finos/morphir#1146, REL-1 of the morphir-dotnet adoption; reconciled in #584 e8f4a00b): future legacy assets morphir-<rid>[.exe] and morphir-<rid>-v<version>.tar.gz carry the same bytes as the native-aot offering, assets already published stay as they are, and the trimmed managed single-file build is retired. There are four offerings, not five. publish-release runs cli-release.ts legacy-aliases. It takes the platforms from the pinned LegacyAsset.TrimmedSingleFile (win-x64, osx-arm64, linux-x64, linux-arm64), extracts each packed and qualified native-aot archive after checking its SHA-256, copies the executable under the bare name, and writes the tarball with the executable under <rid>/, which the proto plugin strips. It refuses an alias whose bytes differ from the executable. The manifest lists each alias with the artifact it aliases. Nothing calls PublishSingleFile.

MCK-1. One runner, standalone, with the old command tree

The contributor's gate becomes cargo run -p morphir-mck-cli -- check spec/ir/mck instead of cargo run -p morphir -- mck check spec/ir/mck. crates/morphir-mck-cli builds the binary morphir-mck from the moved command modules and a clap tree copied from the old MckAction; the moved tests drop the leading mck argument and nothing else. Two behaviours had come from the product and are now stated in the runner: serde_json's preserve_order (JSON member order, which the frozen package reports depend on; without it 6 acceptance tests and 1 JSON test failed) and the multi-threaded runtime. The .NET CLI's morphir mck ARGS starts morphir-mck ARGS, which merged source PR #590 implements; spec/mck/cli-contract.md states the rule. The copied-binary acceptance still runs with an empty PATH; its product checks (the metadata preview and the two itest package examples) left with the product. The runner is development-only and stays in Rust only until the .NET runner replaces it.

DEV-1. A narrow internal development tool

crates/morphir-dev-tools builds morphir-dev with the kb tree unchanged. The library-level gates that lived in the CLI crate's tests (mep_contract, tool_release_metadata_conformance, package_runtime) are this crate's tests, because they never started the CLI. The tool has no product commands and is never released. Parent acquisition behavior is checked separately by the .NET implementation against this checkout's fixed corpus, using main's toolchain-contracts job and independent test pin. Its metadata-only TypeScript checks retain the contract-files, coverage and narrative gates. The Rust acquisition checker deleted by #1147 stays deleted. Alternative: putting kb into morphir-mck (mixes kit and knowledge base) or porting it to TypeScript now (scope; the kb skill and the morphir-scala port depend on this behaviour).

DOC-1. Remove what can no longer be regenerated

docs/cli, docs/man and completions were generated from the Rust binary and checked for freshness against it. With the binary gone they would describe a product that does not exist and could not be refreshed, so they are deleted with their generator, their sidebar entry and the usage tool pin. User guides that describe Rust CLI commands are not rewritten here.

Migration plan

  1. Parent #1147 merged as 836deccc. Normally merge current parent main, preserving the three held commits through a6a75bb5, its .NET acquisition corpus job/filter/gates and the deletion of the Rust acquisition checker. Retained Cargo dependency versions stay unchanged.
  2. The gitlink, config, uses and ref now name the 0.5.0-alpha.1 release commit 318b1bfd. Remove source.candidate once the tag v0.5.0-alpha.1 names that commit, then repeat the dry run (SRC-2).
  3. Accept a final release pin only after the source version/tag and qualification gates pass, updating the whole delivery tuple together. No source version is chosen or bumped here.
  4. Tag v<version> from main only when the maintainer decides to release, with a version newer than every existing v* tag. Rollback is deleting the new tag before any release exists; an existing release is never replaced.

The merged #1152 family-version policy is retained unchanged, including any valid SemVer prerelease label. The chosen extension state version remains 0.1.0-preview.1; existing acquisition fixture versions are not renumbered by this migration. The merged #1151 extension package decisions also remain controlling: VERIFY-B checks structure at launch and hashes fully at install/on request; LAUNCH-A starts from the shared store under a process-tree lease and collects explicitly. Those host behaviors are outside this delivery change.

Open questions

  • The first official version is not decided. It must be newer than v0.4.0-beta.12 (REL-1), and it is the source's release: morphir-dotnet chooses it, and this repository's gate only refuses a version that does not move forward.
