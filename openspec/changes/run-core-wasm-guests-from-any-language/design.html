Goals and non-goals

Goals:

  • The worker host runs any WASM module guest that conforms to morphir/mep-bytes-v1/v1-draft and MEP 0.2.0-draft.1, with no code for a particular language. (The first draft said the core-wasm-process route; main retired that route, and FIT-5 moved the goal to the worker host.)
  • Contract 0.2.0 pins and MoonBit guest behavior stay the same.
  • The new logic is pure MoonBit (source collection, claim selection, descriptor checks), so that the worker host can reuse it.

Non-goals:

  • Installing core-Wasm bundles from a repository, and joining installed extensions to invocation. These belong to acquire-extensions-from-repositories (morphir-ukvn.5.64.34) and morphir-ukvn.5.64.30.
  • Verifying signatures or GitHub artifact attestations. That is add-extension-trust.
  • Ion morphir-model for the Gleam guest. The guest does not offer it.
  • Incremental compilation, dependencies and exposed-module lists in the request.
  • The browser route and the native WASM worker. Those are in host-extensions-as-workers.
  • Changes to finos/morphir-gleam, finos/morphir-rust or finos/morphir.

One Gleam compile, from command to result

A user has a Gleam project in /work/shop. Its modules are src/shared/numbers.gleam, src/app/money.gleam and src/app/orders.gleam, and money and orders import shared/numbers. The user downloads the morphir-gleam 0.4.0 bundle, writes a contract 0.2.0 pin over it, and runs this from the project directory:

export MORPHIR_EXTENSION_PIN=/work/gleam-pin.json
morphir extension compile src --package acme/shop --output model
morphir extension generate model/model-envelope.json --output generated

The diagram below shows what happens for the compile. There are two guest sessions. The first one only asks the guest what it is. The CLI uses that answer to build the second one, which does the work. The MoonBit worker host hashes the module bytes once and runs only those bytes in both sessions, so a file that changes between the two sessions cannot change what runs. The second session is interactive: the host reads the initialize answer and checks it before it sends the operation.

Decisions

SEL-1. A describe-only probe session gives the claims

For compile and generate, the CLI first runs a describe-only session through the same pin checks, and decodes the answer with Claims::from_describe. It then builds the operation session from those claims. The operation session sends no describe: the host compares the identity and claims of the initialize answer with the probe, and fails with extension.claims_mismatch, exit 2, before the operation (FIT-3, answered by Damian Reeves on 2026-10-31; the first draft said extension.claims_changed). This is the same pattern as the native route ("describes an immutable executable copy and closes that probe") and as probe and activation in the worker host.

Alternatives. (a) Take claims from the descriptor only, in one session. It does not work for assembly form pins, which have no descriptor, so the route would need two ways to choose a language. (b) An interactive session in the helper. It changes the helper protocol, which the worker host replaces anyway. (c) A required --language flag. It moves knowledge the guest already has to every user. Cost: one more worker start and one more module compile for each command. The task records the measured time for the 11 MB Gleam module.

SEL-2. The host offers every model tuple in preference order; --model-format requires one

Decided by Damian Reeves, 2026-10-30. The CLI advertises every model tuple that it supports for the operation, in its order of preference. The first tuple is the default. Today that is the Ion tuple (morphir-model, ion-binary), then the JSON tuple (morphir-ir, morphir-json). The order is the only signal for the default: there is no new wire field. The guest returns the intersection of its own support with the offer, in the host's order. The Rust SDK does this in NegotiatedModelTransport::select, and the MoonBit guest SDK does it in select_models (pkgs/morphir-moonbit/mep/model_transport.mbt). The session uses the first agreed tuple.

A guest that does not support the default but supports another offered tuple is a valid partner, not an error. Only an empty intersection is extension.tuple_unavailable. When the user gives --model-format, the CLI requires that format: it offers only that tuple, and a guest that does not claim it gives extension.tuple_unavailable with the claimed tuples in the message. generate offers the tuple of its input envelope first, and the CLI converts the model when the guest does not claim that tuple (SEL-4).

The probe claims select a tuple before the operation session: the first offered tuple that the guest claims for the operation. An empty selection fails before the operation session. The worker host on main reads the initialize answer before it sends the operation, so the agreement arrives before the request. The host requires the first agreed tuple to be the selected tuple, or the command fails with extension.agreement_mismatch, exit 2, sends no operation and publishes nothing. Answered by Damian Reeves on 2026-10-31 (FIT-3): keep main's codes and exit status 2, and keep this one check, which main does not do yet (task 1.13). generate needs it, because the CLI converts the model to the selected tuple before the session (SEL-4). The first draft assumed a pipelined session and exit 1.

Decided by Damian Reeves, 2026-10-31. An agreement that differs from the probe claims has its own code. The first draft used extension.claims_changed, but that code means that the guest describes itself differently in the two sessions. In an agreement mismatch the claims can be the same in both sessions: the guest's negotiation does not follow its own claims or the host's order. A separate code tells the user to examine the guest's tuple negotiation, for example its SDK, and not its identity or capabilities. The name follows the <subject>_mismatch form of the existing worker host codes in pkgs/morphir-host/worker/outcome.mbt: extension.claims_mismatch, extension.digest_mismatch, extension.platform_mismatch and extension.abi_mismatch. The exit status is 2, because the host reads the agreement before it sends the operation (FIT-3). When the claims also differ, extension.claims_mismatch wins, because the host compares the claims before the agreement. The worker host uses the same code for an answer outside its offer or its order (finos/morphir-moonbit#283).

This changes a rule on main. extension_messages in apps/morphir/cli/extension.mbt says "Rich operations offer exactly the selected tuple: there is no silent codec fallback", and apps/morphir/docs/extension.md says "There is no fallback between them" and that initialization must "return the offered tuple". After this change, a compile without --model-format offers both tuples. This is not a silent fallback: the offer is explicit, the report records the agreed tuple, and the envelope names its own tuple. With --model-format there is still no fallback. Every command line that runs today runs the same way: the MoonBit guest claims Ion and gets Ion. Only a command that failed with extension.tuple_unavailable because the guest lacks the default now runs.

Evidence. finos/morphir-gleam#31 adds a host test that offers morphir-model with ion-binary first and the JSON tuple second; the morphir-gleam 0.4.0 guest agrees on JSON and compiles. Related. A matching text change to the MEP model transport section (spec/mep/model-transport.md) is open in finos/morphir#1115. This change does not edit finos/morphir.

Alternatives. (a) Keep Ion as the only offered default and fail early when the guest lacks it. This was the first draft of this design. It is too strict: it refuses a guest that supports a format the host also supports. (b) Add a wire field that marks the default. The offer order already says it, and a new field needs a protocol change. (c) Default to the only claimed tuple with a one-tuple offer. It gives the same result for the Gleam guest but hides the host's preference from the guest.

SEL-3. Language, extensions and target come only from claims

The selected LanguageClaim gives the language ID and the file extensions; --language selects one when the guest claims several. The only claimed backend target is the default target. The MoonBit checks extension.moonbit_source_required and the fixed default target moonbit go away. For the MoonBit guest, the claims give the same values, so its runs do not change. A guest that claims several languages needs --language; without it, the command fails with extension.input_invalid, exit 2, and the message names the claimed languages. Every source refusal keeps main's code extension.input_invalid, exit 2 (FIT-1, answered by Damian Reeves on 2026-10-31); the first draft planned the new codes extension.source_required and extension.language_required.

SEL-4. The host library converts the model for generate when the guest does not claim the envelope's tuple

Rule decided by Damian Reeves, 2026-10-31; details (A to E below) decided by Damian Reeves, 2026-10-31. Decision E was changed on 2026-10-31: the host reports the conversion as a diagnostic, not as a file. The envelope fixes the tuple of the model that the user gives, but the guest can claim a different generate tuple. If the host can convert the model to a tuple that the guest claims, it does the conversion for the guest and sends the converted model. The generate runs; this is not an error. Only when the guest claims no tuple that the host offers does the command exit 2 with extension.tuple_unavailable.

The offer follows SEL-2. The envelope's tuple comes first, because it needs no conversion. The other tuples that the host can convert to follow. A guest that claims the envelope's tuple always gets the envelope unchanged.

Lossless preference decided by Damian Reeves, 2026-10-31. Among the claimed tuples that the host can convert to, the host prefers the first one in host order whose conversion is lossless for this model. Only when no claimed tuple can be reached without loss does the host take the first convertible one, and then the loss rules of decision D below apply. The host knows the loss of each conversion before the operation session, because it has the model. So it puts this preference into the offer order: the envelope's tuple, then the tuples that it can reach without loss, in host order, then the tuples that it can reach only with loss, in host order. The session still uses the first agreed tuple (SEL-2), and the agreement check does not change. With the two tuples of today, at most one tuple needs a conversion, so the preference changes nothing yet; it matters when the host supports more tuples. The spec "Prefer a lossless conversion" makes it normative.

As for compile, the probe claims select the tuple before the operation session, because the request names its input tuple and carries the model. So the conversion runs before the operation session, and a refused conversion starts no operation session. The operation session must then agree on the selected tuple, or the command fails with extension.agreement_mismatch.

For example, a user generates from an Ion envelope with a guest that claims only morphir-ir with morphir-json for morphir.backend.generateModel. The host offers the Ion tuple, then the JSON tuple. The guest claims JSON, so the host converts the model to Morphir JSON. If the model has no metadata, provenance or non-profile annotations, the conversion loses nothing and the generate runs. If it has source provenance, the command stops with data.lossy_conversion and tells the user about --allow-model-loss. With that flag, the generate runs, the CLI writes a warning that provenance was dropped, and the command reports the conversion with the extension.model_converted diagnostic. The output folder holds only the guest's artifacts.

The decisions:

  1. A. Who converts. The host library, pkgs/morphir-host, converts with the codec registry of the engine (pkgs/morphir-engine/data/registry.mbt). That registry already has the morphir-json and Ion codecs and the loss check that bare morphir-json export uses. Every host front end, which is the CLI, the browser host and the worker host, calls the same conversion. No front end has its own converter.
  2. B. Directions. Both. morphir-ir with morphir-json to morphir-model with ion-binary is always lossless: a JSON model has no rich metadata to lose. morphir-model to morphir-ir with morphir-json is allowed only when it is lossless, unless the user gives --allow-model-loss. The flag applies to one generate command only; no configuration file or environment value sets it.
  3. C. Identity. The converted envelope keeps the modelId of the envelope that the user gave. Its revision is sha256: followed by the lowercase hexadecimal SHA-256 of the converted payload bytes, so the same input gives the same revision. The converted envelope holds no link to the original; the conversion diagnostic (E) holds it.
  4. D. Lossy conversion. Without the flag, a conversion that would drop data is refused with data.lossy_conversion, exit 2, before the operation session, with nothing published (committed: []). This is what the built-in morphir generate does today (apps/morphir/scripts/test-generation.ts). The message names the flag. It is not extension.tuple_unavailable: the guest claims a tuple that the host can send, and the refusal is about the user's model. With the flag, the command exits 0 when the generate succeeds, writes one warning to stderr for each kind of dropped data (metadata, provenance, annotations), and the JSON report has conversion: {from, to, dropped}. The report has the conversion object for every conversion; dropped is empty when nothing was lost.
  5. E. Reporting the conversion. The host reports the conversion as one diagnostic of the command, with the code extension.model_converted and severity info. Its data holds the original and the converted tuple, the original revision and payload SHA-256, the converted revision and payload SHA-256, and the dropped list (empty without the flag). The diagnostic is in the diagnostics of the JSON report, and the CLI writes it as one human-readable line on stderr, in default and in JSON mode. The host writes no file for the conversion in the output folder and does not copy the original model bytes; the payload SHA-256 identifies them. The guest's own retention sidecars (mep/source-model.ionb and mep/source-envelope.json for the MoonBit guest) stay as the guest returns them, so after a conversion they describe the converted envelope. With --allow-model-loss, the warnings of decision D for each kind of dropped data stay.

Diagnostic decided by Damian Reeves, 2026-10-31. This decision replaces the earlier decision E, which had the host write a conversion record, mep/conversion.json, reserve that path in the output and refuse a guest artifact at that path with extension.result_invalid. None of that remains: there is no record file, no reserved path and no refusal for it. Decisions A to D and the lossless preference do not change. The diagnostic data keeps the members that Damian Reeves accepted for the record: exactly from, to and dropped. from describes the envelope that the user gave and to the converted envelope that the host sent. Each has exactly profile, codec, revision and payloadSha256, the lowercase hexadecimal SHA-256 of the decoded payload bytes. The spec "Conversion diagnostic data" makes these members normative. The diagnostic in the report after a lossy conversion with the flag looks like this:

{
  "severity": "info",
  "code": "extension.model_converted",
  "message": "converted the model from morphir-model/ion-binary to morphir-ir/morphir-json",
  "data": {
    "from": {
      "profile": "morphir-model", "codec": "ion-binary",
      "revision": "rev-2026-10-31", "payloadSha256": "<64 hex digits>"
    },
    "to": {
      "profile": "morphir-ir", "codec": "morphir-json",
      "revision": "sha256:<64 hex digits>", "payloadSha256": "<64 hex digits>"
    },
    "dropped": ["metadata", "provenance"]
  }
}

The CLI already writes each diagnostic of an extension command to stderr as one line (extension_diagnostic_line, apps/morphir/cli/extension.mbt), and the worker Diagnostic already has the info severity and a data member (pkgs/morphir-host/worker/diagnostic.mbt). So in default mode the stderr line is info extension.model_converted: converted the model from morphir-model/ion-binary to morphir-ir/morphir-json, and stdout holds only the summary. In JSON mode stdout holds only the one report object. The diagnostic does not change the exit status. When the guest fails after a conversion, the failed report still has the diagnostic, because the conversion ran; it has no result.

The report object and the diagnostic agree. The change keeps both, and does not merge them. The conversion object of a successful report's result is equal to the data of the extension.model_converted diagnostic. A consumer that reads only result finds the conversion there, and a consumer that reads the diagnostics finds it with the other messages of the run. Because the two values are equal, they cannot disagree. The spec "Report records the conversion" makes this normative.

The conversion itself is not part of extension_generate_offer on main today: that function offers only the envelope's tuple, and says that the host does not convert a model (finos/morphir-moonbit#284). This change replaces that rule.

Alternatives. (a) Keep the rule that generate requires the envelope's tuple. It refuses a guest that the host can serve. (b) Tell the user to convert the model with another command first. It gives every user work that the host can do. (c) A converter in each front end. The three front ends would drift, and the loss check would exist in more than one place. (d) Copy the original model bytes into the output. It doubles the output size; the digest in the conversion diagnostic identifies the original. (e) A conversion record file, mep/conversion.json, next to the guest's artifacts. This was the first decision E. It adds a file that the guest did not write to the guest's output, needs a path reserved for the host in that output and a refusal rule for a guest that uses the path. The diagnostic carries the same data without these rules. (f) Only the diagnostic, with no conversion object in result. A consumer that reads only result would then have to search the diagnostics for the conversion.

SRC-1. Relative URIs from a source base, no sources.root

Each URI is the path relative to the source base: --source-base, or else the directory that the user names. The current directory does not change the URIs; it only makes relative paths absolute. A single file without --source-base keeps today's rule, so MoonBit requests are byte for byte the same. Thus without --source-base a directory compile sends the URIs that main sends today.

Default decided by Damian Reeves, 2026-11-01 (option B). The first version of this decision made the current directory the default base (option A). Damian Reeves chose option B on 2026-11-01 because option A broke the published Elm 0.5.0-preview.2 and Python 0.4.2 extensions in the extension qualification suite (scripts/extension-qualification.mbtx, finos/morphir-moonbit#298). Both name a module from its path below the source directory. Under option A, compile generated/src from the parent directory sent generated/src/Acme/Rules/Main.elm, and the Elm guest refused it with elm.module_name ("the module Acme.Rules.Main must be in Acme/Rules/Main.elm"). compile src sent src/acme/rules.py, so the Python guest named the module src.acme.rules, generated src/acme/rules.py below the output folder, and the consumer's import acme.rules failed. The Gleam guest does not need the current directory: since finos/morphir-gleam#29 (191a35e, release extension/gleam/v0.4.0) it keeps the full path of a relative URI and removes a leading path up to a src segment. Thus compile src (URI app/money.gleam) and compile . (URI src/app/money.gleam) both give the module app/money; the check with the released module gave byte-identical models.

Why not the current directory? It makes the URIs depend on where the user runs the command, and it breaks the extensions above. A user who names a directory below the root of the module paths, such as compile src/app, gives that root with --source-base; without it, the URIs are money.gleam and orders.gleam and the Gleam guest names the modules money and orders. Follow-up. A Cargo-style source root, in which the project manifest and the extension's workspace discovery give the root, is tracked separately; it is not part of this change. Why not synthetic absolute URIs with a root, as the guest's own host test does (file:///src/... with root file:///src/)? They would put invented absolute paths into diagnostics and source provenance, and the protocol root is meant to be a real location. Why not the real absolute paths with a real root? Host paths in the model break reproducibility across machines and break the existing rule that absolute host paths never enter provenance.

SRC-2. One portable source collector, with the Extism limits

A new pure function collects a tree into documents. It takes the claimed extensions, the language ID, the source base and the limits, and returns sorted documents or a typed refusal. Its file-system walk is an effect at the edge, with the same no-follow and bounded listing calls as extism_sources. The limits are the ones the Extism route already qualifies: 1,024 documents, 2 MiB of source in total, depth 32 and 16,384 entries. The core-Wasm limit of 1 MiB for one file stays. The 4 MiB framed request limit stays the final check, because JSON escaping can make the request larger than the sources. extism.mbt moves to the same collector with language python and .py, so the two routes cannot drift; its behavior and error codes stay the same. (Main has no extism.mbt now: the Extism guest uses extension_sources on the worker host.) Every refusal of the collector is extension.input_invalid, exit 2, with a message that names the limit, the relative path or the URI (FIT-1). The first draft planned four new codes: extension.source_required, extension.resource_limit, extension.invalid_source_path and extension.invalid_source_encoding. Damian Reeves dropped them on 2026-10-31.

Alternative: raise the request limit to the Node host's 16 MiB. The helper and the CLI both bound the request at 4 MiB today, and the Gleam real-world fixtures (13 files) fit well within it. A larger limit can come with the worker host, which owns the channel limits.

SRC-3. URI segments are percent-encoded, plain names are unchanged

The protocol says a frontend decodes path segments once and refuses encoded separators. The collector encodes each segment as an RFC 3986 path segment. Unreserved characters (letters, digits, -, ., _, ~) stay as they are, so ordinary paths and all existing MoonBit and Python requests are unchanged. Unsure: the Gleam guest's parsed_path must decode such segments correctly. The acceptance task includes one file name with a space to show it.

SRC-4. The walk skips main's directories and honors ignore files

Decided by Damian Reeves, 2026-10-31 (FIT-4). The walk keeps main's skip list: hidden directories (names that start with .) and .git, .mooncakes, _build, node_modules and .venv. It also honors ignore files: the .gitignore files and the other layers that Git reads, and a Morphir-specific .morphirignore in each directory. Both files use Git's gitignore syntax and nesting rules, and .morphirignore can include a path again with !.

Consider a Gleam project. gleam new writes a .gitignore with /build, and build/ holds the downloaded packages and can hold links. When a user compiles the project directory, the walk does not enter build/, so it neither reads those sources nor refuses their links. The project can also keep a .morphirignore with test/, so that Morphir does not read the tests that Git tracks. And when a generated file such as src/model_gen.gleam matches a .gitignore pattern but belongs in the model, !src/model_gen.gleam in .morphirignore includes it again.

Details decided by Damian Reeves, 2026-10-31 (IGN-1 to IGN-5). By default the walk follows Git, so that the documents agree with what git status shows. In a Git work tree it reads the same layers as Git: the global excludes file (core.excludesFile, else $XDG_CONFIG_HOME/git/ignore), the repository's .git/info/exclude, and the .gitignore files from the work-tree root down through the walked tree (IGN-2, IGN-3). Each directory can also hold a .morphirignore, read in the same places. Outside a Git work tree, Git does not honor .gitignore, so the walk reads only the .morphirignore files of the walked tree.

The last matching pattern decides. The global file comes first, then .git/info/exclude, then the ignore files of each directory from the highest down; in one directory, .morphirignore comes after .gitignore, so it wins there, and a deeper directory decides over a higher one (IGN-1). This is Git's own rule with one more file per directory. As in Git, a path under an excluded parent cannot be included again, and an ignored entry is never refused as a link. An ignore file in any layer has the 1 MiB bound of a source file.

Consider a user in /work/shop, a Git work tree, who runs compile src. The root .gitignore has *_gen.gleam, so src/app/model_gen.gleam is not read, as git status would not list it. When the same user names the file, compile src/app/model_gen.gleam, the CLI reads it: ignore files filter only directory walks, and a file that the user names is an explicit choice (IGN-5). For the same reason a pattern above the input does not exclude a directory that the user names. Confirmed by Damian Reeves, 2026-10-31: the CLI walks a directory that the user names even when a pattern above it matches, and the ignore files still filter the entries below it.

Contained mode, for reproducible runs. The Git layers make the documents depend on the user's Git configuration and on files outside the tree. --ignore-mode contained turns all of them off: the walk then reads only the .gitignore and .morphirignore files in the walked tree, in or outside a work tree, so two machines give the same documents for the same tree and options. CI and qualification runs should use it. Between the two modes, --skip-ignore-layer turns off one layer: global, info-exclude or above (the ignore files above the walked directory). The flag names are this update's choice; review can change them without changing the behavior.

Scope. .morphirignore applies only to morphir extension compile in this change (IGN-4). Follow-up changes makes it a project-wide rule.

Library. Damian Reeves asked for a reusable ignore-file library and moonx tool in moonrockz/moonx-tools (moonrockz/moonx-tools#16): Git-compatible by default, custom ignore files such as .morphirignore, layer and containment switches, and an explain mode like git check-ignore -v. Task 2.6 uses that library and waits for it. The candidate moonbit-community/ignore is prior art that the library issue evaluates. The scenarios of this change are the acceptance for Morphir.

PIN-1. One contract 0.2.0 pin for a WASM module

Restated on 2026-10-31 (FIT-5, answered by Damian Reeves). Main retired the 0.1.0-draft.1 pins and the core-wasm-process route. A WASM module now has main's contract 0.2.0 pin: artifact ({path, sha256}), runtime ({kind: "wasm"} with an optional abi), origin and a descriptor ({path, sha256}). The pin has no extensionId or version, so the descriptor identity is compared with the live claims, not with the pin. The descriptor entry is the one whose sha256 equals the pin's artifact.sha256. The worker host reads the module, refuses one above 512 MiB, hashes it and runs only those bytes. The first draft, kept below for the record, added a module form to the old contract.

First draft. The artifact member gets a second form, chosen by form: "module". A member without form is the assembly form, so old pins stay valid. Exact field sets keep the forms apart. The module form follows the Extism pin (directory, descriptorSha256, extensionId, version), but names the descriptor file, because the Gleam bundle calls it morphir-gleam-0.4.0.release.json, not release.json. The module file name comes from the descriptor artifact whose digest equals moduleSha256.

Alternative: a new contract version such as 0.1.0-draft.2. It would mark the change more clearly, but it forces the MoonBit pins to be rewritten for no gain, and the worker host retires this contract for 0.2.0 anyway.

PIN-2. An installed morphir-bytes-v1 pin needs the descriptor; a local pin may omit it

Decided by Damian Reeves, 2026-10-31 (option C). A pin for a morphir-bytes-v1 module SHALL name the release descriptor (release.json) when the extension is installed from an extension repository. A hand-written local pin, given with --extension-pin or MORPHIR_EXTENSION_PIN, may omit it, for example for a module that a developer just built. The host then runs the module and warns that the descriptor checks were skipped: the digest against the published release, the critical runtime and executionProfile members, and live claims equal to the published claims. A local pin without a descriptor has only its own digest.

Codes confirmed by Damian Reeves, 2026-10-31 (PIN-3). An installed pin without a descriptor is refused with main's extension.pin_invalid, exit 2, because the pin lacks a member that it needs, and the message names descriptor. The warning is a diagnostic with severity warning and the new code extension.descriptor_checks_skipped, in the report diagnostics and as one stderr line. Main does not yet run installed extensions (morphir-ukvn.5.64.30), so task 3.6 proves the installed refusal with unit tests and uses it when installed selection joins invocation. finos/morphir-moonbit#292 explores how morphir trust (add-extension-trust) could cover local and descriptor-less pins; until it decides, this rule stands.

First draft. The descriptor was required for the module form, not a new manifest. The release descriptor is already the language-neutral record. A publisher writes it from a live describe, it names the runtime and the execution profile as critical members, and repository acquisition and the worker host both plan to read it. A new language-neutral manifest would be a third file with the same facts. The descriptor is required, because without it the route would have no record of the profile the module claims to implement, and no claims to compare. A module built from a source checkout gets a descriptor from the publisher's own bundle task (for Gleam, mise run rust:bundle).

INT-1. The CLI decodes the descriptor; the worker host checks the module

INT-2. Claims are compared, never trusted for authority

Three comparisons use Claims equality, which compares sorted sets: descriptor claims with the probe claims (extension.claims_mismatch, exit 2, before the operation), the probe with the initialize answer (extension.claims_mismatch, exit 2, before the operation; FIT-3), and descriptor identity with live identity (extension.descriptor_invalid; FIT-5). Without --model-format, the same command line gives an Ion envelope for one guest and a JSON envelope for another (SEL-2). The report records the agreed tuple, and generate reads the tuple from the envelope. A user or a script that needs one format gives --model-format, which has no fallback.

The MEP text change is open in finos/morphir#1115. finos/morphir-moonbit#283 aligns the worker host's "Model tuple negotiation" requirement (see Relation to the worker host).
A converted model is not the model that the user gave, so generate output from the same envelope can depend on the guest (SEL-4). The conversion refuses to lose data unless the user gives --allow-model-loss for that command. The converted envelope has its own deterministic revision, and the extension.model_converted diagnostic and the equal conversion report object link the run to the original revision and payload digest.
The output folder holds no record of the conversion, so a reader of the output alone cannot see that the guest got a converted model (SEL-4, E). Decided trade-off. The probe session adds a worker start and a compile of an 11 MB module to each command. Measured in the acceptance task. The worker host hashes the module once and runs the same bytes in both sessions.

No authenticated publisher: a pin over a tampered release is still "valid". The pin digests are the explicit trust root, as for every pin today. Attestation verification is add-extension-trust.
The worker host lowers a memory maximum above 4,096 pages instead of refusing it (FIT-5), so a module can run with less memory than it declares. Answered questions

  1. Default tuple (SEL-2). Damian Reeves decided on 2026-10-30: the host offers every supported tuple in preference order, the first is the default, and the session uses the first agreed tuple. An explicit --model-format offers only that tuple. Only an empty intersection is an error. Main does this (finos/morphir-moonbit#284).
  2. Agreement code (SEL-2). Damian Reeves decided on 2026-10-31 that an agreement that differs from the probe claims has a new code, extension.agreement_mismatch, not extension.claims_changed. Main has the code, with exit 2 (FIT-3).
  3. Conversion for generate (SEL-4). Damian Reeves decided on 2026-10-31 that the host converts the model when the guest does not claim the envelope's tuple, and then decided the details: the host library converts with the engine codec registry for every front end; both directions, JSON to Ion always lossless, Ion to JSON only when lossless unless --allow-model-loss; the converted model keeps its modelId and gets a sha256: revision of its payload; a lossy conversion without the flag is data.lossy_conversion, exit 2; and the host reports the conversion. See SEL-4.
  4. Lossless preference (SEL-4). Damian Reeves decided on 2026-10-31 that, among the claimed tuples that the host can convert to, the host prefers the first one in host order whose conversion is lossless, and takes the first convertible one only when none is lossless.
  5. Conversion diagnostic in place of a record file (SEL-4, E). Damian Reeves decided on 2026-10-31 that the host writes no conversion record file. It reports the conversion as an info diagnostic with the code extension.model_converted, in the report diagnostics and as one stderr line, with from and to (each with profile, codec, revision and payloadSha256) and dropped in its data. This replaces two earlier answers of the same day: the members of mep/conversion.json (now the members of the diagnostic data) and extension.result_invalid for a guest artifact at that path (no longer needed, because the path is not reserved).
  6. Scope after the worker host. Damian Reeves decided on 2026-10-31 to cut the change to the work that main does not do yet, as long as every requirement is still met. See Scope after the worker host.
  7. Pin contract version (PIN-1). No longer applies: main retired the 0.1.0-draft.1 pins. PIN-1 is restated for the contract 0.2.0 pin (FIT-5).
  8. FIT-1. Error codes of the worker host. Damian Reeves decided on 2026-10-31: use main's codes everywhere, extension.describe_failed (not extension.incomplete_session), extension.digest_mismatch (not extension.identity_mismatch), extension.descriptor_invalid and extension.pin_invalid (not extension.invalid_descriptor and extension.invalid_pin).   9. FIT-2. Operations from claims. Damian Reeves decided on 2026-10-31: follow main for now. A compile operation is allowed when the guest claims morphir.frontend.compile or compileModel, and a generate operation when it claims morphir.backend.generate or generateModel. finos/morphir-moonbit#293 (a task graph for high-level commands across extensions, based on docs/design/draft/extensions/tasks.md in finos/morphir) is where the long-term rule is decided.

  14. IGN-1. Precedence in one directory. Damian Reeves decided on 2026-10-31 (option A, the spec as it was): in one directory, .morphirignore is read after .gitignore, so the last matching pattern decides and .morphirignore wins there; a deeper directory decides over a higher one. This is Git's rule with one more file per directory. The rejected options were a .morphirignore that replaces the .gitignore of its directory, and .morphirignore patterns after every .gitignore of the tree.
  15. IGN-2. Git configuration. Damian Reeves decided on 2026-10-31 (option B, a change): match Git. See SRC-4.
  16. IGN-3. Ignore files above the walked directory.
