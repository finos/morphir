- **Shipped, experimental.** The host landed in [finos/morphir-dotnet#570](https://github.com/finos/morphir-dotnet/pull/570) (`12082e9e`, 12 November 2026): the Extism profile on Wasmtime, the bounds, the sandbox, the worker and the runtime report. - **Windows x64 is refused.** A guest that traps on `win-x64` ends the process with `0xC0000409` (CET context validation). The released host refuses WASM on that platform with `win_x64_trap_unsupported` before it loads the engine or a module, and other commands still run. A fix that keeps CET and Spectre protections is tracked in [finos/morphir-dotnet#609](https://github.com/finos/morphir-dotnet/issues/609).
- **Not qualified.** No host qualification report exists for a released artifact, and the .NET result has not been compared with the Rust CLI's.
- **The runner has no installed entry point.** The crafted-case runner and `report-check` are in `src/Morphir.Conformance/WasmHost` with their tests. The product `morphir mck` forwards to a separately installed `morphir-mck`, and the development entry point that runs the kit waits on [finos/morphir-dotnet#607](https://github.com/finos/morphir-dotnet/pull/607), still a draft.

Done: 1.1 to 1.6, 2.1 to 2.6, 3.1 to 3.5, 4.1, 4.2, 5.1 and 5.3. Open: 1.7, 4.3, 5.2, 5.4 and group 6.

Dependencies: group 1 fixes the contract and the crafted corpus. Group 2 builds the engine layer and proves the kernel approach. Group 3 adds the Extism profile on group 2. Group 4 needs a working profile and starts after group 3. Group 5 needs group 2 for something to package and can run beside groups 3 and 4. Group 6 consolidates after all of them. `add-bounded-model-access` task 5.2 can start after groups 3 and 4. Keep implementation changes in their owning repositories.

MEP line: MEP `0.1` is not supported (decided 9 November 2026, design decision MEP-1). The .NET host offers the `0.2` line only, has one instruction budget and uses the Python `0.6.0` bundle pinned in `.config/published-extension-bundles.toml` wherever a task names the Python guest. Python `0.4.2` speaks `0.1` only.

Runner home: the conformance runner is moving from the Rust `morphir mck` to the .NET host in morphir-dotnet (decided 9 November 2026). The corpus, expectations and report contract in group 1 stay here as data. Tasks 1.5 and 4.3 add runner code in morphir-dotnet, not in `crates/morphir-mck`.

- The .NET runner executes the crafted cases as Gherkin features generated from the JSON corpus. The maintainer decided on 9 November 2026 that the compatibility kit moves from JSON to Gherkin; moving the authored form of this corpus is part of that work, not of this change.
- `mep/generic-guest-profile` requires a legacy tier that negotiates MEP `0.1`. The maintainer decided on 10 November 2026 that the kit drops it. The separate change `drop-generic-guest-legacy-tier` removes the requirement and gives the kit one session on the `0.2` line. Until it is applied, task 4.3 covers the kit's model tier only. The Rust `guest-run` cannot skip the legacy tier and is not changed; how task 4.3 is carried out in morphir-dotnet is decided in finos/morphir-dotnet#570.
- The published guests answer a bare `0.2.0-draft.1` offer with error -32011 and a message that says they support only `0.1`. They accept the same version when the request carries a model transport offer. Report this to the extension SDK's repository.
- The SDK fixture guest of finos/morphir-moonbit (`apps/morphir/fixtures/sdk-guest`) speaks MEP `0.1` only, so the .NET host cannot run it and tasks 3.5 and 4.3 do not include it. It is the one real guest in the kit that imports the Morphir host functions; the crafted corpus covers those functions meanwhile. When finos/morphir-moonbit builds it for `0.2.0-draft.1` with JSON model tuples at `3.0.0`, run it through the kit's model tier as well.
- The worker's JSON lines use the MoonBit CLI's `morphir/command-event` and `morphir/command-result` documents, which no shared contract defines. Now that two hosts write them, state them in a shared contract.
