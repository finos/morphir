Context and evidence

See the proposal for motivation. This section records what exists today, because three repositories each hold part of the answer and none holds all of it.

Goals and boundaries

Goals. Published Extism bundles run under the .NET host, in every offering, with the bounds and refusals the MoonBit host already applies. The Native AOT executable keeps zero trim and AOT warnings. A conformance runner can qualify the .NET host over stdio alone, with no code path that exists only for .NET.

Boundaries. This design delivers a runtime and one way to reach it directly, the worker mode. It does not decide which product commands select a WASM analyzer or generator: morphir-dotnet's roadmap steps 2a and 4 and add-bounded-model-access task 5.2 consume the runtime. It grants a guest nothing beyond the fixed policy; user-granted capabilities, which the roadmap places in step 5, stay a follow-up because they need a consent model this change does not have. It installs nothing and scans no folders. It does not change the Rust host.

One module's journey and the decisions along it

The running example is the published Python extension 0.6.0, the bundle pinned in .config/published-extension-bundles.toml: one 4.8 MB Extism module that imports eight kernel functions. The earlier 0.4.2 module speaks only MEP 0.1, which the .NET host does not offer (MEP-1). A developer sets extensions.python.path to it. Each stage below is a point where the host must choose, and the decision is introduced there.

Before the journey starts

PROF-1. Write the profile contract once, in this repository, from what MoonBit already does

The .NET host needs rules to implement. They exist today as MoonBit source and one MoonBit spec. If .NET copied them into its own spec, a third description would start to drift, and the Rust host shows that drift is already real.

The contract therefore lives here as mep/wasm-execution-profiles, version 0.1.0-draft.1. It states MoonBit's observable rules in host-neutral terms and fixes morphir_get_workspace_info as () -> i64, the signature the SDK that builds the guests uses. MoonBit's spec keeps what is specific to MoonBit: worker processes, Node threads and Web Workers.

Alternatives. Specify only in morphir-dotnet: fastest, but it leaves the parent documents naming profiles nobody defines. Move MoonBit's spec here unchanged: it mixes shared rules with MoonBit's process model, and the .NET host deliberately differs on that (see ENG-1).

Stage 1. The host opens the file

CLS-1. Classify from the engine's validated view of the module, before instantiation

The first question is which profile the Python module has. Its imports answer it: functions from extism:host/env make it extism-kernel-v1. A module that imports env.open_socket has no profile and is refused by name.

The host reads imports and exports from the module the engine has already validated, then checks each one against the contract's table. No guest code has run at that point, because WASM runs nothing until instantiation. The engine is configured without threads, 64-bit memory and multiple memories, so a module that needs one fails validation and becomes extension.wasm_feature_unsupported.

Alternative. A separate managed reader of the binary format, as MoonBit has. It would refuse a bad module a little sooner, but it is a second parser that can disagree with the engine about what the module contains. MoonBit needs one because its reader must build on targets its engine does not.

Cost. Validation includes compilation, so refusing a large module takes as long as compiling it. That is acceptable for a refusal.

Stage 2. The host needs something to run it on

ENG-1. One Wasmtime engine in the host process, one store per session

The spike settled the engine: Wasmtime 50.0.1. What remains is where it runs. MoonBit starts a worker process per guest because its engine cannot be stopped safely from the same process on every target. Wasmtime can interrupt a guest from another thread, so the .NET host runs guests in its own process:

  • One engine per process, with fuel metering and epoch interruption on. A thread of the host's own advances the epoch every 10 ms. It is not a thread-pool timer. When every processor is busy, which a spinning guest causes, the .NET pool adds no thread and a pool timer stops: a 500 ms deadline took 4.3 s on a CI runner before this was changed.
  • One store per session. The store owns the instance, its memory, its fuel and its deadline, and is disposed when the session ends for any reason.
  • Compiled modules are kept in memory for the life of the process, keyed by module digest, so a frontend and backend from one module compile once.

Why not a worker process per guest. It would double the start-up cost, require the AOT single-file executable to find and re-launch itself, and duplicate process-group clean-up that the engine makes unnecessary. A trap in Wasmtime is a returned error, not a crash.

What this gives up. A fault in the engine's native code takes the host down with it. Process isolation would contain that. The risk table records it, and the worker mode (WRK-1) remains available as an out-of-process way to run a guest.

Stage 3. The host has a session core that only speaks streams

SES-1. Give the host session a message channel, and make streams one implementation of it

A WASM guest cannot be read like a pipe. Each handle call takes one message and returns at most one. Morphir.Mep already has this shape on the guest side and lacks it on the host side.

The host session is changed to talk to a channel with two operations: send a request and receive its response, and send a notification. The existing stream framing becomes one channel. The WASM adapter is another. Negotiation, id counting, limits and lifecycle stay in one place, so a process guest and a WASM guest cannot diverge on protocol behavior.

{"jsonrpc": "2.0", "id": 2, "method": "morphir.frontend.compile", "params": {"language": "python", "documents": [{"uri": "orders.py"}]}}

That message is one handle call. What differs from a stream is below the channel: the adapter decides whether a notification such as morphir.initialized reaches the guest at all (NTF-1).

Alternative. Wrap each guest in an in-memory stream pair and keep the session unchanged. It needs a thread per guest to pump frames and it reintroduces Content-Length parsing between two pieces of code in the same process.

Stage 4. There is a second kind of module the host could meet

ABI-1. Host one profile; do not carry the byte profile into .NET

The Gleam extension 0.4.0 is not an Extism module. It is a morphir-bytes-v1 guest: it reads its request by calling input_byte once per byte and writes its response with output_byte. The first draft of this design hosted both profiles. This one hosts only Extism, and the shared contract marks the byte profile as transitional.

The byte profile was introduced for one reason, recorded in the Gleam extension's own design: at the time, the MoonBit CLI could run Extism modules only for Python on macOS arm64 and had no browser route. That is no longer true. The MoonBit worker host runs Extism guests on native, Node and browser through one shared kernel, and the Extism project itself is active. Its users today are the Gleam extension, which was an Extism plugin through 0.3.0, the MoonBit portable guest and the Elm preview built from it.

Nothing the byte profile offers is out of reach for Extism. A guest needs no PDK: importing five kernel functions (input_length, input_load_u8, alloc, store_u8, output_set) gives the same pull-bytes, push-bytes shape, so any language that can import a function can be an Extism guest. Morphir-specific host functions already live in Extism's extism:host/user namespace. The one real difference, notifications, is closed by NTF-1.

Keeping it has a measured cost in this host. A 1 MiB message is more than two million host calls, and the spike timed the two ways to serve them:

Binding1 MiB echo (measured)64 MiB message (projected)AOT warnings
Wasmtime.Dotnet untyped callbacks149 msabout 9.5 s of a 10 s deadline0
Wasmtime.Dotnet typed callbacks18 msabout 1.2 s1 or more (IL3050)

The untyped path spends the whole deadline moving bytes, and the typed path breaks the zero-warning rule. Hosting the byte profile would therefore need a hand-written unmanaged binding to the engine's C API, for a profile with three users. An Extism guest moves its bytes through the kernel, WASM to WASM, and never asks the host for one.

The .NET host still classifies a byte-profile module correctly, so that it can refuse it by name: extension.abi_unsupported, stating that the host does not run morphir-bytes-v1.

Alternatives. Host both, as first drafted: the binding above, a second adapter, a second deadline and a third of the qualification corpus, to run one published extension. Keep the byte profile and drop Extism: the published Python, Avro, OpenAPI and Rust bundles would all need rebuilding, and the Rust host runs nothing else.

What this asks of others. The Gleam extension ships a release on Extism again; its byte adapter is about 100 lines over the dispatcher the SDK's Extism macro already uses. The MoonBit portable guest and the Elm preview retarget. The MoonBit host keeps the byte profile until those releases exist, then removes it. None of that gates this change. See Migration.

Stage 5. The Python module expects an Extism runtime

KRN-1. Run the Extism kernel module on our engine; do not ship the Extism library

The Python module imports functions such as alloc, input_length and output_set. In Extism these are not native host code. They are exported by a small WASM module, the Extism kernel, which holds the input and output buffers in its own memory. The Extism runtime links the kernel to the plugin and adds a handful of native functions on top.

The .NET host does the same linking itself. It instantiates the kernel module, pinned by digest and embedded in the host, in the session's store, links its 20 exports under extism:host/env, and implements the remaining functions in managed code. Per call it sets the input through the kernel, calls handle, and reads the output and error back from the kernel.

The kernel it embeds is the one MoonBit already ships: the module from moonrockz/extism, built from Zig and differentially tested against upstream extism-runtime.wasm. It has the same 20 exports and handle values as upstream, with three differences that suit a strict host. It uses no reference types and omits upstream's extism_context global, so the engine needs no extra WASM features. alloc returns 0 when memory is exhausted where upstream traps. An out-of-bounds load or store returns 0 or does nothing where upstream traps. Sharing the bytes means a guest sees the same kernel under both hosts, down to the digest in the report.

This gives four things the alternative does not:

  • One engine and one native library. The Extism library is itself built on Wasmtime, so shipping it means a second copy of the engine in every offering on every platform.
  • One set of bounds. Fuel, the deadline and the memory limit apply to the store, so they cover the guest and the kernel together.
  • The result of handle. The host calls the export directly. The SDK's Plugin.Call hid it.
  • No host call per byte. A PDK reads its input through kernel calls in a loop. Those are WASM-to-WASM calls and never cross into managed code, so the host needs no fast callback binding (ABI-1).

Alternatives. libextism through the Extism .NET SDK: least code, but the spike recorded four defects against it, listed in the context table. Reimplement the kernel's functions in managed code: possible, but every byte the guest loads would become a host call, which is the cost ABI-1 removes. Embed upstream extism-runtime.wasm: it works, but it needs reference types enabled and traps where the shared kernel returns 0, so the two hosts would differ on a guest that runs out of memory.

Assumption to prove first. The kernel links and runs under the AOT host with zero warnings, the limiter applies to the kernel's memory as well as the guest's, and the moonrockz/extism licence allows embedding its kernel bytes in morphir-dotnet. Task 3.1 proves this with the Python module before any other Extism work. If it fails, this decision returns for review. The implementation does not switch to an alternative on its own.

Consequence to state plainly. The engine's limit is per memory, and an Extism session has two. The resident bound for an Extism guest is therefore twice the ceiling, 512 MiB, and the runtime report says so.

MEP-1. The .NET host speaks the MEP 0.2 line only

On 9 November 2026 the maintainer decided that MEP 0.1 is not supported: the hosts have no users on it, and carrying two protocol versions costs more than it returns. The .NET host offers versions of the 0.2 line and does not offer, bridge or test 0.1. Three things follow here.

  • There is one instruction budget, 5,000,000,000. The MoonBit host also has 1,000,000,000 for 0.1 sessions; the contract no longer carries it.
  • The guest for sessions is Python 0.6.0. Python 0.4.2 answers 0.1 only.
  • The host's morphir.initialize carries a model transport offer. Measured on the pinned bundles (Python 0.6.0, Avro 0.4.0, OpenAPI 0.5.0, Rust 0.4.0): each answers 0.2.0-draft.1 only to a request that has one. To a bare 0.2.0-draft.1 request each replies with error -32011, and the message wrongly says the extension supports only 0.1.

The generic guest kit still requires a tier that negotiates 0.1, and the Rust guest-run command cannot skip it. On 10 November 2026 the maintainer decided that the kit drops that tier. The separate change drop-generic-guest-legacy-tier removes the requirement and gives the kit one session on the 0.2 line. Until it is applied, a run against the .NET host covers the kit's model tier only. New runner code goes to morphir-dotnet (decision record 0004); how task 4.3 is carried out there is decided in finos/morphir-dotnet#570.

Stage 6. The host has something to tell the guest that is not a request

NTF-1. Deliver notifications to an Extism guest that asks for them

After the handshake the host sends morphir.initialized, and at the end morphir.exit. Both are notifications: messages with no id and no response. Today every host drops them for an Extism guest, because the published guests were written to answer requests and nobody knows what their handle does with anything else. A byte-profile guest does receive them. Retiring that profile should not remove the ability.

The guest opts in. In its morphir.initialize result it says how it wants notifications delivered, the same way MEP already gates $/cancelRequest on what the extension advertises. With the value call the host passes each notification to handle as it would a request, and the guest returns with no output. An output of zero bytes is how Extism already says "nothing to return". morphir.exit is delivered and then the instance ends.

{"jsonrpc": "2.0", "id": 1, "result": {"protocolVersion": "0.2.0-draft.1", "capabilities": {"notificationDelivery": "call"}}}

The member is a string with a fixed set of values, not a flag. A flag can say only whether the guest wants notifications. There are three ways to answer how they arrive:

ValueHow a notification reaches the guestIn this draft
noneIt does not. This is also what an absent member meansDefined, and the default
callOne handle call between requestsDefined
pollThe guest asks the host for pending notifications while a call runsReserved. It needs a new host function

A host reads a value it does not know as none. That keeps one rule for every case in which a guest gets no delivery: a host on the earlier contract ignores the member, a host on this draft does not know poll, and a guest spelled the value wrong. A guest therefore cannot depend on delivery, and no session fails over a value added later.

GuestHost sends morphir.initializedHost sends morphir.exit
Published bundle, advertises nothingNot delivered, as todayInstance ends without a call, as today
Advertises callOne handle call, no output expectedOne handle call, then the instance ends
Advertises call, then returns output for a notificationThe session fails: a notification has no response
Advertises a value the contract does not listNot deliveredInstance ends without a call

MEP 0.2.0-draft.1 already lets an extension send capability members the draft does not name, so the member is valid on that draft. The next MEP draft names it in the handshake model (task 1.7).

This needs no new import and no ABI change, so every published bundle keeps running unchanged and an old host simply never delivers. It is a contract rule for hosts, which is why it belongs in the shared profile and not in .NET alone.

What it does not do. call delivery cannot deliver $/cancelRequest during a call. A WASM guest runs one call at a time, so the host cancels by interrupting the engine (BND-1). Cooperative cancellation is what the reserved poll value is for. This decision also does not let the guest send a notification to the host, such as morphir.progress. Both need a new host function, which changes the import surface, and are left as an open question.

Alternatives. A boolean such as capabilities.notifications, matching cancellation and progress: it cannot express polling, so adding that later would need a second member and a rule for when the two disagree. A list of the methods the guest accepts: MEP already gates each notification on its own capability, so the list would repeat it. Deliver to every Extism guest: it risks failing published bundles whose behavior for a message without an id is unknown. Signal with a marker export in the module: it works before the handshake, but it puts protocol capability in the binary, where MEP's own negotiation cannot see it.

Stage 7. The guest reaches outside

SBX-1. Accept the imports, bound the calls

The Python guest links http_request and WASI's path_open even though compiling a Morphir model needs neither. Refusing those imports would refuse every published bundle. The contract's policy table accepts them and gives the guest nothing through them. The .NET host implements that table exactly:

  • WASI is configured with no preopened directory, no arguments, no environment and an empty stdin. Standard output and error go to a bounded buffer that becomes guest output.
  • http_request records the method and URL as guest output, stops the call and fails the session, as the MoonBit host does. The host never resolves the name.
  • The variable store and IR cache are plain in-memory maps owned by the session, with the contract's limits, and are dropped with the store.
  • morphir_get_workspace_info reports a private empty directory created for the session and removed with it.

The roadmap's later "host grants" would relax individual rows for a named extension with the user's consent. Nothing in this design prevents that. This change adds no configuration that could do it.

Alternative. Link Extism's own host functions unchanged. Its HTTP function makes real requests when the manifest allows a host, and a policy that depends on never setting a field is weaker than code that cannot connect.

Stage 8. The guest does not return

BND-1. Three independent bounds, each mapped to its own outcome

Suppose a model sends the Python guest into a loop. Three mechanisms can stop it, and they exist for different failures:

BoundMechanismEngine signalReported as
Instruction budgetFuel set before each call: 5,000,000,000Out-of-fuel trapextension.budget_exhausted
Call deadlineEpoch deadline set before each call: 30 sInterrupt trapoutcome deadline
CancellationThe cancellation handler moves the epoch deadline to nowInterrupt trapoutcome cancelled
Memory ceilingStore limit of 256 MiB per memoryGrowth returns -1See BND-2
Anything elseNoneAny other trapextension.guest_trap

The budget value is MoonBit's. Its engine counts differently from Wasmtime, so the same number is not the same amount of work. The contract says the unit is engine-defined. No qualification case depends on where the default budget runs out: a runaway call may end at the budget or at the deadline, and a separate case with a budget of 1,000,000 tests exhaustion. The .NET host measured the published guests at no more than 3,321,411 units of Wasmtime fuel per call on the kit's input.

Alternative. Deadline only, as an engine without metering must. Then a tight loop holds a core for the full 30 seconds before anything stops it.

BND-2. Report the memory limit when a call fails at the ceiling

The PRD left this open: Wasmtime refuses growth by returning -1 to the guest, and the guest may carry on. The engine's C API takes numeric limits only. It has no callback that tells the host a growth was refused, so the host cannot know the cause of a later abort for certain.

The MoonBit host does know: its engine calls back on every refused growth, so it reports the memory limit for any failing call in which one happened. The contract requires the part both hosts can do, and lets a host that sees more report more.

For .NET the rule is the one the host can observe exactly. When a call ends in a trap and the guest's memory, or the kernel's, is at its ceiling, the failure is extension.memory_limit. A trap carries no cause, so the host infers one from the memory. The kernel's memory counts because an Extism guest's input and output live there. Every other end keeps its own code, also at the ceiling: a failure the guest reported itself, such as an Extism error, a failure the host detected, such as a response over its limit, and a stop by the host for the budget, the deadline or a cancellation. MoonBit does the same: it reports the memory limit only for a call its engine stopped. Every failure diagnostic states the guest's memory size and the ceiling, so a guest that aborted after one large refused request is still explained: the user sees a trap at 100 MiB of a 256 MiB ceiling. A guest that handles the refusal and answers is a success.

Reading a memory's size needs a handle on it, and Wasmtime gives a host a memory only through an export. Many modules do not export theirs. Most crafted modules with a memory do not, the module of bounds/grow-to-ceiling-then-trap among them. For such a module the host compiles a copy with one added export entry, the memory under the name morphir:host/guest-memory. The code, the memory, the classification and the digest in every report are the original's, and a module that exports its memory runs unchanged. The maintainer accepted this on 9 November 2026.

Alternatives. Treat any trap as a possible memory failure: it would mislabel ordinary guest bugs. Rewrite the module's code to report failed growth: it changes what the guest executes, so the digest in every report would no longer describe it. The added export changes no instruction and is not that. Require every guest to export its memory: published bundles and the crafted corpus would both have to change for a host's convenience.

At start-up the host does not touch the engine. The first command that needs a WASM extension, or the runtime report, probes for it once and turns a missing or unloadable library into extension.runtime_unavailable with a reason. Commands that never use WASM pay nothing and cannot be broken by a packaging fault.

Alternative. A separately installed runtime component that the host downloads when first needed. It keeps the base executable small, but it makes a build depend on the network, which add-deployment-and-acquisition rules out for ordinary commands.

PKG-2. The tool becomes platform-specific, with a fallback package that has no engine

Morphir.Tool is one platform-neutral package today. A native library forces platform-specific packages: one per supported platform, plus the pointer package that dotnet tool install resolves. Left there, a user on Linux musl could no longer install the tool at all, and they would lose commands that never needed WASM.

The package set therefore includes a platform-neutral fallback with no engine. On a platform without its own package the tool installs, every existing command works, and the runtime report lists wasm as unavailable.

Assumption to verify. .NET 10 platform-specific tools accept an any fallback package alongside the specific ones. Task 5.4 checks this against the SDK the repository pins. If the SDK cannot do it, the change keeps a second, neutral package identity for those platforms and does not drop them.

Stage 10. Someone has to check all of this

WRK-1. A worker mode with MoonBit's command shape

A conformance runner starts a host executable and speaks Content-Length framed MEP over stdio. The .NET host gains morphir extension worker with the arguments MoonBit's worker takes, so one invocation serves both hosts by changing the host path.

The runner itself is the Rust morphir mck today, and it is moving to the .NET host in morphir-dotnet. This decision does not depend on where the runner lives: the worker mode is a stdio contract, and any runner that can start a process can use it. The example shows today's runner:

# Proposed worker arguments, shown with today's runner. Identical to the MoonBit invocation except for the host path.
$ morphir mck mep guest-run \
    --kit spec/mep/mck/guest-generic-json.json \
    --host /path/to/dotnet/morphir \
    --host-arg extension --host-arg worker \
    --host-arg --abi --host-arg extism-kernel-v1 \
    --host-arg --module --host-arg /path/to/morphir-python-binding.wasm \
    --report .dev/mep-generic-dotnet.json

Inside, the worker is a stream channel on one side and a WASM channel on the other, joined by the same session code product commands use. It is not a second implementation. The command is internal and marked experimental, as it is in MoonBit.

Alternative. Have the runner load the .NET runtime as a library. That ties the runner to one host, which the qualification spec forbids, and it tests a different path from the one users run. The same holds if the runner moves into morphir-dotnet: it would still drive its own host through the worker, as it drives every other.

QUAL-1. Qualify the host with modules that misbehave on purpose

The corpus is authored as JSON in this repository. The .NET runner does not execute that JSON directly: it generates Gherkin features from it, never edited by hand, and a test requires the JSON and the features to give the same cases. On 9 November 2026 the maintainer decided that the compatibility kit as a whole moves from JSON to Gherkin. Until that move, the JSON here is the source and the features are derived from it.

Running the Python guest through the worker shows the happy path. It cannot show that the host refuses a socket import or stops a loop, because the Python guest does neither. The qualification spec adds a corpus of crafted modules, each a few lines of WebAssembly text with one fault, with expectations written from the contract.

One limit is worth stating. A module that only computes cannot tell the budget from the deadline: on a metering host the budget always ends a busy loop first. The corpus therefore checks the property users depend on, that a runaway guest is stopped no later than its deadline, and records which bound stopped it. A metering host's deadline is observed only where the budget is not enforced.

The corpus is built from text in this repository, so it needs no guest toolchain and belongs to no host. MoonBit already has crafted fixtures of its own. Adopting the shared ones is a MoonBit follow-up that this change makes possible and does not require.

CACHE-1. No compiled-module cache on disk

Compiling the Python module takes time on every process start, and the engine can serialize compiled code to skip it. The spike recommended doing so. This design does not, yet.

A serialized module is native machine code, and the engine trusts it when it loads it. A cache file that another process can write is therefore a way to run arbitrary code inside the host. Making that safe needs a cache location, an integrity check and a clean-up rule, which is a design of its own. The first delivery measures the compile time and reports it; the in-memory cache in ENG-1 covers repeated use within one process.

Acceptance and delivery sequence

The change is complete when:

  1. The generic guest kit passes through the .NET worker mode for the Python 0.6.0 guest, on the kit's model tier, with IR equal to the kit's expectations. The SDK fixture guest speaks MEP 0.1 only and is not part of this until it is rebuilt.
  2. Every crafted case for the Extism profile gives its expected observation on the .NET host, and a byte-profile module is refused by name, with the memory ceiling and call deadline reported as enforced.
  3. One published bundle from .config/published-extension-bundles.toml runs in both the Native AOT host and dotnet-morphir. This is the roadmap's own completion evidence for step 5.
  4. Each offering and platform that claims the runtime has a report produced from its released artifact on a clean machine.
  5. The Native AOT publish shows zero IL2026 and IL3050 warnings and no suppressions.

Migration and rollback

Nothing existing changes behavior. Process guests keep their stream channel, and no configuration key changes meaning. The runtime is reachable only through the experimental worker mode until a product command adopts it, so a release can ship the runtime before any user-facing command depends on it.

The tool packaging change is the one step users can notice. It ships with release notes and updated installation guidance in the same release, as the PRD requires. Rollback is to publish the next release with the previous single package; the fallback package keeps the tool installable in the meantime.

Retiring the byte profile. The shared contract marks morphir-bytes-v1 as transitional from 0.1.0-draft.1: a host may run it, no new host has to, and no new guest should target it. The order is: the Gleam extension, the MoonBit portable guest and the Elm preview each ship on Extism; the MoonBit host then removes its byte adapters and the contract drops the profile in its next draft. The crafted byte-profile cases stay in the corpus until then and apply only to a host that declares the profile. Each of those steps is tracked in its own repository and none gates this change.

There is no switch that turns the runtime off. An engine defect found after release is fixed by a patch release. Until then a user avoids it by not configuring a WASM extension: nothing else in the CLI loads the engine, so every other command is unaffected.

Open questions

None of these changes the specs or the task breakdown.

  • Should loading errors have codes? A file that cannot be read, a file that is not a WASM module and a declared digest that differs have no extension.* code in the contract. A worker reports the first two as fault failure before started, and a host session reports all three with a diagnostic only.
  • Is a slimmer engine build, without the compiler features Morphir never uses, worth maintaining? The spike did not measure one.
  • What location, integrity check and clean-up rule would make an on-disk compiled-module cache safe (CACHE-1)?
  • Should the worker mode become a documented public command once a second host uses the same shape? finos/morphir-moonbit#297 asks the same of MoonBit.
  • Should a guest be able to send the host a notification, such as morphir.progress? It needs a new function in extism:host/user, and a module that imports it would be refused by hosts on the current contract (NTF-1). The same holds for the reserved poll delivery, which would let a guest see $/cancelRequest during a call.
  • When the roadmap's host grants are designed, do they belong in the shared profile contract or stay host-specific?
