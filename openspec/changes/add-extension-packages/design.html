Context

The proposal says why this change exists. This section lists only what the design builds on. These rows describe today's code and pages. After this change the contract pages define the package rules, and the Rust source is evidence, not the authority.

Goals and non-goals

Goals. An extension can be a tree of files that a host unpacks once, checks against a digest its descriptor names, stores read-only and starts by one entry point. Two hosts reach the same answer for every archive. A single-file artifact that is the executable itself keeps its meaning. A host that knows nothing of packages never runs a package's archive.

Non-goals.

  • Packages for WASM, daemon or .NET tool deliveries. A WASM module is one file, and a .NET tool is installed by its own manager.
  • Non-ASCII entry names, symbolic links inside a package, and archive formats other than ZIP and gzip-compressed tar.
  • Sharing files between packages, deduplicating them, or applying patches between versions.
  • Any change to who is trusted, to how a repository or recipe is authenticated, or to the claim check.
  • Keeping the released Rust CLI working, or reading earlier drafts.
  • Edits to the toolchain contracts. TC-1 lists their follow-up as tasks.

Decisions

The journey below follows one artifact from release to removal: the F# frontend org.finos.morphir.fsharp-frontend 0.6.0 for x86_64-pc-windows-msvc, published as fsharp-frontend-0.6.0-win-x64.zip, installed by the Native AOT morphir host into a home on Windows, and later removed. Each decision appears where it first matters.

PKG-1. A package is an artifact with a package member

The release job has a published folder and must describe it in release.json.

{
  "schemaVersion": "<the package draft>",
  "extensionId": "org.finos.morphir.fsharp-frontend",
  "critical": ["artifacts.package"],
  "artifacts": [ {
    "platform": "x86_64-pc-windows-msvc",
    "runtime": "process",
    "filename": "fsharp-frontend-0.6.0-win-x64.zip",
    "sha256": "<SHA-256 of the archive>",
    "package": {
      "format": "zip",
      "root": "fsharp-frontend",
      "entryPoint": "morphir-fsharp-frontend.exe",
      "treeSha256": "<SHA-256 of the tree manifest>"
    },
    "claims": { "extension": { "id": "org.finos.morphir.fsharp-frontend", "version": "0.6.0" } }
  } ]
}

The Linux artifact of the same release has "format": "tar.gz", "entryPoint": "morphir-fsharp-frontend" and "executables": ["createdump"].

Decision.

  • The member. An artifact is a package when it has a package member, and a single-file artifact otherwise. package has format, entryPoint and treeSha256, and optionally root and executables.
  • Always critical. A descriptor or index record with a package lists artifacts.package in critical, and a catalog with a package entry lists extensions.package. A reader of the package drafts refuses a package that is not marked critical (package.not_critical).
  • Formats. format is zip or tar.gz, and the file name ends in .zip, or in .tar.gz or .tgz, to match. Only process artifacts can be packages.
  • Single files. An artifact without package is the executable itself, read, stored, recorded and started as before. A process artifact without package whose name ends in .zip, .tar.gz, .tgz or .tar is refused (package.archive_without_package): it was never something a host could run.
  • Hosts without package support. A host that reads the package drafts but cannot install packages refuses a package with package.unsupported.

Why critical is required. This closes the most serious gap of the first revision. The descriptor, record and catalog are must-ignore-unless-critical documents. Under PKGVER-A the package drafts are #1149's drafts refined in place, and finos/morphir-dotnet#567 is being built against those drafts now. Without critical, a build that implements #1149 but not this change would read a draft.3 descriptor and ignore package. It would then take fsharp-frontend-0.6.0-win-x64.zip as a single-file process artifact, store it, and start the archive as the program. With critical, that host refuses the document by rule 1, under either version outcome, before it stores anything. Rule 3 already uses the same mechanism for requires.host.

The two existing single-file shapes. Both are named in .config/published-extension-bundles.toml:

  • A raw executable, such as morphir-scala-elm. It needs no change, and a recipe binds the executable file itself.
  • One executable shipped inside an archive, such as morphir-elm 0.4.1's .tgz. It had no runnable meaning before: publication refused it, and a host that stored it would have started the archive. To be installed by a current host it is published with a package member naming its one executable, a one-file package. Under #1149 it must be published again at a new draft anyway. #1150's Decision 13 makes morphir-dotnet's bundle authoring the publisher of that republication, so the package member travels with it rather than adding a second one, and that publisher writes it.

Why these formats. They are the two forms the toolchain recipes already bind (.zip on Windows, .tgz elsewhere), and the forms both the Rust tool extractor and the .NET base class library read. A third format would add a reader to every host for no artifact that needs it.

Why an explicit member, not the file name. With the member, a host reading the descriptor knows exactly what to do. With only a name, a host would have to guess.

VER-1. Which drafts carry packages

The descriptor, the index record, the catalog and the extension lock all gain the package member. finos/morphir#1149 has already moved the same four documents to new drafts: the descriptor, record and catalog to 2.0.0-draft.3, and the lock to 2.0.0-draft.1. It merged on 10 November 2026 as an approved proposal (9690dfc37), but its tasks have not run.

OutcomeDraftsCost
PKGVER-A: one bump covering both changesRefine #1149's 2.0.0-draft.3 and lock 2.0.0-draft.1 in place to add package
  • #1149's sentence "2.0.0-draft.3 differs from 2.0.0-draft.2 only in the id grammar" gains "and the package member".
  • #1149's page work (its task 1.4) and this change's (task 1.2) land together.
  • The .NET installer builds against one set of drafts once, and the F# guests are published once.
PKGVER-B: a following draftDescriptor, record and catalog at 2.0.0-draft.4; lock at 2.0.0-draft.2

  • Readers read only the current drafts, so everything written at draft.3 is written again at draft.4, and every host implements two successive drafts.
  • Every home a current host has written then holds old state. Under #1150's Decision 10 a host offers to move it to a marked backup, or the user runs morphir doctor --fix, so every user of a draft.3 host reinstalls once.

Decision. Choose by a fact that can be checked. PKGVER-A applies when this change is approved only if both of these hold:

  • no released host, publisher or tool reads or writes #1149's drafts;
  • no repository outside TEST-ONLY fixtures holds a document at them.

Otherwise PKGVER-B applies. "Released" means a tagged release, a published package (NuGet included) or a release asset. Test fixtures, merged examples and unreleased builds do not count. Task 1.1 lists the release pages and repositories it checks and what it found. The spec says "the package drafts" throughout, so it holds in either order.

Why this rule is now about cost only. Before critical was required, the outcome decided safety: a released reader of unrefined draft.3 would have run an archive. That hazard came from a released reader, not from a published document, which is why "released" is part of the definition. With package always critical, a reader that does not understand it refuses it under either outcome. The rule only decides whether hosts implement one draft or two. Refining a draft before anything released reads it is what AGENTS.md allows.

TREE-1. The tree manifest and two digests

The release job now needs the value of treeSha256, and every installer must compute the same bytes from the same archive.

Decision. The tree manifest is ASCII text without a byte order mark. It has a header line, then one line per file in ascending byte order of its tree path. Each file line holds the kind, the size, the SHA-256 and the path, separated by single spaces, and every line ends with one LF:

morphir-package-tree 1
f 1153536 4a1f…e2 FSharp.Compiler.Service.dll
f 1062912 9bc0…7d FSharp.Core.dll
…
x 152576 07d3…a9 morphir-fsharp-frontend.exe
…
f 4096 c51e…10 zh-Hant/FSharp.Core.resources.dll
  • Kind. x when the path is the entry point or is listed in executables, otherwise f. It comes from the descriptor, never from the archive, so the digest is the same on every platform and for archives made on Windows, which carry no Unix modes.
  • Size. Decimal without leading zeros; an empty file is 0.
  • Digest. The SHA-256 is lowercase hexadecimal, over the file's bytes after decompression, with line endings and encodings untouched.
  • Path. The tree path after the optional root is removed. A path may contain spaces but no control character, so a reader splits a line at its first three spaces only. Entry names are ASCII (EXT-1), so byte order and UTF-16 order agree, and no host can sort differently by using its platform's string comparison.
  • Not covered. Directories are implied by file paths and are not listed. Owners, timestamps, permission bits and extended attributes do not appear.

The tree digest is the SHA-256 of the manifest's bytes. The artifact's sha256 stays the archive's SHA-256. Both are recorded:

DocumentArchive digestTree digest
Release descriptor and index recordartifacts[i].sha256, as todayartifacts[i].package.treeSha256
Installed catalog entry and extension lockthe artifact digest, as todaythe package member, copied unchanged
Toolset recipe and portable lockartifactSha256, as todaythrough the bound descriptor (TC-1)

Why both. The archive digest is what a repository and a recipe authenticate: it is the TUF target's hash, and a recipe binds it today. It cannot check an unpacked tree once the archive is gone. The tree digest names what actually runs, and it can be checked offline at any time against files on disk.

The independent review computed one manifest by hand from the spec text alone: files run, lib/a.dll and one more, 254 bytes, digest e1aea23c…d9c5. It found every byte determined. Its only second readings, the size 0, the byte order mark and UTF-16 ordering, are now settled above.

RD-1. How an archive's entries are read

Before any rule can say "refuse an entry named ../x", two hosts must agree on what the entries are, what each one is named, what type it has and in what order they come. The first revision left that to "the archive's features", and the review found archives that two careful hosts would read differently. This decision fixes the reading for each format.

ZIP.

  • The central directory is authoritative. It gives the entries and their order, found through the end-of-central-directory record and, when present, its zip64 record. Zip64 records and extra fields are always accepted: some streaming writers emit them below 4 GiB, and refusing them would make validity depend on the writer.
  • Layout (package.zip_layout). Refused: no end record, or one that names another disk; bytes before the first local header, as in a self-extracting stub; gaps or overlaps between entries; any byte after the end record and its comment.
  • Local headers (package.zip_header_mismatch). Each local header matches its central entry in name, method, flags, CRC-32 and both sizes, or, when flag bit 3 is set, its data descriptor does. Layout and headers are checked over the whole archive before any entry rule. So a streaming reader and a central-directory reader cannot see different bytes, and the "first" fault cannot depend on which order a host chose.
  • Unsupported features (package.zip_unsupported). Encryption (flag bit 0 or 6), methods other than stored (0) and deflate (8), and the Info-ZIP Unicode Path extra field (0x7075), which would give an entry a second name. Decompressed bytes that do not match the CRC-32 or size are package.zip_crc.
  • Type. An entry is a directory exactly when its name ends in /. When version-made-by's high byte is 3 (Unix) and the external attributes' high 16 bits are not zero, their file type is read as well:
    • a symbolic link is package.link_entry, as lib/current with mode 0120777 and no slash is;
    • a device, FIFO or socket is package.special_entry;
    • a directory type without the slash, or a regular type with it, is package.entry_type_mismatch, and so is the DOS directory attribute without the slash.
    observed Rust reads the Unix mode the same way (validate_zip_entry_kind). .NET's ZipArchive exposes only the raw external attributes, so the .NET host decodes them itself (task 2.2).

tar.gz.

  • gzip (package.gzip_layout). Exactly one member as RFC 1952 defines it, with a CRC-32 and size trailer that match, and no byte after it. A stream of two concatenated members is refused.
  • Blocks (package.tar_layout). 512-byte headers in stream order, each with a correct checksum. The size is in octal or GNU base-256. The stream ends with two zero blocks, and any byte after them must be zero, since tar pads to a record size. Also refused: a malformed pax record, and a pax or GNU long-name header that is repeated before one entry or followed by none.
  • Name. The path of a pax extended header (x) before the entry. Else the payload of a GNU long-name header (L) up to its first NUL. Else, for the POSIX ustar magic with a non-empty prefix, the prefix, / and the name. Else the name. A host that ignored GNU long names would see an entry named ././@LongLink, so the rule is stated.
  • Size. A pax size overrides the header; observed Rust honors it too. Other pax keys (times, owners, extended attributes) are ignored.
  • Types.
    • 0 and NUL are regular files and 5 is a directory.
    • 1, 2 and K are package.link_entry; K only ever precedes a link.
    • 3, 4 and 6 are package.special_entry.
    • Every other type (7, g, S, V, M, D, N and the rest), and any pax key starting GNU.sparse., is package.tar_unsupported.
    • A regular entry whose name ends in / is package.entry_type_mismatch.
  • Bound. A pax or long-name payload over 1 MiB is package.tar_header_too_large, refused from the size field before the payload is read.

Both formats.

  • A directory entry with a non-zero size is package.directory_with_data.
  • An entry named exactly ./ is ignored, and one leading ./ is removed from every other name, so an archive made by tar -C dist -czf x.tgz . reads as run and lib/a.dll. Names that become equal are duplicates.

Order of faults. A ZIP archive's whole-archive checks come before its entries, because the central directory gives them up front. A tar.gz archive is read as a stream, so a fault is reported where a streaming reader meets it:

  1. the gzip header;
  2. each entry;
  3. the tar end blocks;
  4. the gzip trailer.

A host that reads the whole stream twice still reports the same first fault.

EXT-1. Safe unpacking, as refusals with stable codes

The host has read the 239 entries of the F# frontend's archive. Now it must turn them into files without writing anywhere it should not, and without two files that one file system would treat as one.

Decision. One code per rule, prefixed package., checked in a fixed order, and a host reports only the first refusal. The order is:

  1. the archive codes (archive_too_large, archive_digest_mismatch, archive_format);
  2. the format's whole-archive codes (RD-1);
  3. each entry: first the format rules of RD-1, then the rules in the table below, in its order;
  4. the tree rules.

Elsewhere a host reports these codes:

  • package.runtime, package.not_critical, package.archive_without_package and package.unsupported, for the descriptor (PKG-1);
  • package.publish_busy and package.store_not_one_volume, at publication (STORE-1);
  • package.tree_changed, at activation (VFY-1).

The first revision had a file_count code. It could never be the first refusal: every file is an entry, both limits were 4096, and entry_count came first. So it is gone.

ASCII names, as a limit of this draft. Entry names are ASCII from 0x20 to 0x7E, and case collision is ASCII case folding, as the table defines it. The pinned Unicode version says how to normalize. It does not require non-ASCII names in packages, and the F# frontend has none (assumption, task 2.1). Without Unicode in the security core, three things disappear, along with the Unicode data every host would ship:

  • normalization, and with it the question of names that are not NFC;
  • code points that Unicode 17.0.0 leaves unassigned, which a later file system could fold;
  • Unicode case mapping, whose case-folding and uppercase keys differ for letters such as the dotless i.

It also agrees with the morphir-dotnet installer plan, whose ARC-1 already requires ASCII names compared ignoring ASCII case. The plan keeps that rule. What lifting the limit would need is under the open questions.

MODE-1. File modes and what read-only means

On Linux and macOS the frontend's apphost must be executable. Some .NET runtime files, such as createdump, are executable too.

Decision.

  • Unix. A host gives x files mode 0555 and f files 0444, set in staging. Once the package is published, it gives the directories 0555, and sets no setuid, setgid or sticky bit.
  • Windows. A host sets the read-only attribute on every file and writes no alternate data stream; a Windows entry point is executable because it ends in .exe.
  • The executable set. The entry point plus executables, from the descriptor. Nothing else from the archive is used: not modes, owners, groups, timestamps or extended attributes.

What this enforces, and what it does not. The modes make an accidental write fail at the moment it is made, for example a guest that tries to write a log beside its executable on Linux. That is better than the write succeeding and the next activation refusing the tree. They are not a security boundary: any process with the user's rights can change the modes and then write. On Windows the read-only attribute is not honored on directories, so a guest can still add a file to the tree there; the activation check of VFY-1 finds it. The first revision called the tree "immutable". The accurate statement is read-only by mode and checked at activation.

Why the directories are made read-only only after publication. On Linux, renaming a directory to a new parent needs write permission on that directory. rename(2) lists EACCES when "oldpath is a directory and does not allow write permission (needed to update the .. entry)". A read-only staging directory could not be published.

Why the descriptor decides the executable set, not the archive. A ZIP file written on Windows has no Unix modes, and a tar file's modes differ between build machines. Taking the set from the authenticated descriptor keeps the tree digest independent of the archiving tool, and the set cannot change without changing the descriptor's digest. observed The Rust tool extractor marks any entry with an executable mode bit instead; this rule replaces that for extensions.

STORE-1. Store layout, publication and recording

The checked files must end up where no host can read them half-written, and where collection cannot remove them between publication and recording.

MORPHIR_HOME/store/extensions/
  sha256/<digest>/<filename>            single-file artifacts, unchanged
  packages/
    .stage-<random>.owner                lock file guarding the staging directory
    .stage-<random>/                     staging: manifest, tree/
    .trash-<random>/                     a package being removed
    sha256/<treeSha256>.lease            lock file held while the package runs
    sha256/<treeSha256>/
      manifest                           the tree manifest bytes
      tree/morphir-fsharp-frontend.exe   the entry point
      tree/…                             the other files

Decision.

  1. Stage, outside the state lock. The host creates .stage-<random>.owner, opened as lock files are, and locks it exclusively. Only then does it create .stage-<random>/ on the same volume. It unpacks into tree/, hashing each file from the bytes it writes, sets file modes, flushes each file, writes manifest and flushes it. On Unix it also syncs the directories.
  2. Verify, outside the state lock: every rule of EXT-1, the tree digest, and the Windows path check of RUN-1.
  3. Publish and record, under one hold of the state lock. If the published path holds a tree that passes the activation check of VFY-1, the host uses it and removes its staging directory. Otherwise it moves any tree there to .trash-<random> and renames its staging directory to the published path. It sets the directory modes, then writes the lock and the catalog entry through #1149's journal.

Why one state-lock scope. The first revision published outside the state lock and recorded later under it. Collection, which runs under the state lock, could then remove a freshly published tree that no lock named yet. The installer would then record a lock pointing at nothing, as both reviews found. Now collection runs wholly before publication or wholly after recording. A tree that install finds already published is checked under the same hold, so it cannot be collected between the check and the record. The cost is small: the state lock is held for a rename, a few chmod calls on directories, a structure check of an existing tree, and the journal commit, which is milliseconds, not the seconds of unpacking. A lease handed over before publication would also work, but it adds a second lock order for every install.

The owner and lease files sit beside their directories, not inside. A host renames the staging directory, and collection renames a package directory. A lock file held open inside a directory can stop that rename on Windows. Microsoft's knowledge-base article Q130589 reports an error "if there is an open file in the directory", and the reviewer's suspicion was the same. assumption Whether it always does is untested (task 2.3). Keeping both lock files outside the directories they guard makes the design safe either way.

The rename. It never replaces and never copies:

  • it uses renameat2 with RENAME_NOREPLACE on Linux, renamex_np with RENAME_EXCL on macOS, and MoveFileExW without MOVEFILE_REPLACE_EXISTING on Windows, because plain rename(2) replaces an empty target directory: its newpath "must either not exist, or it must specify an empty directory". RENAME_NOREPLACE returns "an error if newpath already exists". It needs file-system support: from Linux 3.15 on ext4, 3.17 on btrfs and tmpfs, and 4.0 on xfs;
  • a sharing or access error, which a real-time scanner can cause by opening a new executable, is retried for up to 10 seconds, then package.publish_busy;
  • a cross-volume error, for example when sha256/ is a mount or junction, is package.store_not_one_volume, never a copy.

VFY-1. What verified means, and when it is checked

A project compiles many times a day, and each compile starts the frontend once. The single-file rule rehashes the artifact at every activation. Applied to a package, that rule meets 239 files and about 121 MB.

Verified means three things: the archive matched sha256, no rule refused it, and the tree digest computed from the written bytes equalled treeSha256. A package that is not verified is never published, recorded or started.

CheckWhat it readsEstimated cost for 239 files and 121 MB assumption
Full verification at installThe archive, every decompressed byte, 239 writesAbout 1 to 3 seconds, once per install
Structure check at each activationThe manifest (about 25 KB) and its SHA-256, plus a listing, size and mode of every fileAbout 5 to 30 ms; up to about 100 ms on Windows with real-time scanning
Full rehash at each activation239 opens and 121 MB of SHA-256About 0.1 to 0.3 seconds with a warm cache; 0.5 to 2 seconds cold, and more with real-time scanning
Private copy at each activation (the single-file practice)121 MB written to 239 new filesAbout 0.5 to 3 seconds, plus scanning of each new executable file, and twice the disk while it runs

The estimates assume SHA-256 at 0.5 to 2 GB/s and solid-state storage. Task 2.4 measures them on the first-delivery platforms.

Decision provisional. Open question Q-VERIFY; the spec states outcome VERIFY-B:

  • At install, and when the user asks to verify installed extensions: full verification.
  • At each activation, under the state lock:
    • the lock and catalog agree on package;
    • the SHA-256 of manifest equals treeSha256;
    • tree/ holds exactly the manifest's files, as regular files, with the manifest's sizes and, on Unix, the read-only modes of MODE-1.
    A failure is package.tree_changed, and nothing starts.
  • Under VERIFY-A: activation also rehashes every file.

Why VERIFY-B is recommended. It catches what happens in practice for a few milliseconds per compile: deleted, truncated, added or replaced files, changed modes, and a manifest edited out of step with the lock. The read-only modes make accidental writes fail loudly. What it misses is a same-size change to a file's bytes made after its modes were changed back. No outcome stops a process with write access to the home: it can rewrite the tree, the manifest, the lock and the catalog consistently. Under VERIFY-A it could still swap a file after the rehash and before the start. A full rehash at launch therefore adds detection of same-size accidental corruption, not a security boundary. The full check stays one command away.

RUN-1. Activation and launch

The compile now needs the frontend running.

Decision choice to confirm. The host starts the entry point from the store; it does not copy it. This changes the existing activation rule for single files, which starts a private copy. So it is recorded as a choice for the maintainer to confirm, Q-LAUNCH, and the design follows it until then.

  • Program. The absolute path of tree/<entryPoint>, in the platform's native spelling, without a verbatim prefix, as C:\Users\dev\.morphir\store\extensions\packages\sha256\<treeSha256>\tree\morphir-fsharp-frontend.exe.
  • Arguments. The argument vector is that path followed by the locked arguments.
  • Working directory. The project directory for a project command, otherwise a new private directory outside the store, never inside it. The environment is filtered as for a single-file process.
  • Lease. The lease and the guest's process tree are tied together (LIFE-1).

Windows path limits. A Windows entry point ends in .exe, compared ignoring ASCII case (the installer plan's Q-WINLAUNCH). Before it publishes, a host refuses a package with package.install_path_too_long, naming the longest path and its length, in two cases:

  • any file's store path would exceed 259 UTF-16 code units;
  • any directory's store path would exceed 247.

The numbers come from Microsoft's Maximum Path Length Limitation. MAX_PATH is 260 characters including the terminating null. When creating a directory, "the directory name cannot exceed MAX_PATH minus 12". And CreateProcessW is not among the functions the long-path opt-in frees from MAX_PATH. A host does not write with the verbatim prefix. Staging paths, packages\.stage- and 16 random characters, are shorter than published ones, packages\sha256\ and 64 hexadecimal digits. So unpacking never fails on a path the final check would allow.

The arithmetic, with real numbers. For the default home C:\Users\<name>\.morphir, the store prefix before a tree path is 122 UTF-16 code units plus the user name's length U:

  • Files. A file at tree path length T fits when U + T ≤ 137.
  • Directories. A directory at tree path length D fits when U + D ≤ 125.
  • What the 120-unit bound leaves. A package whose tree paths reach the bound fits only for user names of 17 characters or fewer. That is short for first.last accounts, so the bound alone does not leave room.
  • What the frontend leaves. The F# frontend's real longest path is what leaves room: assumption about 70 units, which fits user names up to about 67 (task 2.1 measures it).
  • Other homes. A relocated MORPHIR_HOME changes the prefix accordingly.

Why from the store. A private copy per launch costs a large write on every compile (VFY-1). The reasons for copies do not hold for packages:

  • update installs a new tree under another digest, so no running file is replaced;
  • uninstall never deletes a package (REM-1);
  • a verified, read-only tree in the user's own home is as trusted as a copy written from it.

The single-file artifacts keep their private copies; that is not changed here.

LIFE-1. A lease that lasts as long as the guest

The F# compiler inside the frontend opens reference assemblies when it needs them, not all at start. If its files disappear while it runs, the compile breaks. The automated review found the gap in the first revision. The lease was the host's, so a host that exited while its guest ran released it, and collection could then delete files the guest had not opened yet. On Unix a running process keeps only the files it already has open.

Two ways to close it were weighed:

OptionWhat it guaranteesCost
Tie the lease to the guest's process treeThe lease lasts while the guest or any descendant that kept it livesUnix: hand the leased descriptor to the child. .NET opens files close-on-exec (O_CLOEXEC in SafeFileHandle.Unix.cs), so the host clears FD_CLOEXEC on that one descriptor, and it must start the child in a new process group, which System.Diagnostics.Process cannot do: a platform call to posix_spawn or a small launcher. Windows: an inherited handle does not extend the lock. Microsoft's LockFileEx says "If the file handle is inherited by a process created by the locking process, the child process is not granted access to the locked region", so this alone does not work there.
End the process tree before the lease is releasedNo process of the tree outlives the leaseWindows: a job object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE, which "Causes all processes associated with the job to terminate when the last handle to the job is closed" (Microsoft). That holds even when the host crashes, because the system closes the host's handles. Unix: a process group the host signals when the session ends. That is not guaranteed when the host is killed, because Linux's parent-death signal reaches only the direct child and macOS has none.

Decision. Each platform uses the mechanism that holds there, and the host also ends the tree on a normal exit:

  • Unix. The host takes the shared lease, passes the descriptor to the guest as inherited, and starts the guest in a new process group. A flock lock belongs to the open file description. flock(2) says it is released "when all such file descriptors have been closed". So the lease lasts while the guest, or any descendant that kept the descriptor, lives, even if the host is killed. At the end of a session the host waits for the guest, ends any process left in the group, and only then closes its own descriptor.
  • Windows. The host starts the guest in a job object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE and no breakaway, created directly in the job, so no descendant can escape before assignment. At the end of a session it ends the job, waits until it holds no process, then releases the lease. If the host crashes, the system closes the job handle and ends every process in it.

What remains, stated. Two gaps remain:

  • Unix. A descendant that closes inherited descriptors, leaves the process group, and outlives a killed host can lose its package's files to an explicit collection.
  • Windows. After a host crash the system releases the lease and ends the job's processes, and "the time it takes for the operating system to unlock these locks depends upon available system resources" (LockFileEx). So a collection run in that instant could see a free lease while a guest is still ending.

Both need an explicit collection at the wrong moment, against a package no lock names. Task 2.3 tests the normal cases.

REM-1. Removal and collection

The user uninstalls the frontend while a compile is still running it.

Decision. Uninstall and update remove or replace the extension's lock and catalog entry, and never delete or change a published package. The running process keeps its files.

A separate, explicit collection command deletes packages. Under the state lock, it deletes a published package only when three things hold:

  • no extension lock in the home names its tree digest;
  • it can take an exclusive lock on the package's lease file without waiting;
  • the home holds no toolchain generation receipt, until the toolchain contracts define how a receipt names a package (task 4.2).

Collection clears the read-only modes, renames the package to .trash-<random>, deletes it, then removes its lease file. A rename that fails, as it can on Windows while a file is open, leaves the package for a later run. Collection also removes .trash- directories and abandoned staging directories (STORE-1).

After an old home is moved aside. #1150's Decision 10 moves old extension locks and the catalog to backups/extensions-<time>/, asking first or through morphir doctor --fix, and never moves the store. Published packages therefore stay where they are. Collection reads only locks/extensions/, not the backup, so once no current lock names a package, an explicit collection may delete it. A user who restores a backup by hand may then need to reinstall. That is consistent with the move, which already asks the user to start fresh.

Why. observed Today nothing deletes store bytes; the installer plan keeps that rule ("Removal never deletes store objects"). A package is about 121 MB, so some deletion is needed. Tying it to an explicit command keeps uninstall fast and safe while the extension runs. The lease is what makes deletion safe across hosts and processes: the state lock alone is not held while a guest runs. Whether collection should instead run at uninstall time, with no new command, is part of Q-LAUNCH.

TRUST-1. A package changes nothing about trust

Decision. A package does not change who is trusted. Claim checks and publisher authentication stay separate facts.

  • What a host may conclude from a verified package: its tree is the one the descriptor names. When the descriptor is authenticated, by a repository's signed targets or a recipe's digest, the tree is therefore the one its publisher released.
  • What a host may not conclude. Unpacking says nothing about the publisher. A code signature inside the tree, such as Authenticode on the entry point, is not authentication and grants nothing. The executables list grants no permission beyond the executable bit. The package's claims are still decided by the probe, run from the published tree.

CONF-1. Shared conformance cases

The .NET host and the MoonBit host must refuse the same archives with the same codes.

Decision. Publish the cases in finos/morphir, beside a normative package page, as data. Each case is a small archive file, generated deterministically by a checked-in script, plus a JSON entry naming the archive, the descriptor's package member and the expected outcome: valid with its tree digest, or the refusal code and the entry name it names. Many refusals cannot be produced with ordinary archiving tools: links, devices, .., mismatched ZIP headers, gaps, two gzip members, GNU long names. Migration plan

Nothing is converted. Raw-executable single-file artifacts are unchanged. Process extensions that ship one executable inside an archive, such as morphir-elm, are published with a package member when they are next released at the new drafts, which #1149's republication requires anyway, by morphir-dotnet's bundle authoring (#1150's Decision 13). A host that reads the package drafts but does not yet install packages refuses them with package.unsupported, and a host that does not read them refuses them by critical. Rolling back a host leaves published packages in the store, where they occupy disk until a collection by a host that knows them. No existing home holds a package, so no home needs a migration step.

Open questions

Two questions are for the maintainer. The version sharing is settled by the timing rule of VER-1. The formats, digests, reading, refusals, modes, store, lifetime and removal are settled by this design.

Q-VERIFY. What does a host check each time it starts a package? provisional requirement

Today. A single-file artifact is rehashed at every activation and run from a private copy. A package is about 239 files and 121 MB, and the F# frontend starts once per compile. No outcome stops a process with write access to the home, which can rewrite the tree, the manifest, the lock and the catalog together.

  • VERIFY-A. Rehash every file at every activation, as for single files. Cost: about 0.1 to 2 seconds per compile, more with real-time scanning. It adds detection of same-size accidental corruption.
  • VERIFY-B. At every activation, check the manifest's digest and that the files match it in names, sizes and modes; rehash every file at install and on request. Published files are read-only. Cost: a few milliseconds per compile. A same-size change is found only by the full check.
  • VERIFY-C. Check only at install. Cost: nothing per compile. Deleted or truncated files surface as failures inside the guest.

Recommendation: VERIFY-B, with the read-only modes, so accidental writes fail at once rather than at the next activation. Depends on it: the spec's "Activation checks the published tree", and tasks 2.2 and 2.4.

Q-LAUNCH. Does a host start a package from the shared store, and who deletes packages? choice to confirm

Today. The design page and the installer plan start a private copy of a verified single file, and never delete store bytes. This change starts packages in place from the shared store and adds an explicit collection command, a new command surface in every host. That changes the existing activation rule, so the maintainer confirms it.

  • LAUNCH-A. As designed: start from the store, with a lease tied to the guest's process tree, and an explicit collection command. Cost: the lease and process-tree work of LIFE-1 in each host, and one command.
  • LAUNCH-B. Start from the store, but collect an unreferenced, unleased package at uninstall time, with no new command. Cost: the same lease work. Uninstall becomes slower and can fail to free space while the package runs.
  • LAUNCH-C. Start a private copy of the tree, as for single files. Cost: about 121 MB written per compile and scanning delay (VFY-1). No lease and no collection race.

Recommendation: LAUNCH-A. Depends on it: the spec's "A host starts a package's entry point from the store", the lease and collection requirements, and tasks 2.2, 2.3 and 2.6.

Later: non-ASCII entry names

Not a question to answer now. This draft limits entry names to ASCII (EXT-1). The maintainer may lift that in a later draft. Lifting it would need:

  • names required to be NFC under Unicode 17.0.0;
  • a collision rule defined in the text: for example two keys per prefix, one from full case folding and one from full uppercase mapping, because the two disagree on letters such as the dotless i;
  • a decision on code points that 17.0.0 leaves unassigned;
  • normalization and case data shipped by every host, MoonBit included;
  • a C1-control rule, and cases for all of it;
  • a new draft of the descriptor, because the change narrows what a reader may refuse.
