add-extension-packages: design

OpenSpec change | 10 November 2026 | proposed for maintainer review, nothing implemented

The reasons are in proposal.md; the normative rules are in the extension packages spec; the work is in tasks.md. Facts marked observed were read from this repository on origin/main at 9690dfc37 with its pinned submodules (ecosystem/morphir-rust at c9f79da), from the toolchain contracts on origin/feat/morphirup-deployment-acquisition at 1451c081f, and from the morphir-dotnet installer plan openspec/changes/add-extension-installation/ (finos/morphir-dotnet#567) in its local checkout. Everything else is a proposed interface unless it is marked assumption, and each assumption has a task that settles it. Requirements marked provisional depend on an open question.

Maintainer decisions of 9 November 2026 that bind this design:

  • the shared extension contract is extended so that an extension can be a multi-file package (finos/morphir#1146, the comment on the installed form of a multi-file extension);
  • the Rust CLI is legacy: work goes to the morphir-dotnet and morphir-moonbit hosts, and Rust is optional later work that gates nothing;
  • transient pre-1.0 document formats are not read or converted;
  • one installed catalog for every extension id (finos/morphir#1149);
  • MEP 0.1 is not supported; the supported protocol is the 0.2 line;
  • publisher authentication and claim checks are separate facts, and a checksum is integrity, not authentication;
  • NFC in the toolchain contracts is Unicode Normalization Form C as defined by Unicode 17.0.0 (finos/morphir#1146).

Goals and non-goals

Goals. An extension can be a tree of files that a host unpacks once, checks against a digest its descriptor names, stores immutably and starts by one entry point. Two hosts reach the same answer for every archive. A single-file artifact keeps its meaning.

Non-goals.

  • Packages for WASM, daemon or .NET tool deliveries. A WASM module is one file, and a .NET tool is installed by its own manager.
  • Symbolic links inside a package, and archive formats other than ZIP and gzip-compressed tar.
  • Sharing files between packages, deduplicating them, or applying patches between versions.
  • Any change to who is trusted, to how a repository or recipe is authenticated, or to the claim check.
  • Keeping the released Rust CLI working, or reading earlier drafts.
  • Edits to the toolchain contracts. TC-1 lists their follow-up as tasks.

Decisions

The journey below follows one artifact from release to removal: the F# frontend org.finos.morphir.fsharp-frontend 0.6.0 for x86_64-pc-windows-msvc, published as fsharp-frontend-0.6.0-win-x64.zip, installed by the Native AOT morphir host into a home on Windows, and later removed. Each decision appears where it first matters.

PKG-1. A package is an artifact with a package member

The release job has a published folder and must describe it in release.json.

{
  "platform": "x86_64-pc-windows-msvc",
  "runtime": "process",
  "filename": "fsharp-frontend-0.6.0-win-x64.zip",
  "sha256": "<SHA-256 of the archive>",
  "package": {
    "format": "zip",
    "root": "fsharp-frontend",
    "entryPoint": "morphir-fsharp-frontend.exe",
    "treeSha256": "<SHA-256 of the tree manifest>"
  },
  "claims": { "extension": { "id": "org.finos.morphir.fsharp-frontend", "version": "0.6.0" } }
}

The Linux artifact of the same release has "format": "tar.gz", "entryPoint": "morphir-fsharp-frontend" and "executables": ["createdump"].

Decision.

  • The member. An artifact is a package when it has a package member, and a single-file artifact otherwise. package has format, entryPoint and treeSha256, and optionally root and executables.
  • Formats. format is zip or tar.gz, and the file name ends in .zip, or in .tar.gz or .tgz, to match.
  • Runtime. Only process artifacts can be packages.
  • Single files. An artifact without package is read, stored, recorded and started as before, whatever its name.
  • Hosts without package support. A host that reads the package drafts but cannot install packages refuses a package with package.unsupported. It never runs the archive as if it were the program.

Why these formats. They are the two forms the toolchain recipes already bind (.zip on Windows, .tgz elsewhere), and the forms the Rust tool extractor and the .NET base class library both read. A ZIP file is the native form on Windows, and tar keeps Unix conventions on the other platforms. A third format would add a reader to every host for no artifact that needs it.

Why an explicit member, not the file name. Inferring a package from .zip would change the meaning of an existing single-file artifact whose name happens to end that way. With the member, a host reading the descriptor knows exactly what to do.

Why process only. The F# frontend is a process. A WASM guest is one module by definition, and a daemon or .NET tool is installed by other means.

It merged on 10 November 2026 as an approved proposal (9690dfc37), but its tasks have not run, so nothing is published at those drafts yet.

TREE-1. The tree manifest and two digests

The release job now needs the value of treeSha256, and every installer must compute the same bytes from the same archive.

Decision. The tree manifest is UTF-8 text: a header line, then one line per file in ascending order of the UTF-8 bytes of its tree path. Each line holds the kind, the size, the SHA-256 and the path, separated by single spaces, and every line ends with one LF:

morphir-package-tree 1
f 1153536 4a1f…e2 FSharp.Compiler.Service.dll
f 1062912 9bc0…7d FSharp.Core.dll
…
x 152576 07d3…a9 morphir-fsharp-frontend.exe
…
f 4096 c51e…10 zh-Hant/FSharp.Core.resources.dll
  • Kind. x when the path is the entry point or is listed in executables, otherwise f. It comes from the descriptor, never from the archive, so the digest is the same on every platform and for archives made on Windows, which carry no Unix modes.
  • Size and digest. The size is decimal without leading zeros. The SHA-256 is lowercase hexadecimal, over the file's bytes after decompression, with line endings and encodings untouched.
  • Path. The tree path after the optional root is removed: /-separated and NFC (EXT-1). A path cannot contain LF, because control characters are refused, so the line format is unambiguous.
  • Not covered. Directories are implied by file paths and are not listed. Owners, timestamps, permission bits and extended attributes do not appear.

The tree digest is the SHA-256 of the manifest's bytes. The artifact's sha256 stays the archive's SHA-256. Both are recorded:

DocumentArchive digestTree digest
Release descriptor and index recordartifacts[i].sha256, as todayartifacts[i].package.treeSha256
Installed catalog entry and extension lockthe artifact digest, as todaythe package member, copied unchanged
Toolset recipe and portable lockartifactSha256, as todaythrough the bound descriptor (TC-1)

Why both. The archive digest is what a repository and a recipe authenticate: it is the TUF target's hash, and a recipe binds it today. It cannot check an unpacked tree once the archive is gone. The tree digest names what actually runs, and it can be checked offline at any time against files on disk. Recording only the tree digest would break the recipe's binding to authenticated targets. Recording only the archive digest would force a host to keep or re-download every archive to check anything.

Why a manifest and not a per-file list in the descriptor. The manifest has the same information as a per-file list, but the descriptor stays small, and the bytes that are hashed are defined once. A host keeps the manifest next to the tree (STORE-1), so a per-file check needs no network.

EXT-1. Safe unpacking, as refusals with stable codes

The host downloads the archive and checks its SHA-256 against the descriptor. Now it must turn about 239 archive entries into files without writing anywhere it should not, and without two files that one file system would treat as one.

Decision. One code per rule, prefixed package., checked in a fixed order. A host reports only the first refusal. The order is the order of the table. Archive-level rules come first, then each entry in archive order, then the tree rules, then the install path.

Elsewhere a host reports package.runtime (a package on a non-process artifact), package.unsupported (PKG-1) and package.tree_changed (VFY-1).

Unicode. Paths may hold non-ASCII characters in NFC, as Unicode 17.0.0 defines it, the version the toolchain contracts pin. A host ships its own normalization and case data of that version and does not use the operating system's, for the reason the toolchain decision gives: the result must be the same on every machine. NFC is unique, so two different NFC paths are never canonically equivalent. Normalization therefore cannot make two accepted paths collide; only case can.

Collision keys. Every prefix of every path (lib, then lib/a.dll) has two keys: the NFC of its full case folding (CaseFolding.txt statuses C and F), and the NFC of its full uppercase mapping without language-specific rules. Two different prefixes collide when either key is equal. This is observed the Rust tool extractor's rule, with the Unicode version pinned. The two keys cover different cases:

  • straße.txt and strasse.txt collide by case folding;
  • ı.dll (dotless i) and i.dll collide by uppercase, as NTFS's uppercase table treats them, while case folding keeps them apart.

The rule refuses some pairs that no first-delivery file system would confuse, such as straße and strasse on NTFS. That costs nothing a real package needs.

Root. Archives made by zip -r or tar -C often wrap everything in one directory. root names that directory, so the tree does not depend on how the archive was made, and anything outside it is refused rather than silently dropped.

Sizes are counted as bytes come out of the decompressor, never taken from headers, and the host stops at the first byte past a limit. That one rule covers decompression bombs; no separate compression ratio is needed.

MODE-1. File modes

On Linux and macOS the frontend's apphost must be executable. Some .NET runtime files, such as createdump, are executable too.

Decision. On Unix a host gives x files mode 0755, f files 0644 and directories 0755, and sets no setuid, setgid or sticky bit. On Windows it sets no attribute and writes no alternate data stream; a Windows entry point is executable because it ends in .exe. Nothing else from the archive is used: not modes, owners, groups, timestamps or extended attributes. The x set is the entry point plus executables, from the descriptor.

Why the descriptor decides, not the archive. A ZIP file written on Windows has no Unix modes. A tar file has modes, but they differ between build machines. Taking the executable set from the authenticated descriptor makes the tree digest independent of the archiving tool, and means the set cannot change without changing the descriptor's digest. observed The Rust tool extractor instead marks any entry with an executable mode bit. That is the behavior this rule replaces.

STORE-1. Store layout and atomic publication

The checked files must end up somewhere that no host can read half-written, and where every later check can find the manifest.

MORPHIR_HOME/store/extensions/
  sha256/<digest>/<filename>            single-file artifacts, unchanged
  packages/
    .stage-<random>/                     staging: owner, manifest, tree/
    .trash-<random>/                     a package being collected
    sha256/<treeSha256>/
      manifest                           the tree manifest bytes
      lease                              no content; held while the package runs
      tree/morphir-fsharp-frontend.exe   the entry point
      tree/…                             the other files

Decision.

  1. Stage. The host creates packages/.stage-<random>/ on the same volume and holds an exclusive lock on its owner file throughout. It unpacks into tree/, hashing each file from the bytes it writes, then flushes each file, writes manifest and flushes it. On Unix it also syncs the directories.
  2. Verify. It applies every rule of EXT-1 and compares the manifest's SHA-256 with treeSha256.
  3. Publish. It renames the staging directory to sha256/<treeSha256>/. If that path already exists, another install published the same tree. The host verifies the existing tree in full: if it matches, the host discards its staging directory and uses it; if not, it moves the existing tree to .trash- and publishes its own.
  4. Record. Under the state lock, through the transaction journal, it writes the lock and the catalog entry with the package member.

A published package is never changed. Unpacking and hashing about 121 MB takes seconds, so steps 1 to 3 run outside the state lock. Only step 4 takes it, which keeps other hosts' commands from waiting on an unpack.

Interrupted duringWhat is leftWhat recovery does

Why key by the tree digest. The tree is what runs, and the digest that names it can be checked on disk. Two archives with the same files, for example one recompressed, share one tree. The archive is not kept. A repair downloads it again, so a home holds about 121 MB per installed frontend, not 121 MB plus the archive.

VFY-1. What verified means, and when it is checked

A project compiles many times a day, and each compile starts the frontend once. The single-file rule rehashes the artifact at every activation. Applied to a package, that rule meets 239 files and about 121 MB.

Verified means three things: the archive matched sha256, no rule of EXT-1 refused it, and the tree digest computed from the written bytes equalled treeSha256. A package that is not verified is never published, recorded or started.

CheckWhat it readsEstimated cost for 239 files and 121 MB assumption
Full verification at installThe archive, every decompressed byte, 239 writesAbout 1 to 3 seconds, once per install
Structure check at each activationThe manifest (about 25 KB) and its SHA-256, plus a listing and size of every fileAbout 5 to 30 ms; up to about 100 ms on Windows with real-time scanning
Full rehash at each activation239 opens and 121 MB of SHA-256About 0.1 to 0.3 seconds with a warm cache; 0.5 to 2 seconds cold, and more with real-time scanning
Private copy at each activation (the single-file practice)121 MB written to 239 new filesAbout 0.5 to 3 seconds, plus scanning of each new executable file, and twice the disk while it runs

The estimates assume SHA-256 at 0.5 to 2 GB/s and solid-state storage. Task 2.4 measures them on the first-delivery platforms.

Decision provisional. Open question Q-VERIFY; the spec states outcome VERIFY-B:

  • At install, and when the user asks to verify installed extensions: full verification.
  • At each activation, under the state lock:
    • the lock and catalog agree on package;
    • the SHA-256 of manifest equals treeSha256;
    • tree/ holds exactly the manifest's files, as regular files, with the manifest's sizes and, on Unix, executable bits.
    A failure is package.tree_changed, and nothing starts.
  • Under VERIFY-A: activation also rehashes every file.

Why VERIFY-B is recommended. It catches what happens in practice: deleted, truncated, added or replaced files, and a manifest edited out of step with the lock. It does so for a few milliseconds instead of a fraction of a second on every compile. What it misses is a same-size change to a file's bytes. A process running as the same user could make that change, but such a process could equally change the host or the lock, so a rehash at launch is not a security boundary against it. The full check stays one command away.

RUN-1. Activation and launch

The compile now needs the frontend running.

Decision. The host starts the entry point from the store; it does not copy it.

  • Program. The absolute path of tree/<entryPoint>, in the platform's native spelling, without a verbatim prefix, as C:\Users\dev\.morphir\store\extensions\packages\sha256\<treeSha256>\tree\morphir-fsharp-frontend.exe.
  • Arguments. The argument vector is that path followed by the locked arguments.
  • Working directory. The project directory for a project command, otherwise a new private directory outside the store, never inside it. The environment is filtered as for a single-file process.
  • Lease. While it holds the state lock after the activation check, the host takes a shared lock on the package's lease file. It keeps the lease until the started process exits: flock(LOCK_SH) on Unix, and LockFileEx without LOCKFILE_EXCLUSIVE_LOCK over the full range on Windows, the same calls #1149's state lock uses in shared form.

Windows.

  • A Windows entry point ends in .exe, compared ignoring ASCII case. That is the installer plan's recommendation in Q-WINLAUNCH: CreateProcessW starts .exe files directly, and anything else would go through a command interpreter.
  • Before it publishes, a host refuses a package with package.install_path_too_long when any of its store paths would exceed 259 UTF-16 code units. The message names the longest path and its length. The store prefix in a typical home is about 130 code units (C:\Users\dev\.morphir\store\extensions\packages\sha256\, 64 hexadecimal digits, \tree\), and a tree path is at most 120 (EXT-2), so the limit binds only for long home paths.
  • assumption CreateProcessW and the loaders of the runtimes inside a package do not accept longer paths without long-path support, so 259 is the safe limit. Task 2.5 checks this. If the assumption is wrong, the rule is relaxed for hosts that detect long-path support.

Why from the store. A private copy per launch costs a large write on every compile (VFY-1). It also gains nothing for packages, because the reasons for copies do not apply. Update installs a new tree under another digest, so no running file is replaced. Uninstall never deletes a package (REM-1). And a verified, immutable tree in the user's own home is as trusted as a copy written from it. The single-file artifacts keep their private copies; that is not changed here.

REM-1. Removal and collection

The user uninstalls the frontend while a compile is still running it.

Decision. Uninstall and update remove or replace the extension's lock and catalog entry, and never delete or change a published package. The running process keeps its files.

A separate, explicit collection command deletes packages. Under the state lock, for each published package, it requires two things: no extension lock in the home names its tree digest, and an exclusive lock on its lease can be taken without waiting. It renames such a package to .trash-<random>, then deletes it. A rename that fails, as it can on Windows while a file is open, leaves the package for a later run. Collection also removes .trash- directories and abandoned .stage- directories (STORE-1).

Why. observed Today nothing deletes store bytes; the installer plan keeps that rule ("Removal never deletes store objects"). A package is about 121 MB, so some deletion is needed. Tying it to an explicit command keeps uninstall fast and safe while the extension runs. The lease is what makes deletion safe across hosts and processes. The state lock alone cannot do it, because it is not held while a guest runs.

A toolchain generation's receipt can also point into the store. The toolchain follow-up (TC-1) says how collection treats a package that a receipt names.

TRUST-1. A package changes nothing about trust

Decision. A package does not change who is trusted. Claim checks and publisher authentication stay separate facts.

  • What a host may conclude from a verified package: its tree is the one the descriptor names. When the descriptor is authenticated, by a repository's signed targets or a recipe's digest, the tree is therefore the one its publisher released.
  • What a host may not conclude. Unpacking says nothing about the publisher. A code signature inside the tree, such as Authenticode on the entry point, is not authentication and grants nothing. The executables list grants no permission beyond the executable bit. The package's claims are still decided by the probe, run from the published tree.

An unsigned developer package from a local repository stays unsigned developer content, admitted only under explicit developer policy.

TC-1. Recipes and locks in the toolchain contracts

The toolchain contracts bind the frontend's archive today and leave multi-file artifacts open as their question M2. This change answers M2 differently from that question's recommended default: a package, not a self-extracting single file. The follow-up is task group 4, on those contracts, not edits here:

  • close M2, and make final the rule that a process provider's artifactTarget is one archive per platform;
  • state that artifactSha256 is the archive digest, and that the tree digest comes from the bound descriptor, so the portable lock needs no new member. A frozen restore already has the descriptor, because it binds descriptorTarget and descriptorSha256;
  • add the recipe consistency check that a package artifact's package.format matches the target's suffix;
  • say that a receipt's launch.program for a package names the entry point inside the published tree, and how extension collection treats a package that a receipt names;
  • regenerate the signed F# frontend fixtures as packages with a treeSha256.

CONF-1. Shared conformance cases

The .NET host and the MoonBit host must refuse the same archives with the same codes.

Decision. Publish the cases in finos/morphir, beside a normative package page, as data. Each case is a small archive file, generated deterministically by a checked-in script, plus a JSON entry naming the archive, the descriptor's package member and the expected outcome: valid with its tree digest, or the refusal code and the entry path it names. Many refusals cannot be produced with ordinary archiving tools (links, devices, .., mismatched ZIP names), so the generator writes archive bytes directly and the bytes are checked in. A runner reads the bytes, not the script.

REPO-1. Delivery order

  1. finos/morphir. This change is approved. The normative package page and its cases land, and distribution-and-acquisition.md defines the package member in the descriptor, record, catalog and lock at the package drafts (VER-1).
  2. finos/morphir-dotnet. The installer of finos/morphir-dotnet#567 installs, verifies, starts and collects packages, and runs the cases. The F# frontend is published as a package for each platform (the installer plan's adoption task 3.3). Its Q-MULTIFILE closes in favor of this form, and its Q-ARCHIVE rule "a target archive holds exactly one executable" is replaced: an archive artifact is a package, even with one file.
  3. MoonBit host. Its owning repository adopts the rules and runs the cases. Until then it refuses packages with package.unsupported.
  4. Toolchain contracts in finos/morphir (TC-1).

Optional later work, gating nothing. finos/morphir-rust's morphir-distribution could reuse its tool extractor for extension packages. Its publication path would stop refusing archives that carry a package member, and the Rust CLI could install them. No ecosystem/morphir-rust pin move is planned.

Risks and trade-offs

RiskMitigation
A same-size change to a stored file goes unnoticed until a full verification.Accepted under VERIFY-B; a same-user process could change the host as easily. The full check is one command, and Q-VERIFY lets the maintainer choose VERIFY-A.
Hosts compute different collision keys because their Unicode data differ.The version is pinned, hosts ship their own data, and the cases include non-ASCII collisions.
A long MORPHIR_HOME on Windows refuses a package that installs elsewhere.A refusal before anything is published, naming the path and its length, with a 120-unit bound on tree paths.
A guest starts a process that outlives the host, which then releases the lease, and collection removes the tree under it.On Unix the running process keeps its open files. On Windows the rename fails while files are open, and collection skips the package. Collection runs only on request.
Unused packages fill the disk.An explicit collection command; uninstall reports that the files stay until collection.
A real package needs a symbolic link.Refused with a clear code. A later draft can allow links that stay inside the root.
PKGVER-B is needed after all, and the F# guests are republished.The timing rule picks A whenever it is still possible (VER-1).
Antivirus delays the first start of each new file.Files are written once, at install, not at each launch (RUN-1).

Migration plan

Nothing is converted. Single-file artifacts are unchanged. Publishers start writing packages at the package drafts once a host can install them; the first is the F# frontend. A host that reads the package drafts but does not yet install packages refuses them with package.unsupported. Rolling back a host leaves published packages in the store, where they occupy disk until a collection by a host that knows them. No existing home holds a package, so no home needs a migration step.

Q-VERIFY. What does a host check each time it starts a package? provisional requirement

Today. A single-file artifact is rehashed at every activation and run from a private copy. A package is about 239 files and 121 MB, and the F# frontend starts once per compile.

  • VERIFY-A. Rehash every file at every activation, as for single files. Cost: about 0.1 to 2 seconds per compile, more with real-time scanning.
  • VERIFY-B. At every activation, check the manifest's digest and that the files match it in names, sizes and executable bits. Rehash every file at install and on request. Cost: a few milliseconds per compile. A same-size change to a file's bytes is found only by the full check.
  • VERIFY-C. Check only at install. Cost: nothing per compile. Deleted or truncated files surface as failures inside the guest.

Recommendation: VERIFY-B. Depends on it: the spec's "Activation checks the published tree", and tasks 2.2 and 2.4.
