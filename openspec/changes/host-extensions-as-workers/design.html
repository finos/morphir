Context

See proposal.md, "Why", for the motivation. This section records only the current state that the design builds on. Research for this design read the code in this repository, the source of moonbitlang/async 0.22.4, the Python, Elm and MoonBit extension releases, the MEP specification in finos/morphir and the Extism JavaScript SDK.

Goals and non-goals

Goals

  • The session rules (see specs/extensions/worker-sessions) exist once, as a pure MoonBit state machine, and every worker kind drives them.
  • Effects stay in adapters: spawning, pipes, threads, Web Workers, timers and the file system. This follows the repository's functional core, imperative shell rule.
  • No user-supplied helper, pin of a runtime or Node path on any route that acquisition uses.
  • Session semantics are kept: interactive order, response checks, limits, outcome classes and exit status.
  • The browser route is shown to work with real guests, with no change to the session code.
  • Any extension that conforms to MEP and to a supported runtime and ABI profile runs with no host change. The host holds no list of languages or extensions: language, file types and operations come from claims, so a Gleam or Elm extension needs no host work. The published extensions are qualification examples, not the definition of support.

Non-goals

  • Warm worker pools, a daemon or reuse of one worker across commands. morphir-ukvn.5.64.7 owns the connected daemon; it can add a channel kind later.
  • Wire cancellation. No released guest implements $/cancelRequest, so the host stops workers instead and says so.
  • A sandbox for native process workers. A native executable has the user's authority minus its environment. This is the same as today and is documented.
  • The WebAssembly Component Model and WASI preview 2. WASI preview 1 is supported only as the sandbox in WASM-4.
  • Product use of the browser host in the Workbench, and the Elm extension in a browser.
  • Any change to the Rust CLI.

One compile, from command to result

A user with no Node installed runs the native CLI on a Python file. Today this needs an extism-wasm pin, a Node runtime, three pinned helper modules and a 106 MiB Rust host. After this change the user gives only the artifact:

morphir extension compile src/loans.py --package acme/loans --ir-version 4 \
  --extension-pin python.json --output model --json
{
  "contractVersion": "0.2.0",
  "artifact": { "path": "/work/python/morphir-python-binding-0.4.2.wasm", "sha256": "10acafa0…" },
  "runtime": { "kind": "wasm", "abi": "extism-kernel-v1" },
  "descriptor": { "path": "/work/python/release.json", "sha256": "72770f73…" },
  "origin": "finos/morphir-python extension/python/v0.4.2"
}

The CLI decodes the pin into a WorkerSpec at the boundary. It reads the WASM file through a no-follow descriptor, hashes the bytes it read and writes them into a private directory. It reads the module's import and export sections and classifies it as extism-kernel-v1; the pin's declared ABI agrees. The native host cannot run WASM in its own process safely, so it starts its own executable in worker mode, as a process worker in a new process group, with an empty environment and the private directory as its working directory.

The worker process loads the module into the engine from moonrockz/extism, with a 256 MiB memory ceiling and the instruction budget. It now serves Content-Length frames on stdio. From here the host sees exactly what it would see from the Elm executable or the native MoonBit guest: a channel that carries whole MEP messages.

The session state machine sends morphir.extension.describe to a first worker, compares the live claims with release.json and stops that worker. It starts a fresh worker, sends initialize with MEP 0.1, checks the returned identity and the stable capabilities of the offered line against the claims, and, on the model line, that the agreed tuples are offered tuples in the host's order within the offered limits (SES-3), sends initialized, then morphir.frontend.compile, and checks the reply ID, shape and size. It sends shutdown and exit. Inside the worker, each request is one call of the guest's handle export; notifications are not delivered, and exit ends the instance and the process. The host confirms the process group is gone, renames model.morphir-partial to model, and writes one morphir/command-result object to stdout.

The npm CLI follows the same steps, except that the guest runs in a Node worker thread, and the channel is a message port instead of stdio. In a browser it runs in a Web Worker. The Elm executable and the native MoonBit guest skip the WASM steps and are process workers directly.

Parts and where they run

The host has one portable core and a set of adapters. The core does not know what a process or a thread is; it sees a Channel that carries whole messages and a Launcher that turns a WorkerSpec into a channel. Each host wires the launchers it supports, and that set is what Host::supports reports.

The contract acquisition uses

Acquisition (morphir-ukvn.5.64.34) gets four things, and each one maps to a requirement in specs/extensions/worker-sessions. The sketch below is the intended shape, not final code.

pub(all) enum WorkerRuntime {
  Process(platform~ : Platform, args~ : Array[String])
  Wasm(abi~ : WasmAbi?)
}

pub(all) enum WasmAbi {
  ExtismKernelV1
  MorphirBytesV1
}

pub struct WorkerSpec {
  artifact : ArtifactRef      // path and Sha256; validated at the boundary
  runtime : WorkerRuntime
}

pub(open) trait Channel {
  async send(Self, Message) -> Unit raise ChannelError
  async receive(Self) -> Message raise ChannelError
  async close(Self) -> WorkerStop          // after exit: grace, then tree stop, confirm
  async abort(Self, StopReason) -> WorkerStop
}

pub fn Host::supports(self : Host, runtime : WorkerRuntime) -> Bool
pub async fn Host::probe(self : Host, spec : WorkerSpec, deadline~ : Deadline) -> Description raise HostError
pub(all) enum Offer {
  Legacy                    // MEP 0.1: compile and generate
  Model(Array[ModelTuple])  // MEP 0.2.0-draft.1: one operation's tuples, in the host's order of preference
}

pub fn Offer::select(claims : Claims, operation : Operation, profile? : Profile, codec? : Codec) -> Offer raise Refusal
// every tuple the host supports for the operation, in the host's order (Ion, then JSON);
// a given profile or codec requires that one tuple; refuses when the claims hold none of them
pub fn Launcher::launch(self : Self, spec : WorkerSpec, limits : Limits) -> Channel raise  // frame limits come from negotiation
pub async fn Host::activate(
  self : Host, spec : WorkerSpec, expected~ : Claims, offer~ : Offer, deadline~ : Deadline, stop~ : StopSignal,
) -> Session raise HostError
pub async fn Session::compile(self : Session, request : CompileRequest) -> Outcome[Compiled] raise HostError
pub async fn Session::generate(self : Session, request : GenerateRequest) -> Outcome[Generated] raise HostError
pub async fn Session::close(self : Session) -> SessionReport
  1. Describe probe. probe runs describe and exit on a staged, verified artifact and returns identity, version and claims. Acquisition compares them with the index entry.
  2. Activation. activate takes the stored artifact, its recorded runtime, the recorded claims and an Offer. initialize must carry the protocol offer and, for model methods, the offered tuples in the host's order, so the caller chooses the offer before the worker starts. Offer::select derives it from the claims and the requested operation, so the CLI and acquisition share one selection rule. The session uses the first tuple that the worker agrees on (SES-3). A StopSignal wraps a Moon-Lander stop token; a stop interrupts a pending receive. Acquisition rehashes the stored artifact first (its own requirement); the host hashes the bytes it copies again, so the check covers the bytes that run.
  3. Calls. compile and generate pick the method from the protocol line negotiated at activation. Model calls carry the five-part tuple. Limits and diagnostics are those in the specs.
  4. Host support. supports lets acquisition offer only WASM artifacts in a browser.

The catalog records the runtime with the same fields as WorkerRuntime. The JSON form is the runtime object of the pin, so a lock entry and a pin read through one decoder.

Decisions

SES-1. The session is a pure state machine, driven one message at a time

The session core takes events (a reply arrived, a channel closed, the deadline passed) and returns the next step (send this message, wait for that ID, finish with this outcome). The driver is a short async loop that executes the steps over a channel. Tests drive the core with recorded transcripts, including those in tests/fixtures/mep-smithy, without any process.

Alternatives. Keep the pipelined batch: it cannot check claims before it sends the operation, which activation requires. Port the Rust Session type as written: it mixes effects and checks, and this repository's rules ask for a functional core.

SES-2. One session type serves MEP 0.1 and 0.2.0-draft.1

The protocol line is a closed enum. The host offers the line that the requested operation needs: MEP 0.1 for legacy compile and generate, which the Elm and Python guests use, and 0.2.0-draft.1 for model methods, which the MoonBit guest uses. The CLI picks the operation from the guest's describe answer, so a user does not choose a protocol.

Alternative. Separate session types per line. They would duplicate lifecycle and response checks, which are identical.

SES-3. The host offers every model tuple in preference order; a required format offers one

Decided by Damian Reeves, 2026-10-30. On the model line, the host offers in initialize every model tuple that it supports for the operation, in its order of preference. Today that is the Ion tuple (morphir-model, ion-binary), then the JSON tuple (morphir-ir, morphir-json). The first tuple is the host's default. The order is the only signal for the default: there is no new wire field. The worker returns the intersection of its own support with the offer, in the host's order. The Rust SDK does this in NegotiatedModelTransport::select. The session uses the first agreed tuple.

For example, a compile with no --model-format and the morphir-gleam 0.4.0 guest, which supports only JSON, offers Ion and then JSON. The guest agrees on JSON, and the compile runs with JSON. The host test in finos/morphir-gleam#31 shows this. The MoonBit guest supports both tuples, so it agrees on Ion, as before.

When the caller requires one format, for example because the user gives --model-format, the host offers only that tuple. A worker that does not support it gives an empty agreement, and the host reports extension.tuple_unavailable. Without a requirement, a worker that does not support the default is a valid partner. Only an empty agreement is an error. An answer that holds a tuple that the host did not offer, or that does not keep the host's order, is extension.agreement_mismatch. This is the code that run-core-wasm-guests-from-any-language (finos/morphir-moonbit#281) adds for an agreement that does not match what the host expects. Today the host reports such an answer as extension.tuple_unavailable.

The same rule goes into the MEP text in finos/morphir#1115 and into SEL-2 of run-core-wasm-guests-from-any-language. The first version of this design offered exactly one tuple, which Offer::select chose from the probe claims. Groups 1 and 6 implemented that version. Task 6.6 changes the code to this rule.

Alternatives. (a) Keep the one-tuple offer chosen from the probe claims. It gives the same tuple for the guests of today, but it hides the host's preference from the worker and differs from the MEP text. (b) Add a wire field that marks the default. The offer order already says it, and a new field needs a protocol change.

CHAN-1. A channel carries whole messages; framing belongs to the stdio transport

The channel API is send, receive, close and abort, like the Rust morphir_host::Channel trait that native-services/diagnostics.rs wraps. The stdio channel adds Content-Length framing with @mep.Decoder and encode_frame. A worker-thread or Web Worker channel posts one message per MEP message, so it needs no framing. Size limits are checked in each transport before a body is allocated, and again in the core.

Alternative. Make every transport carry frames, so all workers look like stdio. That adds a framing step to message ports for no benefit and moves limit checks away from the reads that allocate.

PROC-1. The native host owns spawn with its own stubs

On Unix, a C stub calls posix_spawn with POSIX_SPAWN_SETPGROUP and process group 0, dup2 of three pipes that the stub creates itself (pipe2 with O_CLOEXEC on Linux; pipe and FD_CLOEXEC under the spawn lock on macOS), and closes every other descriptor. Only the host's ends are given to the event loop, as @raw_fd.RawFdStream. @pipe.pipe() is not used: it registers both ends with epoll, and the end handed to the child keeps a stale registration that gives false readiness to a later pipe with the same descriptor number (seen as EAGAIN reads in about one Linux run in 30). Stop uses killpg, first SIGTERM, then SIGKILL, and confirms the group is empty with killpg(pgid, 0), the way supervision.mts does today. Waiting uses @process.wait_pid, which already works for any child through pidfd or kqueue. On Windows, the stub creates a job per worker with kill-on-close, starts the process suspended with PROC_THREAD_ATTRIBUTE_JOB_LIST (or assigns it before resume), and stops it with TerminateJobObject.

Alternatives. @process.spawn: no group, one PID is signalled, and grandchildren survive (moonbitlang/async#648, open). platform.c morphir_host_process: right group handling, but synchronous and buffered to files. We will offer the group support upstream; when @process provides it, the stub can go.

PROC-2. The npm CLI uses Node child_process through extern "js"

@process does not build for js. The Node adapter spawns with detached: true, piped stdio and windowsHide, reads stdout through @js_async.ReadableStream, and stops with process.kill(-pid) on Unix and taskkill /T /F on Windows, then waits for the exit event. Node cannot create a job object without the PowerShell and C# bridge that this change retires, so the npm CLI on Windows uses tree termination and reports it (see specs/extensions/process-workers).

WASM-1. The host classifies a module by ABI profile, never by extension

The host reads only the import and export sections and matches them against the import surface of two profiles, extism-kernel-v1 and morphir-bytes-v1. A module may use any part of its profile's surface; a module that imports anything outside it is refused before instantiation, with the import named. A declared ABI must agree with the classification. The profile is the contract, so a new conformant extension in any language runs without a host change, and a module still cannot gain authority that its profile does not grant.

Alternative. Accept exactly the imports of the extensions we know (the first draft of this design took the 8 imports of the Python module). Every new PDK or SDK version would then need a host change, which is the opposite of what a protocol is for.

WASM-4. The Extism import surface and what each import may do

The surface is what upstream Extism hosts offer and what the Morphir extension SDK uses. Each import is linked, and its policy decides what it can reach:

ImportsPolicy in the Morphir host
extism:host/env kernel (all 20 functions)Served by the Zig kernel module (EXT-3).
extism:host/env config_get, var_get, var_set No configuration. Variables live only for the session.
extism:host/env log_*, get_log_levelBounded diagnostics in the stderr tail.
extism:host/env http_request, http_status_code, http_headersLinked, always fail; the report records the refused request.

WASM-2. The native CLI runs WASM guests in a worker mode of its own executable

The host starts its own verified executable as morphir extension worker --abi … --module …, as a process worker. The worker loads the engine, serves frames on stdio and exits after exit. A deadline or cancellation is then a process-group stop, the same as for any process worker, and a crash in the C engine cannot take the CLI down. The host passes its build identity; the worker refuses to serve if its own differs, so a CLI replaced during an upgrade cannot serve an old host. --json in worker mode controls a startup and diagnostic report on stderr, never stdout.

Alternatives. Run the engine in a CLI thread: stopping a C engine call from outside is engine-specific and not portable, and a crash ends the CLI. Ship a separate worker executable: it needs its own pin, packaging and version check, for no gain over the CLI's own bytes.

WASM-3. Node and the browser run WASM in threads, with the same adapters

The worker entry module is MoonBit compiled to js. It uses the same classifier and adapters and the moonrockz/extism js engine, which wraps WebAssembly. The engine has no instruction metering on js, so the deadline is terminate(), and the memory ceiling is set by rewriting the module's memory maximum before compilation, as embedding/wasm-memory.mts does today. The kernel functions run inside the worker, so no SharedArrayBuffer and no cross-origin isolation headers are needed.

EXT-1. A MoonBit Extism host lives in a new repository, moonrockz/extism

Hosting Extism plugins is not specific to Morphir, and no MoonBit Extism host exists. A separate repository gives it its own release cycle and users, and keeps this repository to Morphir concerns. This repository pins its published package. See the repository section.

Alternatives. Use @extism/extism: its latest version is 2.0.0-rc13 from May 2025, it has no fuel, its maxPages does not limit guest memory, and it cannot serve the native CLI. Use libextism: a 33 to 40 MiB prebuilt Rust library with no Windows arm64 build. Keep the kernel inside this repository: workable, but it would not be reusable, and Damian proposed the separate repository.

EXT-2. The first native engine is WAMR, built from C source with Zig

WAMR is Apache-2.0 C, so the Zig already pinned in this repository builds it for every CLI platform, with no prebuilt binary and no Rust toolchain. Its fast interpreter supports the features the Python module uses (bulk memory, reference types, multi-value, sign extension, non-trapping float conversion, mutable globals). The moonrockz/extism group starts with a qualification gate: the Python 0.4.2 fixture must compile within the 30-second call deadline on the slowest qualified platform, with the Zig kernel bound as in EXT-3, and instruction metering must work. If the gate fails, the engine layer takes the Wasmtime C API, linked with Zig, as its first engine instead. The engine is behind the engine layer, so the choice does not reach this repository's code.

Alternatives. Wasmtime C API first: full parity with today's fuel, epoch and memory limits and a JIT, but a prebuilt Rust-built library of about 13 MiB compressed per platform. wasm3: in minimal maintenance.

EXT-3. The Extism kernel is written once in Zig and shipped as one WASM module

Official Extism does not run its kernel as host code. Its kernel is a small no_std Rust crate compiled to WASM (runtime/src/extism-runtime.wasm, 3,474 bytes), with its own linear memory, linked into the plugin's store under extism:host/env. The plugin's kernel imports are then calls from one WASM module to another, and the host reads the output from the kernel's memory through output_offset and output_length. The Go, Java, Erlang and WAMR SDKs embed that same file. The JavaScript SDK is the exception: it has a second kernel written in JavaScript.

moonrockz/extism writes the kernel in Zig, about 300 lines with no libc, and compiles it to wasm32-freestanding with an explicit CPU feature set that every engine we use supports. The .wasm is embedded as bytes in the MoonBit library. The same artifact then runs on native (WAMR), Node and browsers, so the block allocator, handle encoding, out-of-memory behavior and limits are identical everywhere. That is a stronger guarantee than upstream gives. The kernel keeps the upstream export names and signatures (20 functions, including the 8 that the Python plugin imports). It leaves out the upstream extism_context externref global, so it needs no reference types.

Binding differs only per engine. On js the host passes the kernel instance's exports as the plugin's imports. On WAMR the first binding is the pattern that extism/wamr-sdk already uses: each kernel import is a native function that calls the kernel instance. WAMR's load-time multi-module linking is measured as an alternative and kept only if it is faster and works in the interpreter mode we use. A native C-ABI build of the same Zig source is added only if measurement shows that forwarding is too slow; both builds then run the same Zig tests.

Alternatives. A kernel in MoonBit: portable across MoonBit targets, but every engine binding would call back into host code for every byte the guest reads, and nothing else could use it. A native Zig static library first: the fastest on native, but Node and browsers would need a second kernel, which repeats the split in upstream Extism.

CLI-1. Explicit pins move to contract 0.2.0; helper options are retired

A pin now names an artifact and a runtime, the same shape the catalog records. Old pins named a helper, a Node runtime and twelve host modules, and none of those exist on the new host. Old pins and the options --extension-helper and --node are refused with a pointer to the migration section, not ignored. The binding field disappears, because the runtime and the classified ABI determine the route.

CLI-2. One report and one exit table for every route, as a deliberate break

Today the portable route writes a morphir/cli/extension-command report and exits 2 on refusal, and the native and Extism routes write morphir/command-result and exit 1 on an expected refusal. With one host, the commands write morphir/command-result 0.1.0 and keep the portable route's exit table (0, 1, 2, 124, 130), which is the documented and more precise one.

This breaks the existing successful JSON schema of the portable route. AGENTS.md normally forbids that: commands that already emit JSON keep their successful result schema, and command-result is the standard for new results only. The maintainer decided on 30 October 2026 that, at this stage of the CLI, a clean break is better than carrying two report schemas. This decision is an explicit exception for these three commands, made together with the pin break in CLI-1. The breaking-change notes in group 9 list the old and new fields so that consumers can migrate.

Alternatives. Keep extension-command for every route, which preserves the portable consumers but leaves the extension commands as the only ones without the standard envelope. Or add a versioned report option, which keeps both schemas alive.

BRW-1. The browser proof uses real guests and the product session code

A Playwright test loads a page that runs the browser launcher and the session core, compiled to js, against the MoonBit portable guest and the Python extension. It checks describe, compile and generate results against the Node results, a runaway guest stopped by terminate(), and refusal of a process artifact. The Elm extension needs a WASM or worker-module asset from finos/morphir-elm; that is a separate request to that repository, not part of this change.

MIG-1. No Rust bridge

The new host uses no Rust host library. The existing helper routes stay as they are, with no new work, until the new host is qualified (group 7). Group 9 then removes them. This is the only overlap, and it ends inside this change.

Risks and trade-offs

  • [WAMR's interpreter is too slow for Python compiles] → The EXT-2 gate measures the real fixture first; the Wasmtime C API is the named fallback, behind the same engine layer.
  • [A conformant guest needs a WASI function that the sandbox answers with an error] → The guest fails with its own diagnostic, not a host refusal. Conformance fixtures built with the Rust, Zig and JavaScript PDKs exercise the functions those toolchains call at start-up, and the sandbox adds a function only with a reviewed policy.
  • [Calls between the plugin and the kernel instance are slow on WAMR] → The EXT-2 gate measures the Python fixture with the forwarding binding first. Multi-module linking and a native build of the same Zig kernel (EXT-3) are the measured alternatives.
  • [WAMR has no maintained build.zig, and Windows MSVC needs MASM files that Zig cannot assemble] → moonrockz/extism owns a build.zig that follows WAMR's CMake source selection, and uses WAMR's general C invokeNative on Windows. Windows linking against the MSVC C runtime is checked in group 4 before any other platform work depends on it.
  • [Zig releases break source compatibility] → The Zig code stays small, and the Zig version is pinned with the repository's existing pin.
  • [Instruction metering is missing on js and may be missing in a WAMR build] → Deadlines and the memory ceiling always apply; the report lists the instruction budget as not enforced where it is not.
  • [A grandchild that ignores stdin end of file survives a killed CLI on Unix] → Host exit closes stdin and the released guests exit on end of file. Linux parent-death signals need a fork path; we document the limit and revisit it if a guest needs it.
  • [Windows qualification uses scarce runners] → One deliberate qualification run per release candidate, reviewed by the build-master; no new per-push Windows job. Results carry a Tested-on: trailer.
  • [The new repository delays this repository] → Groups 1, 2 and 3 do not depend on it. Group 5 can develop against a local path dependency and lands only on a published version.
  • [The CLI binary grows by the engine size] → Measured in group 5 and reported in the pull request; WAMR's interpreter is expected to be about 1 MiB.
  • [Breaking pins, the report profile and exit codes for scripts] → Only explicit pins are affected; refusals point to a migration section with before and after pins; the qualification tasks are rewritten in the same group.
  • [Self re-execution finds a different executable after an upgrade] → The build identity check in WASM-2 refuses the mismatch with extension.worker_runtime_mismatch.

Migration plan

  1. Groups 1 to 6 add the host and wire the commands to it. Old pins keep working on the old routes until group 6 switches the commands; the switch and the new pin contract land together.
  2. Group 7 qualifies the published extensions on the new host. Qualification tasks (test:portable-mep-cli, test:cli-native-prerequisites, test:cli-extism-python) are rewritten to use 0.2.0 pins.
  3. Group 9 removes the TypeScript helpers and the invocation role of the Rust native-services helper. Acquisition removes the helper's distribution role in its own groups.
  4. Rollback before group 9 is a revert of the group 6 switch. After group 9 it is a revert of that group.
