allow-dotted-extension-ids: design

OpenSpec change | 9 November 2026, revised 10 November 2026 after review | merged as a proposal (9690dfc37), nothing implemented

The reasons are in proposal.md; the normative rules are in the extension identity spec; the work is in tasks.md. Facts marked observed were read from this repository on origin/main at 04143a238, with its pinned submodules, and from morphir-dotnet's origin/main at e8837c3e. The 10 November revision re-read the Rust facts at the same ecosystem/morphir-rust pin, c9f79da. Everything else is a proposed interface unless it is marked assumption. Requirements marked provisional depend on an open question and state each outcome.

Three maintainer decisions of 9 November 2026 shape this design:

  • the Rust CLI is legacy, and work goes to the morphir-dotnet and morphir-moonbit hosts first ("we want to focus on morphir-dotnet and morphir-moonbit hosts and only possibly invest in Rust once 1 or both of those 2 are functional"); Decision 16 has since gone further (below);
  • transient pre-1.0 document formats are not read or converted ("we are paying too much of a cost to support transient pre 1.0 contracts");
  • one installed catalog, rather than a separate partition for dotted ids, with older hosts not protected ("we don't have users to support the cost of maintaining 2 versions").

A fourth, of 10 November 2026 (Decision 10), answers what a host does with a home that an older CLI wrote: it moves the old state aside after asking, --yes skips the question, and morphir doctor --fix runs the same repair by hand (OLD-1). Decision 11 confirmed its four readings. Decision 13 makes morphir-dotnet's bundle authoring the publisher of every extension at the new version (REPO-1).

Two more of 10 November 2026 change this design:

  • Decision 15. One preview version per contract family, carried by a required $schema URL instead of per-file versions; a format not ready for 1.0 is 0.x.0-preview.N, matched exactly (AGENTS.md, "Contract Versioning"; morphir-cli decision 0004). The extension state family is the release descriptor, the index record, the installed catalog, the extension lock, the transaction journal, the repositories configuration and the capability claim set, and it restarts at 0.1.0-preview.1 (VER-1).
  • Decision 16. The Rust CLI is to be deleted from finos/morphir, not only retired: "I want it to be clear that the Morphir CLI actually comes from .NET". Its exact scope is still being settled. This change therefore plans no Rust reader or writer work, and no Rust CLI is a host it keeps working.

Context

Today one rule, in one place, decides what an extension id may be: the Rust implementation. The table below says where ids live and what each place enforces. These rows describe today's Rust code, which is to be deleted (Decision 16) and is used here only as evidence of today's behavior. After this change the contract pages define the rule and the shared files (DEF-1), and the Rust source is not the authority.

Goals and non-goals

Goals. One id grammar for every host and contract. Dotted ids are published, installed, locked and bound end to end. The shared home and repository files have one definition, on the contract pages, that every installer follows.

Non-goals.

  • No namespace registry, reservation or verification of reverse-DNS prefixes.
  • No renaming of any existing extension, and no change to shortId, to release tag conventions or to the content-addressed store.
  • No change to the MEP protocol versions (the 0.2 line). The capability claim set joins the extension state family (VER-1).
  • Hosts that predate this change are not protected. A writer writes the family version in every home and repository, including one that a host reading only earlier versions also uses. That host refuses or fails on each such document. Keeping it working is not a goal, and neither is reading or converting earlier versions. This was a requirement before the 10 November revision; it is a non-goal because no current implementation can be tested against it.
  • No work on the Rust distribution library or the Rust CLI. The Rust CLI is to be deleted (Decision 16).
  • Binding providers from several repositories in one recipe stays later work.

Decisions

The journey below follows one extension from release to use: morphir-dotnet's F# frontend, org.finos.morphir.fsharp-frontend 0.6.0, whose guest already reports that id. Each decision appears at the step where it first matters.

ID-1. The grammar

The release job writes release.json. The first question is whether org.finos.morphir.fsharp-frontend is a well-formed id at all.

Decision. Adopt morphir-dotnet's rule as is: one or more segments joined by .. Each segment starts with a lowercase ASCII letter, contains only lowercase ASCII letters, digits and -, and ends with a letter or digit. A single-token id is the one-segment case, so every id valid today stays valid and means the same extension.

Why. It is the rule the guests already use. It only adds the . separator, and every character an id can contain is safe in a file name on all first-delivery platforms. Lowercase-only ASCII means case-insensitive file systems cannot fold two ids together. The toolchain contracts' provider identity grammar is not yet this rule: it limits segments to 64 characters and has no device-name rule. Group 4 of the tasks aligns it (REPO-1).

{
  "$schema": "https://morphir.finos.org/schemas/extensions/0.1.0-preview.1/release.schema.json",
  "extensionId": "org.finos.morphir.fsharp-frontend",
  "shortId": "fsharp-frontend",
  "version": "0.6.0",
  "platformDifferences": "none",
  "artifacts": [ { "platform": "x86_64-pc-windows-msvc", "runtime": "process",
    "filename": "win-x64.zip", "sha256": "<64 hexadecimal digits>",
    "claims": { "extension": { "id": "org.finos.morphir.fsharp-frontend", "version": "0.6.0" } } } ]
}

ID-2. Lengths and device names

Before the release is accepted, its id must be safe to turn into file names on Windows, macOS and Linux.

Decision. The total limit stays at 238 characters, dots included, and there is no per-segment limit. The first segment must not be con, prn, aux, nul, com1–com9 or lpt1–lpt9.

Why. 238 is the existing budget: the longest name derived from an id is <id>.json.transaction, which must fit a 255-unit file name component. Dots do not change that arithmetic. A per-segment limit, for example the 64 characters the toolchain contracts apply, would make valid single-token ids of 65 to 238 characters invalid. That would be a breaking change, so the toolchain contracts align to this rule instead (REPO-1).

The device-name rule is what upstream already enforces for single tokens: con is refused today. Windows treats the part of a file name before its first dot as the device stem, which is why the rule applies to the first segment only. acme.con is a valid id, and con.example is not.

morphir-dotnet's rule lacks this check, so as written it accepts con.example. That id would then fail on a Windows store, so morphir-dotnet adopts the refinement (REPO-1).

COM0, LPT0 and the superscript digits. The review of 10 November suspected that Windows also reserves COM0 and LPT0. Microsoft's current page, Naming Files, Paths, and Namespaces (dated 28 August 2024, source commit 63e70903, read 10 November 2026), lists the reserved names as "CON, PRN, AUX, NUL, COM1, COM2, COM3, COM4, COM5, COM6, COM7, COM8, COM9, COM¹, COM², COM³, LPT1, LPT2, LPT3, LPT4, LPT5, LPT6, LPT7, LPT8, LPT9, LPT¹, LPT², and LPT³". It does not list COM0 or LPT0. The page's NT namespace section mentions "COM0 and COM1 under the 'Global??' subdirectory" as symbolic links to serial devices, but that describes the device namespace, not the reserved file names. So the rule does not add com0 or lpt0: the documented list does not name them, and adding them would make ids that are valid today invalid, against ID-1. A case pins com0.tools and lpt0 as valid. If Microsoft's list changes, adding them is a grammar change and takes a new draft. The superscript forms need no rule: the grammar admits only ASCII, so com¹ is refused as grammar before the device-name rule is reached. CONIN$ and CONOUT$, which upstream also refuses as file names, cannot be ids because $ is not in the grammar.

Which rule a refusal names. An id can break several rules: con..x has an empty segment and a device-name first segment. So that two hosts report the same rule, the rules are checked in a fixed order, grammar, then length, then device-name, and a refusal names the first one broken. The shared cases record that name.

Path budget. docs/spec/draft/names.md budgets IR distribution trees, not Morphir home, but its warning about Windows MAX_PATH applies. Derived names sit under MORPHIR_HOME/locks/extensions/ and extensions/ in a repository. A 238-character id is already possible today, so dotted ids add no new path length risk; Risks keeps the long-path note.

PATH-1. Names derived from an id

The repository publishes the release, and later a host installs it. Each of them writes files named after the id.

Decision. Keep every derivation as it is: the whole id followed by a fixed suffix, in the directories every id already uses. In the catalog the id stays a member value: extensions is an array of entries, each with extensionId, at most one entry per id, in ascending byte order of the id. No layout changes.

Why it is safe. Appending a fixed suffix is injective, so two different ids can never derive the same name. Ids are lowercase ASCII, so case-insensitive file systems do not fold them together.

  • acme.tools.json and acme-tools.json are different files.
  • An id may end in a segment that looks like a suffix. x.json's lock is x.json.json, distinct from the lock and journal of x.
  • observed The Rust index reader uses Path::file_stem, which removes only the last extension, so org.finos.morphir.fsharp-frontend.jsonl yields the full id. The contract page states the rule itself: the id is the file name without its final .jsonl.
  • The compile cache keeps dots in its sanitized segment and appends a hash, so it needs no change.

BIND-1. Descriptor, claims and session ids stay equal

At publication and installation the host probes the guest, and at first use it initializes a session. Each of these compares the guest's reported id with the descriptor's.

Decision. The rule that the descriptor id equals the claims id, and that both equal the session id, stays exactly as it is: byte equality, no mapping, no normalization. A dotted id is never shortened to a single token anywhere.

Why. This equality is what lets a recipe or lock bind an extension. The descriptor filed under a name is the one whose artifacts claim that name and report it when they run. The failure paths stay as they are: authoring, publication and installation refuse a release whose claims name another id, and the host rejects a session that reports another id before calling the extension.

TRUST-1. A name is not a credential

A user installing org.finos.morphir.fsharp-frontend might read the prefix as a statement about who published it.

Decision. A requirement states that an id is a name only. Nothing verifies domain ownership, and an id grants no trust, permission, precedence or built-in status. Publisher authentication, by authenticated repository targets and recipe digests, and the claim check stay separate facts.

Why. Reverse-DNS ids invite exactly this misreading. Writing it down as a requirement, with a scenario, gives reviewers and implementers something to test against: an unsigned developer artifact named org.finos.… is still an unsigned developer artifact. Reserving or verifying namespaces for publishers would need a registry, keys and a policy that do not exist; that is out of scope (open question Q-PREFIX).

A host rule that already exists. On 9 November 2026 the maintainer decided, for finos/morphir-dotnet, that every id starting with morphir. is reserved for built-in frontends and backends, and that org.finos.morphir.* is not reserved. That rule stops an installed extension from passing itself off as a host's built-in: the .NET host refuses to install morphir.example. It does not give any id trust, and it is not a publisher namespace. The requirement allows it in so many words: a host may refuse ids under a prefix it keeps for its own built-ins, and the refusal grants nothing. Whether every host must keep the same prefix is not asked here; this change does not make it a shared rule.

VER-1. One family version, carried by a schema URL, written for every id

The descriptor reaches hosts of different ages, and it must say which grammar its ids follow.

Decision (Decision 15, 10 November 2026). The extension state family has one version, 0.1.0-preview.1. The family is the release descriptor, the repository index record, the installed catalog, the extension lock, the transaction journal, the repositories configuration and the capability claim set.

  • The schema URL carries the version. Every document has a required $schema member, written first, whose value is its file's URL: https://morphir.finos.org/schemas/extensions/0.1.0-preview.1/<file>.schema.json. The files are release, index-record, catalog, lock, journal, repositories and claims. There is no schemaVersion member.
  • Claims. A claim set inside a descriptor, record or catalog entry carries nothing of its own; the enclosing document's schema covers it. A claim set that stands alone, as morphir.extension.describe returns it, carries the claims URL in place of claimsVersion.
  • Unchanged. MEP versions stay the 0.2 line. The id is still an unconstrained string there.

A writer writes the family's URLs in every document, whatever the form of the ids in it.

Why a new version rather than keeping the earlier ones. Under the earlier per-file rule these documents had reached 2.0.0-draft.3, and the lock and journal 2.0.0-draft.1, though nothing here is ready for 1.0. The maintainer replaced that rule: one version for the set, a preview label below 1.0, and a published schema that carries it. The new URLs also keep the property the earlier drafts were for. A document's $schema says exactly which grammar its ids follow, so an earlier host never reads a dotted id as if it were a single token. That host finds no schemaVersion it reads, and refuses or fails before reading any id.

Why for every id. An earlier version of this design wrote new versions only for documents that name a dotted id. That rule existed only so that existing documents stayed byte-identical for earlier hosts, and keeping those hosts working is no longer a goal. One URL per file means a current host reads one version (VER-2) and a writer never chooses a version by content.

Each file needs its schema published. The schemas are not written in this change. Task 1.7 publishes them under website/static/schemas/extensions/0.1.0-preview.1/, which the site serves at https://morphir.finos.org/schemas/extensions/0.1.0-preview.1/.

VER-2. Readers read the current schema URLs only

Decision. A reader accepts a document of the family only when its $schema is that file's current URL, compared as exact text. It does not read any other document, including every document an earlier host wrote with a schemaVersion member ("1.0", major 1, 2.0.0-draft.1, 2.0.0-draft.2), and journals at integer 1. Nor does it read a later preview's URL: a preview promises nothing to the next. No conversion between versions is part of the contract. A reader that meets another document refuses it and names the file and the URL it reads.

Why. It follows the maintainer's decision that transient pre-1.0 formats are not read or converted, and it is what the author of finos/morphir-dotnet#567 asked for. The earlier versions were written only by the Rust tooling and the Rust CLI before 1.0. The merged text said a reader "need not" read earlier versions. That let one host read draft.2 and another refuse it, so the two would report different outcomes for the same shared case. "SHALL NOT" makes every host refuse.

What this means for an existing home is OLD-1, and for existing published releases HIST-1 and Q-PUBLISHER (Decision 13).

STATE-1. One catalog, one lock directory, one history directory

Ada's home already holds morphir-elm. She installs the frontend with the .NET host.

Decision. Every id, dotted or not, lives in the same places:

Accepted cost. An older host is not protected. observed The Rust CLI loads catalog/extensions.json whole before every install, update, uninstall, list and activation, and its extension search and extension repository verify read every history in extensions/. So once a current host has written a home's catalog, every extension command of an older CLI in that home fails on it. Once a repository holds a current record, an older client's search and verification of it fail. The maintainer accepted this: "we don't have users to support the cost of maintaining 2 versions".

What a user of a released older CLI sees, and how to get back. The Rust CLI is to be deleted (Decision 16), so this is only for a user who still has a released copy. It cannot read catalog/extensions.json. Removing the dotted extensions does not help, because the catalog stays at the family version. To use the older CLI again, the user needs three things:

  • Its own Morphir home (MORPHIR_HOME), where they reinstall its extensions.
  • Its repositories again. config/extensions/repositories.json lives in the home, so a new home starts with no configured repositories, and the user re-adds each one.
  • Repositories that no current writer has published to. A separate home does not help with a shared repository. observed The older CLI's extension search reads every history and stops at the first error, and resolving an id whose history holds a current line fails at that line. So a repository that both CLIs publish to, such as a local one, is unusable by the older CLI once a current writer has added a current record. The older CLI needs a repository of its own.

Why. One catalog is the layout every host already uses, so there is one set of files to define and test, no partition invariant and no wrong-partition refusal.

What this change does not yet define. It fixes each file's path, schema URL, encoding, unknown-member rule, locking and recovery. It does not give the member tables of a catalog entry, an extension lock or the repositories configuration. Those tables are task 1.4's work on the design page, whose home-layout cases then carry whole expected documents. Writing them here would copy the Rust structs into the change before the page is reviewed. So an installer cannot be built from this change alone. Task 1.4 unblocks finos/morphir-dotnet#567, and until it lands the Rust source is the only statement of those members. The merged text and the first revision of this design claimed more than that, and this paragraph replaces the claim.

Encoding and equality. Every shared JSON document is UTF-8 without a byte order mark, and is I-JSON (RFC 7493). No member name repeats in an object. Every number is an integer written without a fraction or an exponent, so 123.0 is refused where 123 is meant. Strings compare code point by code point without normalization. Array order is significant. An absent member differs from a member set to null, and null is refused unless the member allows it. Two installers conform when their documents are equal as parsed values; bytes, member order, spacing and line endings may differ. A reader refuses a catalog whose entries are out of order or name an id twice: the order is a reader rule as well as a writer rule. The home root is MORPHIR_HOME when it is set and not empty, and otherwise .morphir in the user's home directory, as today. Where a page and the Rust source differ, the page wins.

Recursive member-policy correction. The enclosing document's rule applies at every nested object, including packages, source/provenance, summaries, languages and embedded claims. Locks close their embedded claims; open documents keep nested metadata open unless critical. This corrects inconsistent schema contexts without changing the approved rule.

Unknown members. The three documents that carry a claim set keep the page's existing rule 1, "must-ignore unless critical". The lock, the journal and the repositories configuration stay closed: an unknown member is refused. That is what observed the Rust readers do today, and finos/morphir-dotnet#567 keeps its .NET-only facts in its own inventory because the lock is closed. Opening the lock would let each installer add members the others drop on their next write.

The repositories configuration joins the family. The first revision kept it at version 1, so that a user's configured repositories survived the move of OLD-1 and the Rust-written path spelling stayed readable. Decision 15 puts it in the family, so it carries the repositories URL like every other file. A repositories file an older CLI wrote, at schemaVersion 1, is now old state: the move takes it to the backup too, and the user re-adds their repositories. That is the one cost this adds to Decision 10's move. It also means a current host never reads a Rust-written repository path, so the verbatim-path reader rule is gone (DEF-4).

Why. observed Today neither the page nor a published schema states the grammar or the catalog, journal and repository-configuration members; the Rust code is the rule. The Rust CLI is now legacy, so it cannot stay the definition that the .NET and MoonBit hosts must match. The merged text listed the descriptor, record, catalog, lock, journal and state lock, but left out the repositories file and its lock, the journal's version and encoding, the unknown-member rules, path spelling, temporary files and the lock primitive. Two hosts could follow it and still not see each other's repositories, replay each other's journals or exclude each other. Byte equality would tie every installer to one JSON serializer's spacing and key order without making two homes mean anything different.

DEF-2. The transaction journal

Ada's install of the frontend changes two files: its new lock and the catalog. If the process stops between them, the next host to take the state lock must finish or undo the change.

Decision. The journal keeps its path, locks/extensions/<id>.json.transaction, and its two saved files, and carries the family's journal URL:

{
  "$schema": "https://morphir.finos.org/schemas/extensions/0.1.0-preview.1/journal.schema.json",
  "nextLock": [123, 10, 32, 32, 34, …],
  "nextCatalog": [123, 10, 32, 32, 34, …]
}
  • nextLock and nextCatalog are both present. Each is null, meaning the file is to be absent, or an array of integers from 0 to 255 holding the file's exact bytes. This is today's encoding.
  • One at a time. A host does not write a journal while another exists. observed Rust's cleanup_committed_journal only logs "transaction journal cleanup deferred" when it cannot remove a committed journal. So one lock hold that commits two extensions can leave two journals, each with a whole catalog, and replaying them in directory order can restore the older catalog last. Here a host that cannot remove a committed journal fails the command and reports it, and the next state command recovers it before anything else.
  • Order under the state lock.
    1. Detect old state. Read each file's $schema, and read the journals in full. Old state is a catalog, extension lock, journal or repositories configuration whose $schema is missing or not its current URL, more than one journal, or a journal that fails its checks.
    2. If there is old state, release the state lock and offer the move of OLD-1 (Decision 10); recover nothing from old state.
    3. Otherwise recover the one journal, if there is one: write the lock, then the catalog, then remove the journal.
  • The checks. A journal passes when its $schema is the current journal URL and its saved lock and catalog pass full validation, as each document's reader validates it, including ids, order and critical members. "Valid JSON at a version" was too loose: two hosts could differ on a saved catalog with an invalid id.

Why a refused journal is old state. A journal that fails its checks, or a second journal, cannot be replayed. Refusing it alone would wedge the home, because no command would clear it. Treating it as old state gives it the same way out as an older CLI's files: the move to a backup of OLD-1. Detection runs first, so a home that the Rust CLI left mid-install reports old state with the way out, rather than a journal refusal with none.

Why the journal carries a URL. observed Today recovery writes a journal's saved bytes without parsing them. A journal left by an older CLI holds a "1.0" lock and an earlier catalog, so replaying it would write earlier-version files back into a current home. Under VER-2 a current host must not read the old journal at all, and the $schema is how it tells the two apart: an older journal has an integer schemaVersion and no $schema.

Why check the saved documents. The check costs one parse of two documents that recovery would otherwise write blind. It makes "recovery never writes an earlier-version file" something a case can test, whatever wrote the journal.

Why keep the byte arrays. They are unambiguous, and they are the encoding journals already use. Base64 would be shorter, but it adds a second encoding choice (padding, alphabet) for implementers to agree on, for a file that exists only while a change is in flight.

DEF-3. The state lock primitive

The .NET host and, later, the MoonBit host may run at the same moment against Ada's home. "An OS lock" is not enough for them to exclude each other.

Decision. Both lock files are taken with one primitive per platform:

PlatformPrimitive
Linux, macOS and other UnixOpen with open(path, O_RDWR | O_CREAT | O_CLOEXEC, 0644), take no other lock on the file, then flock(fd, LOCK_EX), which blocks
WindowsOpen with read and write access and FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE, then LockFileEx with LOCKFILE_EXCLUSIVE_LOCK and without LOCKFILE_FAIL_IMMEDIATELY, from offset 0, over 0xFFFFFFFF low and 0xFFFFFFFF high bytes, which waits

The state lock is held from before old-state detection until after the last write or removal of the catalog, a lock or a journal. The repositories lock is held around each read-modify-write of the repositories configuration. A host never holds both at once; observed Rust takes them one after the other (repository.rs, state.rs). A host waits for the lock. It may give up after a time it reports, but it never goes on without it. A host creates an absent lock file, writes nothing to it and never removes it.

Why these calls. They are what observed the Rust host uses through fs2 0.4.3, which calls LockFileEx(handle, flags, 0, !0, !0, …). On Linux, flock locks and POSIX fcntl record locks do not interact: flock(2) says "there is no interaction between the types of lock placed by flock()". So a host that used record locks and a host that used flock could both hold "the lock" at once. On Windows a lock over a zero-length range conflicts with nothing, so the range must be named. Without LOCKFILE_FAIL_IMMEDIATELY, LockFileEx on a synchronous handle "waits until the lock is granted" (Microsoft).

Why the open is specified. A host that opens the file the wrong way fails at open instead of waiting. On Windows, .NET's FileStream opened for writing shares only reading by default, so a second host's open hits a sharing violation before it reaches LockFileEx. On Unix, observed .NET takes an advisory lock of its own when it opens a file. SafeFileHandle.Unix.cs in dotnet/runtime (main at 275ff40c) calls FLock(this, lockOperation | LOCK_NB), with LOCK_EX for FileShare.None and LOCK_SH otherwise. When that returns EWOULDBLOCK it throws. So while another host holds LOCK_EX, a .NET FileStream or File.OpenHandle open of the lock file throws instead of waiting. And while a .NET host holds an ordinary FileStream on the file, its hidden LOCK_SH blocks every other host's LOCK_EX. The .NET host therefore opens the lock file with a direct open call, or sets the runtime switch System.IO.DisableFileLocking (environment variable DOTNET_SYSTEM_IO_DISABLEFILELOCKING), and then calls flock itself. Tasks 2.3 and 3.2 check this with a test that runs two processes, because a data case cannot hold a lock.

Homes on network file systems. They are not supported, because the primitive does not keep its guarantees there. flock(2) says: "Since Linux 2.6.12, NFS clients support flock() locks by emulating them as fcntl(2) byte-range locks on the entire file", and "Since Linux 5.5, flock() locks are emulated with SMB byte-range locks on the entire file". So the no-interaction property above fails, and a lock across a network also depends on the server. A host that can tell, for example from statfs on Linux or macOS or from GetDriveTypeW returning DRIVE_REMOTE on Windows, refuses state commands and names the home. A host is not required to detect it; the contract promises nothing there.

DEF-4. Path spelling and temporary files

Ada adds a local repository, C:\ext-repo, with the .NET host. Later the MoonBit host updates the frontend from it, and must find that repository again from the lock.

Decision on paths. endpoint.path in the repositories configuration and index.identity in a lock are the absolute path of the repository root with symbolic links resolved: what realpath reports on Unix, and what GetFinalPathNameByHandleW with FILE_NAME_NORMALIZED reports on Windows.

  • A writer does not write the verbatim prefix \\?\. It writes \\?\UNC\server\share\… as \\server\share\…, a drive letter in uppercase, and no trailing separator except at a volume root (D:\).
  • On Windows the path is what GetFinalPathNameByHandleW with FILE_NAME_NORMALIZED and VOLUME_NAME_DOS reports for the open root. A .NET host calls it through a platform call; assumption the base class library has no equivalent (task 2.3). That call, not the typed path, decides the spelling: a subst drive, an 8.3 name or a typed C:\Ext-Repo on a volume that stores ext-repo each become what the call reports. assumption For a mapped network drive, the call's result is a UNC path (task 2.3).
  • A reader refuses a repository path that carries the verbatim prefix, and compares paths by their bytes.
  • On Unix, realpath keeps the typed case in a case-folding directory, so /srv/Repo and /srv/repo stay two repositories there. That is a stated limit, not a rule to fold case.

Why the reader rule changed. The earlier revision read a prefixed path as the plain one, only so that repositories files the Rust CLI wrote at version 1 kept working. Decision 15 puts the repositories file in the family (DEF-1), so a Rust-written file is now old state and is moved aside, not read. No current writer produces the prefix, so a current file that holds one is wrong and is refused.

Why no verbatim prefix. observed The Rust host stores fs::canonicalize's result, which on Windows is the verbatim form, for example \\?\C:\ext-repo. The prefix is a Win32 API instruction to skip path parsing, not part of where the directory is. Other runtimes, .NET's path functions among them, do not produce it. If one host wrote it and another did not, the same repository would have two spellings and a byte comparison would treat them as two.

Decision on temporary files. A writer replaces a shared file by writing a temporary file in the same directory, flushing it, and renaming it over the target. Its name starts with .stage-. Every reader of catalog/, locks/extensions/ or a repository's extensions/ ignores entries whose names start with ., and entries that are not regular files. No id, and so no derived name, starts with ., so the rule cannot hide a real file.

Why. observed Rust's atomic_write_bytes leaves .stage-… files beside the target when a process stops mid-write. Today's journal scan skips them only because their names do not end in .json.transaction. A second host listing the lock directory needs the rule stated, not inferred.

HIST-1. A history holds one version

The morphir-elm maintainers publish 0.8.0 with a current publisher into an existing repository, whose extensions/morphir-elm.jsonl already holds 0.6.0 and 0.7.0 as lines with schemaVersion 2.0.0-draft.2. Histories are append-only.

Decision. A history is read whole. Lines are separated by LF and numbered from 1, and a line of only JSON whitespace is skipped but counted. Each line carries its own $schema. If any line is not an index record whose $schema is the current index-record URL, the reader refuses the whole file, names it and the first such line, and selects no release from it. A publisher does not append a current line to a history that holds a line without the current URL; it refuses the same way and leaves the file unchanged. An existing extension gets a current history when morphir-dotnet's publisher writes its next release, starting the history again (Q-PUBLISHER, Decision 13).

Why each line carries $schema. A JSONL file has no header line today, and every line is one index record, read and checked on its own. The two choices:

  • Per line, chosen. Each record is a complete JSON document that validates alone against index-record.schema.json, as an editor or a validator sees it. Readers already parse line by line, the mixed-history rule stays a per-line test, and a publisher appends a line without rewriting a header. The cost is the same URL repeated on every line, about 90 bytes each.
  • A header line for the file, not chosen. It would change the format: line 1 would be a different kind of document from the others, and a record copied out of the file would no longer say what it is.

Why refuse the file, not skip the line. A reader's history checks need every line. Two examples: that versions are not published twice, and that every record names the history's id. A reader that skipped 0.7.0's earlier line would accept a later current line that published 0.7.0 again with other bytes. Skipping would also make the revision digest, which a lock pins, cover lines the reader never read. observed The Rust reader already refuses the whole file at the first unsupported line, and refuses a history that names two ids or publishes one version twice (index.rs parse_jsonl). finos/morphir-dotnet#567 currently reads an earlier line for its history checks and never selects it (its DOC-1). Under this rule it refuses the file instead; that answers its ask 3.

Why the publisher refuses too. Without it a current publisher would produce the mixed file that every current reader then refuses.

Edge cases. A CR before LF is JSON whitespace, so CRLF histories are valid. A history with no record, empty or only blank lines, is refused, as observed Rust's EmptyHistory does.

The publish lock. observed Rust's local publisher holds StateGuard::acquire(&self.root.join(".publish.lock")) (repository_authoring.rs) while it reads and appends a history. Two publishers without it could both read morphir-elm.jsonl and both append, and the refusal of mixed histories would race. Every publisher to a local repository holds .publish.lock at the repository root, with the state lock's primitive and opening rules, from before it reads a history until it has written it. Under Decision 13, morphir-dotnet's bundle authoring is the publisher of current releases (task 2.7), and it holds the same lock.

OLD-1. A home that an older CLI wrote

Ada has used the Rust CLI for a year. Ada's default home holds a 2.0.0-draft.2 catalog and "1.0" locks. The first .NET global install goes to the same shared catalog.

Under VER-2 the .NET host does not read those files. What it does next was open question Q-OLDHOME. The maintainer answered it on 10 November 2026 (Decision 10, recorded on finos/morphir#1146):

"I like the auto approach but we should offer resolution through a fix option under the morphir doctor subcommand i.e. morphir doctor --fix. When we encounter this we can run the same code we would when fixing this scenario (thus we have both an automated and manual invoked path). A user can bypass being prompted to accept this by using --yes like we use elsewhere"

Old state. A home holds old state when it has any of these:

  • a catalog, or a repositories configuration, whose $schema is missing or not its current URL;
  • an extension lock or journal in locks/extensions/ whose $schema is missing or not its current URL;
  • more than one journal;
  • a journal that fails its checks (DEF-2).

Detection runs under the state lock before any journal is recovered. When any file is old state, every extension's state in the home is moved: a current catalog beside one old extension lock goes too. That is intended, because the home's files are one transaction's state and cannot be split safely.

Decision. Two paths reach one move.

  • Automatic path. A command that needs extension state and finds old state shows what the move would take and asks the user to accept moving it to a marked backup. On acceptance it makes the move, writes a notice naming the backup directory on stderr, and goes on with the command. This is OLDHOME-B's move with a prompt. It is neither OLDHOME-A's refusal nor a silent move.
  • --yes skips the prompt.
  • Manual path. morphir doctor --fix makes the same move by hand (DOC-1).
  • One implementation. The automatic path runs the code that morphir doctor --fix runs. The spec requires the two to produce the same backup: the same files, order, layout and marker.
  • Nothing is read or converted. OLDHOME-C, converting in place, stays rejected, so VER-2 holds.

--yes where it is "used elsewhere". The approved change add-deployment-and-acquisition defines it for morphirup setup: "--yes authorizes the displayed setup operation in automation. It never means bypass signatures, ignore incompatibility, modify unrelated installations or install a system SDK." Here it has the same meaning: it authorizes the displayed move, and nothing else. It never makes a host read or convert old state, and it never moves the store, a current repositories configuration or a lock file. morphir-dotnet's morphirup documentation (docs/content/docs/cli/morphirup.md, "Exit code 2") is the only shipped use of the option so far, and no morphir command has --yes yet.

The move is the same transaction whichever path starts it, under the state lock:

MORPHIR_HOME/
  backups/extensions-20261110T093000Z/
    locks/extensions/morphir-elm.json        moved first: every journal and extension lock
    catalog/extensions.json                  moved next, if there is one
    .complete                                written last
  config/extensions/repositories.json        stays
  store/extensions/sha256/…                  stays
  locks/extensions.state.lock                stays (a lock file, not an extension lock)

The backup is named by the UTC time as YYYYMMDDTHHMMSSZ. Each file keeps its path relative to the home. After the move the home has no catalog, and the next write creates a current one.

Completion is marked, not inferred. Old state can have no catalog at all, for example when an older CLI's first install stopped after its journal. So the move writes an empty .complete last, and only a backup without it is unfinished:

  • Exactly one backup lacks the marker. The move puts any old state left into it, then writes the marker. With nothing left to move, any state command except morphir doctor without --fix only writes the marker, without asking: no state moves, so there is nothing to accept.
  • More than one lacks it, a file to move already exists at its target, or a new directory's name is taken. The host refuses and names them. Two moves in the same second therefore fail rather than merge.

The move inside another command. The automatic path runs inside a command that has its own lock use:

  1. The command takes the state lock, as every state command does, and detects old state.
  2. It releases the state lock before it asks. Waiting on a person while holding the lock would stop every other host's extension command in that home.
  3. On acceptance, or with --yes, it takes the state lock again and detects old state again. If what it finds differs from what it showed, another process changed the home meanwhile: it shows the new state and asks again, or with --yes moves what it now finds.
  4. In that same hold it makes the move, then makes the command's own state change against the now-empty state.

With --yes and no change, steps 2 and 3 collapse into one hold. The repositories lock is not involved: a command reads the repositories configuration under that lock and releases it before it takes the state lock, so the two are never held together. The backup rules therefore hold unchanged inside another command, because the move always runs under one hold of the state lock and writes the marker last.

What the triggering command does next. It continues against the now-empty state:

  • an install writes a new current catalog holding only what it installs;
  • a list shows nothing;
  • an uninstall or update of an extension the old catalog listed reports that the extension is not installed;
  • a compile that needs an installed extension reports that it is missing, as it would in a fresh home.

The notice on stderr names the backup directory, so the user can see what was moved and reinstall from it by hand.

Readings Decision 10 did not state, confirmed as Decision 11. Decision 10 did not say what happens when the host cannot ask, when the user says no, or what morphir doctor does without --fix. These readings were put to the maintainer as Q-OLDHOME-READINGS and confirmed as written on 10 November 2026 (Decision 11, recorded on finos/morphir#1146):

  1. with no terminal and no --yes, the command is refused and changes nothing, and the message names the file, morphir doctor --fix and --yes;
  2. when the user declines the prompt, the same refusal follows, with nothing changed;
  3. morphir doctor without --fix reports the old home and what --fix would move, and changes nothing;
  4. morphir doctor --fix shows what it will move and asks before moving, unless --yes is given.

No existing rule in the specs gives a better reading. The approved deployment design's "--yes authorizes the displayed … operation in automation" supports reading 1: without --yes, automation has no authorization. "No terminal" means that standard input is not a terminal, because a host cannot read an answer otherwise. The prompt itself goes to stderr, so a command's result on stdout stays clean.

Why this fits. The first install succeeds once the user accepts, and nothing disappears from view without the user seeing the list first. That was the reason the earlier revision gave for OLDHOME-A, and it is kept by the prompt. Scripts get a deterministic answer (--yes, or a refusal that names the fix), and a user who prefers to repair deliberately has morphir doctor --fix.

The merged text, "refuse and change nothing", left the user removing files by hand. Its own recovery advice, "start on a fresh home or reinstall", could not be followed in place, because reinstalling needs the refused catalog.

DOC-1. A morphir doctor command, as far as this decision needs it

observed No morphir doctor exists yet:

  • the .NET host has none: its only doctor is morphirup doctor, a different program (src/Morphirup/Cli.fs in morphir-dotnet; the local checkout's origin/main at 09db613);
  • the Rust CLI in this repository has none (crates/);

  • --fix. Makes the move, or completes an unmarked backup. It shows what it will move and asks first (Decision 11, reading 4).

CFG-1. Project configuration quotes dotted ids

Ada configures the frontend in her project's morphir.toml.

# Correct: one quoted key
[extensions."org.finos.morphir.fsharp-frontend"]
command = "morphir-fsharp-frontend"

# Refused: TOML reads this as nested tables named org, finos, morphir …
[extensions.org.finos.morphir.fsharp-frontend]
command = "morphir-fsharp-frontend"

# Valid, unchanged: extension acme with its config table
[extensions.acme.config]
x = 1

Decision. A dotted id in configuration is one quoted key. The rule needs to tell an extension's own config table from an unquoted dotted id, so it names the settings members and their types: path, url and command are strings, args is an array of strings, enabled is a boolean, and config is a table. A reader of an extensions entry:

  1. refuses the entry when its key is not a valid id, naming the rule (ID-2);
  2. treats a member whose value is a table and whose name is not config as a nested entry. It refuses the entry, with a suggestion, even when the member's name is a settings name such as path;
  3. refuses a settings member of any other wrong type (config = 1, or [[extensions.acme.args]]), naming it and its expected type;
  4. refuses any other member whose value is an array of tables ([[extensions.acme.x]]);
  5. ignores any other member, as today.

For a refusal under 2, the reader follows the nested tables down to the first table that holds a settings member of its settings type. That stopping rule settles [extensions.acme.path] with command = "x": the path under acme is a table, not a string, so the walk goes on to it, finds command, and suggests [extensions."acme.path"]. In the first example, org holds only finos, finos holds only morphir, morphir holds only fsharp-frontend, and fsharp-frontend holds command. When each table above the stopping one has exactly one member, and the joined keys form a valid id, the message suggests that id as one quoted key: [extensions."org.finos.morphir.fsharp-frontend"]. Otherwise it names the key path and suggests nothing.

So [extensions.acme.config] is always extension acme's config table, and an extension whose id is acme.config must be written quoted. Diagnostics that print a configuration key for a dotted id print it quoted, as [extensions."org.finos.morphir.fsharp-frontend"].command.

Why. TOML gives an unquoted dotted key a different meaning: nested tables. observed The Rust configuration model reads extensions as a map from string keys, so the unquoted form above would be read as an extension named org, and it ignores unknown members, so nothing is refused. The merged rule refused an entry "whose value nests further tables in place of the extension's settings". Two readers could disagree on [extensions.acme.config], which is valid today, because the rule did not say which tables are settings. Naming config as the one table-valued settings member makes it decidable. The merged example also wrote command as an array; the model has one string.

Migration plan

Nothing is converted. Writers write the family's current $schema URLs from the first release that implements this change. Readers read those URLs only. Hosts that read only earlier versions refuse what current writers produce, by version. A user who needs such a host gives it its own Morphir home, re-adds its repositories, and uses repositories that no current writer publishes to. A current host in a home that an older CLI wrote offers to move the old state to a marked backup, or the user runs morphir doctor --fix (OLD-1, Decision 10). Existing releases stay unreadable by current hosts. New releases of the existing extensions become installable once morphir-dotnet's publisher writes them at the family version, starting each history again (Decision 13). The toolchain fixtures stay on hyphenated ids until REPO-1 step 4, so they never depend on a host that has not shipped.

Q-PUBLISHER. Who publishes the existing extensions at the new version? answered 10 November 2026

Answered by the maintainer as Decision 13, recorded on finos/morphir#1146, choosing PUBLISHER-B: "since we are using morphir-dotnet as the main CLI for Morphir I think this should be owned by the .NET version of Morphir." morphir-dotnet's bundle authoring publishes descriptors and index records at the family version for every extension (tasks 2.7 and 6.1). The Rust writers are not extended, so PUBLISHER-A and PUBLISHER-C were not taken; the identifiers stay as names of the options weighed.

What republishing can and cannot reach. Each existing release's own release.json asset is at schemaVersion 2.0.0-draft.2 or earlier. A current host refuses it (VER-2), so rewriting history lines alone makes no existing release installable. A current host can install only a release whose descriptor carries the current $schema. So under every option below, only new releases are published at the family version, and existing versions stay uninstallable by current hosts. The only exception would be replacing their published assets, which changes digests that existing index lines and lock files record; this change does not propose it. A history that holds earlier lines cannot take a current line (HIST-1). The first current release of an extension therefore starts its history again, holding only current lines. That is a new file with a new revision digest; no current lock can pin the old one, because no current host reads it.

The decision and the order of work are in REPO-1, "Republishing the existing extensions".
