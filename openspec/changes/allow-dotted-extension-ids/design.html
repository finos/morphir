Context

Today one rule, in one place, decides what an extension id may be. The table below says where ids live and what each place enforces.

One lowercase portable token: a letter, then letters, digits and -, ending in a letter or digit. At most 238 bytes (255 minus .json.transaction). Package paths in spec/package/ use their own "dotted authority" grammar for package names. That grammar is not shared with extension ids and is not changed.

Goals and non-goals

Goals. One id grammar for every host and contract. Dotted ids are published, installed, locked and bound end to end. Every existing extension, store, lock, catalog and index works byte-for-byte as before. Hosts that predate the change refuse a dotted id cleanly instead of misreading it.

Non-goals. No namespace registry, reservation or verification of reverse-DNS prefixes. No renaming of any existing extension. No change to shortId, to release tag conventions, or to the content-addressed store. No change to the MEP protocol or the claims version. Binding providers from several repositories in one recipe stays later work.

Decisions

The journey below follows one extension from release to use: morphir-dotnet's F# frontend, org.finos.morphir.fsharp-frontend 0.6.0, whose guest already reports that id. Each decision appears at the step where it first matters.

ID-1. The grammar

The release job writes release.json. The first question is whether org.finos.morphir.fsharp-frontend is a well-formed id at all.

Decision. Adopt morphir-dotnet's rule as is: one or more segments joined by .. Each segment starts with a lowercase ASCII letter, contains only lowercase ASCII letters, digits and -, and ends with a letter or digit. A single-token id is the one-segment case, so every id valid today stays valid and means the same extension.

Why. It is the rule the guests already use. It only adds the . separator, and every character an id can contain is safe in a file name on all first-delivery platforms. Lowercase-only ASCII means case-insensitive file systems cannot fold two ids together. The rule is also the toolchain contracts' grammar.

{
  "schemaVersion": "2.0.0-draft.3",
  "extensionId": "org.finos.morphir.fsharp-frontend",
  "shortId": "fsharp-frontend",
  "version": "0.6.0",
  "platformDifferences": "none",
  "artifacts": [ { "platform": "x86_64-pc-windows-msvc", "runtime": "process",
    "filename": "win-x64.zip", "sha256": "<64 hexadecimal digits>",
    "claims": { "extension": { "id": "org.finos.morphir.fsharp-frontend", "version": "0.6.0" } } } ]
}

ID-2. Lengths and device names

Before the release is accepted, its id must be safe to turn into file names on Windows, macOS and Linux.

Decision. The total limit stays at 238 characters, dots included, and there is no per-segment limit. The first segment must not be con, prn, aux, nul, com1–com9 or lpt1–lpt9.

Why. 238 is the existing budget: the longest name derived from an id is <id>.json.transaction, which must fit a 255-unit file name component. Dots do not change that arithmetic. A per-segment limit, for example the 64 characters the toolchain contracts apply, would make valid single-token ids of 65 to 238 characters invalid. That would be a breaking change, so the toolchain contracts align to this rule instead (REPO-1).

The device-name rule is what upstream already enforces for single tokens: con is refused today. Windows treats the part of a file name before its first dot as the device stem, which is why the rule applies to the first segment only. acme.con is a valid id, and con.example is not.

morphir-dotnet's rule lacks this check, so as written it accepts con.example. That id would then fail on a Windows store, so morphir-dotnet adopts the refinement (REPO-1).

Path budget. docs/spec/draft/names.md budgets IR distribution trees, not Morphir home, but its warning about Windows MAX_PATH applies. Derived names sit under MORPHIR_HOME/locks/extensions/ and extensions/ in a repository. A 238-character id is already possible today, so dotted ids add no new path length risk; Risks keeps the long-path note.

PATH-1. Names derived from an id

The repository publishes the release, and later a host installs it. Each of them writes files named after the id.

Decision. Keep every derivation as it is: the whole id followed by a fixed suffix, or the whole id as a key. No layout or index key changes.

Why it is safe. Appending a fixed suffix is injective, so two different ids can never derive the same name. Ids are lowercase ASCII, so case-insensitive file systems do not fold them together.

  • acme.tools.json and acme-tools.json are different files.
  • An id may end in a segment that looks like a suffix. x.json's lock is x.json.json, distinct from the lock and journal of x.
  • observed The index reader uses Path::file_stem, which removes only the last extension, so org.finos.morphir.fsharp-frontend.jsonl yields the full id.
  • The compile cache keeps dots in its sanitized segment and appends a hash, so it needs no change.

Existing installed stores, locks and catalogs therefore keep working unchanged, because nothing about a single-token id's names changes.

BIND-1. Descriptor, claims and session ids stay equal

At publication and installation the host probes the guest, and at first use it initializes a session. Each of these compares the guest's reported id with the descriptor's.

Decision. The rule that the descriptor id equals the claims id, and that both equal the session id, stays exactly as it is: byte equality, no mapping, no normalization. A dotted id is never shortened to a single token anywhere.

Why. This equality is what lets a recipe or lock bind an extension. The descriptor filed under a name is the one whose artifacts claim that name and report it when they run. The failure paths stay as they are: authoring, publication and installation refuse a release whose claims name another id, and the host rejects a session that reports another id before calling the extension.

TRUST-1. A name is not a credential

A user installing org.finos.morphir.fsharp-frontend might read the prefix as a statement about who published it.

Decision. A requirement states that an id is a name only. Nothing verifies domain ownership, and an id grants no trust, permission, precedence or built-in status. Publisher authentication, by authenticated repository targets and recipe digests, and the claim check stay separate facts that a receipt records beside each other.

Why. Reverse-DNS ids invite exactly this misreading. Writing it down as a requirement, with a scenario, gives reviewers and implementers something to test against: an unsigned developer artifact named org.finos.… is still local-developer. Reserving or verifying namespaces would need a registry, keys and a policy that do not exist; that is out of scope.

VER-1. Release, index and catalog versions

The descriptor reaches hosts of different ages. A host released before this change must not misread it.

Decision. Add an exact draft, 2.0.0-draft.3, to the release descriptor, the repository index record and the installed catalog. It differs from 2.0.0-draft.2 only in the id grammar.

  • A writer uses it when the id is dotted. For a single-segment id it keeps writing 2.0.0-draft.2 until the oldest host it targets reads draft.3, so the bytes it writes do not change.
  • A draft.3 reader also reads 1.0, draft.1 (converted as today) and draft.2.
  • The capability claims (0.1.0-draft.2) and MEP versions stay. Both already carry the id as an unconstrained string, and only the equality with the descriptor id binds them.

Why. AGENTS.md allows refining a draft in place, because drafts promise no compatibility with each other. Here, though, released hosts already read 2.0.0-draft.2. Refined in place, a dotted draft.2 document would reach those hosts and fail deep in parsing as an "invalid extension id". With a new draft number they refuse it at the version check, with the message that names the supported versions.

observed Today's reader refuses any version other than the listed exact drafts, so draft.3 is refused cleanly by every existing host. This is the same path the draft.1 to draft.2 rename took. A next major (3.0.0-draft.1) would also work, but it signals a reshaped format for what is a grammar widening.

VER-2. Local lock version

The host installs the frontend and writes locks/extensions/org.finos.morphir.fsharp-frontend.json. A user may later run an older host against the same Morphir home, for example after a downgrade.

Decision. An extension lock that names a dotted id is written at 2.0.0-draft.1, the first draft of the lock's next major under the rule in AGENTS.md. A lock for a single-segment id stays at "1.0". The installed catalog follows VER-1, writing 2.0.0-draft.3 as soon as any entry is dotted.

Why. An older host must refuse a lock it cannot read before acting on it. A version it does not list gives that refusal. A "1.0" lock with a dotted id would fail later, as a parse error, and possibly after other locks had been read.

Recovery. The older host refuses only the dotted extension's lock and catalog, with its unsupported-version message. Installing the newer host again restores normal use. Nothing is rewritten.

CFG-1. Project configuration quotes dotted ids

Ada configures the frontend in her project's morphir.toml.

# Correct: one quoted key
[extensions."org.finos.morphir.fsharp-frontend"]
command = ["morphir-fsharp-frontend"]

# Refused: TOML reads this as nested tables named org, finos, morphir …
[extensions.org.finos.morphir.fsharp-frontend]
command = ["morphir-fsharp-frontend"]

Decision. A dotted id in configuration is one quoted key. A configuration reader refuses an extensions entry whose value nests tables in place of extension settings, and its message shows the quoted spelling. Diagnostics that print a configuration key for a dotted id print it quoted.

Why. TOML gives an unquoted dotted key a different meaning: nested tables. observed The configuration model reads extensions as a map from string keys, so the unquoted form above would be read as an extension named org. assumption Whether the nested tables are then ignored or refused depends on how the extension settings treat unknown members. The task checks this and adds the refusal.

CONF-1. Shared conformance cases

The Rust host, the .NET host and the MoonBit host must reach the same answer for every id.

Decision. Publish the rule as language-neutral data in finos/morphir: a case manifest beside a normative extension id page, each case naming an input and an expected outcome. The runner lives in morphir-dotnet (src/Morphir.Conformance), following the maintainer's decision of 9 November 2026. The Rust crates run the same data in their own tests, and no new runner code goes into this repository.

REPO-1. Delivery order and submodule pins

  1. finos/morphir. This change is approved. Its contract half lands: the normative extension id page, the case manifest and the updated design pages.
  2. finos/morphir-rust. morphir-distribution adopts the grammar and the drafts in its readers and writers (VER-1, VER-2). morphir-common adds the configuration refusal (CFG-1). Their tests run the shared cases, and the change ships in a release.
  3. finos/morphir. One pull request moves the ecosystem/morphir-rust pin to that release and updates the Rust CLI's quoted diagnostics. This proposal covers exactly that pin move. The CLI path-depends on morphir-distribution, so the pin move and the CLI change must land together. The host compatibility suite must still pass every bundle in .config/published-extension-bundles.toml unchanged.
  4. MoonBit host. Its owning repository adopts the rule and runs the cases. ecosystem/morphir-moonbit moves only if that repository is the submodule; at its current pin it has no id code, so no move is expected.
  5. finos/morphir-dotnet. It already accepts dotted ids. It adopts the device-name refinement, runs the shared cases through its conformance runner, and its task that waits on dotted descriptor ids unblocks.
  6. Toolchain contracts in finos/morphir, after finos/morphir#1147 or within it if it has not merged. Their provider identity grammar drops its 64-character segment limit to match ID-2. The TEST-ONLY signed F# fixtures move from morphir-fsharp-frontend and morphir-fsharp-backend to the dotted ids, and the open question on dotted provider identities in toolset-recipe.md closes.

No other submodule moves. The Elm, Python, Gleam, Scala, TypeScript and examples submodules are guests or bindings whose ids are single tokens.

Alternatives not chosen

AlternativeWhy not
Keep single tokens and have morphir-dotnet publish hyphenated ids such as org-finos-morphir-fsharp-frontendThe guest would need two names, one in the store and one in MEP, and the equality rule (BIND-1) would force the guest to report the hyphenated one. That contradicts the maintainer's decision and morphir-dotnet's registry, where the dotted id is the identity.
Let the descriptor id differ from the claims id (a single-token descriptor id, dotted claims)It weakens binding. A recipe or lock binds a descriptor by its id; if the claims could name something else, a descriptor could be filed under any name, and the check that the bytes that run are the bytes that were bound would lose its anchor.
Refine 2.0.0-draft.2 in placeReleased hosts read draft.2 and would fail on a dotted id with a parse error instead of a version refusal (VER-1).
A next major, 3.0.0-draft.1Works, but marks a reshaped format for a grammar widening and would ask every writer to move. Draft.3 keeps single-segment documents byte-identical.
A per-segment limit of 64 charactersWould invalidate single-token ids of 65 to 238 characters that are valid today (ID-2).
Allow uppercase or _, as in Java packagesUppercase would let two ids fold together on case-insensitive file systems, and _ adds a spelling that is visually close to - without enabling anything new.
Encode dots in derived names, for example org%2Efinos…Unnecessary, because . is safe in file names on every first-delivery platform. It would also make every derived name harder to read and add a decoding step that each host could get wrong.

Look-alike ids such as morphir.elm and morphir-elm confuse users or invite impersonation.Ids are distinct by rule, listings show both, and TRUST-1 says no id carries trust. Authentication decides what a user installs from where.

A user writes an unquoted dotted key in morphir.toml.The reader refuses it and shows the quoted spelling (CFG-1).
A catalog or index that this repository does not vendor contains an id that is not a single token.A task reads every id in the pinned bundles' catalogs. Any such id would already be refused by today's reader.

Migration plan

Nothing existing migrates. Single-segment extensions, their descriptors, index histories, locks, catalogs and configuration keys stay byte-identical, and writers keep their current versions for them. A dotted extension can be published once its repository's tooling writes draft.3. It can be installed by hosts that read draft.3, and hosts that do not refuse it by version.

Rollback. Removing draft.3 support from a host makes it refuse dotted documents by version, the same behavior as today's hosts. Single-segment use is unaffected. The toolchain fixtures stay on hyphenated ids until REPO-1 step 6, so they never depend on a host that has not shipped.

Open questions

None that change the specs or the task breakdown. The questions this design needs the maintainer to confirm are in the report that accompanies it: the draft numbers, the device-name refinement, and the per-segment limit.
