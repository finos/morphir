allow-dotted-extension-ids: design

OpenSpec change | 9 November 2026 | proposed for maintainer review, nothing implemented

The reasons are in proposal.md; the normative rules are in the extension identity spec; the work is in tasks.md. Facts marked observed were read from this repository on origin/main at 04143a238, with its pinned submodules, and from morphir-dotnet's origin/main at e8837c3e. Everything else is a proposed interface unless it is marked assumption.

Three maintainer decisions of 9 November 2026 shape this design:

  • the Rust CLI is legacy, and work goes to the morphir-dotnet and morphir-moonbit hosts first ("we want to focus on morphir-dotnet and morphir-moonbit hosts and only possibly invest in Rust once 1 or both of those 2 are functional");
  • transient pre-1.0 document formats are not read or converted ("we are paying too much of a cost to support transient pre 1.0 contracts");
  • one installed catalog, rather than a separate partition for dotted ids, with older hosts not protected ("we don't have users to support the cost of maintaining 2 versions").

Context

Today one rule, in one place, decides what an extension id may be: the Rust implementation. The table below says where ids live and what each place enforces. These rows describe today's Rust code, which is now legacy. After this change the contract pages define the rule and the shared files (DEF-1), and the Rust source is not the authority.

Goals and non-goals

Goals. One id grammar for every host and contract. Dotted ids are published, installed, locked and bound end to end. The shared home and repository files have one definition, on the contract pages, that every installer follows.

Non-goals.

  • No namespace registry, reservation or verification of reverse-DNS prefixes.
  • No renaming of any existing extension, and no change to shortId, to release tag conventions or to the content-addressed store.
  • No change to the MEP protocol or the claims version.
  • Keeping a home or repository readable by hosts that read only earlier versions is not a goal, and neither is reading or converting earlier drafts.
  • Changes to the Rust distribution library and the Rust CLI do not gate this change (REPO-1).
  • Binding providers from several repositories in one recipe stays later work.

Decisions

The journey below follows one extension from release to use: morphir-dotnet's F# frontend, org.finos.morphir.fsharp-frontend 0.6.0, whose guest already reports that id. Each decision appears at the step where it first matters.

ID-1. The grammar

The release job writes release.json. The first question is whether org.finos.morphir.fsharp-frontend is a well-formed id at all.

Decision. Adopt morphir-dotnet's rule as is: one or more segments joined by .. Each segment starts with a lowercase ASCII letter, contains only lowercase ASCII letters, digits and -, and ends with a letter or digit. A single-token id is the one-segment case, so every id valid today stays valid and means the same extension.

Why. It is the rule the guests already use. It only adds the . separator, and every character an id can contain is safe in a file name on all first-delivery platforms. Lowercase-only ASCII means case-insensitive file systems cannot fold two ids together. The rule is also the toolchain contracts' grammar.

{
  "schemaVersion": "2.0.0-draft.3",
  "extensionId": "org.finos.morphir.fsharp-frontend",
  "shortId": "fsharp-frontend",
  "version": "0.6.0",
  "platformDifferences": "none",
  "artifacts": [ { "platform": "x86_64-pc-windows-msvc", "runtime": "process",
    "filename": "win-x64.zip", "sha256": "<64 hexadecimal digits>",
    "claims": { "extension": { "id": "org.finos.morphir.fsharp-frontend", "version": "0.6.0" } } } ]
}

ID-2. Lengths and device names

Before the release is accepted, its id must be safe to turn into file names on Windows, macOS and Linux.

Decision. The total limit stays at 238 characters, dots included, and there is no per-segment limit. The first segment must not be con, prn, aux, nul, com1–com9 or lpt1–lpt9.

Why. 238 is the existing budget: the longest name derived from an id is <id>.json.transaction, which must fit a 255-unit file name component. Dots do not change that arithmetic. A per-segment limit, for example the 64 characters the toolchain contracts apply, would make valid single-token ids of 65 to 238 characters invalid. That would be a breaking change, so the toolchain contracts align to this rule instead (REPO-1).

The device-name rule is what upstream already enforces for single tokens: con is refused today. Windows treats the part of a file name before its first dot as the device stem, which is why the rule applies to the first segment only. acme.con is a valid id, and con.example is not.

morphir-dotnet's rule lacks this check, so as written it accepts con.example. That id would then fail on a Windows store, so morphir-dotnet adopts the refinement (REPO-1).

Path budget. docs/spec/draft/names.md budgets IR distribution trees, not Morphir home, but its warning about Windows MAX_PATH applies. Derived names sit under MORPHIR_HOME/locks/extensions/ and extensions/ in a repository. A 238-character id is already possible today, so dotted ids add no new path length risk; Risks keeps the long-path note.

PATH-1. Names derived from an id

The repository publishes the release, and later a host installs it. Each of them writes files named after the id.

Decision. Keep every derivation as it is: the whole id followed by a fixed suffix, or the whole id as a key, in the directories every id already uses. No layout or index key changes.

Why it is safe. Appending a fixed suffix is injective, so two different ids can never derive the same name. Ids are lowercase ASCII, so case-insensitive file systems do not fold them together.

  • acme.tools.json and acme-tools.json are different files.
  • An id may end in a segment that looks like a suffix. x.json's lock is x.json.json, distinct from the lock and journal of x.
  • observed The Rust index reader uses Path::file_stem, which removes only the last extension, so org.finos.morphir.fsharp-frontend.jsonl yields the full id. The contract page states the rule itself: the id is the file name without its final .jsonl.
  • The compile cache keeps dots in its sanitized segment and appends a hash, so it needs no change.

BIND-1. Descriptor, claims and session ids stay equal

At publication and installation the host probes the guest, and at first use it initializes a session. Each of these compares the guest's reported id with the descriptor's.

Decision. The rule that the descriptor id equals the claims id, and that both equal the session id, stays exactly as it is: byte equality, no mapping, no normalization. A dotted id is never shortened to a single token anywhere.

Why. This equality is what lets a recipe or lock bind an extension. The descriptor filed under a name is the one whose artifacts claim that name and report it when they run. The failure paths stay as they are: authoring, publication and installation refuse a release whose claims name another id, and the host rejects a session that reports another id before calling the extension.

TRUST-1. A name is not a credential

A user installing org.finos.morphir.fsharp-frontend might read the prefix as a statement about who published it.

Decision. A requirement states that an id is a name only. Nothing verifies domain ownership, and an id grants no trust, permission, precedence or built-in status. Publisher authentication, by authenticated repository targets and recipe digests, and the claim check stay separate facts.

Why. Reverse-DNS ids invite exactly this misreading. Writing it down as a requirement, with a scenario, gives reviewers and implementers something to test against: an unsigned developer artifact named org.finos.… is still an unsigned developer artifact. Reserving or verifying namespaces would need a registry, keys and a policy that do not exist; that is out of scope.

VER-1. New exact drafts, written for every id

The descriptor reaches hosts of different ages, and it must say which grammar its ids follow.

Decision. The release descriptor, the repository index record and the installed catalog move to a new exact draft, 2.0.0-draft.3. It differs from 2.0.0-draft.2 only in the id grammar. The extension lock moves to 2.0.0-draft.1, the first draft of its next major under the rule in AGENTS.md, which differs from "1.0" only in the id grammar. A writer writes these versions for every document, whatever the form of the ids in it. The capability claims (0.1.0-draft.2) and MEP versions stay; both already carry the id as an unconstrained string.

Why a new draft rather than refining draft.2 in place. AGENTS.md allows refining a draft in place. But then one version string, 2.0.0-draft.2, would name two grammars, and a document's version would no longer say whether a reader can read it. An earlier host handed a dotted draft.2 document would fail deep in parsing with "invalid extension id" instead of at the version check, with the message that names the supported versions. The lock is released at "1.0", so it cannot be refined in place at all.

Why for every id. The earlier version of this design wrote the new drafts only for documents that name a dotted id. That rule existed only so that existing documents stayed byte-identical for earlier hosts, and keeping those hosts working is no longer a goal. Writing one version per document means a current host reads one version (VER-2) and a writer never chooses a version by content.

VER-2. Readers read the current drafts only

Decision. A reader reads 2.0.0-draft.3 descriptors, index records and catalogs, and 2.0.0-draft.1 locks. It need not read "1.0" or released major-1 descriptors, 2.0.0-draft.1 or 2.0.0-draft.2 documents, or "1.0" locks. No conversion between versions is part of the contract. A reader that does not read a version refuses the document by version and names the file and the versions it reads.

Why. It follows the maintainer's decision that transient pre-1.0 formats are not read or converted, and it is what the author of finos/morphir-dotnet#567 asked for. The earlier drafts were written only by the Rust tooling and the Rust CLI before 1.0. The consequence for existing published releases and existing homes is open question 9.

STATE-1. One catalog, one lock directory, one history directory

Ada's home already holds morphir-elm. She installs the frontend with the .NET host.

Decision. Every id, dotted or not, lives in the same places:

MORPHIR_HOME/
  catalog/extensions.json                  every installed extension, 2.0.0-draft.3
  locks/extensions.state.lock              the one state lock
  locks/extensions/<id>.json               every lock (2.0.0-draft.1) and its journal
  store/extensions/sha256/<digest>/…       shared, content-addressed, unchanged

repository/
  extensions/<id>.jsonl                    every history, records at 2.0.0-draft.3

Accepted cost. An older host is not protected. observed The Rust CLI loads catalog/extensions.json whole before every install, update, uninstall, list and activation, and its extension search and extension repository verify read every history in extensions/. So once a current host has written a home's catalog, every extension command of an older CLI in that home is refused by version. Once a repository holds a draft.3 record, an older client's search and verification of it fail. The maintainer accepted this: "we don't have users to support the cost of maintaining 2 versions".

What a user of an older CLI sees, and how to get back. The older CLI reports catalog/extensions.json as an unsupported extension schema version. To use it again, give it its own Morphir home (MORPHIR_HOME) and install its extensions there. Removing the dotted extensions does not help, because the catalog stays at draft.3.

Why. One catalog is the layout every host already uses, so there is one set of files to define and test, no partition invariant and no wrong-partition refusal.

DEF-1. The contract pages define the shared files

The .NET installer (finos/morphir-dotnet#567) and, later, the MoonBit host share a home with each other.

Decision. docs/design/draft/extensions/distribution-and-acquisition.md defines the members and values of:

  • the release descriptor and the index record at 2.0.0-draft.3;
  • the installed catalog at 2.0.0-draft.3;
  • the extension lock at 2.0.0-draft.1;
  • the transaction journal;
  • the state lock and the home and repository paths.

An installer conforms when it writes equal members and values; its bytes need not equal another installer's. Where a page and the Rust source differ, the page wins.

Why. observed Today neither the page nor a published schema states the grammar or the catalog and journal members; the Rust code is the rule. The Rust CLI is now legacy, so it cannot stay the definition that the .NET and MoonBit hosts must match. Byte equality would also tie every installer to one JSON serializer's spacing and key order without making two homes mean anything different.

CFG-1. Project configuration quotes dotted ids

Ada configures the frontend in her project's morphir.toml.

# Correct: one quoted key
[extensions."org.finos.morphir.fsharp-frontend"]
command = ["morphir-fsharp-frontend"]

# Refused: TOML reads this as nested tables named org, finos, morphir …
[extensions.org.finos.morphir.fsharp-frontend]
command = ["morphir-fsharp-frontend"]

Decision. A dotted id in configuration is one quoted key. A configuration reader refuses an extensions entry whose value nests tables in place of extension settings, and its message shows the quoted spelling. Diagnostics that print a configuration key for a dotted id print it quoted.

Why. TOML gives an unquoted dotted key a different meaning: nested tables. observed The Rust configuration model reads extensions as a map from string keys, so the unquoted form above would be read as an extension named org. Every host that reads [extensions.<id>] tables applies the rule.

CONF-1. Shared conformance cases

The .NET host and the MoonBit host must reach the same answer for every id.

Decision. Publish the rule as language-neutral data in finos/morphir: a case manifest beside a normative extension id page, each case naming an input and an expected outcome. The runner lives in morphir-dotnet (src/Morphir.Conformance), following the maintainer's decision of 9 November 2026. No runner code goes into this repository, and no case requires a Rust host.

REPO-1. Delivery order

  1. finos/morphir. This change is approved. Its contract half lands: the normative extension id page, the case manifest, and the design pages that define the shared files (DEF-1).
  2. finos/morphir-dotnet. It already accepts dotted ids. It adopts the device-name refinement and runs the shared cases through its conformance runner. Its installer (finos/morphir-dotnet#567) writes the one catalog, the locks and the journals at the new drafts, with the members and values the design pages define, and reads only the new drafts. It publishes the F# guests at draft.3 under their dotted ids, and its task that waits on dotted descriptor ids unblocks.
  3. MoonBit host. Its owning repository adopts the rule and runs the cases. ecosystem/morphir-moonbit moves only if that repository is the submodule; at its current pin it has no id code, so no move is expected.
  4. Toolchain contracts in finos/morphir, after finos/morphir#1147 or within it if it has not merged. Their provider identity grammar drops its 64-character segment limit to match ID-2. The TEST-ONLY signed F# fixtures move from morphir-fsharp-frontend and morphir-fsharp-backend to the dotted ids, and the limit on dotted provider identities in toolset-recipe.md closes.

Optional later work, gating nothing. To read homes and repositories that current hosts write, the Rust tooling would need the work below. No ecosystem/morphir-rust pin move is planned.

  • morphir-distribution: the grammar with the device-name rule in ExtensionId, and the new drafts in its readers and writers.
  • morphir-common: the configuration refusal of CFG-1.
  • The Rust CLI: quoted diagnostics and documentation.

No other submodule moves. The Elm, Python, Gleam, Scala, TypeScript and examples submodules are guests or bindings whose ids are single tokens.

Alternatives not chosen

AlternativeWhy not
A separate home partition (catalog/extensions-dotted.json, locks/extensions-dotted/) and repository directory (extensions-dotted/) so that older hosts never read a dotted idThe earlier version of this design. The maintainer chose one catalog: protecting older hosts is not worth two layouts, a partition invariant, wrong-partition refusals, per-partition journal recovery and a downgrade test against the previous release.
The new drafts only for documents that name a dotted id, so that existing documents stay byte-identicalIts only purpose was to keep older hosts reading. It would make a current host read and write two versions of each document, which the maintainer's decision on transient formats rules out (VER-1, VER-2).
Refine 2.0.0-draft.2 in placeOne version string would name two grammars, and an earlier host would fail on a dotted id with a parse error instead of a version refusal. The released lock "1.0" cannot be refined in place (VER-1).
A next major, 3.0.0-draft.1, for the descriptorWorks, but marks a reshaped format for what is a grammar widening.
Keep single tokens and have morphir-dotnet publish hyphenated ids such as org-finos-morphir-fsharp-frontendThe guest would need two names, one in the store and one in MEP, and the equality rule (BIND-1) would force the guest to report the hyphenated one. A recipe or lock binds a descriptor by its id; if the claims could name something else, a descriptor could be filed under any name, and the check that the bytes that run are the bytes that were bound would lose its anchor.

Allow uppercase or _, as in Java packagesUppercase would let two ids fold together on case-insensitive file systems, and _ adds a spelling that is visually close to - without enabling anything new.
Encode dots in derived names, for example org%2Efinos…Unnecessary, because . is safe in file names on every first-delivery platform. It would also make every derived name harder to read and add a decoding step that each host could get wrong.
Installers that write the same bytes as the Rust hostTies every installer to one serializer and keeps the legacy Rust source as the definition (DEF-1).

Migration plan

Nothing is converted. Writers write the new drafts from the first release that implements this change. Readers read the new drafts. Hosts that read only earlier versions refuse what current writers produce, by version. A user who needs such a host gives it its own Morphir home. The toolchain fixtures stay on hyphenated ids until REPO-1 step 4, so they never depend on a host that has not shipped.

Open questions

Question 8, a separate partition or one catalog, is answered: one catalog. Questions 1 and 2, on versions, are settled by VER-1 and VER-2. These remain for the maintainer:

  1. Add the first-segment device-name rule, and ask morphir-dotnet to adopt it? Recommendation: yes. Upstream already refuses con as an id. Without the rule con.example is valid in morphir-dotnet and fails on a Windows store.
  2. No per-segment length limit? Recommendation: none, as in morphir-dotnet. The toolchain contracts drop their 64-character segment limit to match.
  3. Where do the rule page and its cases live? Recommendation: a new docs/spec/ extension id page with its case manifest beside it, in finos/morphir, run by morphir-dotnet's conformance runner.
  4. Which repository holds the MoonBit host's extension installation? The pinned ecosystem/morphir-moonbit has none. The MoonBit host is now a first-delivery host, so group 3 needs the answer before it can start.
  5. Reserve or check reverse-DNS prefixes? Recommendation: no, not in this change. It needs a registry, keys and a policy that do not exist, and TRUST-1 makes names carry no trust.
  6. Do current hosts read the existing published releases and homes? Existing repositories and the bundles pinned by .config/published-extension-bundles.toml are at 2.0.0-draft.2 or earlier, and existing homes hold "1.0" or 2.0.0-draft.2 catalogs and "1.0" locks. Under VER-2 a current host need not read them. Recommendation: apply the decision on transient formats to all of them. A current host installs only releases published at draft.3, and a repository that current hosts must read republishes its releases at draft.3. A user starts current hosts on a fresh home or reinstalls. Task 1.3 records which published releases are affected.
