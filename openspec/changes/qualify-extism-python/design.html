Qualify Python Extism support

Bead morphir-ukvn.5.98 · 2026-10-28 · Implemented; macOS arm64 candidate qualification

The approved route runs the existing Python WASM compiler through the shared Rust Extism host, selected by a new explicit extism-wasm pin. It uses legacy MEP 0.1 JSON operations. It does not turn the current core-WASM host into Extism or promise rich-model transport. See the proposal for motivation and the behavior contract for acceptance scenarios.

Goals and boundaries

The adapter boundary must let users know exactly which bytes, protocol and representation ran. Domain validation remains pure in the MoonBit shell where it owns command planning; the shared host owns MEP session validation and Extism execution. Decode external strings into closed binding, operation, IR-version and resource-policy types. Capability claims describe supported operations; they never grant filesystem or network access.

This design covers explicit local bundle invocation. It does not add automatic installed-provider selection, WASM publish/install/update, a new compiler, general dependency resolution, wire cancellation, a component runtime, or top-level language routing. Existing native-process argument arrays retain their ownership and exact forwarding. Signed provenance remains optional. The separate installed-native outcome stays with morphir-ukvn.5.64.30.

A Python workflow

A user obtains a version-2 Python release bundle or builds one with the Python repository's existing extension:bundle task. Acquisition remains separate from invocation. A verified descriptor and WASM file are selected in an explicit pin, with the qualified host executable and the helper/runtime closure. The commands below show the selected syntax. Multi-module use requires the corrected explicitly advertised bundle and a passing candidate receipt.

morphir extension describe --extension-pin python-extism.json --extension-helper /qualified/extism.mjs --json
morphir extension compile src --package acme/example --ir-version 3 --model-format json --extension-pin python-extism.json --extension-helper /qualified/extism.mjs --output compiled-v3 --json
morphir extension generate compiled-v3/morphir-ir.json --ir-version 3 --model-format json --extension-pin python-extism.json --extension-helper /qualified/extism.mjs --output generated-v3 --json

For this binding, compilation accepts a single file or a directory of UTF-8 .py files. The directory snapshot uses sorted clean relative paths, preserves module layout, rejects symlinks and duplicate normalized paths, and obeys the source-count claim and aggregate byte budget. Absolute source paths never become guest filesystem authority. The user selects IR 3 or 4 explicitly. JSON is the Extism default; requesting Ion is an error. The same commands with a different explicit output directory exercise IR 4.

The host reads verified immutable bytes, discovers the extension and opens a checked MEP 0.1 session against that identity. It sends source documents in the compile request. The guest statically parses them without importing Python. The CLI validates the returned plain IR, closes the session, stages the result and publishes morphir-ir.json. Generate reads that JSON without wrapping it as a MorphirModel, validates the version and capabilities, and publishes returned Python artifacts through the same safe output rules. The user can recompile those generated sources. A Python interpreter used to check generated code belongs only to the qualification harness, never to plugin authority.

Decisions

HOST-1: Reuse the shared Extism host in an isolated helper process

Extend the existing Rust native-services executable with an explicitly tagged Extism request, using ExtensionContainer, ExtismChannel, CheckedConnection, HostConfig and Session. Continue using shared distribution types for version-2 descriptors and SHA-256 values. Do not invoke the Rust product CLI. A new internal request tag and versioned boundary distinguish legacy Extism operations from existing native rich operations. Existing request schemas remain accepted unchanged.

A separate process makes hard cancellation and cleanup observable even when an Extism call is blocked. A MoonBit-native Extism implementation would duplicate the Rust host and engine integration. Running this guest under the Node core-WASM byte ABI would require a different guest ABI, so it is not an adapter shortcut. Component Model hosting is independent work.

The implementation uses the shared RestrictedExtismPolicy API landed in morphir-rust#315, tree 74183388a7e65672a426ae7d5530ceb574eef05b. The parent source pin is the validated immutable commit fc9f723a2cf0adae1299892c6cc4bee5ebcf4560 from morphir#1108. It denies HTTP hosts, preopened paths and inherited environment and applies finite discovery, request, reply and engine limits. The opt-in MoonBit qualification runs the canonical upstream policy tests against this adapter's locked Extism engine, rather than copying them or relying on a different upstream lockfile. There is no local host fork or widened legacy frame ceiling.

PIN-1: Pin the whole executed closure and preserve unchecked provenance

The new pin has contractVersion 0.1.0, binding extism-wasm, an executionProfile morphir/extism-mep-0.1/v1, host executable/SHA-256/sourceRevision, runtime executable/version/SHA-256, helper root/exact module digest map, artifact bundle directory/descriptor SHA-256/WASM SHA-256/extensionId/version, and origin. The profile fixes policy ceilings; callers can request lower limits through existing timeout controls, never a larger profile. It carries neither native executable args nor a Node byte-ABI manifest. Unknown fields or bindings are refused by the new branch without weakening old pin parsing.

Read bounded descriptor and WASM files through no-follow handles. Validate regular files, relative artifact references, version-2 descriptor selection and digest agreement before constructing the runtime. Snapshot the bytes that were hashed and instantiate from those bytes. The helper/runtime closure must likewise run from verified private copies using the portable helper's existing immutable-staging pattern. A package-manager integrity record can supplement this check, not replace it. The Rust executable's embedded libraries and qualified system runtime dependencies are recorded in the receipt.

Compare discovery identity/version and operation capabilities with the pin and descriptor; compare initialized capabilities with the live discovery claim using the shared checks. Keep recorded distribution claims marked unchecked until their actual scoped checks run, and report runtime observations separately. No digest or successful probe authenticates an author. Missing optional signatures are not a baseline refusal.

MEP-1: Keep the existing Python protocol intact

The maintainer requires a corrected Python bundle with frontend.multiDocument=true. Python 0.4.1 omits that member; its observed implementation does not override the SDK meaning that omission permits exactly one source document. The adapter checks compile/generate flags, language, target, IR and source count explicitly before dispatch, because the shared legacy session does not currently enforce those operation scopes. There is no digest exception. Single-document requests to 0.4.1 remain eligible for the ordinary checks, while the full qualification requires the corrected release. The separate release workspace is tracked by morphir-ukvn.5.98.5 and preserves the independent documentation work.

Offer only 0.1 for this profile and use morphir.frontend.compile and morphir.backend.generate. Discover through the shared describe flow; initialize a fresh operational container held to that description and verified bytes; call once; require shutdown acknowledgement; drop the container; reap the helper; then publish. The describe-only probe is also dropped before host exit. No stdio Content-Length frames are inserted into Extism's request bytes, and CLI result envelopes stay outside MEP.

Validate the JSON-RPC envelope, ID, error/result exclusivity, result shape and success flag. Compile requires Python frontend language, supported source count and IR version; generation independently requires target python, generate support and the input IR version. Missing capabilities, drift and malformed results fail even when installation accepted unchecked claims. Preserve guest diagnostic code, severity, location and related information. success:false is a failed operation even if transport and process exit succeeded.

The MEP model-transport draft preserves legacy JSON shapes and requires exact 0.2.0-draft.1 for compileModel/generateModel. A future rich Python bundle needs a separately qualified execution profile and complete operation/profile/codec/envelope/IR tuple intersection. Do not infer that support from a new SDK dependency, a modelTransport member or an IR version number.

The Python binding normalizes version aliases and writes integer formatVersion through its shared codecs. IR 4 remains draft despite the spelling 4.0.0. Compile validates the result's declared IR version against the requested version and its actual JSON header, then decodes with the corresponding existing MoonBit versioned codec. Preserve the returned JSON value without migration or lossy projection. Byte formatting can change during serialization, so this route promises semantic JSON retention, not rich-envelope byte identity.

The MoonBit versioned JSON dispatcher reads the header and selects a version-specific decoder without migration. That common entry point is necessary but does not prove all Python values cross the boundary. Qualify actual v3 classic distributions and v4 compact types, values, names, integer precision, local imports and multiple modules against the independent Python API. Unsupported shapes fail visibly; never trim fields to force acceptance. Document a file-interchange recipe only for the fixture subset proven by those receipts. Rich-model provenance or retention metadata requires a separate explicitly reviewed conversion outside this profile.

LIM-1: Enforce a fixed bounded authority profile

Use the legacy shared response policy. WASI support needed by the Rust guest may be enabled with no preopened paths, no inherited user environment and no network hosts. Deny subprocesses and direct output publication; permitted Morphir callbacks are limited to the existing bounded workspace-info/cache/log interface and receive an empty private workspace, no user paths or secrets. Test denied HTTP and filesystem access against the actual constructed plugin. Extism's manifest documentation distinguishes an empty host allowlist from unrestricted hosts; encode denial explicitly rather than trusting a nullable default.

The shared legacy MEP request/response ceiling of 64 MiB remains unchanged. The adapter applies its smaller budgets and rejects oversized Extism outputs before copying them into its reply. The engine memory cap still bounds guest-side allocation. Per-call fuel resets must be verified against the pinned engine, including multiple calls and metadata discovery. No automatic use of the newer 1 GiB generated-artifact policy is permitted. Exact-bound and one-over fault fixtures establish these distinctions.

Cancellation is a host action, not a guest notification guarantee. Kill the owned process group, reap it, then delete temporary storage. A shared channel reporting Stopped does not establish container destruction. Fail closed on uncertain cleanup and record lifecycle observations without claiming graceful shutdown. Generated paths must be relative, nonempty and unique after platform normalization; reject traversal, symlinks, case collisions and invalid base64. Write into staging and commit a new destination only after full validation and closure, leaving existing destinations untouched.

JSON-1: Make failures machine readable without changing the wire

The owning CLI parser declares --json for each affected command and retains its existing help/self-test schemas. New Extism finite output uses profile morphir/command-result, contractVersion 0.1.0, command extension.describe, extension.compile or extension.generate, state, exitCode and diagnostics. Success carries result with binding, session protocol/IR facts, identity, scoped capability checks, output digests and lifecycle observations. Failure carries error.code/message instead of result. Child logs go to stderr. Success follows required writes and cleanup.

Use stable adapter codes under extension. for unsupported_binding, unsupported_target, invalid_pin, integrity_mismatch, identity_mismatch, protocol_mismatch, capability_mismatch, unsupported_model_format, ir_version_mismatch, invalid_result, resource_limit, timeout, unsafe_artifact and incomplete_session. Preserve Python PY001, PY005, warning PY006 and other guest codes inside diagnostics rather than flattening them into a transport error. Use the existing execution.cancelled code for cancellation. Expected JSON validation refusal exits 1, cancellation 130 and parser syntax 2. Document human-mode behavior and keep existing routes' abort/status mappings and successful JSON schemas unchanged.

Build decision assessment

The opt-in candidate task implements this placement; no recurring CI workflow changes are included. Integrity/publication failure has high impact and targeted regressions must pass before implementation merge. Platform/linker/cleanup failures have moderate to high impact and must be detected before claiming or promoting that cell. Existing mandatory checks remain enforced. Candidate receipts enforce source, toolchain, executable, helper, bundle and check identities, plus four successful entry points and both IR consumers. Missing evidence blocks the corresponding support claim. Only the macOS arm64 cell has this evidence; no installed host distribution is released here. A local run observed a 106 MiB host and first describe invocations of 3.9 to 4.4 seconds through the four entry points, with no disk-cache control. These observations are not a cross-platform benchmark or startup guarantee. Confidence is high for the demonstrated fixture and refusal cases and unknown for other target cells. The existing mandatory CI and release gates remain separate. An all-platform PR matrix conflicts with the repository's scarce-runner policy. The chosen manual candidate qualification preserves that policy without pretending a workflow already runs these new cases.

Risks and trade-offs

  • Shared policy defaults may grant more authority than intended → add and test an explicit upstream deny-access policy and repin before adapter acceptance.
  • Legacy JSON can omit rich provenance → refuse rich envelopes and document the proven plain-IR subset; never synthesize guarantees or silently project metadata.
  • Matching IR major numbers can conceal codec differences → compare actual Python output with MoonBit decoders and Python API fixtures, including compact v4 representations and integer precision.
  • Dropping a future or closing a channel may leave an Extism worker alive → use process isolation, engine bounds and observed kill/reap before cleanup.
  • Rust/Extism increases host build size and cold-start time → reuse the pinned shared host, build once per compatible target and record size/startup in receipts before packaging claims.
  • The Python docs proposal may move before implementation → retain its intent name/path and owning bead reference, then update canonical links when it lands; it remains independently deliverable.

Migration and review plan

This change began as a separate proposal and has since received implementation and landing approval. The maintainer also authorized the corrected Python release in a new workspace. Synchronize the implementation groups with their actual evidence. There is no default switch. Establish the shared policy and pinned host first, then explicit pin/command routing, then legacy Python JSON operations and packaged acceptance. Each group carries its own refusal tests and documentation. The task list records files, verification and real dependencies.

Rollout adds an opt-in binding. Rollback removes or disables that binding and its host profile without changing existing pins or deleting user outputs. An upstream host change requires independent approval and repinning. Merges and releases retain maintainer approval. Archive only after implemented requirements and required qualification evidence pass; update asset paths and bead spec IDs according to the repository's archive instructions.
